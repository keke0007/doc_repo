### 1.2 关键要点速记
- **B+ Tree vs B-Tree**:B+ 树叶子相连便于范围扫描,非叶节点不存数据故扇出更高、树更矮。
- **聚簇索引一张表只能一个**(就是主键),无主键则选第一个非空唯一索引,再无则隐藏 6 字节 `ROW_ID`。
- **回表**:二级索引拿到主键 → 回到聚簇索引取完整行。**覆盖索引可消除回表**。
- **索引下推 ICP**:存储引擎层提前过滤,而非取出后到 Server 层过滤,**减少回表次数**。
- **加索引会锁表吗?**:5.6+ Online DDL,普通索引 `ALGORITHM=INPLACE, LOCK=NONE` 不锁表;但主键/唯一索引仍可能短暂锁。

```
              乐观锁 vs 悲观锁(横向对比)
   ┌────────────────────┬─────────────────────────┐
   │      悲观锁        │        乐观锁           │
   ├────────────────────┼─────────────────────────┤
   │ DB 层加锁(for      │ 应用层加版本号/CAS      │
   │ update / 隐式行锁) │                         │
   │ 假设冲突一定发生   │ 假设冲突很少            │
   │ 串行高、并发低     │ 并发高、冲突要重试      │

   └────────────────────┴─────────────────────────┘
```

```
              死锁产生与解决
    事务 A: lock(行1) → 等待 lock(行2)
                          ▲
                          │ 循环等待
                          ▼
    事务 B: lock(行2) → 等待 lock(行1)

  解决:① InnoDB 自动检测(wait-for graph)→ 回滚代价小的事务
       ② innodb_lock_wait_timeout 超时
  避免:① 同一顺序访问资源     ② 缩短事务、减小锁粒度
       ③ 给 update 条件加索引(否则全表临键锁退化)
```

### 2.2 关键要点速记
- **行锁实现在索引上**:`update where 非索引列` 会让 MySQL 给**全表所有行**加 Next-Key,等价表锁。
- **意向锁的作用**:让表锁(LOCK TABLES)能 O(1) 判断"是否有人持有行锁",不必扫描每一行。
- **插入意向锁**特殊间隙锁:多个事务在同一间隙插入不同值**互不阻塞**,但与 Gap Lock **冲突**。
- **SELECT...FOR UPDATE**:有索引→行锁;无索引→表锁(实际是退化的全表 Next-Key)。
- **可重复读隔离级别下,间隙锁才存在**;读已提交不需要间隙锁(允许幻读)。

                                  ┌───────────────────────────────┐

```

```
              幻读的解决路径
   ┌─────────────────────────────────────────────┐
   │ 普通快照读(select)  → MVCC ReadView 解决   │
   │ 当前读(for update / │ → Next-Key 锁解决     │
   │ insert/update/del) │                       │
   └─────────────────────────────────────────────┘
              ↑
              │ 所以 RR 下"幻读"被解决但并非彻底:
              │ 同一事务中先快照读再当前读会"幻象"再现
              │ → 真正彻底解决:Serializable
```

### 3.2 关键要点速记
- **原子性来自 Undo Log**,持久性来自 Redo Log,隔离性来自 锁+MVCC,一致性是结果。
- **ReadView 四元组**:`m_ids`(活跃事务列表)、`min_trx_id`、`max_trx_id`、`creator_trx_id`。
- **RR 与 RC 的核心区别**:ReadView 何时生成。RC 每语句一次,RR 事务首次快照读一次。
- **幻读两类**:快照读用 MVCC 解决;当前读用 Next-Key 解决;两者交叉时仍可能出现幻象。

### 4.2 关键要点速记
- **Redo Log 是 InnoDB 特有,Binlog 是 Server 层**。Redo 循环写、Binlog 追加写。
- **Undo Log 同时承担两个作用**:事务回滚 + MVCC 多版本链。
- **两阶段提交**核心解决 Redo 与 Binlog 一致性,**崩溃恢复以 Binlog 是否完整为准**。
- Row 格式定位故障最准,**生产强烈推荐 Row**。

              ├──────────────────────────────────┤

   │              BufferPool 三大链表                │
   ├──────────────────┬───────────────┬──────────────┤
   │ Free List        │ LRU List      │ Flush List   │
   │ (空闲页)         │(冷热分区改进  │(脏页待刷盘)  │

   │      页分裂 & 页合并(磁盘碎片的根源)          │
   ├─────────────────────────────────────────────────┤
   │ 页分裂:插入数据,目标页已满 → 分裂出新页      │
   │   → 触发场景:无序主键(UUID)、插入到中间      │
   │   → 副作用:IO 翻倍、碎片、降低查询效率        │
   │ 页合并:删除/更新使页占用 < 50% → 与邻页合并   │
   │   → 副作用:IO、锁竞争                         │
   │ 缓解:① 主键自增有序 ② OPTIMIZE TABLE          │
   └─────────────────────────────────────────────────┘
```

### 5.2 关键要点速记
- **BufferPool 改进 LRU**:加冷热分区(midpoint),全表扫描时新页放在冷区,避免污染热区。
- **脏页刷盘时机**:Redo Log 满、BufferPool 空闲不足、空闲时机、正常关闭。
- **页分裂根本原因**:有序索引被无序写打乱;解决之道**主键自增**。
- **change buffer**:对二级索引非唯一列的写,缓冲到内存,延迟合并以减少随机 IO。

```
       ┌───────────────────────────────────────────────┐
       │           一条更新 SQL 的执行流程              │
       └───────────────────────────────────────────────┘

   1. 读到该行(BufferPool 命中 or 加载)
   2. 旧值写入 Undo Log               (可回滚 / 供 MVCC)
   3. 修改 BufferPool 中的数据页 → 脏页
   4. 写 Redo Log Buffer(prepare 状态)
   5. Server 层写 Binlog               ┐
   6. Redo Log Buffer commit           ├ 两阶段提交
                                       ┘
   7. 后台刷脏页到磁盘
```

```
       ┌───────────────────────────────────────────────┐
       │              JOIN 的算法演进                  │
       ├───────────────────────────────────────────────┤
       │  ① NLJ  (Nested-Loop Join,内表用索引)     │
       │  ② BNL  (Block NL,内表无索引 → 全扫,慢)  │
       │  ③ Hash Join(8.0+ 默认替代 BNL)            │
       │     建小表 hash 表 → 扫大表探测              │
       └───────────────────────────────────────────────┘
              ┌──────────────────────────────────────┐
              │ 优化:小表驱动大表、被驱动表加索引   │
              └──────────────────────────────────────┘
```

```
       ┌───────────────────────────────────────────────┐
       │           Order By 的两种排序方式             │
       ├───────────────────────────────────────────────┤
       │ ① 全字段排序: select 字段全放 sort_buffer    │
       │              排完直接返回                     │
       │ ② rowid 排序: 仅放排序列+主键,排完回表     │
       │              (单行字段太大时触发)            │
       │ ③ 利用索引天然有序 → 无需排序(最优)        │
       │                                               │
       │ sort_buffer_size 不够 → 借助磁盘临时文件      │
       └───────────────────────────────────────────────┘
```

```
       ┌───────────────────────────────────────────────┐
       │      count() 性能排序                         │
       ├───────────────────────────────────────────────┤
       │  count(字段)  < count(主键 ID) < count(1) ≈   │
       │  count(*)                                     │
       │                                               │
       │ 解释:                                         │
       │ • count(*)/count(1)→ 优化器选择最小二级索引   │
       │ • count(字段) → 需判断 NULL,且可能要回表    │
       │ • 无 WHERE 时,MyISAM 直接读元数据,InnoDB    │
       │   仍需扫描(MVCC 致每事务可见性不同)         │
       └───────────────────────────────────────────────┘
```

### 6.2 关键要点速记
- **查询缓存** MySQL 8.0 已移除,因更新即失效,大多无用。
- **两阶段提交**只在更新流程出现(prepare → write binlog → commit)。
- **Hash Join 仅适用于等值连接**,非等值仍走 NLJ。
- **count(*) 是约定优化**,SQL 标准上"统计行数"。

## 7. 主从复制与高可用

### 7.1 关系图

```
                  ┌──────────────────────────────┐
                  │     主从复制核心原理         │
                  └───────────────┬──────────────┘
                                  ▼
        ┌────────────┐       ┌──────────────────────────┐
        │ 主库       │       │ 从库                     │
        │            │       │ ┌──────────────────────┐ │
        │ 写 Binlog  │ ────▶│ │ I/O Thread 拉 Binlog │ │
        │            │       │ │ 写入 Relay Log       │ │
        │            │       │ └──────────┬───────────┘ │
        │            │       │            ▼             │
        │            │       │ ┌──────────────────────┐ │
        │            │       │ │ SQL Thread 重放      │ │
        │            │       │ │ Relay Log → 数据库   │ │
        │            │       │ └──────────────────────┘ │
        └────────────┘       └──────────────────────────┘
```

```
              复制模式:
    ┌──────────────────────────────────────────────────┐
    │ 异步复制(默认):主库不等从库,可能丢数据      │
    │ 半同步:主库等至少一个从库返回 ACK 再 commit     │
    │ 组复制 MGR:基于 Paxos,多主写入,自动故障转移   │
    └──────────────────────────────────────────────────┘
```

```
              GTID:全局事务标识
   格式: server_uuid:transaction_id
   作用:
   ① 主从切换时定位"我执行到哪个事务"
   ② 自动跳过已执行事务,避免人工算 binlog 位点
   ③ 配合 MGR 实现自动故障转移
```

```
              高可用方案演进
   单主单从 → 一主多从 + 读写分离 → MHA(自动主备切换) →
   MGR(组复制,多写自治) → MySQL InnoDB Cluster
                  │
                  ▼
   ┌─────────────────────────────────────────────────┐
   │  保证主备一致的核心组合:                       │
   │   半同步 + Row 格式 Binlog + GTID + 校验工具    │
   │              (pt-table-checksum)                │
   └─────────────────────────────────────────────────┘
```

```
              主从不一致原因 → 解决
   ① 主库异步丢失       → 半同步
   ② Statement 不确定函数 → Row 格式
   ③ 从库写入          → super_read_only
   ④ 主从延迟          → 并行复制 / 改善硬件
   ⑤ 数据修复          → pt-table-sync / 重新同步
```

### 7.2 关键要点速记
- **GTID 是高可用现代化的基础**,无 GTID 时切换主库要手算 binlog 文件名+位点,极易出错。
- **半同步并非完全同步**:主库等"已写 relay log"的 ACK,不等"已重放"。
- **组复制不等于读写分离**:MGR 是真正多主自治,通过 Paxos 投票决定事务顺序。

## 8. 优化与设计

### 8.1 关系图

```
                ┌─────────────────────────────┐
                │     SQL 性能优化方法论      │
                └──────────────┬──────────────┘
                               │
   ┌───────────┬───────────┬───┴───┬───────────┬──────────────┐
   ▼           ▼           ▼       ▼           ▼              ▼
 索引优化  减少回表    JOIN 优化  分页优化  避免锁竞争    架构优化
   │         │           │         │         │              │
   │         │           │         │         │              │
建合适索引 覆盖索引  小表驱动大表 延迟关联  短事务/有索引  读写分离
 失效场景  索引下推    被驱动表  WHERE 条件 缩小事务范围  分库分表
                       要有索引   利用主键   降低隔离级别  缓存(Redis)
```

```
              亿级数据 name=sk 快查策略
   ┌──────────────────────────────────────────────────┐
   │ ① 给 name 加索引(必须,否则全表扫秒杀)         │
   │ ② 覆盖索引:idx(name, 需要返回的列)             │
   │ ③ 分页:用 id > last_id 替代 OFFSET 大偏移      │
   │ ④ 分库分表:按 name hash 或 id range            │
   │ ⑤ 数据归档:冷热分离                            │
   │ ⑥ 引入 ES / TiDB / Doris 等专门搜索引擎          │
   └──────────────────────────────────────────────────┘
```

```
              单表数据量限制 & 扩容
   ┌────────────────────────────────────────────┐
   │ 无硬性上限,但建议:                       │
   │  • 单表 < 2000 万行 / < 10GB              │
   │  • 树高过深(>4 层)→ 查询变慢            │
   │ 扩容:                                     │
   │  • 垂直拆:大表抽冷字段                    │
   │  • 水平拆:hash/range 分片(中间件)      │
   │  • Online DDL:大表加列、加索引不停机     │
   │  • 不停机迁移:双写 → 校验 → 切流         │
   └────────────────────────────────────────────┘
```

```
              字段设计原则
   ┌────────────┬────────────────────────────────┐
   │ CHAR/VARCHAR│CHAR 定长(<=固定长度,如手机号)│
   │             │VARCHAR 变长(变化大、长字符串)│
   ├────────────┼────────────────────────────────┤
   │datetime/   │datetime 8字节 1000-9999 无时区 │
   │timestamp   │timestamp 4字节 1970-2038 有时区│
   ├────────────┼────────────────────────────────┤
   │ NOT NULL   │ NULL 会:                       │
   │            │ ① 占位+1bit 位图               │
   │            │ ② 索引失效情况增多             │
   │            │ ③ count/=表现易踩坑           │
   ├────────────┼────────────────────────────────┤
   │ 自增 ID    │ BIGINT 上限 2^63-1,工业上几乎 │
   │            │ 用不完;INT 风险大,建议从头BIGINT│
   │            │ 用完 → 改 BIGINT / 雪花 / UUID │
   ├────────────┼────────────────────────────────┤
   │高并发主键   │ InnoDB 自增锁(AUTO-INC LOCK) │
   │ 重复?     │ 模式控制,默认不会重复,但可能 │
   │            │ 不连续(回滚也消耗)           │
   └────────────┴────────────────────────────────┘
```

### 8.2 关键要点速记
- **Online DDL** 三档:`COPY`(锁) / `INPLACE`(可不锁) / `INSTANT`(8.0,瞬时,仅加列)。
- **NULL 影响索引统计、聚合函数语义、`!=` 行为**,定要用 `NOT NULL DEFAULT ''/0`。
- **datetime 推荐**:无时区歧义,范围更大;**timestamp 适用跨时区**应用。
- **CHAR 适合一定长度**,VARCHAR 适合长度差异大;**末尾空格行为不同**(CHAR 截断空格)。

## 9. 主题串联:四条核心主线

### 主线 A:一次更新引发的全栈联动

```
  UPDATE t SET c=c+1 WHERE id=1;
        │
        ▼
  [SQL 执行] 连接器→分析器→优化器→执行器
        │
        ▼
  [索引]   走聚簇索引找到 id=1 的页
        │
        ▼
  [BufferPool] 数据页加载到内存
        │
        ▼
  [事务/MVCC] 旧值进 Undo Log,新值产生 trx_id
        │
        ▼
  [锁]     给该行加 X 行锁(还有意向锁 IX)
        │
        ▼
  [日志]   Redo prepare → Binlog → Redo commit
        │
        ▼
  [主从]   主库 Binlog → 从库 Relay → 重放
        │
        ▼
  [持久化] 后台刷脏页到 .ibd 文件
```

### 主线 B:幻读的彻底防御链

```
   是否快照读? ────否──▶ 当前读 ──▶ 加 Next-Key Lock ──▶ 阻止插入 ──▶ 不幻读
        │
        是
        ▼
   读 ReadView ──▶ 沿 Undo Log 找可见版本 ──▶ 不幻读
```

### 主线 C:可用性与一致性的取舍

```
   异步复制(高性能,弱一致)
        │ 牺牲一致
        ▼
   半同步(主库等 ACK)
        │ 牺牲性能
        ▼
   组复制 MGR(强一致 + 自动选主)
        │ 牺牲简洁
        ▼
   InnoDB Cluster / 分布式 DB
```

### 主线 D:索引优化与锁的因果链

```
  WHERE 无索引 ──▶ 全表扫描
        │
        ▼
  update/for update 走全表 ──▶ 所有行 Next-Key 锁
        │
        ▼
  并发线程被阻塞 ──▶ 看上去像"表锁"
        │
        ▼
  根本解决:WHERE 条件加合适索引
```

## 10. 高频面试题速查表

| 主题 | 高频题 | 一句话答 |
|---|---|---|
| 索引 | 为什么用 B+ 树? | 多叉降树高 + 叶子链便于范围扫描 |
| 索引 | 什么是覆盖索引? | select 字段全在索引里,免回表 |
| 索引 | 索引失效场景? | 函数/隐式转换/前缀模糊/!=/OR 无索引/最左前缀 |
| 锁 | 行锁加在哪儿? | 索引上;无索引退化为全表 Next-Key |
| 锁 | RR 怎么防幻读? | 快照读靠 MVCC,当前读靠 Next-Key |
| 锁 | 死锁怎么避免? | 一致顺序加锁、短事务、加索引、超时回滚 |
| 事务 | ACID 各靠什么? | A=Undo,D=Redo,I=锁+MVCC,C=结果 |
| MVCC | RC 与 RR 区别? | ReadView 生成时机不同 |
| 日志 | 三大日志区别? | Undo 回滚/Redo 物理崩恢/Binlog 逻辑复制 |
| 日志 | 两阶段提交? | Redo prepare → Binlog → Redo commit |
| 执行 | count 性能? | count(*)=count(1) > count(主键) > count(字段) |
| 执行 | JOIN 算法? | NLJ / BNL / Hash Join,小表驱动大表 |
| 复制 | GTID 作用? | 全局事务 ID,主从切换无需算 binlog 位点 |
| 复制 | 半同步意义? | 主库等从库 ACK 才 commit,降低丢数据 |
| 优化 | 大偏移分页? | 利用 id > last_id 走索引跳过 |
| 设计 | 为什么 NOT NULL? | 空间小、索引/聚合无歧义、性能更优 |
| 设计 | 自增 ID 会重复? | InnoDB 自增锁保证不重复,但可能不连续 |
