# MySQL 日志体系与崩溃恢复深度剖析

> 本文聚焦 MySQL 三大日志的协作机制 —— Redo / Undo / Binlog 各自承担什么角色,「两阶段提交」如何保证 Redo 与 Binlog 一致,以及崩溃发生在任何环节时数据库如何精确地决定提交还是回滚。

---

## 一、为什么 MySQL 需要三种日志?(分工动机)

```
        ┌─────────────────────────────────────────────────┐
        │ 数据库要解决的「三个不同时空」问题              │
        └─────────────────────┬───────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────────┐
        ▼                     ▼                         ▼
   ┌──────────┐         ┌──────────┐            ┌──────────┐
   │ 过去    │         │ 现在     │            │ 未来      │
   │ 回滚到  │         │ 崩溃就在 │            │ 主从复制  │
   │ 事务前  │         │ 这一秒   │            │ 数据归档  │
   └────┬─────┘         └─────┬────┘            └─────┬────┘
        ▼                     ▼                       ▼
   ┌──────────┐         ┌──────────┐            ┌──────────┐
   │ Undo Log │         │ Redo Log │            │ Binlog   │
   │ 「回头看」│         │ 「立刻刷」│           │ 「向外说」│
   └──────────┘         └──────────┘            └──────────┘
```

**一句话总结:**
- **Undo**:回滚 + MVCC 旧版本
- **Redo**:崩溃恢复 + 持久化保证(物理日志)
- **Binlog**:主从复制 + 数据归档(逻辑日志,Server 层)

## 二、三大日志全方位对比

```
┌─────────────┬──────────────────┬──────────────────┬──────────────────┐
│   维度      │     Undo Log     │     Redo Log     │      Binlog      │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 所属层      │ 存储引擎(InnoDB)│ 存储引擎(InnoDB)│ Server 层(所有引擎)│
│ 日志性质    │ 逻辑日志         │ 物理日志         │ 逻辑日志         │
│             │ "反操作 SQL"     │ "页号+偏移+变化" │ "SQL 或行镜像"   │
│ 主要作用    │ 事务回滚         │ 崩溃恢复         │ 主从复制         │
│             │ MVCC 版本链      │ 持久化           │ 数据归档/恢复    │
│ 写入特点    │ 随事务产生       │ 顺序循环写       │ 顺序追加写       │
│             │ 与数据一同 buffer│ 大小固定(覆盖)  │ 文件不覆盖        │
│ 写入时机    │ 事务执行中       │ prepare/commit   │ commit 前        │
│ 存储位置    │ Undo Tablespace  │ ib_logfile0/1    │ mysql-bin.NNNNNN │
│ 是否能关闭  │ 不能             │ 不能             │ 可关(主从必开)  │
│ 引擎是否有  │ 仅 InnoDB        │ 仅 InnoDB        │ 所有引擎共用     │
└─────────────┴──────────────────┴──────────────────┴──────────────────┘
```

**关键对比记忆:**
- Redo = 物理日志,循环写; Binlog = 逻辑日志,追加写
- Redo 解决「单机崩溃恢复」; Binlog 解决「跨机复制 / 归档」
- 一条 UPDATE → 一个 Undo Log 记录 + 若干 Redo Log 记录 + 一条 Binlog 事件

## 三、为什么需要两阶段提交?(Why 2PC)

### 3.1 假设没有两阶段会发生什么

```
   假设流程:执行 UPDATE → 先写 Redo → 再写 Binlog
                                            │
                              如果在这中间崩溃 ↓

   情况 ①:Redo 写完,Binlog 没写
   ─────────────────────────────────
   崩溃后:Redo 重做了数据修改   ✓ 主库有
          Binlog 不存在         ✗ 从库无
          → 主从不一致

   假设反过来:先写 Binlog → 再写 Redo
   情况 ②:Binlog 写完,Redo 没写
   ─────────────────────────────────
   崩溃后:Redo 不能重做         ✗ 主库无
          Binlog 已经流到从库   ✓ 从库有
          → 主从又不一致
```

### 3.2 两阶段提交的方案

```
       ┌──────────────────────────────────────────────────┐
       │           两阶段提交 2PC 流程                     │
       └──────────────────────────────────────────────────┘

   ① 执行器写 Undo Log
            │
            ▼
   ② 执行器在 BufferPool 修改数据,产生脏页
            │
            ▼
   ③ 写 Redo Log,标记为 PREPARE 状态  ◀── 第一阶段
            │
            ▼
   ④ 写 Binlog                          ◀── Server 层
            │
            ▼
   ⑤ 提交事务,Redo Log 由 PREPARE → COMMIT  ◀── 第二阶段
            │
            ▼
   ⑥ 后台慢慢把脏页刷盘
```

## 四、崩溃恢复的精确决策(以 Binlog 为准)

```
   ┌────────────────────────────────────────────────────────┐
   │ 重启时,InnoDB 扫描 Redo Log 找到所有 PREPARE 事务      │
   │ 然后对每个 PREPARE 事务做如下判断:                     │
   └────────────────────────────────────────────────────────┘

                    Redo PREPARE 已存在
                            │
                            ▼
                ┌──────────────────────┐
                │ Binlog 中找得到吗?  │
                └────────┬─────────────┘
              是         │           否
        ┌──────────────┐ │ ┌────────────────────┐
        │ 提交事务     │ │ │ 回滚事务            │
        │ (Redo COMMIT)│ │ │ (用 Undo Log 回滚)  │
        └──────────────┘ │ └────────────────────┘
                         │
                ┌────────┴─────────┐
                │  Redo 已 COMMIT  │
                │  → 直接重做即可  │
                └──────────────────┘
```

**为什么以 Binlog 为准?**
- Binlog 一旦写入,可能已经流到从库
- 若主库回滚而 Binlog 已被从库执行 → 主从不一致
- 所以一旦 Binlog 完整 → 主库必须提交(向 Binlog 看齐)

## 五、崩溃发生在不同阶段的处理

```
   流程的六个时间点,任意一个崩溃,InnoDB 都能精确决策:

   ┌────┬──────────────────────┬──────────────────────────────────┐
   │ #  │  崩溃时机             │  处理结果                        │
   ├────┼──────────────────────┼──────────────────────────────────┤
   │ 1  │ 读取数据页阶段        │ 无影响(数据没变)               │
   │ 2  │ 修改 BufferPool       │ 无影响(没写 Redo,无法重做)   │
   │ 3  │ Undo 写完后           │ 无影响(没写 Redo,无法重做)   │
   │ 4  │ Redo PREPARE 写完     │ Binlog 未完成 → 用 Undo 回滚    │
   │ 5  │ Binlog 写完前         │ 同上,回滚                       │
   │ 6  │ Binlog 写完,COMMIT前│ Binlog 已可能流出 → 主库提交     │
   │ 7  │ COMMIT 之后才崩       │ 已成功提交,直接重做即可         │
   └────┴──────────────────────┴──────────────────────────────────┘
```

## 六、Binlog 的三种格式

```
┌─────────────┬──────────────────────┬─────────────────────────────┐
│   格式      │      内容             │   优缺点                    │
├─────────────┼──────────────────────┼─────────────────────────────┤
│ Statement   │ 记录原始 SQL          │ ✓ 体积小                    │
│             │                       │ ✗ 含 NOW()/UUID/RAND() 时   │
│             │                       │   主从可能不一致             │
│             │                       │ ✗ 自增列 + ROLLBACK 也不稳   │
├─────────────┼──────────────────────┼─────────────────────────────┤
│ Row(推荐)  │ 行变化前后镜像        │ ✓ 主从完全确定              │
│             │                       │ ✓ 可基于 binlog 做数据闪回  │
│             │                       │ ✗ 体积大(批量 update 暴增)│
├─────────────┼──────────────────────┼─────────────────────────────┤
│ Mixed       │ 默认 Statement,      │ 折中,但 MySQL 5.7+ 强烈    │
│             │ 不安全时切 Row        │ 推荐直接用 Row              │
└─────────────┴──────────────────────┴─────────────────────────────┘
```

**生产实践:`binlog_format = ROW`**(目前事实标准)
- 配合 RC 隔离级别使用最稳
- 大批量 UPDATE 时 Binlog 暴增 → 可以加 `binlog_row_image=MINIMAL` 减少体积

## 七、Redo Log 的写盘策略(性能 vs 持久性)

```
   ┌─────────────────────────────────────────────────────────────┐
   │   innodb_flush_log_at_trx_commit 三档配置                   │
   ├─────────────────────────────────────────────────────────────┤
   │ 0  │ 每秒后台线程刷 → OS Cache → 磁盘                       │
   │    │ ─ 性能最好,但崩溃丢最近 1s 数据                       │
   │    │                                                         │
   │ 1  │ 每次 commit 都 fsync 到磁盘(默认,ACID 完全)         │
   │    │ ─ 安全性最高,性能受 IOPS 限制                          │
   │    │                                                         │
   │ 2  │ 每次 commit 写 OS Cache,后台每秒 fsync                 │
   │    │ ─ MySQL 进程崩溃不丢,操作系统崩溃丢 1s                │
   └─────────────────────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────────────────────┐
   │   sync_binlog 三档配置                                       │
   ├─────────────────────────────────────────────────────────────┤
   │ 0  │ 完全靠 OS 调度刷盘 → 性能好,风险高                    │
   │ 1  │ 每次事务提交都 fsync(默认)                            │
   │ N  │ 每 N 个事务 fsync 一次                                  │
   └─────────────────────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────────────────────┐
   │ 「双 1 配置」:redo=1 + binlog=1                              │
   │ 强 ACID + 严格主从一致性,但 IOPS 压力大,需要 SSD          │
   └──────────────────────────────────────────────────────────────┘
```

## 八、Undo Log 的双重身份

```
   Undo Log 不只是"回滚日志"

           ┌──────────────────────────────┐
           │      Undo Log 的两个职责     │
           └──────────────┬───────────────┘
                          │
              ┌───────────┴────────────┐
              ▼                        ▼
     ┌──────────────────┐    ┌──────────────────┐
     │  ① 事务回滚      │    │  ② MVCC 版本链  │
     │                  │    │                  │
     │ 用反操作还原原值  │    │ 旧版本通过       │
     │ INSERT → DELETE  │    │ roll_ptr 串联     │
     │ DELETE → INSERT  │    │ 供快照读使用     │
     │ UPDATE → 反向UPD │    │                  │
     └──────────────────┘    └──────────────────┘
                          │
                          ▼
              ┌─────────────────────────────────┐
              │ Purge 线程负责清理:             │
              │  ─ 已无活跃事务依赖的旧版本     │
              │  ─ 已提交事务的回滚段           │
              │                                  │
              │ 长事务会卡住 Purge → undo 膨胀  │
              └─────────────────────────────────┘
```

## 九、一条 UPDATE 引发的"日志风暴"全流程

```
   SQL: UPDATE t SET name='mary' WHERE id=10;

   ┌────────────────────────────────────────────────────────┐
   │ Step 1  Server 层:连接器/分析器/优化器/执行器          │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 2  存储引擎:从 BufferPool 取该行(未命中则磁盘)  │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 3  生成 Undo Log:记录原值 name='tom'             │
   │         事务可回滚 + 旧版本进 roll_ptr 链              │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 4  在 BufferPool 中修改:name='mary'              │
   │         数据页变成脏页                                  │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 5  写 Redo Log Buffer,标记 PREPARE                │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 6  Server 层写 Binlog Cache → 文件                 │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 7  Redo Log 从 PREPARE → COMMIT                    │
   │         事务正式提交,客户端拿到 OK                     │
   └────────────────────────────────────────────────────────┘
                          ▼
   ┌────────────────────────────────────────────────────────┐
   │ Step 8  后台线程异步刷脏页到 .ibd 文件                  │
   └────────────────────────────────────────────────────────┘
```

## 十、面试高频追问汇总

**Q1:Redo Log 既然能恢复数据,为什么还要 Binlog?**
A:Redo 是 InnoDB 引擎自己的,作用域是「单机崩溃恢复」。Binlog 是 Server 层的,跨引擎、跨实例,负责主从复制 + 数据归档。Redo 解决不了"把变更同步到另一台机器"的问题。

**Q2:两阶段提交解决了什么问题?**
A:解决 Redo 和 Binlog 的一致性 —— 防止「Redo 写了但 Binlog 没写」或「Binlog 写了但 Redo 没写」导致的主从不一致或数据丢失。

**Q3:崩溃恢复为什么以 Binlog 为准?**
A:Binlog 一旦完整写入,可能已被从库消费。如果主库回滚,主从将永久不一致。所以策略是:Binlog 完整 → 提交;Binlog 不完整 → 回滚。

**Q4:Redo Log 是什么时候持久化的?**
A:取决于 `innodb_flush_log_at_trx_commit`:
- 0:每秒后台刷
- 1:每次 commit 都 fsync(默认)
- 2:写 OS Cache,每秒 fsync

**Q5:Undo Log 存在哪儿?**
A:Undo Tablespace(MySQL 8.0 独立)。早期版本在共享表空间 `ibdata1` 中,容易导致空间无法回收。

**Q6:为什么生产强烈推荐 Row 格式?**
A:
- Statement 在 RC + 隔离级别下不稳(执行顺序不同)
- 包含 NOW()/UUID() 等非确定性函数时主从会漂移
- Row 格式让主从重放确定性强,且可基于 Binlog 做行级闪回

**Q7:Binlog 和 Redo Log 谁先写?**
A:在两阶段提交中:**Redo PREPARE → Binlog → Redo COMMIT**。Redo PREPARE 先于 Binlog,Binlog 又先于 Redo COMMIT。

**Q8:大事务对日志的影响?**
A:
- Undo Log 膨胀,Purge 无法清理
- Redo Log Buffer 不够用,频繁 flush
- Binlog Cache 超 `binlog_cache_size` 时溢出到磁盘临时文件
- 一旦回滚,代价巨大
- **生产准则:事务不超过 1 秒、不跨远程调用、批量操作分批提交**

**Q9:Redo Log 文件多大合适?**
A:`innodb_log_file_size` × `innodb_log_files_in_group`。太小会频繁切换 + 触发脏页刷盘风暴;太大恢复时间长。生产常设为 1~4GB/文件,2~4 个文件。

**Q10:可以同时关掉 Redo 和 Binlog 吗?**
A:Redo 不能关。Binlog 可以关(`log_bin = OFF`),但无 Binlog 就不能做主从复制和按时间点恢复 —— 生产强烈不建议。
