# MVCC 与事务隔离级别完全解析

> 本文聚焦「读不加锁却又能看到一致快照」这一 InnoDB 高并发的核心机制 —— MVCC,并理清 RR / RC 的真实差异、幻读为什么 RR 下"看似解决又没完全解决"。

---

## 一、为什么要有 MVCC?(动机)

```
   ┌──────────────────────────────────────────────────────────┐
   │ 单纯靠锁的并发控制存在两个矛盾                            │
   ├──────────────────────────────────────────────────────────┤
   │ 矛盾 1:读写互斥 → 读多场景下吞吐被锁住                   │
   │ 矛盾 2:长事务持锁 → 阻塞链放大,死锁/超时频发            │
   └────────────────────────────┬─────────────────────────────┘
                                ▼
              ┌─────────────────────────────────────┐
              │ MVCC 思路:                          │
              │  ─ 写操作走加锁路径                  │
              │  ─ 读操作走「快照读」 → 不加锁       │
              │  ─ 每行数据有多个历史版本            │
              │  ─ 用「事务可见性算法」决定看哪一版  │
              └─────────────────────────────────────┘
                                │
                                ▼
                  ┌─────────────────────────────┐
                  │ 实现 = 三隐藏列 + Undo 链   │
                  │       + ReadView 可见性算法 │
                  └─────────────────────────────┘
```

## 二、三个隐藏列(MVCC 的物理基础)

```
   每行记录 InnoDB 自动加了 3 个隐藏列:

   ┌──────────────────┬───────────────────────────────────────────┐
   │ DB_TRX_ID        │ 6 字节,最近一次修改该行的事务 ID         │
   ├──────────────────┼───────────────────────────────────────────┤
   │ DB_ROLL_PTR      │ 7 字节,回滚指针,指向 Undo Log 中的旧版本│
   ├──────────────────┼───────────────────────────────────────────┤
   │ DB_ROW_ID        │ 6 字节,无主键时用作隐式聚簇索引          │
   └──────────────────┴───────────────────────────────────────────┘
```

## 三、版本链 = Undo Log 链表

```
   假设有一行 id=1, name='a',被三次更新:

   ┌────────────────────────────────────────────────────────┐
   │  当前行(BufferPool / 数据页中的最新版本)              │
   │  id=1, name='d', trx_id=400, roll_ptr ─────┐           │
   └─────────────────────────────────────────────│──────────┘
                                                  ▼
                  ┌──────────────────────────────────────────┐
                  │ Undo Log 版本 V3                          │
                  │ name='c', trx_id=300, roll_ptr ────┐      │
                  └─────────────────────────────────────│─────┘
                                                        ▼
                                  ┌──────────────────────────┐
                                  │ Undo Log 版本 V2          │
                                  │ name='b', trx_id=200,     │
                                  │ roll_ptr ──────────┐      │
                                  └────────────────────│──────┘
                                                       ▼
                                       ┌──────────────────────┐
                                       │ Undo Log 版本 V1      │
                                       │ name='a', trx_id=100  │
                                       └──────────────────────┘

   ─ 沿着 roll_ptr 从最新一路回溯,可以重建该行历史的任意版本
   ─ Undo Log 不仅服务于事务回滚,还作为 MVCC 的「历史版本仓库」
```

## 四、ReadView:可见性算法的"裁判"

### 4.1 ReadView 四元组

```
   每次开启「一致性视图」时,InnoDB 记录当下并发状态的快照:

   ┌─────────────────────────────────────────────────────┐
   │ m_ids         活跃事务 ID 列表(尚未提交)           │
   │ min_trx_id    m_ids 中的最小值 (= 低水位)           │
   │ max_trx_id    系统下一个将分配的事务 ID (= 高水位)  │
   │ creator_trx_id 创建该 ReadView 的事务自己的 ID      │
   └─────────────────────────────────────────────────────┘
```

### 4.2 可见性判断算法

```
   对于某行版本的 row_trx_id,判断当前事务是否能"看见":

                  ┌──────────────────────────────────┐
                  │ row_trx_id == creator_trx_id?    │
                  │ (是不是自己改的)                 │
                  └──────────┬───────────────────────┘
                       是    │否
                ┌────────────┘
                ▼
            可见 ✓
                                 │
                                 ▼
                    ┌────────────────────────────┐
                    │ row_trx_id < min_trx_id?   │
                    │ (在 ReadView 创建前就已提交)│
                    └──────────┬─────────────────┘
                         是    │否
                ┌──────────────┘
                ▼
            可见 ✓
                                  │
                                  ▼
                     ┌─────────────────────────────┐
                     │ row_trx_id >= max_trx_id?   │
                     │ (在 ReadView 之后才启动)    │
                     └──────────┬──────────────────┘
                          是    │否
                ┌───────────────┘
                ▼
            不可见 ✗ → 沿 roll_ptr 找旧版本
                                  │
                                  ▼
                     ┌──────────────────────────┐
                     │ row_trx_id ∈ m_ids?      │
                     │ (创建时正在并发执行)     │
                     └──────────┬───────────────┘
                         是    │否
                ┌──────────────┘
                ▼
            不可见 ✗ → 找旧版本           可见 ✓
```

**记忆模型:**
```
        过去  ─────────────┬───────────────  现在  ───────  未来
       已提交               │活跃事务                   未启动
   (min_trx_id 之前)       │ (m_ids 中)             (max_trx_id 之后)
        ↓                   ↓                           ↓
        可见               不可见                      不可见
```

## 五、RR 与 RC 的本质差异:ReadView 何时生成

```
   ┌────────────────────────────────────────────────────────────┐
   │                  RR vs RC 核心差异                          │
   ├────────────────────────────────────────────────────────────┤
   │ 隔离级别   │  ReadView 生成时机                              │
   │            │                                                 │
   │ RC         │  每条 SELECT 语句执行前都重新生成               │
   │            │  → 每条 SQL 看到的都是「最新已提交」            │
   │            │  → 同一事务内两次读可能不同 → 不可重复读        │
   │            │                                                 │
   │ RR         │  事务首条快照读时生成一次,后续复用             │
   │            │  → 整个事务内看到的是同一个快照                 │
   │            │  → 多次读结果一致 → 可重复读                    │
   └────────────────────────────────────────────────────────────┘
```

**示例对比:**

```
              主事务 T(隔离级别 RR)               并发事务 T2

   ① BEGIN;
   ② SELECT * FROM t WHERE id=1;  ← V1='a'
                                                BEGIN;
                                                UPDATE t SET name='b' WHERE id=1;
                                                COMMIT;
   ③ SELECT * FROM t WHERE id=1;  ← V1='a' ✓ 仍然看到 a (复用 ReadView)
   ④ COMMIT;

   ──── 如果是 RC ────
   ③' SELECT ...                  ← V1='b' ✗ 不可重复读
```

## 六、四种隔离级别 vs 三大问题

```
┌────────────────────┬──────────┬──────────────┬──────────┐
│       隔离级别      │  脏读    │  不可重复读   │  幻读    │
├────────────────────┼──────────┼──────────────┼──────────┤
│ 读未提交 RU         │  ✗       │   ✗          │  ✗      │
│ 读已提交 RC         │  ✓       │   ✗          │  ✗      │
│ 可重复读 RR(默认)│  ✓       │   ✓          │ ~✓(锁) │
│ 串行化 Serializable│  ✓       │   ✓          │  ✓      │
└────────────────────┴──────────┴──────────────┴──────────┘
                                           ▲
                                           │
                            ┌──────────────┴──────────────┐
                            │ RR 下解决幻读的"两条路径"   │
                            │ 1. 快照读 → MVCC ReadView   │
                            │ 2. 当前读 → Next-Key Lock   │
                            └─────────────────────────────┘
```

## 七、幻读的"未彻底解决"两个场景

### 场景 A:快照读 + 更新操作

```
   表数据:t (id=10, name='a'), (id=11, name='b')
   隔离级别:RR

   事务 T1                          事务 T2
   ─────────────                    ──────────────────
   BEGIN;
   SELECT * WHERE id>=10;   ← 看到 2 行(快照 V1)
                                    INSERT INTO t VALUES (12, 'c');
                                    COMMIT;
   UPDATE t SET name='X'     ← 影响 3 行!? T2 插入的也被改了!!
        WHERE id>=10;
   SELECT * WHERE id>=10;   ← 看到 3 行(name='X' 的 id=12 也出现了)
                              幻象重现!
   COMMIT;
```

**根因:**
- 第一次 SELECT 是**快照读**,MVCC 拒绝看见 T2 的新行
- UPDATE 是**当前读** + 写入,会"激活"新行的 `trx_id = creator_trx_id`
- 之后再 SELECT,虽然仍走快照,但因为自己更新过,所以**看见自己改过的行**

### 场景 B:快照读 + 当前读

```
   事务 T1                          事务 T2
   ─────────────                    ──────────────────
   BEGIN;
   SELECT * WHERE id>=10;   ← 看到 2 行
                                    INSERT INTO t VALUES (12, 'c');
                                    COMMIT;
   SELECT * WHERE id>=10
        FOR UPDATE;          ← 当前读 → 看到 3 行
                              幻象出现!
   COMMIT;
```

**根因:**
- 第一次 SELECT 走快照
- 第二次 FOR UPDATE 走**当前读**,绕过 ReadView,直接看到最新已提交数据

### 彻底防御:开事务后立即当前读

```
   ─────────── 推荐做法 ───────────

   BEGIN;
   SELECT * WHERE id>=10 FOR UPDATE;  ← 立即加 Next-Key Lock
                                        阻止其他事务 INSERT
   ...
   COMMIT;
```

## 八、MVCC 与 Undo Log 的"性能债务"

```
   ┌────────────────────────────────────────────────────┐
   │ MVCC 的代价:Undo Log 占空间 + 长事务阻塞清理       │
   └────────────────────────────────────────────────────┘

   ① 长事务持有旧 ReadView →  对应版本的 Undo Log 不能清理
   ② Undo Log 堆积 → 表空间膨胀 → 性能下降
   ③ 极端场景:Undo Tablespace 撑爆磁盘

   ──── 排查 ────
   SHOW ENGINE INNODB STATUS;       ← 看 History list length
   SELECT * FROM information_schema.innodb_trx
        ORDER BY trx_started ASC;   ← 找最老的长事务

   ──── 治理 ────
   • 禁止长事务(应用层超时控制)
   • 程序不要 BEGIN 后做远程调用
   • 大批量更新分批 COMMIT
```

## 九、ACID 与底层支撑的对应关系

```
   ┌────────────────────────────────────────────────────────┐
   │ A 原子性  ◀──── Undo Log     (任意时刻可回滚)         │
   │ C 一致性  ◀──── A + I + D 三特性 + 约束 共同保证        │
   │ I 隔离性  ◀──── 锁 + MVCC                              │
   │ D 持久性  ◀──── Redo Log    (崩溃重做)                │
   └────────────────────────────────────────────────────────┘

   推论:
   ─ 没有 Undo Log → 不能回滚 → 也不能做 MVCC
   ─ 没有 Redo Log → 崩溃后丢数据
   ─ 没有 锁 + MVCC → 并发下脏读/幻读全无防御
```

## 十、面试高频追问汇总

**Q1:什么是当前读?什么是快照读?**
A:
- 快照读:普通 SELECT,走 MVCC,不加锁,读历史版本
- 当前读:SELECT … FOR UPDATE / LOCK IN SHARE MODE / INSERT / UPDATE / DELETE,走最新版本并加锁

**Q2:ReadView 的高水位是当前最大事务 ID 吗?**
A:不是。是「**下一个将分配的事务 ID**」(`max_trx_id`)。等于 `当前最大已分配事务 ID + 1`。

**Q3:RR 隔离级别下事务 A 已开始,事务 B 提交了,A 能看到 B 的修改吗?**
A:看 ReadView 创建时机。如果 B 在 A 第一次快照读之前就已提交,B 的修改对 A 可见;如果 B 是在 A 创建 ReadView 之后才提交,A 看不到。

**Q4:为什么 RR 默认级别下还能"出现幻读"?**
A:幻读防御依赖 Next-Key Lock,而 Next-Key Lock 只在「当前读」时加。如果事务先做快照读再做当前读,或者快照读后做 UPDATE,前后扫到的行集合可能变化 —— 这就是 RR 下幻读的"残留"。

**Q5:MVCC 解决了脏读吗?**
A:解决了。即使是 RU 隔离级别也能实现"读已提交"逻辑 —— MVCC 的本质就是只读已提交的版本。所以 RU 在 InnoDB 下意义不大,它会让 SELECT 真的读到未提交数据(锁层面),但 MVCC 读还是过滤了。

**Q6:删除一行后 MVCC 还能看到吗?**
A:能。DELETE 本质是给行打 deleted 标记 + 记录 Undo Log,旧版本仍在版本链上。直到 Purge 线程清理。

**Q7:RC 是不是没有 ReadView?**
A:有,但每条 SELECT 都重新生成。这就是 RC 表现得"始终读到最新提交"的原因。

**Q8:为什么互联网公司常用 RC 而非默认的 RR?**
A:
- RC 下没有间隙锁 → 死锁率显著降低
- RC 下并发更高 → 锁范围小
- 业务通常能容忍不可重复读
- 代价:幻读重现 + binlog 必须用 ROW 格式

**Q9:可不可以说 MVCC = Undo Log + ReadView?**
A:更准确的说法是 **MVCC = 隐藏列 + Undo Log 版本链 + ReadView 可见性算法**,三者缺一不可。
