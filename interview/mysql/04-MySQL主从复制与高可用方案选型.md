# MySQL 主从复制与高可用方案选型

> 本文聚焦「为什么主从会延迟」、「半同步真的同步吗」、「GTID 解决了什么」、「MGR 与传统主从的本质差异」这条主线,并给出从异步复制到 InnoDB Cluster 的完整选型路径。

              │ ─ 异地多活的基础           │

## 二、主从复制的核心原理(三线程模型)

```
              ┌─────────────────────────────────────────┐
              │             Master (主库)              │
              │  ┌─────────────────────────────────┐   │
              │  │ ① 业务执行 SQL → 提交事务      │   │
              │  │ ② 写 Binlog                     │   │
              │  │ ③ 唤醒 Dump Thread             │   │
              │  └────────────────┬────────────────┘   │
              │                   │                     │
              │  ┌────────────────┴──────────┐          │
              │  │ Dump Thread (每从库一个) │          │
              │  │ 从 Binlog 实时读取事件   │          │
              │  └─────────────┬─────────────┘         │
              └────────────────│────────────────────────┘
                               │  (网络流式发送)
                               ▼
              ┌─────────────────────────────────────────┐
              │             Slave (从库)               │
              │  ┌─────────────────────────────────┐   │
              │  │ I/O Thread                     │   │
              │  │ 接收 Binlog → 写入 Relay Log   │   │
              │  └────────────────┬────────────────┘   │
              │                   ▼                     │
              │  ┌─────────────────────────────────┐   │
              │  │ SQL Thread / Worker Threads    │   │
              │  │ 读 Relay Log → 重放至从库数据  │   │
              │  └─────────────────────────────────┘   │
              └─────────────────────────────────────────┘
```

**三线程职责:**
- **Dump Thread**(主):将 Binlog 事件推送到从库
- **I/O Thread**(从):接收并落地为 Relay Log
- **SQL Thread**(从):重放 Relay Log → 同步数据变更

## 三、三种复制模式对比

```
┌───────────────┬──────────────────────┬─────────────────────────────┐
│   复制模式     │      工作机制         │   一致性 / 性能特征         │
├───────────────┼──────────────────────┼─────────────────────────────┤
│ 异步(默认)  │ 主库提交即返回客户端  │ ✓ 性能最好                  │
│               │ 不等从库              │ ✗ 主库崩溃可能丢数据         │
├───────────────┼──────────────────────┼─────────────────────────────┤
│ 半同步         │ 主库等"至少一个从    │ ✓ 减少数据丢失风险           │
│ (Semi-Sync)  │ 库已落 Relay Log"     │ ✗ 受网络延迟影响             │
│               │ 的 ACK 再返回         │ → 注意:从库收到≠从库已重放 │
├───────────────┼──────────────────────┼─────────────────────────────┤
│ 同步           │ 主库等从库 Relay Log │ ✓ 零数据丢失                │
│               │ + 重放完成再返回      │ ✗ 性能严重劣化              │
│               │                       │ 几乎只在 MGR 中以变种存在    │
└───────────────┴──────────────────────┴─────────────────────────────┘
```

```
   ┌──────────────────────────────────────────────────────────┐
   │ 半同步的"半"在哪里?                                     │
   ├──────────────────────────────────────────────────────────┤
   │ 主库只等「从库已收到 Binlog 并写入 Relay Log」          │
   │ 不等「从库 SQL Thread 实际重放成功」                     │
   │                                                          │
   │ 所以半同步保证的是「数据不丢」,不保证「读到最新」      │
   └──────────────────────────────────────────────────────────┘
```

### 半同步的退化与超时

```
   主库写 Binlog ──▶ 等待至少 1 个从库 ACK
                          │
                          ▼
              ┌─────────────────────────┐
              │ 等待 rpl_semi_sync_     │
              │ master_timeout (默认10s)│
              └──────────┬──────────────┘
                         │
                  超时   │  ACK 到达
              ┌──────────┴─────────┐
              ▼                    ▼
       退化为异步复制         正常提交
       (避免主库被卡死)
```

## 四、GTID:主从复制的现代化基础

```
   ┌──────────────────────────────────────────────────────────┐
   │  GTID = server_uuid : transaction_id                    │
   │                                                          │
   │  例: 3E11FA47-71CA-11E1-9E33-C80AA9429562:5             │
   │       └────────── 服务器唯一ID ─────────┘ └─事务序号─┘  │
   └──────────────────────────────────────────────────────────┘
```

### 4.1 没有 GTID 时的痛点

```
   传统 binlog file + position 模式:

   主库挂了,需要把从库 B 切换跟随从库 C(C 现在升为主)
       │
       ▼
   DBA 必须手动算:
   ─ 老主库挂掉时, B 同步到 binlog 文件名 + 位点
   ─ 这个事务在 C 的 binlog 中对应文件名 + 位点是多少?
       │
       ▼
   一旦算错 → 跳事务、重复事务、主从永久漂移
```

### 4.2 有了 GTID 之后

```
   切换从库:CHANGE MASTER TO MASTER_AUTO_POSITION=1;
       │
       ▼
   新主库自动告诉从库:你已执行到 GTID 集合 X
       │
       ▼
   从库自动从 X 之后继续拉取事件
   ─ 跳过已执行的事务(避免重复)
   ─ 不会漏拉(确保完整性)
```

**GTID 的三大作用:**
1. 简化主从切换 —— 无需算 Binlog 位点
2. 全局唯一标识事务 —— 不会重复执行
3. MGR 自动选主 / 故障转移的基础

## 五、主从延迟的根因与解决

### 5.1 延迟为什么会发生?

```
   ┌──────────────────────────────────────────────────────────┐
   │  延迟 = Master 写 Binlog 时间点 - Slave 重放完成时间点   │
   └──────────────────────────────────────────────────────────┘

   主要瓶颈:SQL Thread 是单线程,而主库有多个并发写线程
   ────────────────────────────────────────────────────────

   主库:  ┃ T1 ┃ T2 ┃ T3 ┃ T4 ┃ T5 ┃ ← 多线程并发提交
         └────┴────┴────┴────┴────┘

   从库:  ┃ T1 ────┃ T2 ────┃ T3 ────┃ T4 ────┃ ← 单线程串行重放
         └─────────────────────────────────────┘
                                              ↑
                                            慢一截
```

### 5.2 并行复制(MySQL 5.7+)演进

```
   ┌──────────────────────────────────────────────────────────┐
   │ 5.6  │ 基于库的并行复制                                  │
   │      │ 不同库的事务可以并行 → 单库场景没用              │
   ├──────┼──────────────────────────────────────────────────┤
   │ 5.7  │ 基于组提交(LOGICAL_CLOCK)                      │
   │      │ 主库同一时刻能并行提交的事务 → 从库也能并行       │
   ├──────┼──────────────────────────────────────────────────┤
   │ 8.0  │ 基于 Write Set                                    │
   │      │ 通过检测行级冲突,确定哪些事务可并行              │
   │      │ → 几乎完美还原主库的并发度                       │
   └──────┴──────────────────────────────────────────────────┘
```

### 5.3 监控与排查

```
   ┌──────────────────────────────────────────────────────────┐
   │  SHOW SLAVE STATUS \G;                                  │
   ├──────────────────────────────────────────────────────────┤
   │  Seconds_Behind_Master   ─ 延迟秒数(粗略)             │
   │  Slave_IO_Running        ─ 网络层是否健康              │
   │  Slave_SQL_Running       ─ 重放是否健康                │
   │  Relay_Log_Pos           ─ 当前重放到 Relay 哪个位置   │
   └──────────────────────────────────────────────────────────┘

   常见根因:
   • 主库有大事务 → 一次 Binlog 巨大,从库重放慢
   • 从库执行 DDL 阻塞 SQL Thread
   • 网络抖动 → I/O Thread 拉取慢
   • 从库硬件配置低 / 索引缺失
```

```
┌──────────────────────────┬──────────────────────────────────────┐
│         根因             │             治理方案                  │
├──────────────────────────┼──────────────────────────────────────┤

   ┌──────────────────────────────────────────────────────────┐

## 七、高可用方案演进路线

```
   ┌──────────────┐    ┌──────────────────┐    ┌────────────────┐
   │ 单主单从     │ ──▶│ 一主多从读写分离 │ ──▶│ MHA 自动切换   │
   └──────────────┘    └──────────────────┘    └───────┬────────┘
                                                       │
                            ┌──────────────────────────┘
                            ▼
   ┌────────────────────────────────────┐    ┌──────────────────┐
   │ MGR 组复制(多主自治)             │ ──▶│ MySQL InnoDB     │
   │ ─ 基于 Paxos 投票决定事务顺序     │     │ Cluster (集大成) │
   │ ─ 自动故障转移                     │     │ MGR+Router+Shell │
   └────────────────────────────────────┘    └──────────────────┘
```

### 7.1 MHA(Master High Availability)

```
   ┌──────────────────────────────────────────────────────────┐
   │ MHA 工作流程                                              │
   ├──────────────────────────────────────────────────────────┤
   │ ① MHA Manager 监控主库心跳                                │
   │ ② 主库失联 → Manager 启动切换                            │
   │ ③ 从从库中找复制偏移量最大的(数据最新)                 │
   │ ④ 用差异 Binlog 补齐其他从库                              │
   │ ⑤ 提升新主库,其他从库 CHANGE MASTER 到新主             │
   └──────────────────────────────────────────────────────────┘

   特点:
   ─ 依赖 SSH 互信 + DBA 脚本
   ─ 切换可在 10~30s 内完成
   ─ MySQL 5.7 之后逐渐被 MGR 替代
```

### 7.2 MGR(Group Replication)

```
   ┌──────────────────────────────────────────────────────────┐
   │ MGR 的本质 = 分布式状态机                                  │
   ├──────────────────────────────────────────────────────────┤
   │ ─ 基于 Paxos 变种协议                                    │
   │ ─ 所有节点对事务提交顺序达成一致                          │
   │ ─ 自动故障检测和成员管理                                  │
   │ ─ 支持单主模式和多主模式                                  │
   │ ─ 节点数推荐:3 / 5 / 7(奇数)                          │
   └──────────────────────────────────────────────────────────┘

   单主 vs 多主模式:
   ┌────────────┬───────────────────────────┬─────────────────────┐
   │   模式     │       特点                 │      使用建议       │
   ├────────────┼───────────────────────────┼─────────────────────┤
   │ 单主(主流)│ 1 写 + N 读,自动选主    │ 业务无冲突时首选    │
   │ 多主       │ 全员可写,Paxos 协调顺序 │ 业务无并发写冲突时  │
   │            │                           │ (例: 不同 shard)   │
   └────────────┴───────────────────────────┴─────────────────────┘
```

### 7.3 MHA 与 MGR 对比

```
┌──────────────────┬──────────────────────┬──────────────────────┐
│      维度        │       MHA            │        MGR           │
├──────────────────┼──────────────────────┼──────────────────────┤
│ 切换决策         │ 外部 Manager 脚本     │ 集群内部 Paxos 协议  │
│ 数据一致性       │ 最大复制偏移 + 补齐   │ 基于 Paxos 强一致    │
│ 切换时间         │ 10~30 秒              │ <10 秒               │
│ 写入扩展         │ 不行(单主写)        │ 支持多主             │
│ 部署复杂度       │ 中(需 SSH 互信)     │ 高(参数多)         │
│ 推荐场景         │ MySQL 5.6 / 老系统    │ MySQL 5.7+ 新系统    │
└──────────────────┴──────────────────────┴──────────────────────┘
```

```
   ┌─────────────────────────────────────────────────────────┐

## 九、生产实践要点速查

| 主题 | 推荐配置 / 实践 |
|------|----------------|
| Binlog 格式 | `binlog_format = ROW` |
| 复制模式 | 半同步 + 双 1 配置(redo=1,binlog=1) |
| 主从切换 | 必开 GTID,禁止用 Binlog Position |
| 从库写保护 | `super_read_only = ON` |
| 延迟监控 | `Seconds_Behind_Master` + 业务侧业务时间戳对比 |
| 并行复制 | MySQL 8.0+ `binlog_transaction_dependency_tracking = WRITESET` |
| 大事务防御 | `max_binlog_cache_size` + 应用层拆分 |
| 备份方案 | 从库做 mysqldump / Xtrabackup,不影响主库 |

## 十、面试高频追问汇总

**Q1:为什么主从会有延迟?**
A:主库多线程并发写,从库 SQL Thread 是单线程重放(老版本)。即使 5.7+ 启用并行复制,大事务、DDL、网络抖动都会引入延迟。

**Q2:半同步真的"同步"吗?**
A:不是。半同步只等"至少一个从库收到 Binlog 并写入 Relay Log"的 ACK,不等"重放完成"。所以保证的是「数据不丢」,而不是「读到最新」。

**Q3:GTID 是什么?为什么需要?**
A:Global Transaction ID,格式 `server_uuid:txn_id`,在整个复制拓扑中全局唯一。它让主从切换不再需要 DBA 手算 Binlog 文件名 + 位点,大幅降低误操作风险。

**Q4:Statement 格式为什么不推荐?**
A:含 NOW() / UUID() / RAND() 等非确定函数的 SQL,在主从执行时会产生不同结果,导致数据漂移。Row 格式记录行变化前后镜像,主从重放确定性高。

**Q5:MGR 和传统主从有什么本质区别?**
A:传统主从基于 Binlog 单向同步,故障切换靠外部工具;MGR 是分布式状态机,组内所有节点通过 Paxos 协议对事务顺序达成共识,自带故障检测和自动选主。

**Q6:MGR 多主模式可以随便用吗?**
A:不可以。多主下并发写不同节点的同一行 → 触发冲突检测 → 回滚后写者。所以多主只适合"业务保证不会跨节点写同一行"的场景(例如按 user_id sharding)。

**Q7:为什么 MGR 推荐奇数节点(3/5/7)?**
A:基于 Paxos 多数派原则(N/2+1)。3 节点容忍 1 个挂,5 节点容忍 2 个挂。偶数节点容错能力与奇数相同但成本更高。

**Q8:主库挂了,主从切换后会丢数据吗?**
A:取决于复制模式:
- 异步:可能丢失主库已提交但未发送的事务
- 半同步:理论只丢从库未确认的事务(通常 0~少量)
- MGR:基于 Paxos,只要存活多数派就不丢

**Q9:Seconds_Behind_Master 不准吗?**
A:这是个常见陷阱。它实际上是「SQL Thread 当前处理的事件时间戳 vs 当前 Master 时间」,不能反映"网络在路上的事务"。更准做法是写"心跳表"对比业务时间戳。

**Q10:从库执行 DDL 为什么会卡很久?**
A:DDL 是 SQL Thread 串行执行的,且 InnoDB 早期 DDL 会锁元数据。大表加索引可能让从库延迟暴增到数小时。生产实践:用 `pt-online-schema-change` 或 `gh-ost`,在线 + 不阻塞复制地改表。

**Q11:不停机扩容怎么做?**
A:典型「双写 + 回填 + 校验 + 切流」四步走。期间通过 Binlog 监听工具(Canal、Debezium)将旧库变更同步到新分片库,直到数据完全一致后切流。
