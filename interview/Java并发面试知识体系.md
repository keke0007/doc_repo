**核心知识点**
| 问题 | 关键答案 |
|------|---------|
| 创建线程几种方式? | 继承Thread / 实现Runnable / 实现Callable+FutureTask / 线程池 |
| run() vs start()? | run()只是普通方法调用,在当前线程执行;start()才会真正开启新线程并由JVM调用run() |
| 线程状态有几种? | 6种:NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED |
| 如何判断线程是否存活? | isAlive():start之后到run结束前都返回true |
| 如何终止线程? | interrupt() + 业务方法响应中断标志;不要用stop() |
| 守护线程? | setDaemon(true);非守护线程全部结束 JVM 才退出;不能用于持久化操作 |
| 子线程异常为什么 try-catch 捕获不到? | 异常上下文绑定线程栈,主线程 try-catch 只能捕获当前栈帧异常,要用 UncaughtExceptionHandler |

### 第 3 章 JMM 与 volatile(可见性 + 有序性核心)

```
   ┌──────────────────────────────────────────────────────────────┐
   │                  JMM Java 内存模型 全图                       │
   └──────────────────────────────────────────────────────────────┘

   ┌────────┐  read   ┌─────────┐   load    ┌─────────┐  use   ┌────┐
   │主内存  │────────▶│ 工作内存│──────────▶│ 工作内存│───────▶│线程│
   │        │         │  副本   │            │  变量   │        │栈  │
   │        │◀────────│         │◀──────────│         │◀───────│    │
   └────────┘  write  └─────────┘  store    └─────────┘ assign └────┘
                  ↑                                  ↑
                  └─────── 8 大原子操作 ──────────────┘
                  (lock/unlock/read/load/use/assign/store/write)

   并发产生的 3 大问题:
   ┌──────────────┬───────────────────────────────────────────┐
   │ ① 可见性     │ A 线程改了变量,B 线程看不到(缓存未同步)   │
   │ ② 有序性     │ JVM/CPU 重排序,代码顺序≠实际执行顺序     │
   │ ③ 原子性     │ i++ 实际是 读-改-写 三步,可能被打断      │
   └──────────────┴───────────────────────────────────────────┘

   ┌─────────────────────────────────────────────────────────────┐
   │                       volatile 解决方案                      │
   └─────────────────────────────────────────────────────────────┘

   ① 解决可见性:                ② 解决有序性:           ③ 无法解决原子性
   ┌──────────────────┐         ┌──────────────────┐    ┌─────────────────┐
   │ 写: lock 前缀     │         │ 内存屏障(barrier) │    │ i++ 仍然有数据   │
   │  → 强制刷主内存   │         │ LoadLoad         │    │ 不一致问题       │
   │ 读: 失效本地副本  │         │ StoreStore       │    │ 需要 synchronized│
   │ MESI 缓存一致性   │         │ LoadStore        │    │ 或 AtomicInteger │
   │ 协议保证          │         │ StoreLoad        │    │                 │
   └──────────────────┘         └──────────────────┘    └─────────────────┘

   ┌─────────────────────── volatile 应用场景 ───────────────────────┐
   │                                                                 │
   │  ① 状态标记位:  volatile boolean stop = false;                   │
   │  ② DCL单例:   volatile Singleton instance;(防指令重排)         │
   │  ③ 独立观察:   一写多读场景                                      │
   │  ④ 配合 CAS:  内置原子类的 state 字段                           │
   └─────────────────────────────────────────────────────────────────┘
```

**DCL 为什么必须 volatile?**

```
   instance = new Singleton();  实际分 3 步:
   ┌─────────────────────────────────────────┐
   │ ① 分配内存空间                            │
   │ ② 调用构造方法初始化对象                  │
   │ ③ 将 instance 指向分配的内存地址          │
   └─────────────────────────────────────────┘
                  │
                  ▼
   若发生重排序(①→③→②),另一个线程可能拿到
   还未初始化完成的"半成品对象"。
   volatile 通过禁止指令重排序解决该问题。
```

### 第 5 章 AQS 框架(Lock 的底座)

```
   ┌─────────────────────────────────────────────────────────────────┐
   │       AQS = AbstractQueuedSynchronizer J.U.C 核心基石            │
   └─────────────────────────────────────────────────────────────────┘

   AQS 三大核心:
   ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
   │ volatile int state│    │ CLH 双向同步队列  │    │  模板方法模式     │
   │ 同步状态:         │    │ Node 链表        │    │ tryAcquire       │
   │  • Lock 持有数    │    │ head/tail        │    │ tryRelease       │
   │  • Sem 许可证数   │    │ waitStatus       │    │ tryAcquireShared │
   │  • CDL countDown  │    │ prev/next        │    │ tryReleaseShared │
   └──────────────────┘    └──────────────────┘    └──────────────────┘

   ┌─────────────────── CLH 队列结构 ────────────────────┐
   │                                                     │
   │  head ──▶ Node(thread=null) ──▶ Node(t1) ──▶ Node(t2) ◀── tail
   │           (虚拟头/已获取锁的线程)   ←── prev ─── prev
   │                                                     │
   │  入队:CAS 修改 tail                                │
   │  出队:头节点出列后将其后继升为新 head              │
   │                                                     │
   └─────────────────────────────────────────────────────┘

   ┌─────────────────── AQS 两种模式 ────────────────────┐
   │                                                     │
   │  排他锁(独占)        共享锁                          │
   │  ┌──────────┐       ┌──────────┐                  │
   │  │ReentrantL │       │Semaphore │                  │
   │  │  ock     │       │CountdownL │                  │
   │  │公平/非公平│       │atch       │                  │
   │  └──────────┘       │ReadLock   │                  │
   │                     └──────────┘                  │
   └─────────────────────────────────────────────────────┘

   ┌────────── 阻塞/唤醒机制(park/unpark) ──────────┐
   │                                                 │
   │  阻塞: LockSupport.park(this)                  │
   │       → Unsafe.park()                          │
   │       → 操作系统挂起线程                       │
   │                                                 │
   │  唤醒: LockSupport.unpark(thread)              │
   │       → 通过 permit 许可证(0/1)实现             │
   │       → 不依赖 monitor,不需要加锁              │
   │                                                 │
   └─────────────────────────────────────────────────┘

   ┌── Q:CLH 为什么是双向链表? ──────────────────────┐
   │ A:                                              │
   │ 1. 中间节点取消时,需要前驱节点指针解除链接    │
   │ 2. 唤醒后继节点时,某些场景需要回溯前驱判断    │
   │ 3. 支持 Condition 等待队列与 CLH 间互转       │
   └─────────────────────────────────────────────────┘

   ┌── Q:唤醒时为什么从 tail 向 head 遍历? ──────────┐
   │ A: 入队时 prev 引用先建立,next 引用后建立,    │
   │ 从 head→tail 用 next 遍历可能丢节点;          │
   │ 从 tail→head 用 prev 遍历能保证完整。         │
   └─────────────────────────────────────────────────┘
```

### 第 6 章 Lock 体系与死锁

```
   ┌─────────────────────────────────────────────────────────────┐
   │                  ReentrantLock 与 synchronized              │
   └─────────────────────────────────────────────────────────────┘

   ┌──────────────────┬─────────────────────┬──────────────────────┐
   │ 维度              │ synchronized        │ ReentrantLock        │
   ├──────────────────┼─────────────────────┼──────────────────────┤
   │ 实现层级          │ JVM(Monitor)        │ JDK(AQS)             │
   │ 用法              │ 方法/代码块          │ 仅代码块,显式锁定    │
   │ 释放锁            │ 自动                │ 必须 finally unlock  │
   │ 可中断            │ 不可中断             │ lockInterruptibly()  │
   │ 公平性            │ 非公平               │ 支持公平/非公平       │
   │ 超时获取          │ 不支持               │ tryLock(time)         │
   │ Condition         │ 单一 wait/notify     │ 多个 Condition       │
   │ 锁升级            │ 偏→轻→重(JDK6+)     │ 无升级                │
   └──────────────────┴─────────────────────┴──────────────────────┘

   ┌────────── 公平锁 vs 非公平锁 ──────────┐
   │                                         │
   │ 公平锁:严格按 FIFO 队列顺序获取        │
   │   优点:线程不会饿死                     │
   │   缺点:吞吐量低,频繁上下文切换         │
   │                                         │
   │ 非公平锁:可以插队尝试                  │
   │   优点:吞吐高,默认实现                 │
   │   缺点:可能出现饿死                     │
   │                                         │
   │ synchronized 仅非公平                  │
   │ ReentrantLock(true) 才是公平           │
   └─────────────────────────────────────────┘

   ┌─────────────────── 死锁 / 活锁 / 饥饿 ───────────────────┐
   │                                                          │
   │  死锁:互相持有对方需要的锁                              │
   │   线程A 持 Lock1 等 Lock2                                │
   │   线程B 持 Lock2 等 Lock1                                │
   │                                                          │
   │  四个必要条件:                                          │
   │   ① 互斥  ② 占有等待  ③ 不可剥夺  ④ 循环等待           │
   │                                                          │
   │  避免方案:                                              │
   │   ① 固定加锁顺序  ② tryLock + 超时                      │
   │   ③ 减少锁粒度    ④ 一次性申请所有锁                    │
   │                                                          │
   │  活锁:线程一直在让,谁都没做事                          │
   │  饥饿:低优先级或非公平锁导致一直拿不到锁               │
   │                                                          │
   │  排查工具:jstack / jconsole / Arthas thread             │
   └──────────────────────────────────────────────────────────┘
```

### 第 7 章 CAS 与原子类(无锁机制)

```
   ┌─────────────────────────────────────────────────────────────┐
   │              CAS = Compare And Swap 比较并交换                │
   └─────────────────────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────────────────┐
   │   if (内存值 V == 预期值 A) {                              │
   │       V = 新值 B;                                          │
   │       return true;                                         │
   │   } else {                                                 │
   │       return false; // 失败则自旋重试                      │
   │   }                                                        │
   └──────────────────────────────────────────────────────────┘

   ┌────────── Q: CAS 不加锁吗? ──────────┐
   │ A: 业务层面无锁,但 CPU 指令层面通过  │
   │    lock cmpxchg 指令加总线锁/缓存锁  │
   │    保证原子性,因此严格说"无应用锁"。│
   └───────────────────────────────────────┘

   ┌─────────── CAS 三大问题 ──────────────────────────────┐
   │                                                        │
   │ ① ABA 问题                                             │
   │   A → B → A,CAS 仍认为没变                            │
   │   解决:AtomicStampedReference + 版本号                │
   │                                                        │
   │ ② 自旋时间过长                                         │
   │   高竞争下大量空转消耗 CPU                              │
   │   解决:退避策略 / 限制次数 / 改用锁                    │
   │                                                        │
   │ ③ 多变量原子性                                         │
   │   CAS 只能保证单个变量                                  │
   │   解决:AtomicReference 包装对象                        │
   │                                                        │
   └────────────────────────────────────────────────────────┘

   ┌────────────── 原子类家族 java.util.concurrent.atomic ───────────┐
   │                                                                  │
   │  基本类型:  AtomicInteger / AtomicLong / AtomicBoolean          │
   │  数组类型:  AtomicIntegerArray / AtomicLongArray                │
   │  引用类型:  AtomicReference / AtomicStampedReference            │
   │             / AtomicMarkableReference                            │
   │  字段更新:  AtomicIntegerFieldUpdater 等                        │
   │  累加器(JDK8): LongAdder / DoubleAdder / LongAccumulator        │
   │                                                                  │
   └──────────────────────────────────────────────────────────────────┘

   ┌────────── LongAdder vs AtomicLong ──────────────┐
   │                                                  │
   │  AtomicLong:                                    │
   │   • 单 value,所有线程竞争同一个变量              │
   │   • 高竞争下大量 CAS 自旋失败                    │
   │   • 适合低-中并发                                │
   │                                                  │
   │  LongAdder:                                     │
   │   • base + Cell[]  分段累加                     │
   │   • 不同线程 CAS 不同 Cell,降低冲突              │
   │   • sum() 时累加所有 Cell + base                │
   │   • 适合高并发计数,但实时性弱于 AtomicLong       │
   │                                                  │
   └──────────────────────────────────────────────────┘

   ┌─────── Unsafe(JVM 后门类) ───────┐
   │  • compareAndSwapInt 等 CAS 原语 │
   │  • park / unpark 阻塞唤醒        │
   │  • allocateInstance 绕过构造器    │
   │  • 直接内存操作(对象偏移量寻址)   │
   │  → AQS / 原子类 都基于 Unsafe     │
   └──────────────────────────────────┘

   ┌────── 保证 i++ 正确的 6 种方案 ──────┐
   │ ① synchronized                       │
   │ ② ReentrantLock                      │
   │ ③ AtomicInteger.incrementAndGet()    │
   │ ④ LongAdder                          │
   │ ⑤ ThreadLocal(避免共享)              │
   │ ⑥ volatile + CAS                     │
   └──────────────────────────────────────┘
```

   │ ② synchronized 包裹,性能差                    │

### 第 10 章 并发工具类(AQS 派生)

   ┌─────────────────────────────────────────────────────────────┐

   ┌─────────────────────────────────────────────────────────────┐

   ┌────────── CountDownLatch vs CyclicBarrier 对比 ──────────┐
   │  维度             │ CountDownLatch │ CyclicBarrier      │
   │  减计数 主体       │ 各子线程 down    │ await 的线程       │
   │  等待方            │ 一个主线程       │ 所有参与线程       │
   │  可重置            │ 不可             │ 可 reset           │
   │  内部实现          │ 共享锁(AQS)     │ ReentrantLock+Cond │
   │  典型场景          │ 主等子           │ 子等子             │
   └─────────────────────────────────────────────────────────────┘

```
   ┌─────────────────────────────────────────────────────────────┐
   │                    线程池核心架构                             │
   └─────────────────────────────────────────────────────────────┘

   ┌─────────────────── 7 大核心参数 ───────────────────┐
   │                                                     │
   │  ① corePoolSize       核心线程数                    │
   │  ② maximumPoolSize    最大线程数                    │

   │                                                     │
   └─────────────────────────────────────────────────────┘

   ┌─────────────────── 任务执行流程 ───────────────────┐
   │                                                     │
   │   submit(task)                                      │
   │      │                                              │
   │      ▼                                              │
   │  [worker数 < core?] ──Y──▶ 创建核心线程执行         │
   │      │ N                                            │
   │      ▼                                              │
   │  [队列未满?] ──────────Y──▶ 加入阻塞队列            │
   │      │ N                                            │
   │      ▼                                              │
   │  [worker数 < max?] ────Y──▶ 创建非核心线程执行      │
   │      │ N                                            │
   │      ▼                                              │
   │   执行拒绝策略                                       │
   │                                                     │
   └─────────────────────────────────────────────────────┘

   ┌─────────────── 4 种拒绝策略 ───────────────┐
   │ ① AbortPolicy(默认)     抛 RejectedExec异常│
   │ ② CallerRunsPolicy      谁提交谁执行         │
   │ ③ DiscardPolicy         默默丢弃             │
   │ ④ DiscardOldestPolicy   丢队首,执行新的     │
   └──────────────────────────────────────────────┘

   ┌─────────────── 5 种内置线程池 ─────────────────────────┐
   │                                                         │
   │ ① newFixedThreadPool      固定 N 个线程                  │
   │    队列: LinkedBlockingQueue 无界 ✗ OOM 风险             │
   │                                                          │
   │ ② newSingleThreadExecutor 单线程顺序执行                │
   │    队列: LinkedBlockingQueue 无界 ✗ OOM 风险             │
   │                                                          │
   │ ③ newCachedThreadPool     0~Integer.MAX_VALUE           │
   │    队列: SynchronousQueue   ✗ 线程数爆炸                │
   │                                                          │
   │ ④ newScheduledThreadPool  延迟/周期任务                  │
   │    队列: DelayedWorkQueue  无界 ✗                       │
   │                                                          │
   │ ⑤ newWorkStealingPool     ForkJoin,JDK8 工作窃取         │

   ┌── Q: 为什么不建议用 Executors? ─┐
   │ 上面 ①②③④ 都有 OOM 风险:        │
   │ 阻塞队列无界 / 线程数无界        │
   │ → 阿里规约要求手动 new ThreadPool│
   │   Executor,显式指定边界。       │
   └────────────────────────────────┘

   ┌────── 线程池大小怎么设? ──────────┐
   │                                    │
   │ CPU 密集型: N = CPU核心数 + 1      │
   │ IO  密集型: N = CPU核心数 × 2      │
   │                                    │
   │ 通用公式:                          │
   │   N = CPU核 × (1 + W/C)            │
   │   W = 等待时间  C = 计算时间        │
   │                                    │
   │ 实践:压测调优,优于公式            │
   └────────────────────────────────────┘

   ┌────────────────── 线程池其他要点 ──────────────────┐
   │                                                     │
   │ • 复用原理:Worker 线程 run() 中 while 循环          │
   │   不断从 workQueue.take() 获取任务执行              │
   │                                                     │
   │ • 核心线程默认不回收;开启 allowCoreThreadTimeOut    │
   │   后,核心线程超时也回收                            │
   │                                                     │
   │ • 线程异常:                                         │
   │   execute() 提交:异常会传播,worker 死亡,自动补  │
   │   submit() 提交:异常被吞,从 Future.get 才能拿到  │
   │   建议:try-catch 在任务内部捕获                     │
   │                                                     │
   │ • 必须 shutdown():否则非守护线程使 JVM 无法退出     │
   │   shutdown()      平滑关闭,等待已有任务完成        │
   │   shutdownNow()   立即停止,返回未执行任务列表      │
   │                                                     │
   │ • 判断任务全部完成:                                  │
   │   ① getCompletedTaskCount == getTaskCount          │
   │   ② CountDownLatch                                  │
   │   ③ shutdown() + awaitTermination()                │
   │   ④ Future.get() 等所有结果                         │
   │                                                     │
   │ • 动态调整: setCorePoolSize / setMaximumPoolSize   │
   │   美团方案:WorkQueue 也支持动态(自定义)            │
   │                                                     │
   └─────────────────────────────────────────────────────┘

                  │  (线程池核心)       │         │ LinkedBQ/ArrayBQ │
                  └─────────┬──────────┘         │ SynchronousQueue │
                            │                    │ DelayedQueue     │
                            │                    │ PriorityBQ       │
                            ▼                    └──────────────────┘
                  ┌────────────────────┐
                  │  应用层使用         │
                  │ Executors / Spring │
                  │ @Async / 业务任务   │
                  └────────────────────┘

  并行存在的隔离方案:
  ┌────────────┐  避免共享        ┌────────────────┐
  │ThreadLocal │ ───────────────▶ │ 每线程独立副本  │
  │            │                  │ 不存在线程安全  │
  └────────────┘                  └────────────────┘

  并发容器:
  ┌──────────────────┐  锁分段/CAS    ┌──────────────────┐
  │ConcurrentHashMap │ ─────────────▶ │ 高并发读写       │
  │CopyOnWriteList   │  写时复制       │ 读多写少         │
  │BlockingQueue     │  ReentrantLock │ 生产消费         │
  └──────────────────┘                └──────────────────┘
```
