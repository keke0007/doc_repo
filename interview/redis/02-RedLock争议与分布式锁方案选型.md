# RedLock 争议与分布式锁方案选型

> 本文聚焦分布式锁的演进、RedLock 的设计原理、Martin vs antirez 的著名争论,以及生产环境如何选型。

---

## 一、分布式锁需要满足什么?

```
   ┌──────────────────────────────────────────────────────┐
   │           分布式锁的 5 大核心属性                     │
   └──────────────────────────────────────────────────────┘

   ① 互斥性  Mutual Exclusion
      └─ 同一时刻只能有一个客户端持有锁

   ② 防死锁  Deadlock Free
      └─ 客户端崩溃后,锁能自动释放(过期时间)

   ③ 防误删  Fault Tolerance
      └─ 客户端 A 不能删除客户端 B 的锁(value=UUID)

   ④ 可重入  Reentrant
      └─ 同一线程多次获取同一锁不被阻塞

   ⑤ 锁续期  Auto Renewal
      └─ 业务未完成时延长锁的有效期(看门狗)
```

## 二、单机 Redis 锁:setnx 实现

### 2.1 演进史

```
   阶段 1: 错误版本
   ─────────────────────
   SETNX lock_key 1          ← 没有过期时间!
   ...业务执行...             ← 如果崩溃 = 死锁!
   DEL lock_key

   阶段 2: 改进版(仍有问题)
   ─────────────────────
   SETNX lock_key 1
   EXPIRE lock_key 30        ← 两步操作,不原子!
                              ← 如果在两步之间崩溃 = 死锁!

   阶段 3: 推荐版(Redis 2.6.12+)
   ─────────────────────────────────
   SET lock_key <uuid> NX EX 30
                    │     │  │
                    │     │  └─ 30秒过期(防死锁)
                    │     └──── 不存在时设置(原子互斥)
                    └────────── UUID 标识持有者(防误删)

   解锁(Lua 脚本保证原子)
   ─────────────────────
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1])
   else
       return 0
   end
```

### 2.2 setnx 为什么是原子的?

```
   Redis 单线程命令模型
        │
        ├─ 所有命令在同一线程串行执行
        ├─ SETNX 是单个命令(不是 GET 再 SET)
        ├─ 命令开始执行后不会被打断
        └─ 天然原子
```

### 2.3 setnx 锁的问题

```
   ❌ 锁过期时,业务还没完成 → 锁失效,其他客户端获取
   ❌ 客户端 GC 停顿 → 锁可能在停顿期间过期
   ❌ 主从切换 → 锁可能在 master 已写但未同步到 slave 时丢失
   ❌ 无可重入
   ❌ 无阻塞获取(需自己写重试)
```

## 三、Redisson:工业级单机 Redis 锁

```
   ┌──────────────────────────────────────────────────────┐
   │              Redisson 解决的问题                      │
   └──────────────────────────────────────────────────────┘

   ① 看门狗(Watchdog)自动续期
      ─ 默认锁超时 30s
      ─ 后台线程每 1/3 超时(10s)检查
      ─ 若线程仍持锁 → 续期到 30s
      ─ 客户端宕机 → 看门狗停止 → 锁自然过期

   ② 可重入(基于 Hash 结构)
      HSET lock_key <uuid:threadId> <count>
      ─ 同线程再次获取 → count + 1
      ─ 释放 → count - 1,直到 0 才真正删除

   ③ Pub/Sub 实现阻塞获取
      ─ 获取失败 → 订阅锁释放通知
      ─ 锁释放时 publish 消息
      ─ 等待方收到通知后再次尝试

   ④ 公平锁 / 读写锁 / 信号量 等丰富 API
```

### 3.1 看门狗机制流程图

```
   ┌────────────┐
   │ tryLock()  │
   └─────┬──────┘
         ▼
   ┌─────────────────────┐
   │ 加锁成功(超时30s)   │
   └─────┬───────────────┘
         ▼
   ┌─────────────────────────────────┐
   │ 启动后台 Timer(每10s触发)      │
   └─────┬───────────────────────────┘
         ▼
   ┌─────────────────────────────────┐
   │ 检查线程是否仍持锁              │
   └──┬─────────────────────────┬────┘
      │ 是                       │ 否(已释放/客户端崩溃)
      ▼                          ▼
   重置过期时间为30s          停止 Timer,锁过期自然释放
      │
      └──→ 循环
```

### 3.2 如果任务执行时间比锁的超时时间长怎么办?

```
   方案 1: 看门狗自动续期(推荐,Redisson 默认)
        └─ 业务无感,锁自动延期

   方案 2: 业务幂等设计
        └─ 即使锁失效产生并发,也不会出错

   方案 3: 估算合理超时时间
        └─ 设置远大于业务执行时间的超时

   ❌ 反模式:在业务里手动 expire 续期
              (无法应对客户端崩溃,需重新实现看门狗)
```

## 四、RedLock 红锁:为多 Redis 节点设计

### 4.1 解决什么问题?

```
   ┌─────────────────────────────────────────────────────────┐
   │ 单 Redis(包括主从) 的故障场景                          │
   └─────────────────────────────────────────────────────────┘

   时间线:
   ─────────────────────────────────────────▶
   t1: 客户端 A 在 master 加锁成功
   t2: master 还没把锁同步给 slave(异步复制)
   t3: master 宕机
   t4: slave 晋升为 master(没有这个锁)
   t5: 客户端 B 来加同一个锁 → 成功!
       → A 和 B 同时持锁,互斥失败 ❌

   ── RedLock 的解决思路 ──
   不依赖主从复制,而是部署 N 个独立的 Redis 实例
```

### 4.2 RedLock 算法步骤

```
   前置:部署 N(通常=5) 个完全独立的 Redis Master 实例

   ┌─────────────────────────────────────────────────────┐
   │ Step 1: 获取当前时间戳 T1                            │
   ├─────────────────────────────────────────────────────┤
   │ Step 2: 依次向 N 个实例请求锁                        │
   │        SET key val NX EX <ttl>                       │
   │        每次请求设置短的超时(几十毫秒)               │
   │        某个实例不可用时快速跳过                       │
   ├─────────────────────────────────────────────────────┤
   │ Step 3: 计算获取总耗时 T2 - T1                       │
   ├─────────────────────────────────────────────────────┤
   │ Step 4: 判断成功条件                                 │
   │        ① 至少 N/2+1 个实例加锁成功                  │
   │        ② 且 (T2 - T1) < 锁有效期 ttl                │
   │        → 锁的实际有效期 = ttl - (T2-T1) - 时钟漂移   │
   ├─────────────────────────────────────────────────────┤
   │ Step 5: 失败处理                                     │
   │        → 向所有实例发送释放命令                       │
   │        (即使部分加锁失败也要释放,防止残留)          │
   └─────────────────────────────────────────────────────┘
```

### 4.3 RedLock 流程示意

```
   ┌─────────┐   T1=100ms              T2=300ms
   │ Client  │ ──┐                    ┌─→ 总耗时 200ms
   └─────────┘   │                    │
                 ▼                    │
              ┌──────────────────────────────┐
              │ 并行(实际依次)向 5 个实例请求│
              └──┬────┬────┬────┬────┬───────┘
                 ▼    ▼    ▼    ▼    ▼
              [R1] [R2] [R3] [R4] [R5]
               ✓    ✓    ✗    ✓    ✓     ← 4/5 成功 ≥ 3 (N/2+1)
                                          ← 耗时 200ms < ttl 1000ms
                                          → 获取成功!
                                          → 有效期 = 1000 - 200 = 800ms
```

## 五、Martin 对 RedLock 的著名批评

> Martin Kleppmann (《DDIA》作者) 2016 年发表 *How to do distributed locking*
> antirez (Redis 作者) 当天发文回应

### 5.1 批评 1: GC 停顿 / 网络延迟

```
   场景演示:
   ─────────────────────────────────────────────────────▶
   t0: 客户端 A 获取 RedLock(有效期 10s)
   t1: A 准备写入数据库
   t2: A 进入长时间 GC 停顿(15s)
   t3: A 的锁过期(t0+10s)
   t4: 客户端 B 获取 RedLock 成功
   t5: B 写入数据库
   t6: A GC 结束,继续执行,以为自己还持锁
   t7: A 写入数据库 → 与 B 并发写,数据损坏 ❌

   ─ A 完全不知道自己已经失去锁 ─
```

### 5.2 批评 2: 时钟漂移

```
   RedLock 算法依赖时间判断:
     ─ 有效期 = ttl - (T2-T1) - 时钟漂移补偿

   但分布式系统的时钟不可靠:
     ─ NTP 时间跳变(管理员手动调时,闰秒)
     ─ 虚拟机时钟漂移
     ─ 多个 Redis 节点时钟不同步

   如果某节点时钟突然向前跳:
     该节点上的锁会被认为已过期 → 提前释放
     → 多数派失效
```

### 5.3 批评 3: 真正的解决方案是 Fencing Token

```
   ┌────────────────────────────────────────────────────────┐
   │  Fencing Token: 单调递增的 token                       │
   └────────────────────────────────────────────────────────┘

   ─────────────────────────────────────────▶ 时间
   ① A 获取锁,拿到 token=33
   ② A 长时间 GC 停顿
   ③ A 锁过期,B 获取锁,拿到 token=34
   ④ B 携带 token=34 写入存储 → 存储记录 token=34
   ⑤ A GC 恢复,携带 token=33 写入存储
   ⑥ 存储发现 33 < 34 → 拒绝 A 的写入 ✓

   关键:存储层必须支持 token 比较,Redis 锁本身不提供
   ZooKeeper 通过 zxid 天然提供 fencing token
```

### 5.4 antirez 的回应

```
   antirez 反驳:
   ─ 时钟跳变可通过运维约束缓解(禁止 NTP 大幅跳变)
   ─ GC 停顿是所有分布式锁的共性问题(包括 ZooKeeper)
   ─ 应用层应该用幂等性兜底
   ─ RedLock 在实际场景已经够用
   ─ 强一致场景本来就该用 Zookeeper / etcd
```

## 七、生产实践对照表

| 场景 | 推荐方案 | 备注 |
|------|---------|------|
| 防止重复提交 | `SET key val NX EX <短时间>` | 简单可靠,前端按钮防抖 |
| 接口幂等控制 | setnx + 请求 ID | 业务级幂等 |
| 库存扣减 | Redisson + 库存预扣减 + DB 校验 | 双层保险 |
| 定时任务防并发 | Redisson | 看门狗续期 |
| 资金交易 | ZK / etcd + 数据库唯一约束 | 强一致 |
| 高并发秒杀 | Redis Lua 脚本扣库存(无锁) | 锁会拖慢性能 |
| 跨数据中心 | etcd / Zookeeper | RedLock 不适合 |

## 八、所有分布式锁方案的「兜底原则」

```
   ┌─────────────────────────────────────────────────────────┐
   │  ★★★ 任何分布式锁都不是 100% 可靠 ★★★              │
   │                                                          │
   │  必须在业务层做幂等设计:                                │
   │  ─ 数据库唯一约束(订单号、流水号)                      │
   │  ─ 状态机(只允许特定状态流转)                          │
   │  ─ 乐观锁(version 字段)                                │
   │  ─ Fencing Token(单调递增标识)                         │
   │                                                          │
   │  分布式锁的作用:降低并发概率,提升吞吐                  │
   │  业务幂等的作用:保证正确性                              │
   └─────────────────────────────────────────────────────────┘
```

## 九、面试高频追问

**Q: setnx 为什么是原子的?**
A: Redis 单线程串行执行命令,SETNX 是单个命令不会被打断;且 Redis 2.6.12+ 的 `SET ... NX EX` 把判断、设值、设过期合在一条命令,彻底原子。

**Q: 解锁为什么要用 Lua 脚本?**
A: 解锁需要先 GET 判断 owner 再 DEL,两步操作之间锁可能过期被别人重新获取,Lua 脚本保证 GET+DEL 整体原子。

**Q: 看门狗机制怎么实现的?**
A: 加锁成功后启动后台定时任务,每 1/3 锁超时时间检查一次,若线程仍持锁则执行 EXPIRE 续期到原超时;客户端宕机则看门狗停止,锁自然过期。

**Q: RedLock 解决了什么问题?**
A: 解决单 Redis(包括主从)在故障转移时锁丢失的问题,通过 N/2+1 多数派部署在独立的 Redis 实例上实现。

**Q: RedLock 真的安全吗?**
A: 不能保证绝对安全,Martin 指出 GC 停顿、时钟漂移、网络分区都可能导致锁失效但客户端不知情;生产环境推荐用 Redisson + 业务幂等,强一致场景用 ZK / etcd。

**Q: 任务比锁的超时时间长怎么办?**
A: 首选看门狗自动续期(Redisson 默认),其次业务幂等设计兜底,合理估算超时时间。
