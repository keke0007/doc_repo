# Redis Cluster 集群路由与分片深度剖析

> 本文聚焦集群分片、路由、扩缩容、故障转移等核心机制,理清「key 是如何找到正确节点的」这条主线。

---

## 一、为什么需要 Redis Cluster?

```
   单机 Redis 的瓶颈
      │
      ├─ 内存上限   ────→ 单机内存有限(通常 < 64GB)
      ├─ 持久化压力 ────→ 内存越大 RDB fork 越慢
      ├─ 写并发瓶颈 ────→ 即使主从也只能扩展读
      └─ 单点故障   ────→ 哨兵能切换主从,但不能水平扩展
                              │
                              ▼
                    ┌──────────────────┐
                    │  Redis Cluster   │
                    │  = 分片 + 主从    │
                    │  + 自动故障转移   │
                    └──────────────────┘
```

## 二、分片方案对比:为什么不用一致性哈希?

```
┌────────────────────┬────────────────────────┬─────────────────────────┐
│      维度          │    一致性 Hash 环       │   哈希槽 (Redis Cluster) │
├────────────────────┼────────────────────────┼─────────────────────────┤
│ 节点变动影响       │ 仅相邻节点受影响        │ 仅迁移涉及的槽           │
│ 均衡性             │ 需大量虚拟节点保证      │ 槽固定,天然均匀         │
│ 路由计算           │ 客户端独立计算          │ 客户端+服务端协作        │
│ 节点感知           │ 客户端需维护节点表      │ 集群广播槽位映射         │
│ 实现复杂度         │ 较高(虚拟节点+排序)    │ 简单清晰                 │
│ 管理粒度           │ 节点级                  │ 槽级(更细)              │
└────────────────────┴────────────────────────┴─────────────────────────┘
```

**核心理由:**
- 哈希槽是「逻辑分片」,数据归属与物理节点解耦,节点变动只迁移槽即可
- 槽数固定 = 16384,集群规模和槽数无关,可控可预测

## 三、CRC16 算法与槽位计算

### 3.1 基础公式

```
   slot = CRC16(key) mod 16384
```

### 3.2 Hash Tag 机制(关键!)

```
   key 中含 {...} 时,只对 {} 内字符计算 CRC16
   ──────────────────────────────────────────

   key = "user1000.profile"  → CRC16("user1000.profile") % 16384
   key = "{user1000}.profile" → CRC16("user1000") % 16384
   key = "{user1000}.orders"  → CRC16("user1000") % 16384
                                       │
                                       └─→ 这两个 key 必然在同一槽!
```

**应用场景:**
- MGET / MSET 多 key 操作要求所有 key 在同槽
- 事务 MULTI/EXEC 涉及的 key 要在同槽
- Lua 脚本中操作的 key 要在同槽

## 四、为什么是 16384 槽?(antirez 官方解释)

```
   ┌───────────────────────────────────────────────────────────┐
   │ 三个核心原因                                              │
   └───────────────────────────────────────────────────────────┘

   ① 心跳包带宽
      节点信息 bitmap 大小 = 槽数 / 8 字节
      16384 槽 → 2KB     ✓ 合理
      65536 槽 → 8KB     ✗ 心跳包过大

   ② 集群规模上限
      Redis 官方推荐节点数 ≤ 1000
      16384 / 1000 ≈ 16 槽/节点   ✓ 足够细粒度
      65536 槽对 1000 节点是浪费

   ③ Bitmap 压缩效率
      节点越少,槽位 bitmap 中连续段越长
      使用 myslots[CLUSTER_SLOTS/8] 压缩传输
      16384 在压缩率和粒度之间是最佳平衡点
```

## 五、路由机制:客户端如何找到正确节点?

### 5.1 三种客户端模式

```
   ┌─────────────────────────────────────────────────────────────┐
   │                客户端路由模式                                │
   └─────────────────────────────────────────────────────────────┘
   ┌──────────────┐   ┌────────────────────┐   ┌────────────────┐
   │ Dummy Client │   │ Smart Client(主流) │   │ Proxy 代理     │
   ├──────────────┤   ├────────────────────┤   ├────────────────┤
   │ 随机连任意节点│   │ 启动时拉取槽位映射  │   │ 客户端无感     │
   │ 接收 MOVED   │   │ 本地缓存路由表      │   │ 由 Proxy 路由   │
   │ 重试到正确节点│   │ 直接路由到目标节点  │   │ 例: codis      │
   │ 性能差        │   │ 路由变化时刷新缓存  │   │                │
   └──────────────┘   └────────────────────┘   └────────────────┘
```

### 5.2 MOVED 重定向(永久)

```
   客户端请求 ──→ 节点 A
                    │
                    ├─ 检查 slot 是否归属自己
                    │
                    └─ 不归属 → 返回 MOVED <slot> <ip:port>

   响应示例:
       MOVED 6789 192.168.1.100:6379

   含义:这个 slot 永久归 192.168.1.100 管,以后直接找它
   客户端动作:更新本地路由表 → 重发请求
```

### 5.3 ASK 重定向(临时,迁移中)

```
   场景:slot 正从节点 A 迁移到节点 B,迁移过程中

   ┌─────────┐   GET key   ┌─────────┐
   │ Client  │ ──────────▶ │ Node A  │  ← 源节点(部分数据已迁走)
   └────┬────┘             └────┬────┘
        │                       │
        │  ASK <slot> <B-ip:port> ← 注意是 ASK 不是 MOVED
        │◀──────────────────────│
        │
        │  ① 先发 ASKING 命令(告知 B 临时接受请求)
        │  ② 再发原命令
        ▼
   ┌─────────┐
   │ Node B  │  ← 目标节点
   └─────────┘

   关键区别:
   ─ MOVED:更新本地路由表
   ─ ASK:  不更新本地路由表(下次还是先找 A)
```

### 5.4 MOVED vs ASK 对比

```
┌──────────────┬─────────────────────┬───────────────────────┐
│              │     MOVED           │       ASK             │
├──────────────┼─────────────────────┼───────────────────────┤
│ 触发场景     │ 槽已完成迁移         │ 槽正在迁移            │
│ 客户端动作   │ 更新本地槽位映射     │ 不更新映射,本次重定向│
│ 前置命令     │ 直接请求             │ 必须先发 ASKING       │
│ 性质         │ 永久                │ 临时                  │
└──────────────┴─────────────────────┴───────────────────────┘
```

## 六、扩容流程详解

```
   [Step 1] 新节点加入
       └─ cluster meet <new-ip> <port>
              │
              ▼
   [Step 2] 重新分片(reshard)
       └─ 计算需要从哪些源节点迁出多少槽
              │
              ▼
   [Step 3] 单个槽迁移流程
       ┌─────────────────────────────────────────────────┐
       │ 源节点:cluster setslot <slot> migrating <to-id> │
       │ 目标节点:cluster setslot <slot> importing <from>│
       │                  │                              │
       │ 循环执行:                                       │
       │   cluster getkeysinslot <slot> <count>          │
       │     ↓                                           │
       │   migrate <to-ip> <port> <key> 0 timeout        │
       │     ↓                                           │
       │   直到槽内 key 全部迁移完毕                      │
       │                  │                              │
       │ cluster setslot <slot> node <to-id>             │
       │   (源、目标、其他节点都执行)                     │
       └─────────────────────────────────────────────────┘
              │
              ▼
   [Step 4] 客户端感知
       └─ 通过 MOVED 重定向逐步更新路由表
```

### 6.1 扩缩容期间是否可服务?

**可以正常服务。** 关键机制:

```
   迁移过程中,key 可能在源 / 目标节点
                    │
                    ▼
        ┌───────────────────────────┐
        │ 客户端请求 GET key        │
        └────────────┬──────────────┘
                     ▼
            ┌────────────────┐
            │ 槽属于源节点?  │
            └───┬────────┬───┘
                │是      │否(已迁完)
                ▼        ▼
       ┌────────────┐  MOVED 重定向
       │ 源节点查找  │
       └─────┬──────┘
             │
       ┌─────┴──────┐
       │ key存在?  │
       └──┬──────┬──┘
         是│     │否
          ▼     ▼
      正常返回  ASK 重定向到目标
```

## 七、Gossip 通信机制

```
   ┌─────────────────────────────────────────────────────────┐
   │                Gossip 协议 4 种消息                      │
   ├─────────┬───────────────────────────────────────────────┤
   │ MEET    │ 通知节点加入集群                              │
   │ PING    │ 心跳,携带部分节点状态信息(随机选若干节点)   │
   │ PONG    │ PING 的响应,也可主动广播                     │
   │ FAIL    │ 节点客观下线时广播                            │
   └─────────┴───────────────────────────────────────────────┘

   通信特征:
   ─ 每个节点每秒随机选 5 个节点 PING
   ─ 优先选 cluster-node-timeout/2 未通信的节点
   ─ 信息最终一致(非强一致)
   ─ 集群规模越大,信息收敛越慢

   ┌──────────────────────────────────────────────┐
   │ 与 Zookeeper Zab 协议对比                    │
   ├──────────────────────────────────────────────┤
   │ Zab:中心化,强一致,适合元数据少的场景       │
   │ Gossip:去中心化,最终一致,适合大规模集群    │
   └──────────────────────────────────────────────┘
```

## 八、故障转移流程

```
   ┌─────────────────────────────────────────────────────────┐
   │  Step 1: 主观下线 PFAIL                                 │
   │     节点 A 在 cluster-node-timeout 内收不到节点 B 响应  │
   │     → 标记 B 为 PFAIL                                   │
   └──────────────────────────┬──────────────────────────────┘
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │  Step 2: PFAIL 通过 Gossip 传播                         │
   │     其他节点收到 PFAIL 信息并自己确认                    │
   └──────────────────────────┬──────────────────────────────┘
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │  Step 3: 客观下线 FAIL                                  │
   │     超过半数主节点都标记 B 为 PFAIL                      │
   │     → 任一节点将 B 升级为 FAIL,广播 FAIL 消息            │
   └──────────────────────────┬──────────────────────────────┘
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │  Step 4: 从节点发起选举                                  │
   │     ① 检测到 master FAIL                                │
   │     ② 等待延迟(防止多个从节点同时发起):              │
   │        delay = 500ms + random(0,500ms) + SLAVE_RANK*1s  │
   │        (复制偏移量越大的从节点,RANK越小,越早发起)    │
   │     ③ 向其他主节点发起 CLUSTER_VOTE_REQUEST              │
   └──────────────────────────┬──────────────────────────────┘
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │  Step 5: 主节点投票                                     │
   │     ─ 每个主节点 1 票,先到先投                          │
   │     ─ 同一选举周期(epoch)只投一次                      │
   └──────────────────────────┬──────────────────────────────┘
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │  Step 6: 获得 N/2+1 票 → 晋升 Master                    │
   │     ─ 撤销自己的从节点身份                              │
   │     ─ 接管原 master 负责的所有 slot                     │
   │     ─ 通过 PONG 广播自己的新身份                         │
   └─────────────────────────────────────────────────────────┘
```

## 九、为什么至少要 3 主节点?

```
   故障转移依赖主节点投票(基于 Raft 思想的多数派原则)

   ┌──────────────────────────────────────────────┐
   │   主节点数 = 2 的尴尬场景                    │
   │   ────────────────────────────                │
   │   1 个挂掉 → 剩 1 票                          │
   │   N/2+1 = 2,无法达成多数派                   │
   │   → 故障无法转移,集群不可用                  │
   └──────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────┐
   │   主节点数 = 3 的合理性                      │
   │   ────────────────────────                    │
   │   1 个挂掉 → 剩 2 票                          │
   │   N/2+1 = 2,达成多数派 ✓                    │
   │   → 故障可正常转移                            │
   └──────────────────────────────────────────────┘

   推荐配置:3 主 3 从(最小生产配置)
   ─ 每个主节点配一个从节点
   ─ 16384 槽均分给 3 主:大约每个主 5461 槽
```

## 十、生产实践要点总结

| 主题 | 要点 |
|------|------|
| 客户端选择 | 必须用 Smart Client(Jedis Cluster / Lettuce / redis-py-cluster) |
| Key 设计 | 跨 key 操作必须用 hash tag,例: `{order:1001}:items` |
| 集群规模 | 推荐主节点数 ≤ 1000,实际多为 10-30 主节点 |
| 槽迁移 | 选业务低峰期,可调 `--pipeline` 加速 migrate |
| 监控指标 | 集群状态 `cluster info`,槽分布 `cluster slots` |
| 故障演练 | 定期 kill 主节点验证故障转移 |
| 大 Key 排查 | 大 Key 迁移会卡住,提前用 `--bigkeys` 扫描 |

## 十一、面试高频追问汇总

**Q: 为什么不用一致性哈希?**
A: 槽位是逻辑分片,数据归属与节点解耦,迁移粒度更细;一致性哈希需虚拟节点保证均衡,实现更复杂。

**Q: hash tag 有什么用?**
A: 强制相关 key 落到同一槽,使 MGET / 事务 / Lua 能跨 key 操作。

**Q: 为什么 16384 槽?**
A: 心跳包带宽(2KB vs 8KB)、推荐节点数 ≤ 1000、bitmap 压缩效率三个因素的折衷。

**Q: MOVED 和 ASK 区别?**
A: MOVED 是永久重定向(更新本地路由表),ASK 是临时重定向(迁移过程中,不更新映射)。

**Q: 扩容时数据怎么迁移?**
A: 单个 slot 迁移,源置 migrating,目标置 importing,migrate 命令逐 key 移动,完成后广播路由变化。

**Q: 一个主节点挂了怎么办?**
A: 主观下线 → Gossip 传播 → 客观下线 → 从节点等待延迟 → 投票选举 → N/2+1 票晋升 → 接管 slot。

**Q: 为什么至少 3 主?**
A: 投票需 N/2+1 多数派,2 主节点 1 个挂掉无法达成多数派,集群将不可用。
