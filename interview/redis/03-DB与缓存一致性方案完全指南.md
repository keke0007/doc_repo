# DB 与缓存一致性方案完全指南

> 本文聚焦 Redis 缓存与 DB 的一致性问题:四种基础方案对比、延迟双删、Canal 订阅 binlog、强一致与最终一致权衡、生产选型。

---

## 一、问题本质:为什么会不一致?

```
   ┌──────────────────────────────────────────────────────────┐
   │  缓存与 DB 是两个独立存储                                 │
   │  无法用单机事务原子更新两者                                │
   │  → 中间必然存在「不一致窗口」                              │
   └──────────────────────────────────────────────────────────┘

   不一致的根因:
   ① 操作顺序问题(谁先谁后)
   ② 部分操作失败(DB 成功缓存失败 / 反之)
   ③ 并发问题(读写交错)
   ④ 主从延迟(读到 slave 旧数据,回填到缓存)
```

---

## 二、四种基础方案对比

### 方案 1:先更新 DB,再更新缓存

```
   线程 A:                    线程 B:
   ─────────                  ─────────
   t1: UPDATE DB → val=1
   t2: 网络抖动延迟...
                              t3: UPDATE DB → val=2
                              t4: SET cache  → val=2
   t5: SET cache → val=1        ← 后到达,覆盖了 val=2

   结果:DB=2,cache=1 ❌ 长期不一致
```

**问题**:并发写入时缓存可能被覆盖为旧值。
**结论**:❌ 不推荐。

---

### 方案 2:先更新缓存,再更新 DB

```
   t1: SET cache → 1
   t2: UPDATE DB → 失败!网络异常

   结果:cache=1(用户看到的),DB=旧值 ❌
```

**问题**:
- DB 是事实来源,缓存超前于 DB 风险高
- 缓存内容很多是计算结果(不只是 DB 行),没必要在写时计算

**结论**:❌ 几乎不用。

---

### 方案 3:先删缓存,再更新 DB

```
   线程 A(写):              线程 B(读):
   ─────────                  ─────────
   t1: DEL cache
                              t2: GET cache → miss
                              t3: SELECT DB → val=旧
                              t4: SET cache → val=旧  ← 回填了旧值
   t5: UPDATE DB → val=新

   结果:DB=新,cache=旧 ❌
```

**问题**:并发读写时,读线程会回填旧值。
**结论**:❌ 单独使用不可靠,需配合「延迟双删」。

---

### 方案 4:先更新 DB,再删缓存(Cache Aside,主流)

```
   线程 A(写):              线程 B(读):
   ─────────                  ─────────
   t1: UPDATE DB → val=新
   t2: DEL cache
                              t3: GET cache → miss
                              t4: SELECT DB → val=新
                              t5: SET cache → val=新

   ✓ 最终一致
```

#### 极小概率的不一致场景:

```
   线程 A(写):              线程 B(读):
   ─────────                  ─────────
                              t1: GET cache → miss
                              t2: SELECT DB → val=旧
                              (此时线程 B 被卡住,极慢)
   t3: UPDATE DB → val=新
   t4: DEL cache
                              t5: SET cache → val=旧 ❌

   触发条件:
   ─ 读线程恰好 cache miss
   ─ 读线程读 DB 之后、回填之前,写线程完成 DB 更新 + DEL
   ─ 读写线程发生这样的精确交错
   → 实际概率极低,可接受
```

**结论**:✅ 主流推荐方案,简称 **Cache Aside Pattern**。

## 三、四种方案总结对比

```
┌─────────────────────────┬────────────────┬──────────────────────────────┐
│        方案             │ 不一致风险      │ 评价                          │
├─────────────────────────┼────────────────┼──────────────────────────────┤
│ ① 先更新DB,后更新缓存  │ 高(并发覆盖)  │ ❌ 不推荐                     │
│ ② 先更新缓存,后更新DB  │ 极高(DB可能失败)│ ❌ 几乎不用                   │
│ ③ 先删缓存,后更新DB    │ 中(读回填旧值)│ ⚠ 需配合延迟双删              │
│ ④ 先更新DB,后删缓存    │ 低(精确交错)  │ ✅ 主流推荐 (Cache Aside)     │
└─────────────────────────┴────────────────┴──────────────────────────────┘
```

## 四、延迟双删(Double Delete)

应对场景:主从架构下,删缓存后从库还没同步完成,读线程从从库回填了旧值。

```
   ┌──────────────────────────────────────────────────────┐
   │              延迟双删流程                             │
   └──────────────────────────────────────────────────────┘

   Step 1: 删除缓存(防止旧值被读到)
        DEL cache

   Step 2: 更新 DB(写主库)
        UPDATE DB

   Step 3: 异步休眠 N 毫秒
        sleep(N)   ← N = 主从同步延迟的经验值,通常 500ms-1s

   Step 4: 再次删除缓存
        DEL cache

   ─ 作用 ─
   即使中间有读线程从从库读到旧值并回填缓存
   第二次 DEL 也会把这个错误缓存清掉
```

### 实现注意点:

```
   ❌ 同步 sleep 会拖慢请求 RT
   ✓ 用消息队列异步延迟删除(MQ 延迟消息)
   ✓ 或起线程池异步执行第二次 DEL
   ✓ 第二次删除失败要重试(写入失败队列)
```

## 五、订阅 Binlog 方案(Canal + MQ)

```
   ┌────────────┐    写    ┌────────┐  binlog   ┌────────┐
   │ 应用       │ ───────→ │ MySQL  │ ────────→ │ Canal  │
   └────────────┘          └────────┘           └────┬───┘
                                                     │
                                                     ▼
                                                 ┌────────┐
                                                 │ Kafka  │
                                                 └────┬───┘
                                                     │
                                                     ▼
                                                 ┌────────────────┐
                                                 │ 消费者         │
                                                 │ → DEL cache    │
                                                 └────────────────┘
```

### 5.1 优点

- **业务代码无侵入**:开发只写 DB,缓存维护交给 Canal
- **解耦**:DB 与缓存通过 binlog 异步打通
- **失败可重试**:MQ ACK 机制保证不丢失
- **顺序保证**:binlog 天然有序

### 5.2 缺点

- **引入额外组件**:Canal、Kafka 都需要运维
- **异步延迟**:仍有秒级的不一致窗口
- **复杂度高**:链路长,故障排查难

### 5.3 适用场景

- 缓存数据复杂、多业务方共享
- 不希望业务代码维护缓存
- 接受秒级最终一致

          ▼                                              ▼

   │ 性能极差          │                    │ 性能好              │
   │ 几乎不用          │                    │ 主流方案            │
   └───────────────────┘                    └─────────────────────┘

          ▼                                              ▼
   ┌───────────────────┐                    ┌─────────────────────┐

## 七、生产决策矩阵

| 业务场景 | 推荐方案 | 不一致容忍度 |
|---------|---------|------------|
| 商品列表/详情 | Cache Aside | 秒级 |
| 用户基本信息 | Cache Aside | 秒级 |
| 用户余额(读多写少) | Cache Aside + 延迟双删 | 毫秒级 |

## 八、常见坑点

### 坑 1:缓存与 DB 都更新成功了,但顺序不对

**问题**:两次写操作并发,缓存被覆盖为更早的值。
**解决**:用消息队列保证同一资源的更新串行化;或 Cache Aside(删除而非更新)。

---

### 坑 2:删缓存失败

```
   场景:UPDATE DB 成功了,DEL cache 失败(网络抖动 / Redis 抖动)

   解决方案:
   ① 重试 N 次
   ② 写入失败队列,异步重试
   ③ 借助 Canal 兜底:即使业务删除失败,binlog 也会触发删除
```

---

### 坑 3:大 Key 删除导致阻塞

```
   缓存值是 List / Hash / Set 包含百万元素
   DEL 大 Key → 同步释放内存 → 阻塞 Redis 主线程

   解决:
   ─ Redis 4.0+ 使用 UNLINK 异步删除
   ─ Redis 6.0+ 配置 lazyfree-lazy-expire / lazyfree-lazy-eviction
```

---

### 坑 4:缓存预热 / 重启冷启动

```
   场景:Redis 重启或新部署,缓存全空
   → 大量请求穿透到 DB
   → DB 被压垮(类似雪崩)

   解决:
   ─ 启动时主动加载热点数据(缓存预热)
   ─ 限流 + 降级保护 DB
   ─ 灰度发布
```

---

### 坑 5:高并发下仍可能不一致

```
   真相:缓存就不应该追求严格一致
   ─ 要强一致 → 直接读 DB(放弃缓存收益)
   ─ 要高性能 → 接受最终一致
```

---

## 九、最佳实践 Checklist

```
   缓存设计三原则
   ─────────────────
   ① 缓存只缓存「读多写少 + 时效性可容忍」的数据
   ② 业务层做幂等设计,不依赖缓存的绝对一致
   ③ 缓存失败要有兜底(降级到 DB / 限流 / 熔断)

   实施 Checklist
   ─────────────────
   □ 选择 Cache Aside 作为默认方案
   □ 写操作:先 UPDATE DB,后 DEL cache
   □ 主从架构 → 加延迟双删
   □ 复杂场景 → Canal 兜底
   □ 大 Key → UNLINK
   □ 删除失败 → 重试 + MQ
   □ 启动预热
   □ 设置随机过期时间(防雪崩)
   □ 监控缓存命中率
```

## 十、面试高频追问

**Q: 为什么选「先 DB 后删 cache」?**
A: 删除是幂等操作,失败重试无副作用;且并发不一致需要精确交错(读 miss → 读 DB → 写线程更新 DB+删 cache → 读线程回填),概率极低。

**Q: 为什么是删除而不是更新缓存?**
A: ① 更新缓存有并发覆盖问题;② 缓存内容可能是计算结果,更新成本高;③ 删除是惰性的,下次读再算,节省资源;④ 删除是幂等的。

**Q: 延迟双删的延迟时间怎么定?**
A: 经验值,基于主从同步延迟。一般 500ms~1s,根据监控的实际延迟调整;过短可能没等同步完成,过长拖慢删除。

**Q: Cache Aside 还有什么问题?**
A: ① 极小概率精确交错不一致;② 删除失败需重试;③ 第一次访问 miss 穿透到 DB(缓存预热);④ 不适合写密集场景(缓存频繁失效)。

**Q: 强一致需求怎么办?**
A: ① 直接读 DB,不用缓存;② 关键资源加分布式锁(性能差);③ 用业务幂等 + 乐观锁兜底。Redis 缓存本质就是为最终一致设计的。

**Q: 主从延迟会导致什么问题?**
A: 写主库后立即读从库可能读到旧值,如果回填到缓存就是「死值」。解决:延迟双删 / 写后强制读主库 / Canal 兜底。

**Q: Canal 方案的延迟有多大?**
A: Binlog 解析 → MQ → 消费者删缓存,通常毫秒到秒级。适合可容忍秒级延迟的场景。
