nanobot:一只住在聊天软件里的 AI 管家

用 Python 写的自托管个人 AI Agent 框架:你在任意聊天软件里说话,它用「大脑 + 双手 + 记忆本」帮你把活干完,再把结果送回同一个聊天窗口。

① 解决什么场景 ② 完整流程闭环 ③ 模块关联地图 ④ 技术栈 ⑤ 适合高并发吗

总览心智模型:像一栋带收发室的大宅 —— 每扇聊天门递进来的信被翻译成统一格式,管家取信后带着记忆本去问大脑、用双手干活,直到把答案写好,再从发件室送回原门。

①

它到底为谁、解决什么场景?

nanobot 的定位非常明确:个人自托管(self-hosted, personal)。它不是给企业搭客服平台的 SaaS,而是让你在自己电脑/服务器上养一个长期在线、有记忆、能动手的私人助理。

痛点

AI 助手分散在每个 App 里

网页版 ChatGPT 不认识你 Telegram 里的上下文;每个工具都要单独开网页、登录、复制粘贴。nanobot 把一个助理接到你所有聊天软件,在哪聊都行。

痛点

聊天机器人只会说不会做

普通 bot 只能回话。nanobot 能真的干活:读写你工作区的文件、跑 shell 命令、搜网页、连 MCP 工具、生成图片,还能派「分身 subagent」并行办事。

痛点

每次开聊都失忆

网页聊天关了就忘。nanobot 有会话历史(JSONL)+ 长期记忆(MEMORY.md),空闲时还会像做梦一样「Dream」自动整理沉淀,越用越懂你。

痛点

数据隐私 & 模型被锁定

一切跑在你自己的机器上;模型随便换 —— Claude/GPT/DeepSeek/本地 Ollama 都行,主模型挂了自动切备用模型,不被任何一家绑架。

它适合高并发场景吗?

先给结论:它是为「一个人」设计的常驻服务,不是为「一万人」设计的在线系统。下面是源码里的直接证据。

✅ 擅长:个人级的多渠道、多会话并发

  • 不同会话真并行:每条消息派一个 asyncio 任务,Telegram、微信、WebUI 多个对话可同时推进(loop.py:1236 run() 逐条取信、按会话派发)。
  • 同会话严格排队:同一 channel:chat_id 的消息按序处理、自动化回合自动延后 —— 保证对话上下文一致。
  • 并发可调:环境变量 NANOBOT_MAX_CONCURRENT_REQUESTS 控制同时进行的请求数(默认不设限);maxConcurrentSubagents 默认 4 个分身并行。
  • IO 密集正好对口 asyncio:绝大头时间在等 LLM 流式返回和等工具进程,单进程事件循环就能轻松挂起成百上千个"等待中"的会话。
  • WebSocket 多路复用:一条连接可同时跑多个 chat_id,一个会话也能镜像到多个连接(两个浏览器标签页同步)。

✕ 不擅长:互联网级的高并发 SaaS

  • 存储是文件不是数据库:会话 = JSONL 文件、记忆 = Markdown、定时任务 = jobs.json,配 filelock 保护 —— 没有事务、没有水平扩展的共享存储。
  • 单进程单实例设计:gateway 用文件锁防止同配置多开;多开要靠「多实例」模式(--config 每个实例独立配置/工作区),而不是同一个服务扩容。
  • 没有分布式队列/集群机制:MessageBus 是进程内的两个 asyncio.Queue,天生单机内存级,断电即失(持久化交给 JSONL 落盘)。
  • 真正的瓶颈在 LLM API:每个活跃对话都在烧 token 和 API 速率配额 —— 并发上限实际等于你的钱包和供应商限流,框架扩到天上去也没用。
  • 安全模型按"个人"设计:Shell 工具、文件系统、工作区访问都默认信任单主人,没有多租户隔离。
