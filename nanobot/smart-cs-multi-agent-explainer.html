意图路由 Agent

分诊台 · 意图细分

它到底解决什么场景的问题？

目标场景：金融 / 电商的在线客服——用户问咨询、办业务、投诉，AI 全流程接住，人只处理 AI 搞不定的。

😱 痛点：AI 客服一本正经胡说八道
→ RAG 知识检索：回答必须来自知识库检索结果，带引用来源标注；查不到就明说并建议转人工；金融话题强制附加风险提示。
⚖️ 痛点：金融合规红线（说错一句话被监管罚）
→ 强制合规关卡：图上所有回复必须经过合规节点——违禁词/PII 正则毫秒级初筛 + LLM 深审越权承诺；不通过自动拦截转人工、PII 打码。
💰 痛点：人工客服又贵又不 7×24
→ 多 Agent 自动化：常见咨询秒答；退款/理赔/开户自动提取要素建工单（返回工单号）；只有高风险/查不到的才升级人工。
🧩 痛点：聊两句就「失忆」，断线重连全忘
→ 三层记忆 + 检查点：Redis 存最近 20 轮对话（30 分钟 TTL），向量库存永久知识；LangGraph Checkpoint 支持对话断点续接。
🕳️ 痛点：AI 系统是黑盒，出错不知道卡在哪
→ 全链路追踪：每个 Agent 每一步都是一个 OTel Span（耗时/成败/Token），Jaeger 里整条调用链一目了然，还有 /api/metrics 指标接口。
🔌 痛点：接新业务系统就要改一堆 Agent 代码
→ MCP 标准协议：工具用 JSON Schema 声明能力，注册即被自动发现调用；订单/工单/风控/知识库全是即插即用的「标准插座」。
🏦 银行 / 理财客服🛒 电商售后🛡️ 保险理赔💼 券商开户咨询☎️ 任何「咨询 + 办理 + 审查」类业务
🎓 诚实定位：README 自述这是「企业级面试项目全攻略」——本质是一个教学/求职样板项目（配套简历模板、STAR 话术、八股题库）。架构是真架构、流程是真流程，但订单/风控等工具是写死的模拟数据，工单/检查点在进程内存里，距离生产还有一段工程化路要走（见下节）。

适用于高并发场景吗？——绿灯红灯各一半

把「设计意图」和「当前实现」分开看，结论才客观。

🟡 结论先行：架构按高并发模型设计（全异步、缓存外置、工具层无状态、可水平扩副本、全程可观测），但当前代码是单机教学级——直接上线扛不住真正的高并发，瓶颈第一在 LLM，第二在三个「进程内存单点」。

🟢 架构已经具备的高并发基础

  • 全链路异步：FastAPI + asyncio（Python）/ goroutine（Go）/ CompletableFuture（Java），I/O 等待不阻塞。
  • 会话状态外置：短期记忆放 Redis，多实例部署时任何副本都能接上对话。
  • 工具层无状态：MCP 调用是无状态请求，天然可扩。
  • 容器化部署：Docker Compose 一键起，配负载均衡即可横向加副本。
  • 可观测性到位：扩容前先能看清瓶颈在哪（P99 延迟、Agent 错误率、Token 消耗都有监控位）。

🔴 当前实现的并发短板

  • LLM 是第一瓶颈：单请求要串行调 3~5 次 LLM（路由 + RAG 三连 + 合规审查），端到端约 2~3 秒；吞吐和成本被 OpenAI 速率限制锁死。
  • 三个进程内存单点：工作记忆（dict+锁）、工单库（TicketStore dict）、LangGraph 检查点（MemorySaver）——多副本各记各的，会话一漂移就失忆、丢单。
  • FAISS 不适合多副本：进程内暴力检索（IndexFlatIP），各副本索引不一致；且演示 embedding 是哈希伪向量，检索语义无效。
  • 没有流量防护：无限流、排队削峰、熔断降级、重试背压——LLM 一抖动就是雪崩。

🛠️ 想上生产扛并发？按这 5 步改造

1
检查点外置：MemorySaver → Redis/Postgres 版 Checkpointer，会话跨副本断点续接。
2
消灭内存单点：工单入 MySQL/PG，工作记忆改 Redis —— 任何副本无差别服务。
3
向量库升级：FAISS → Milvus（分布式）+ 真实 Embedding API，多副本共享一份索引。
4
LLM 降本提速：流式输出（SSE 已预留）、高频答案缓存、路由/重排换小模型、控制并发池。
5
流量防护：网关限流 + 消息队列削峰 + 熔断重试，副本前置负载均衡。
📏 量化感受：当前形态 ≈ 单机演示级（十几~几十并发、秒级响应）；完成 1–5 步改造后，架构骨架（异步 + Redis + 无状态工具层）足以支撑数百到上千 QPS 的客服场景——真正的天花板永远在 LLM 的吞吐与成本上。
