## 1. 集群管理

### 1.1 集群状态检查

**查看集群健康**
```bash
GET /_cluster/health
```

**集群状态三种颜色**：
| 颜色 | 含义 | 说明 |
|-----|------|------|
| 🟢 Green | 健康 | 所有主副本分片都正常运行 |
| 🟡 Yellow | 警告 | 所有数据可用，但有副本未分配；集群功能完全 |
| 🔴 Red | 危险 | 有主分片无法运行，需要尽快修复 |

**协调节点**: 当搜索请求发送到某个节点时，该节点自动成为协调节点，负责广播查询、整合响应。

## 2. 分片与副本

### 2.1 分片分配原则

**设计原则**：
- 分片数 ≤ 节点数：最优分布
- 分片数 > 节点数：某些节点包含多个分片
- 副本数 ≤ 节点数 - 1：否则有副本无法分配（yellow状态）

**分片分配示例**：
```
单个节点:     分片分别分布
│
1分片 0副本  → [P0] on node-2
│
2分片 0副本  → [P0] on node-1, [P1] on node-3
│
3分片 2副本  → 每个节点包含1个主分片+2个副本（均匀分布）
│
4分片 0副本  → node-2有2个分片（分片数>节点数）
```

### 2.2 分片副本最佳实践

**三节点集群推荐配置**：
```json
PUT index_name
{
  "settings": {
    "number_of_shards": 3,      # 主分片数
    "number_of_replicas": 2     # 每个主分片的副本数
  }
}
```

**结果**：总共9个分片（3主+6副），均匀分布在3个节点，每个节点3个分片。

## 3. 故障与恢复

### 3.1 故障转移流程

```
┌─────────────────────────────────────────────────────┐
│         Master 监控集群状态                           │
└──────────┬──────────────────────────────────────────┘
           │
           ▼ 发现节点宕机
┌─────────────────────────────────────────────────────┐
│  1. 第一步：重新选主（从从节点中选出新Master）       │
│  2. 第二步：检测宕机节点的分片副本                   │
│  3. 第三步：数据迁移到其他节点                       │
│  4. 第四步：恢复集群正常状态                         │
└─────────────────────────────────────────────────────┘
```

**关键点**：
- Master故障 → 重新选主
- 从节点故障 → 迁移副本到其他节点
- **节点数 < 一半** → 整个集群不可用（需满足 `gateway.recover_after_nodes`)

### 3.2 恢复命令

```bash
# 暂停节点
docker pause node-2

# 恢复节点
docker unpause node-2
```

## 4. 扩缩容

### 4.1 扩容流程

**步骤**：
1. 创建新节点目录并复制配置
2. 添加IK分词器等插件
3. 修改配置文件（`node.name`, `discovery.seed_hosts`等）
4. 更新Docker Compose配置
5. 启动新节点

**关键配置**：
```yaml
discovery.seed_hosts: ["node-1", "node-2", "node-3"]  # 种子节点
cluster.initial_master_nodes: ["node-1", "node-2", "node-3"]  # 初始主节点候选
```

### 4.2 缩容流程

**步骤**：
```
1. 禁止数据分配
   PUT /_cluster/settings
   {
     "persistent": {
       "cluster.routing.allocation.exclude._name": "node-4"
     }
   }

2. 等待数据迁移完成
   → 监控分片信息变化

3. 停止目标节点
   docker-compose stop node-4

4. 验证集群恢复正常
```

**关键点**：必须先禁止分配再停止节点，否则会丢失数据！

## 5. 分布式文档原理

### 5.1 文档路由计算

**路由算法**：
```
shard = hash(routing) % number_of_primary_shards
```

- `routing` 默认为文档 `_id`，也可自定义
- 余数范围：`[0, number_of_primary_shards-1]`

**重要**：创建索引时确定分片数，永远不能改变（否则文档无法定位）

### 5.2 写入流程（Write Consistency）

```
┌─────────┐
│ Client  │
└────┬────┘
     │ 1. 发送写请求
     ▼
┌────────────────────┐
│ Coordinating Node  │  ← Node 1（接收请求）
│ (任何节点)         │
└────┬───────────────┘
     │ 2. 根据_id计算目标分片
     │    转发到主分片所在节点
     ▼
┌────────────────────┐
│ Primary Shard      │  ← Node 3（主分片）
│ Node 3 - Shard 0   │
└────┬───────────────┘
     │ 3. 执行写操作
     │ 4. 保存文档数据
     ▼
┌──────────┬──────────┐
│ Replica1 │ Replica2 │  ← 副本节点并行复制
│ Node 1   │ Node 2   │
└──────────┴──────────┘
     │ 5. 并行转发到副本
     │ 6. 副本执行写操作
     │ 7. 所有副本返回成功
     ▼
┌────────────────────┐
│ Coordinating Node  │  ← 主分片报告成功
└────┬───────────────┘
     │ 8. 返回客户端
     ▼
┌─────────┐
│ Client  │  ✓ 写入完成
└─────────┘
```

**写入一致性控制**：
```json
// index.write.wait_for_active_shards 参数
1        → 写完主分片立即返回
"all"    → 所有副本写完才返回
```

### 5.3 单文档读取流程

```
Client 
  │ 获取请求
  ▼
Coordinating Node 计算shard位置
  │ (循环选择主/副本，负载均衡)
  ▼
[Primary] or [Replica 1] or [Replica 2]
  │ 返回document
  ▼
Coordinating Node
  │ 转发给客户端
  ▼
Client ✓ 返回文档
```

**注意事项**：
- 可能读到旧数据（副本还未同步）
- 可以通过设置 `preference` 强制读主分片：`?preference=_primary`

### 5.4 更新文档流程

```
1. 客户端 → Coordinating Node（发送更新请求）
2. Coordinating Node → Primary Shard（定位主分片）
3. Primary Shard：
   a. 检索完整文档（从主分片）
   b. 修改 _source 字段
   c. 尝试重新索引
   d. 失败则重试（最多 retry_on_conflict 次）
4. Primary Shard → Replica Shards（发送新版本文档）
5. Replicas 执行写操作
6. 所有副本 → Coordinating Node（返回成功）
7. Coordinating Node → Client（返回成功）
```

**文档复制特性**：
- 转发的是**完整新文档**，不是更新操作
- 更改**异步转发**，不保证顺序
- 避免乱序更新导致的数据不一致

## 6. 索引路由机制

### 6.1 路由核心概念

**两种查询方式**：

| 方式 | 分片扫描 | 场景 |
|------|---------|------|
| 普通查询 | 扫描所有分片 | 不指定routing key |
| 路由查询 | 扫描部分分片 | 指定routing key，提高效率 |

**路由算法**（同写入）：
```
shard = hash(routing_key) % number_of_primary_shards
```

### 6.2 路由查询示例

```json
// 普通查询（扫描3个分片）
GET logstash-village-2022.08.22/_search
{
  "query": { "match": { "name": "龙苑居住区" } }
}

// 路由查询（仅扫描1个分片）
GET logstash-village-2022.08.22/_search?routing=routingKey
{
  "query": { "match": { "name": "龙苑居住区" } }
}
```

**关键点**：
- 读写必须使用**相同的routing key**，否则查询不到数据
- 类似于关系数据库的分库分表路由键

### 6.3 自定义路由问题

**问题**：使用自定义routing后，docid **不再全局唯一**

```
默认routing(_id):
  docid="a" → hash("a") → shard0
  docid="a" → hash("a") → shard0 (同一分片，保证唯一性)

自定义routing(key1):
  docid="a" + routing="key1" → hash("key1") → shard0
  docid="a" + routing="key2" → hash("key2") → shard1 (不同分片，产生重复!)
```

**解决方案**：使用自定义routing时，应用层需要保证docid唯一性。

## 7. 索引别名

### 7.1 别名的作用

```
物理索引（oldindex）
    ↓
逻辑别名（search_index）
    ↓
应用程序（无需修改代码）
```

**使用场景**：
- 索引升级无缝切换
- 数据权限隔离
- 路由优化

### 7.2 别名操作

```json
// 查看别名
GET logstash-village-2022.08.22/_alias

// 创建别名
POST /_aliases
{
  "actions": [{
    "add": {
      "index": "logstash-village-2022.08.22",
      "alias": "logstash-village-1.0"
    }
  }]
}

// 修改别名（无缝切换）
POST /_aliases
{
  "actions": [
    { "remove": { "index": "oldindex", "alias": "search_index" } },
    { "add": { "index": "newindex", "alias": "search_index" } }
  ]
}

// 删除别名
DELETE logstash-village-2022.08.22/_alias/logstash-village-route_key
```

### 7.3 过滤别名

```json
// 创建带过滤条件的别名（权限隔离）
POST /_aliases
{
  "actions": [{
    "add": {
      "index": "logstash-village-2022.08.22",
      "alias": "logstash-village-hn",
      "filter": { "term": { "province": "河南省" } }
    }
  }]
}
// 查询该别名只能看到河南省的数据
```

### 7.4 路由别名

```json
// 创建带路由的别名
POST /_aliases
{
  "actions": [{
    "add": {
      "index": "logstash-village-2022.08.22",
      "alias": "logstash-village-route_key",
      "routing": "key"
    }
  }]
}
// 查询时自动应用routing，无需手动指定
```

## 8. 重建索引

### 8.1 为什么需要重建

**场景**：ES不支持字段类型变更（影响分词、TF/IDF、倒排索引）

### 8.2 重建流程

```
1. 创建旧索引
   PUT oldindex { mappings: { price: double } }
   
2. 创建别名指向旧索引
   POST /_aliases { add: { index: oldindex, alias: search_index } }
   
3. 导入数据
   POST oldindex/_doc/_bulk { ... }
   
4. 创建新索引
   PUT newindex { mappings: { price: integer } }
   
5. 重建索引（数据迁移）
   POST _reindex?wait_for_completion=false { ... }
   
6. 监控任务进度
   GET _tasks/{taskId}
   
7. 别名无缝切换
   POST /_aliases {
     actions: [
       { remove: { index: oldindex, alias: search_index } },
       { add: { index: newindex, alias: search_index } }
     ]
   }
   
8. 删除旧索引
   DELETE oldindex
```

### 8.3 Reindex 参数

```json
POST _reindex?wait_for_completion=false
{
  "conflicts": "proceed",  // 数据冲突继续处理
  "source": {
    "index": "oldindex",
    "size": 2,             // 批量大小（默认1000）
    "_source": ["price"],  // 只同步指定字段
    "query": { "range": { "price": { "gte": 2, "lte": 8 } } }
  },
  "dest": {
    "index": "newindex",
    "op_type": "create"    // 存在则冲突
  }
}
```

**任务管理**：
```bash
# 查看任务
GET _tasks/{taskId}

# 取消任务
POST _tasks/{taskId}/_cancel
```

## 9. 查询操作

### 9.1 全文搜索（Query + Fetch）

#### Query阶段（广播查询）

```
┌─────────┐
│ Client  │ 发送search请求
└────┬────┘
     ▼
┌──────────────────────────────────┐
│ Coordinating Node 创建优先级队列 │
│ 大小 = from + size                │
└────┬─────────────────────────────┘
     │ 广播查询请求
     ▼
┌──────┬──────┬──────┐
│Shard0│Shard1│Shard2│  ← 每个分片执行查询
│      │      │      │
│ 本地优先队列(from+size大小) │
│ 返回ID+排序值              │
└──────┴──────┴──────┘
     │ 返回分片级结果
     ▼
┌──────────────────────────────────┐
│ Coordinating Node                 │
│ 合并所有分片结果到全局优先队列    │
│ 产生全局排序结果                  │
└──────────────────────────────────┘
```

**优先级队列(Priority Queue)**：
- 存储 top-n 匹配文档的有序列表
- 大小由 `from` 和 `size` 决定
- 每个分片都需创建相同大小的队列

#### Fetch阶段（数据获取）

```
Coordinating Node 辨别哪些doc需要取回
  │
  ▼ 发送multi-get请求
┌──────┬──────┬──────┐
│Shard0│Shard1│Shard2│  ← 加载并丰富文档
└──────┴──────┴──────┘
  │ 返回完整文档
  ▼
Coordinating Node 返回给客户端
  ▼
Client ✓ 获得最终结果
```

### 9.2 查询语法

```json
// 1. 查询所有（match_all）
GET index/_search
{
  "query": { "match_all": {} }
}
// 简写: GET index/_search

// 2. 精确查询（match - text字段分词）
GET index/_search
{
  "query": { "match": { "name": "龙苑居住区" } }
}

// 3. 完全匹配（term - keyword字段/分词后）
GET index/_search
{
  "query": { "term": { "province": "河南省" } }
}

// 4. 组合查询（bool）
GET index/_search
{
  "query": {
    "bool": {
      "must": [      // AND，提供得分
        { "match": { "province": "河南省" } },
        { "match": { "city": "郑州市" } }
      ],
      "must_not": [  // NOT，不提供得分（缓存）
        { "match": { "area": "金水区" } }
      ],
      "should": [],  // OR，增加得分
      "filter": []   // AND，不提供得分（缓存）
    }
  }
}

// 5. 过滤查询（constant_score - 所有结果得分=1）
GET index/_search
{
  "query": {
    "constant_score": {
      "filter": {
        "bool": {
          "must": [ ... ],
          "must_not": [ ... ]
        }
      }
    }
  }
}

// 6. 条件过滤（exists）
GET index/_search
{
  "query": {
    "bool": {
      "must": [
        { "exists": { "field": "greening" } }
      ]
    }
  }
}

// 7. 模糊查询（fuzzy - 编辑距离算法）
GET index/_search
{
  "query": { "fuzzy": { "name": "龙源居住区" } }
}

// 8. 纠错提示（suggest）
GET index/_search
{
  "suggest": {
    "name-suggestion": {
      "text": "龙源居住区",
      "term": { "field": "name" }
    }
  }
}
```

### 9.3 结果排序与分页

```json
// 排序（sort）
GET index/_search
{
  "query": { ... },
  "sort": [
    { "greening": { "order": "desc" } },  // desc/asc
    { "_score": { "order": "desc" } }
  ]
}

// 分页（from + size）
GET index/_search
{
  "query": { ... },
  "from": 20,    // 偏移值（默认0）
  "size": 10     // 返回数量（默认10）
}

// 隐藏源数据（提高性能）
GET index/_search
{
  "query": { ... },
  "_source": false
}

// 指定源字段
GET index/_search
{
  "query": { ... },
  "_source": ["name", "greening"]
}
```

### 9.4 深度分页问题

**问题描述**：
```
3个分片，每个10万条数据
查询 from=9999, size=10

协调节点需要：
  shard0: 取10009条 (9999+10)
  shard1: 取10009条
  shard2: 取10009条
  ────────────────────
  总共: 30027条

然后排序，只返回10条
→ 浪费！性能差！容易OOM
```

**限制**：
```
index.max_result_window = 10000 (默认)
→ from + size ≤ 10000
```

**解决方案**：
- 使用Search After（基于上一页最后一个文档）
- 使用Scroll API（游标式翻页）
- 业务层优化：加强检索条件，减少结果集

## 10. 聚合查询

### 10.1 指标聚合（Metric Aggregation）

```json
// 1. 最大值
GET index/_search
{
  "aggs": {
    "max_volume": {
      "max": { "field": "volume", "missing": 0 }
    }
  },
  "size": 0
}

// 2. 最小值
GET index/_search
{
  "aggs": {
    "min_parkings": {
      "min": { "field": "parkings", "missing": 0 }
    }
  },
  "size": 0
}

// 3. 统计（min/max/sum/count/avg）
GET index/_search
{
  "query": { "match": { "province": "河南省" } },
  "aggs": {
    "stats_greenings": {
      "stats": {
        "field": "greening",
        "script": {
          "source": "if (doc['greening'].size() != 0) {doc['greening'].value}"
        }
      }
    }
  },
  "size": 0
}

// 4. 求和
GET index/_search
{
  "aggs": {
    "sum_houses": {
      "sum": { "field": "houses" }
    }
  },
  "size": 0
}
```

### 10.2 分桶聚合（Bucket Aggregation）

```json
// 1. 分组统计（terms - 按字段值分组）
GET index/_search
{
  "aggs": {
    "bucket_terms": {
      "terms": {
        "field": "province",
        "size": 10
      }
    }
  },
  "size": 0
}

// 2. 分组+聚合（嵌套聚合）
GET index/_search
{
  "aggs": {
    "bucket_terms": {
      "terms": {
        "field": "province",
        "size": 10
      },
      "aggs": {
        "sum_houses": {
          "sum": { "field": "houses" }
        }
      }
    }
  },
  "size": 0
}

// 3. 带过滤条件的分组
GET index/_search
{
  "query": { "exists": { "field": "school" } },
  "aggs": {
    "bucket_terms": {
      "terms": {
        "field": "province",
        "size": 10
      },
      "aggs": {
        "sum_houses": { "sum": { "field": "houses" } }
      }
    }
  },
  "size": 0
}
```

### 10.3 管道聚合（Pipeline Aggregation）

```json
// 找出学区房人数最多的省份
GET index/_search
{
  "query": { "exists": { "field": "school" } },
  "aggs": {
    "bucket_terms": {
      "terms": { "field": "province", "size": 10 },
      "aggs": {
        "sum_houses": { "sum": { "field": "houses" } }
      }
    },
    "max_houses": {
      "max_bucket": {
        "buckets_path": "bucket_terms>sum_houses"
      }
    }
  },
  "size": 0
}
// buckets_path: bucket_terms>sum_houses
// 表示在bucket_terms聚合结果上再聚合sum_houses
```

**管道聚合类型**：
- `max_bucket`: 最大值
- `min_bucket`: 最小值
- `sum_bucket`: 求和
- `avg_bucket`: 平均值
- `derivative`: 导数
- `cumulative_sum`: 累积和

### 常见错误及解决

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| Yellow状态 | 副本未分配 | 检查节点数 >= 副本数+1 |
| Red状态 | 主分片丢失 | 检查节点宕机，恢复或重新分配 |
| 深度分页报错 | from+size > 10000 | 使用Search After或增大max_result_window |
| 查询不到数据 | routing key不匹配 | 读写使用相同的routing key |
| Docid重复 | 自定义routing | 应用层保证docid全局唯一 |
| 字段类型错误 | ES不支持改字段类型 | 使用_reindex重建索引 |
