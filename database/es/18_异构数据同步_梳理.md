# 异构数据同步完整梳理

## 1. 核心概念

### 1.1 什么是异构数据同步
异构数据同步是指将来自不同数据源的数据在不同数据库之间进行实时或准实时的同步。本文档主要讲述如何将MySQL数据库中的数据同步到Elasticsearch(ES)搜索引擎中。

**应用场景**：全国小区房产全文检索系统
- MySQL作为主数据库存储所有业务数据
- Elasticsearch作为搜索引擎提供高效全文检索能力
- 两种数据库各司其职，互补优势

---

## 2. 核心方案对比

### 2.1 方案对比表

| 方案 | 工作原理 | 优点 | 缺点 | 适用场景 |
|------|--------|------|------|--------|
| **Canal + MQ + Logstash** | 解析binlog → MQ解耦 → Logstash清洗 | 异步处理、削峰填谷、实时同步、高吞吐 | 系统复杂度高、运维难度大 | 高并发、大数据量、对同步实时性要求高 |
| **双写** | 应用层同时写两个数据库 | 实现简单 | 一致性难保证、重复代码多、耦合度高 | 小规模系统、同步要求低 |
| **定时任务** | 定时全量同步 | 实现简单 | 无法处理增量、延迟大、资源浪费 | 数据量小、实时性要求不高 |
| **Logstash直连** | 日志收集 → Logstash转换 → ES | 配置灵活、插件丰富 | 实时性较差、需配置复杂 | 日志分析、数据清洗 |

---

## 3. 推荐方案：Canal + RabbitMQ + Logstash

### 3.1 架构组件说明

#### **MySQL** - 主数据源
```
职责：
  - 存储所有业务数据
  - 记录所有数据变更到binlog（Binary Log）
  - 开启binlog的ROW模式（记录具体行变更）

配置关键参数：
  - log-bin=mysql-bin        # 开启binlog
  - binlog-format=ROW        # 记录行级变更（完整数据）
  - server_id=1              # MySQL复制标识
```

#### **Canal** - 增量日志解析器
```
职责：
  - 伪装为MySQL从库（Slave）
  - 订阅并解析MySQL binlog
  - 提取INSERT/UPDATE/DELETE操作
  - 发送到消息队列

工作机制：
  1. 向MySQL发送dump请求
  2. MySQL将binlog推送给Canal
  3. Canal解析binlog获取数据变更
  4. 将变更消息投递到RabbitMQ
```

#### **RabbitMQ** - 消息队列
```
职责：
  - 异步化：解耦Canal和Logstash
  - 削峰填谷：缓冲大流量数据
  - 持久化：防止数据丢失
  - 提高吞吐量：支持并行消费

关键配置：
  - 交换器（Exchange）：canal
  - 队列（Queue）：direct_queue
  - 绑定关系（Binding）：exchange → queue
```

#### **Logstash** - 数据处理管道
```
职责：
  - 从RabbitMQ消费消息
  - 解析Canal发送的JSON数据
  - 字段清洗、转换、丰富
  - 将处理后的数据写入ES

处理流程：
  input  → 从RabbitMQ获取数据
  filter → 数据清洗（移除无关字段、类型转换、日期处理）
  output → 写入ES指定索引
```

#### **Elasticsearch** - 搜索引擎
```
职责：
  - 存储清洗后的数据
  - 提供全文检索能力
  - 地理位置搜索（geo_point）
  - 支持复杂分析聚合

关键概念：
  - 索引（Index）：相当于数据库
  - 文档（Document）：相当于数据行
  - 字段（Field）：相当于列
  - 映射（Mapping）：相当于表结构定义
```

## 4. 详细流程解析

### 4.1 全量数据同步 + 增量数据同步

```
初始化阶段：
  1. 创建索引和映射（Index Template）
  2. 导入Excel数据到MySQL
  3. 数据库触发binlog记录
  4. Canal开始监听binlog

增量同步流程：
  MySQL表变更（INSERT/UPDATE/DELETE）
        ↓
   binlog记录变更
        ↓
  Canal解析binlog
        ↓
  构建变更消息（JSON格式）
        ↓
  发送到RabbitMQ
        ↓
  Logstash消费消息
        ↓
  提取data数组中的字段
        ↓
  类型转换与日期处理
        ↓
  删除DELETE操作的文档
        ↓
  写入ES索引
        ↓
  完成同步
```

### 4.2 Canal binlog解析详细链路

```
MySQL Master节点
     ↓
binlog 文件队列
(mysql-bin.000001, ...)
     ↓
Canal伪装为Slave
     ↓
发送Replication Handshake
     ↓
MySQL验证权限
(canal用户需要REPLICATION权限)
     ↓
MySQL推送binlog事件流
     ↓
Canal接收事件
     ↓
解析事件（Event Parser）
  - TableMapEvent（表结构变更）
  - WriteEvent（INSERT）
  - UpdateEvent（UPDATE）
  - DeleteEvent（DELETE）
     ↓
提取行数据（Row Data）
     ↓
构建CanalEntry消息
  {
    "database": "village",
    "table": "t_village",
    "type": "INSERT/UPDATE/DELETE",
    "data": [
      {
        "id": 1,
        "name": "小区名",
        ...
      }
    ]
  }
     ↓
发送到RabbitMQ exchange
     ↓
消息持久化
```

### 4.3 MQ解耦同步架构

```
高并发场景处理：

并发写入 → MySQL
       ↓
    binlog
       ↓
    Canal
    ┌─────┐
    │ TCP │ （11111端口）
    └─────┘
       ↓
    RabbitMQ（缓冲队列）
    ┌──────────────────────┐
    │ canal exchange       │
    │ ↓                    │
    │ direct_queue (消息队列) │
    │ [消息1] [消息2] ...   │
    └──────────────────────┘
       ↓
  可配置并行消费
    ┌─────────────────────┐
    │ Logstash Worker 1   │
    │ Logstash Worker 2   │
    │ Logstash Worker 3   │
    └─────────────────────┘
       ↓
    批量写ES（提高吞吐量）
       ↓
    ES集群
```

## 5. 关键配置详解

### 5.1 MySQL配置

```ini
[mysqld]
# 开启binlog记录
log-bin=mysql-bin

# 使用ROW格式（完整记录行数据，不仅仅是SQL）
binlog-format=ROW
# 其他格式对比：
#   STATEMENT: 记录SQL语句（文件小，但需要重放SQL）
#   MIXED: 混合模式（默认STATEMENT，某些场景自动切ROW）

# MySQL复制标识（必须与Canal的slaveId不同）
server_id=1
```

### 5.2 Canal权限配置

```sql
-- Canal需要以下权限才能解析binlog
CREATE USER canal IDENTIFIED BY 'canal';

GRANT SELECT,              -- 查看数据
      REPLICATION SLAVE,   -- 作为从库接收binlog
      REPLICATION CLIENT   -- 执行SHOW MASTER STATUS
      ON *.* TO 'canal'@'%';

FLUSH PRIVILEGES;
```

### 5.3 Canal配置文件关键参数

```properties
# ===== 服务器配置 =====
canal.ip = 
canal.port = 11111              # Canal服务监听端口
canal.metrics.pull.port = 11112 # 监控端口

# ===== 消息队列模式选择 =====
canal.serverMode = rabbitMQ
# 支持: tcp, kafka, rocketMQ, rabbitMQ

# ===== MQ相关配置 =====
canal.mq.flatMessage = true      # 扁平化消息结构
canal.mq.canalBatchSize = 50     # 批量发送大小
canal.mq.canalGetTimeout = 100   # 获取超时时间

# ===== RabbitMQ连接 =====
rabbitmq.host = rabbit           # RabbitMQ服务地址
rabbitmq.virtual.host = /
rabbitmq.exchange = canal        # 交换器名称
rabbitmq.username = guest
rabbitmq.password = guest
```

### 5.4 Canal instance配置（实例级配置）

```properties
# ===== MySQL连接 =====
canal.instance.master.address = mysql:3306
canal.instance.dbUsername = canal
canal.instance.dbPassword = canal
canal.instance.connectionCharset = UTF-8

# ===== 表过滤正则 =====
# 包含白名单：匹配这个正则的表才会被同步
canal.instance.filter.regex = village\\..*

# 排除黑名单：匹配这个正则的表不会被同步
canal.instance.filter.black.regex =

# ===== TSDB配置（存储binlog位置） =====
canal.instance.tsdb.enable = true  # 持久化同步位置
# 这样重启Canal时不会重新同步已处理的数据
```

### 5.5 Logstash Pipeline配置

```ruby
input {
  rabbitmq {
    host => "rabbit"
    port => 5672
    vhost => "/"
    user => "guest"
    password => "guest"
    exchange => "canal"
    queue => "direct_queue"
    codec => "json"  # Canal消息是JSON格式
  }
}

filter {
  # 删除DELETE操作的文档（不同步删除操作）
  if [type] == "DELETE" {
    drop {}
  }

  # 展开data数组（Canal的data字段是数组）
  split {
    field => "data"
  }

  # 删除不需要的Canal元字段
  mutate {
    remove_field => ["sqlType", "mysqlType", "database", "sql", 
                     "es", "ts", "pkNames", "isDdl", "table", 
                     "tags", "type", "old", "id"]
  }

  # 日期时间处理
  date {
    match => ["create_date", "yyyy-MM-dd HH:mm:ss"]
    target => "@timestamp"
    timezone => "Asia/Shanghai"
  }

  # 地理位置字段处理（GPS坐标）
  if [data][lat_gps] {
    mutate {
      add_field => {
        "[location][lat]" => "%{[data][lat_gps]}"
        "[location][lon]" => "%{[data][lon_gps]}"
      }
      convert => { "[location][lat]" => "float" }
      convert => { "[location][lon]" => "float" }
    }
  }

  # 提取其他业务字段到顶层
  if [data][name] {
    mutate {
      add_field => { "name" => "%{[data][name]}" }
    }
  }
  # ... 其他字段类似处理
}

output {
  elasticsearch {
    hosts => ["node-1:9200"]
    index => "logstash-village-%{+YYYY.MM.dd}"  # 日期分片
  }
}
```

### 5.6 Elasticsearch索引模板

```json
{
  "index_patterns": ["logstash-village-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,    # 3个分片（分布式存储）
      "number_of_replicas": 2   # 2个副本（高可用）
    },
    "mappings": {
      "properties": {
        "@timestamp": {
          "type": "date",
          "format": "strict_date_optional_time||epoch_millis"
        },
        "name": {
          "type": "keyword"      # 精确匹配，不分词
        },
        "province": {
          "type": "keyword"
        },
        "city": {
          "type": "keyword"
        },
        "addr": {
          "type": "text",
          "analyzer": "ik_smart"  # 中文分词（最少切分）
        },
        "location": {
          "type": "geo_point"     # 地理位置类型，支持距离搜索
        },
        "property_cost": {
          "type": "float"
        },
        "floorage": {
          "type": "float"
        },
        "houses": {
          "type": "integer"
        },
        "info": {
          "type": "text",
          "analyzer": "ik_smart"  # 分词以支持全文检索
        }
      }
    }
  }
}
```

## 8. 实时数据流示例

### 8.1 Insert操作流程

```
业务系统执行SQL：
  INSERT INTO t_village (name, city, ...) VALUES ('绿城小区', '杭州', ...);

MySQL处理：
  1. 数据写入表
  2. 记录到binlog:
     {
       "type": "WRITE_ROWS",
       "table": "t_village",
       "data": {
         "id": 1,
         "name": "绿城小区",
         "city": "杭州",
         ...
       }
     }

Canal解析：
  1. 读取binlog事件
  2. 提取行数据
  3. 构建消息：
     {
       "database": "village",
       "table": "t_village",
       "type": "INSERT",
       "data": [{
         "id": 1,
         "name": "绿城小区",
         "city": "杭州",
         ...
       }],
       "ts": 1622000000000
     }

RabbitMQ缓冲：
  消息存入direct_queue，等待消费

Logstash处理：
  1. 消费JSON消息
  2. 展开data数组
  3. 删除Meta字段
  4. 转换数据类型
  5. 计算location地理位置
  
  输出文档：
  {
    "@timestamp": "2021-05-26T08:00:00.000Z",
    "id": 1,
    "name": "绿城小区",
    "city": "杭州",
    "location": {
      "lat": 30.2741,
      "lon": 120.1551
    },
    ...
  }

Elasticsearch存储：
  写入索引：logstash-village-2021.05.26
  文档ID：自动生成
  
  可立即通过REST API查询：
  GET logstash-village-*/_search?q=绿城小区
```

### 8.2 Update操作流程

```
业务系统执行SQL：
  UPDATE t_village SET property_cost = 5.5 WHERE id = 1;

MySQL处理：
  binlog记录：
  {
    "type": "UPDATE_ROWS",
    "before": {"id": 1, "property_cost": 5.0, ...},
    "after": {"id": 1, "property_cost": 5.5, ...}
  }

Canal解析：
  type: "UPDATE"
  data: [{"id": 1, "property_cost": 5.5, ...}]
  old: [{"id": 1, "property_cost": 5.0, ...}]

Logstash处理：
  1. 过滤掉old字段
  2. 提取after数据
  3. 生成新文档

Elasticsearch存储：
  通过_id进行版本控制，自动更新文档
  原文档版本号 +1
```

### 8.3 Delete操作流程

```
业务系统执行SQL：
  DELETE FROM t_village WHERE id = 1;

Canal解析：
  type: "DELETE"
  data: [{"id": 1, ...}]

Logstash处理：
  检测到 type == "DELETE"
  执行 drop{} 过滤器
  **直接丢弃，不写入ES**

这里有设计取舍：
  - 选项1（文档所用）：删除操作不同步到ES
    问题：ES中会有"脏数据"（已删除的小区）
    
  - 选项2：同步DELETE操作到ES
    改进：在Logstash中删除相应文档
    document_id => "%{id}"  # 根据ID匹配文档
    action => "delete"      # 执行删除
```

## 9. 数据一致性保证机制

### 9.1 Canal保证机制

```
1. 位置记录（Offset Tracking）
   - Canal记录已处理的binlog位置
   - 存储在TSDB（内部H2数据库）
   - 重启时从该位置继续消费
   - 不会重复处理相同日志

2. 顺序性保证
   - 单表内的变更按序处理
   - 相同业务主键的操作有序
   - 防止并发导致的数据混乱

3. 批量发送
   - canalBatchSize = 50：每批50条消息
   - 减少RabbitMQ调用频率
   - 提高吞吐量

4. 事务完整性
   - 一个MySQL事务的所有操作作为一个逻辑单元
   - 要么全部成功，要么全部失败
```

### 9.2 RabbitMQ保证机制

```
1. 队列持久化
   - durable = false：消息队列本身不持久化
   - 消息在内存中，快速读写
   - 适合可丢失的日志场景

   改进方案：生产环境应配置
   - durable = true
   - 同时配置消息持久化
   - 防止broker宕机导致数据丢失

2. Consumer Ack
   - Logstash处理成功后才发Ack
   - RabbitMQ收到Ack才移除消息
   - 处理失败时消息会被重新投递

3. 死信队列
   - 多次重试失败的消息
   - 进入死信队列供人工处理
```

### 9.3 Logstash保证机制

```
1. Delivery Semantics（投递语义）
   - Pipeline batch size = 10：每次处理10条消息
   - 失败时自动重试

2. ES索引幂等性
   - 同一数据多次写入相同_id时：
     - 第一次写入：新建文档
     - 后续写入：覆盖更新（_version递增）
     - 结果相同：最终一致性

3. 错误处理
   - 字段缺失：skip该条
   - 类型不匹配：尝试自动转换
   - 连接异常：缓冲重试
```

### 9.4 数据一致性检查

```bash
# SQL级别检查
SELECT COUNT(*) FROM t_village;

# ES级别检查
GET logstash-village-*/_count
{
  "query": { "match_all": {} }
}

# 如果两者数据量不一致，排查思路：
# 1. 检查Canal是否正常运行
# 2. 检查RabbitMQ队列是否积压
# 3. 检查Logstash日志是否有错误
# 4. 手动触发全量重新同步
```

## 11. 常见错误及解决方案

### 11.1 Canal连接MySQL失败

```
错误日志：
  ERROR: Quit canal ack has an error : java.io.IOException: 
  MASTER_BINLOG_CHECKSUM: unknown variable

原因：MySQL和Canal版本不兼容

解决方案：
  1. 检查MySQL binlog_checksum参数
     SHOW VARIABLES LIKE 'binlog_checksum';
  
  2. 若为CRC32，改为NONE
     SET GLOBAL binlog_checksum = NONE;
  
  3. 重启Canal服务
```

### 11.2 Logstash字段映射失败

```
错误现象：
  数据写入ES但字段为null

原因分析：
  1. Canal消息的data字段嵌套层级不对
  2. Logstash过滤器regex不匹配
  3. 字段名大小写不一致

诊断步骤：
  1. 在Logstash中添加临时输出
     stdout { codec => rubydebug }
  
  2. 查看实际消息结构
     检查[data]字段的值
  
  3. 调整mutate规则
     确保字段提取逻辑正确
```

### 11.3 ES索引动态映射被禁用

```
错误信息：
  {
    "type": "strict_mapping_exception",
    "reason": "mapping set to strict, 
              dynamic introduction of [new_field] within 
              [properties] is not allowed"
  }

原因：
  模板中设置 "dynamic": "strict"
  不允许动态添加映射中未定义的字段

解决方案：
  选项1：修改模板
    "dynamic": "true"  # 允许动态添加字段（不安全）
  
  选项2：Logstash端过滤
    确保outout的字段都在mappings中定义
  
  推荐：选项2（严格控制数据结构）
```

### 11.4 数据丢失或重复

```
丢失原因：
  1. Logstash drop过滤器误删关键操作
  2. RabbitMQ队列配置不持久化
  3. Canal位置记录丢失（重启后重复处理早期数据）

重复原因：
  1. Logstash未正确提交offset
  2. ES ID生成不一致导致插入而非更新

防护措施：
  1. 生产环境使用持久化队列
  2. 定期备份Canal的TSDB目录
  3. 实现幂等性id映射机制
  4. 定期数据一致性检查
```

## 12. 性能优化建议

### 12.1 Canal优化

```properties
# 1. 批量处理优化
canal.mq.canalBatchSize = 100        # 增大批处理大小（权衡延迟）
canal.instance.transaction.size = 2048  # 事务缓冲大小

# 2. 解析并行化
canal.instance.parser.parallel = true
canal.instance.parser.parallelThreadSize = 16  # 根据CPU核心数调整

# 3. 内存缓冲优化
canal.instance.memory.buffer.size = 65536      # 增大RingBuffer（需要内存）
```

### 12.2 Logstash优化

```yaml
logstash.yml:
  # 1. 批处理优化
  pipeline.batch.size: 500          # 增大批处理（权衡延迟和吞吐）
  pipeline.batch.delay: 50          # 延迟ms，允许更多消息积累
  
  # 2. 并行处理
  pipeline.workers: 8               # worker线程数（通常=CPU核数）
  
  # 3. 输出优化
  output {
    elasticsearch {
      bulk_max_size => 5000         # 每个bulk请求的最大文档数
      flush_interval => 1           # flush间隔（秒）
    }
  }
```

### 12.3 Elasticsearch优化

```
1. 分片分配优化
   - number_of_shards: 3          # 适应3节点集群
   - number_of_replicas: 2        # 高可用，但写入压力大
   
   改进：
   - 生产级集群：shards = 节点数或稍少
   - 副本数权衡可用性和性能

2. 刷新策略
   - refresh_interval: 30s        # 默认1s，改为30s提高吞吐
   - 牺牲实时性，提高写入性能

3. 合并优化
   - segments_per_tier: 15        # 段合并策略
   - max_merge_at_once: 30

4. 内存锁定
   bootstrap.memory_lock: true     # 锁定堆内存，防止swap
```

### 12.4 整体链路优化

```
瓶颈点                优化策略
─────────────────────────────────────
MySQL binlog读取    → 使用专用复制用户，避免大查询竞争

Canal解析           → 启用并行解析，增加buffer大小

RabbitMQ吞吐量      → 增加队列数，实现sharding

Logstash处理        → 增加worker，扩大batch_size

ES写入              → 增加副本数，优化bulk大小

→ 整体瓶颈转移到ES写入 → 增加节点数，提升硬件配置
```
