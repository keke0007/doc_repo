## 1. 倒排索引

### 1.1 基本概念
倒排索引(Inverted Index)是全文检索的核心基础，与正排索引相反，它以**属性值为关键字**来查询包含该属性值的记录。

**核心数据结构：**
```
Term Index (词项) | PostingList (文档列表) | 位置信息
──────────────────────────────────────────────────
篮球              | [Doc1, Doc3, Doc5]    | [位置0, 位置2]
唱歌              | [Doc2, Doc4]          | [位置1, 位置3]
```

### 1.2 倒排索引三列信息
1. **第一列：分词索引(Term Index)**
   - 通过分词器将字段内容分成词语
   - 例如："喜欢篮球、唱歌" → ["篮球", "唱歌"]

2. **第二列：文档ID列表(PostingList)**
   - 包含该词语的所有文档ID
   - 用于快速定位包含查询词的文档

3. **第三列：位置信息(Position)**
   - 词语在文档字段中的位置
   - 用于搜索结果高亮显示

### 1.3 正排索引 vs 倒排索引

| 特性 | 正排索引 | 倒排索引 |
|------|--------|--------|
| 查找方向 | 文档ID → 字段内容 | 字段内容 → 文档ID |
| 适用场景 | 按ID查询单条记录 | 全文搜索、关键词检索 |
| 查询方式 | 直接扫描→逐字段匹配 | 先查词典→获取文档列表 |
| 常见实现 | MySQL B+树索引 | Lucene、ES |

## 2. 分词与分词器

### 2.1 分词器的作用
将用户输入的**一段文本**按照一定逻辑分析成**多个词语**的工具。

例如：
- 输入: "Mastering Elasticsearch"
- 输出: ["mastering", "elasticsearch"]（自动小写）

### 2.2 分词器的三层结构

```
原文本
  ↓
[Character Filters] - 字符过滤层 (0个或多个)
  ↓
[Tokenizer] - 分词层 (有且仅有1个)
  ↓
[Token Filters] - 词过滤层 (0个或多个)
  ↓
最终词语集合
```

**各层职责：**

| 组件 | 职责 | 示例 |
|------|------|------|
| **Character Filters** | 添加/删除/替换字符 | 去除HTML标签、罗马数转阿拉伯数 |
| **Tokenizer** | 拆分文本为词语 | 按空格拆分英文、分析中文 |
| **Token Filters** | 改变词语 | 小写处理、停词删除 |

### 2.3 分词时机
- **索引时**：对text类型字段建立索引时分词
- **查询时**：对text类型字段的用户输入进行分词

### 2.4 分词器选择顺序

**索引时分词器选择（优先级从高到低）：**
1. 字段指定的analyzer属性
2. Settings中 `analysis.analyzer.default`
3. 默认的standard分词器

**查询时分词器选择（优先级从高到低）：**
1. 查询语句中的analyzer参数
2. Mapping中字段的search_analyzer属性
3. Settings中 `analysis.analyzer.default_search`
4. Mapping中字段的analyzer属性
5. 默认的standard分词器

### 2.5 内置分词器对比

| 分词器 | 描述 | 适用场景 |
|-------|------|--------|
| **standard** | 基于Unicode文本分割，默认分词器 | 英文、一般文本 |
| **simple** | 非字母字符作分界符，转小写 | 简单英文 |
| **whitespace** | 按空格分界，保留大小写 | 精确字段 |
| **keyword** | 不分词，原样返回 | 状态码、ID |
| **stop** | 类似simple，删除停词(如a,the) | 英文 |
| **pattern** | 正则表达式分界 | 自定义格式 |

### 2.6 中文分词器

**IK分词器：** 基于Java的轻量级中文分词工具包

| 类型 | 特点 | 输入示例 | 输出示例 |
|------|------|--------|--------|
| **ik_smart** | 简单分词，支持自定义字典 | "学如逆水行舟,不进则退" | ["学如逆水行舟,不进则退"] |
| **ik_max_word** | 全量分词，细粒度分词 | "学如逆水行舟,不进则退" | ["学如逆水行舟", "学如逆水", "逆水行舟", "逆水", "行舟", "不进则退", "不进", "则", "退"] |

## 3. Mapping 映射

### 3.1 什么是映射
Mapping是对数据处理时的**方式和规则的限制**，类似于关系数据库的**表结构定义**。

**核心作用：**
- 定义字段的数据类型
- 设定字段所使用的分词器
- 指定字段是否被索引、是否存储
- 配置默认值、分析器等

### 3.2 创建映射的两种方式

**方式1：动态映射（被动创建）**
- 不需要事先定义字段和映射类型
- ES自动推断数据类型
- 优点：快速便捷
- 缺点：无法精确控制

**方式2：显式映射（主动创建）**
- 通过PUT {index}/_mapping提前定义
- 精确控制每个字段的特性
- 生产环境推荐方式

### 3.3 动态映射规则

| JSON数据类型 | 推断为ES类型 |
|-------------|-----------|
| null | 不添加字段 |
| true/false | boolean |
| 浮点数 | float |
| 整数 | long |
| object | object |
| array | 取决于第一个非空值类型 |
| string | **有条件** - 日期格式→date / 数值→double/long / 其他→text(+keyword子字段) |

### 3.4 禁用动态映射

**问题场景：**
- 集群元数据频繁变更，导致不稳定
- 数据类型与实际类型不一致
- 异常字段频繁修改mapping，业务不可控

**dynamic参数配置：**

```json
{
  "mappings": {
    "dynamic": "true | false | strict",
    "properties": { ... }
  }
}
```

| 值 | 含义 | 行为 |
|----|------|------|
| **true** | 支持动态扩展 | 新字段自动添加mapping，数据写入成功 |
| **false** | 不支持动态扩展 | 新字段被忽略，数据写入成功 |
| **strict** | 严格禁止 | 新字段导致异常，数据写入失败 |

### 3.5 字符串类型字段

**text类型：**
- 用途：全文搜索内容（Email、产品描述）
- 特点：会被分词、生成倒排索引
- 缺点：不适合排序、很少用于聚合
- 示例：产品介绍、文章内容

**keyword类型：**
- 用途：精确值搜索、过滤、排序、聚合
- 特点：不分词、直接存储
- 适用：姓名、邮箱、主机名、状态码、标签
- 示例：分类标签、用户ID

**key difference：**
```
输入: "北京小区"
text存储: ["北京", "小", "区"] (分词后)
keyword存储: "北京小区" (原样)
```

### 3.6 数字类型

| 类型 | 取值范围 | 精度 |
|------|--------|------|
| **byte** | -128 ~ 127 | 8位 |
| **short** | -2^15 ~ 2^15 | 16位 |
| **integer** | -2^31 ~ 2^31 | 32位 |
| **long** | -2^63 ~ 2^63 | 64位（默认整数） |
| **half_float** | IEEE754 16位 | 半精度 |
| **float** | IEEE754 32位 | 单精度 |
| **double** | IEEE754 64位 | 双精度 |
| **scaled_float** | 缩放浮点 | 指定精度 |

**选择原则：** 优先使用范围小的字段，字段长度越小，索引和搜索效率越高。

### 3.7 日期类型

**JSON表示日期的三种方式：**
1. 格式化日期字符串：`"2015-01-01"` 或 `"2015/01/01 12:10:30"`
2. 毫秒级时间戳：`1420070400000`
3. 秒级时间戳(epoch_second)：`1420070400`

**ES内部处理：**
- 转换为UTC时间
- 使用long型存储毫秒数
- 查询转换为长整形范围查询
- 结果呈现时转为字符串

**默认日期格式：**
```
"strict_date_optional_time||epoch_millis"
```
接受：带时间戳的ISO格式 或 毫秒级时间戳

**常用日期格式参数：**

| 参数 | 说明 |
|------|------|
| **format** | 日期格式(支持多格式用\|\|分隔) |
| **doc_values** | 是否按列式存储(用于排序/聚合/脚本) |
| **index** | 是否索引以便快速查询 |
| **ignore_malformed** | 解析错误是否忽略 |
| **null_value** | null值的替代值 |

### 3.8 其他常用类型

| 类型 | 用途 |
|------|------|
| **boolean** | 存储true/false |
| **range** | 存储范围值(integer_range、float_range、date_range等) |
| **geo_point** | 地理位置坐标(经纬度) |

## 4. 索引管理

### 4.1 索引设计的重要性

**为什么索引设计很关键：**
1. **分片数量不可改变** - 创建后只能通过_split/_shrink成倍增减
2. **字段难以修改** - 只能新增字段，不能修改删除，修改需_reindex重建
3. **性能严重依赖** - 分片大小和数量直接影响查询/写入性能
4. **影响运维成本** - 糟糕的设计会导致后期运维困难

### 4.2 索引命名与分级设计

**基于时间的Index设计：**
```
2022-01-01    2022-01-02    2022-01-03    2022-01-04
  ↓              ↓              ↓              ↓
index-2022-01 index-2022-02 index-2022-03 index-2022-04
```

**时间分割的优势：**
1. **灵活性** - 按需调整Shard个数，无需操作全量数据
2. **性能** - 用户通常查询最近数据，可避免扫描历史数据
3. **易维护** - 按时间段管理，便于备份、删除过期数据

**时间间隔选择：**
- 考虑数据存储周期（如存储6个月，选择"周"间隔合适）
- 考虑业务增长速度（增长快选短间隔如"天"）
- 权衡灵活性 vs Index数量 vs 资源消耗

### 4.3 分片设计

**单个Shard大小限制：**
```
Primary Shard大小上限 ≤ 30GB (Elastic经验值)
```

**理由：**
- Shard过大导致Shard Relocate时CPU/IO高负载
- 节点故障时数据恢复慢
- 系统不稳定

**分片数量评估：**
```
单Index的Primary Shard数 = k × 数据节点数

其中 k = 1 或 2 (推荐整数倍关系)
```

**设计原则：**
1. 保证单个Shard不超过30GB
2. Primary Shard个数不宜过多（消耗元信息、缓存资源）
3. 小Index(几十/几百MB)可只分配1~2个Primary Shard
4. 让Shard均匀分布，充分分散请求到不同节点

### 4.4 索引模板(Index Template)

**定义：** 将已创建索引的参数设置(settings)和映射(mappings)保存为模板，新建索引时重用。

**核心原理：**
- 基于**通配符模式**匹配索引名称
- 同时符合多个模板时，选择**priority最高**的
- 模板仅在**新创建时**起作用，修改模板不影响现有索引
- 索引中的settings/mappings会**覆盖**模板中的定义

**应用场景：** 时间序列相关索引（日志、时间数据）

**模板参数表：**

| 参数 | 必选 | 说明 |
|------|-----|------|
| **index_patterns** | 是 | 通配符表达式数组，用于匹配索引名 |
| **template** | 否 | 包含settings/mappings/aliases |
| **settings** | 否 | 分片数、副本数等配置 |
| **mappings** | 否 | 字段类型和分词器定义 |
| **aliases** | 否 | 索引别名定义 |
| **priority** | 否 | 优先级(高优先级模板优先应用) |
| **composed_of** | 否 | 组件模板列表(按顺序合并) |
| **version** | 否 | 外部版本号 |
| **_meta** | 否 | 用户元数据 |

**创建模板示例：**
```json
PUT _index_template/logstash-village
{
  "index_patterns": ["logstash-village-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 2
    },
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "@timestamp": {
          "type": "date",
          "format": "strict_date_optional_time||epoch_millis||yyyy-MM-dd HH:mm:ss"
        },
        "name": { "type": "keyword" },
        "addr": { "type": "text", "analyzer": "ik_smart" }
      }
    },
    "aliases": { "logstash-village": {} }
  }
}
```

## 5. 核心概念体系

### 5.1 逻辑概念 (关系数据库对比)

| ES概念 | 数据库对应 | 说明 |
|-------|----------|------|
| **Index(索引库)** | Database(数据库) | 一个Index可包含多个Type |
| **Type(类型)** | Table(数据表) | ES 7.x开始默认为_doc，未来版本移除 |
| **Document(文档)** | Row(行) | 索引中的最小数据单元 |
| **Field(字段)** | Column(列) | 文档的属性 |
| **Mapping(映射)** | 表结构 | 定义字段类型、是否索引、是否存储 |

### 5.2 物理概念 (分布式架构)

| 概念 | 说明 |
|------|------|
| **Cluster(集群)** | 一个或多个Node的集合，共同持有完整数据 |
| **Node(节点)** | 集群中的单个服务器，存储数据参与搜索 |
| **Shard(分片)** | Index的逻辑分割，可分布在不同节点上 |
| **Replica(副本)** | 主分片的拷贝，实现冗余和高可用 |
| **Segment(段)** | Shard的最小数据单元，来自Lucene |

### 5.3 Segment段的概念

**Segment来源与作用：**
```
Buffer(内存)
    ↓ (accumulate data)
Segment1 → 磁盘
Segment2 → 磁盘
Segment3 → 磁盘
(多个独立segment)
```

**Segment特点：**
- **最小数据单元** - 一个Shard包含多个Segment
- **不可修改** - 采用批量追加，避免随机写
- **独立查询** - 每个Segment有独立索引，可单独查询
- **删除方式** - 不修改segment，而用另外文件记录删除的DocId
- **查询优化** - Lucene对多Segment进行策略优化

## 6. 分布式集群架构

### 6.1 集群角色划分

**ES的节点角色体系：**

```
集群中的节点角色(非互斥)
│
├─ Master-Eligible Node (候选主节点)
│  └─ 通过选举成为Master Node
│
├─ Data Node (数据节点)
│  └─ 存储数据，执行CRUD/搜索/聚合
│
├─ Ingest Node (预处理节点)
│  └─ 在索引前对数据预处理
│
├─ Machine Learning Node (ML节点)
│  └─ 执行ML相关操作
│
└─ Coordinating-Only Node (仅协调节点)
   └─ 路由请求，处理减少阶段
```

### 6.2 各角色详解

**Master-Eligible Node (候选主节点)：**
- 职责：管理集群变更（创建/删除索引、分配分片）
- 特点：追踪集群中的节点，决定分片分配
- 建议：专用且不与其他角色共用，避免负载影响
- 配置：`node.master: true`

**Data Node (数据节点)：**
- 职责：存储索引数据，执行CRUD/搜索/聚合
- 特点：CPU/内存/I/O密集，需要监控资源
- 扩展：资源不足时添加新数据节点
- 配置：`node.data: true`

**Ingest Node (预处理节点)：**
- 职责：在索引前预处理数据
- 机制：通过processors和pipeline对数据转换、富化
- 特点：不存储数据也不管集群事务
- 类比：Logstash中filter的作用
- 配置：`node.ingest: true`

**Coordinating-Only Node (仅协调节点)：**
- 职责：路由请求、处理搜索减少阶段、分发批量索引
- 机制：
  1. 接收客户端请求
  2. 转发给保存数据的数据节点
  3. 数据节点本地执行并返回结果
  4. 收集合并结果后返回客户端
- 用途：负载均衡，减轻数据节点压力
- 配置：关闭master/data/ingest角色

**Voting-Only Node (仅投票节点)：**
- 职责：仅参与主节点选举投票
- 特点：不能被选举为master，不存储数据
- 用途：三节点集群中实现高可用
- 配置：`node.voting_only: true`

### 6.3 节点角色配置表

| 节点类型 | 配置参数 | 默认值 |
|---------|--------|-------|
| Master-Eligible | node.master | true |
| Data | node.data | true |
| Ingest | node.ingest | true |
| Coordinating-Only | 无(其他为false) | 每个节点默认都是Coordinating |
| Machine Learning | node.ml | true(需enable x-pack) |

### 6.4 集群脑裂问题

**脑裂定义：** 由于网络分区导致集群分裂成多个独立的主节点。

**脑裂发生流程：**

```
初始状态: 3节点集群 (Node1=Master, Node2/3=Data)
    ↓
网络故障: Node1与Node2/3断开连接
    ↓
重新选主: Node2/3认为Node1宕机，重新选主
    ↓
脑裂出现: 
  ├─ 集群1: Node1单独(旧master)
  └─ 集群2: Node2/3新master + Node2/3
    ↓
后续写入: 两个集群独立写入数据
    ↓
数据不一致: 网络恢复后两个集群数据不同步
```

**解决方案：**
```
选票规则: 获得超过 (候选主节点数 + 1) / 2 票才能当选
```

**以3节点集群为例：**
- 需要票数: (3+1)/2 = 2票
- Node3得到Node2/3的2票 → 当选
- Node1只有自己1票 → 未当选
- 结果：仅1个Master，无脑裂

**配置项：**
- 旧版本：`discovery.zen.minimum_master_nodes`
- ES 7.0+：已默认配置，一般不会出现脑裂

## 7. DSL查询体系

### 7.1 查询分类

**Match Query（全文匹配查询）：**
- 对input进行分词，然后查询
- 支持模糊匹配，相关性排序
- 适用：text类型字段

**Term Query（精确查询）：**
- 不进行分词，直接精确匹配
- 适用：keyword类型字段

**Range Query（范围查询）：**
- gt(大于)、gte(大于等于)
- lt(小于)、lte(小于等于)

**Bool Query（复合查询）：**
- must：必须满足
- should：至少满足一个
- must_not：不能满足
- filter：过滤条件

### 7.2 查询实例

```json
# Term精确查询
GET mapping_demo/_search
{
  "query": {
    "term": {
      "name": "北京小区"
    }
  }
}

# Match模糊查询
GET mapping_demo/_search
{
  "query": {
    "term": {
      "city": "北京市"
    }
  }
}

# Range范围查询
GET mapping_demo/_search
{
  "query": {
    "range": {
      "age_range": {
        "gt": 20,
        "lt": 30
      }
    }
  }
}
```

## 8. 聚合分析

### 8.1 聚合概念
聚合是在搜索结果中获得统计数据，可用于分析和汇总。

**常见聚合类型：**
- Count：计数
- Sum：求和
- Avg：平均值

```
    ↓
聚合返回：
  ├─ 分类统计: 自行车鉴赏(12), 自行车大事件(8)...
```

## ASCII流程图

### 流程图1：索引写入流程（Index Flow）

```
客户端请求: PUT /index/_doc/1 {data}
    ↓
协调节点(Coordinating Node)
    ├─ 接收请求
    ├─ 计算routing: hash(doc_id) % num_shards
    └─ 转发到对应Primary Shard
         ↓
    Primary Shard (Data Node)
         ├─ 接收文档
         ├─ 分词处理(如配置了分词器)
         ├─ 构建倒排索引
         ├─ 写入内存Buffer
         ├─ 调用fsync()，确保写入磁盘
         └─ 返回写入成功
              ↓
    Replica Shard (其他Data Node)
         ├─ 接收Primary的flush指令
         ├─ 执行同步写入
         └─ 返回ACK
              ↓
    Primary Shard确认
         └─ 向客户端返回成功

时间线: 写入 → 内存Buffer(秒级) → 磁盘Segment → 副本同步
       |--------- 近实时搜索(1s) ---------|
```

### 流程图2：查询路由与分片读取（Query Flow）

```
用户搜索: GET /index/_search {query}
    ↓
协调节点(Coordinating Node) - Query阶段
    ├─ 接收查询请求
    ├─ 分析query DSL
    ├─ 计算涉及的Shards(Primary + Replica可选)
    └─ 并行转发查询到多个Shard
         ↓
各Shard (Data Node) - 本地查询
    ├─ 遍历倒排索引查找匹配文档
    ├─ 计算TF-IDF相关性分数
    ├─ 返回Top N文档ID + 评分
    └─ 返回给协调节点
         ↓
协调节点 - Fetch阶段
    ├─ 收集各Shard返回的文档ID
    ├─ 全局排序(按相关性分数)
    ├─ 确定最终Top K结果
    └─ 批量获取文档_source
         ↓
各Shard - 获取文档
    ├─ 根据doc_id查找_source
    └─ 返回完整文档
         ↓
协调节点
    ├─ 合并结果
    ├─ 返回给客户端
    └─ 格式: {hits, aggregations, ...}

两阶段: Query(轻) + Fetch(重)
评分: TF-IDF算法(词频-文档反频率)
并行: 充分利用分片并行能力
```

### 流程图3：分片与副本的分配（Shard Allocation）

```
创建Index: PUT /myindex
  settings: {
    number_of_shards: 3,
    number_of_replicas: 2
  }
    ↓
Master Node规划分配
    ├─ 创建3个Primary Shard
    ├─ 为每个Primary创建2个Replica
    └─ 共9个Shard待分配
         ↓
集群拓扑(例：6个Data Node)
    ├─ Node1: P0, R1, R2
    ├─ Node2: P1, R2, R0
    ├─ Node3: P2, R0, R1
    ├─ Node4: R0, R1
    ├─ Node5: R2, 空闲
    └─ Node6: 空闲
         ↓
分配原则:
    1. Primary均衡分布
    2. Replica不与Primary同节点
    3. Replica间尽量分散
    4. 节点利用率均衡
         ↓
故障转移场景:
    Node1宕机
         ↓
    Master检测
         ↓
    Replica转Primary
    ├─ Node2上的R1 → P0
    ├─ Node3上的R2 → P1
    └─ Node4上的R0 → P2
         ↓
    重新分配Replica
    └─ 在其他节点上创建新副本
         ↓
    集群恢复绿色状态(所有Primary+Replica就绪)

颜色标记:
  Green: 所有分片已分配
  Yellow: 副本未全部分配
  Red: 主分片未分配
```

### 流程图4：倒排索引构建（Inverted Index Building）

```
原始文本: "我喜欢学习ElasticSearch和Lucene"
    ↓
分词器处理(IK分词)
    ├─ Character Filter: 去除特殊字符、HTML标签
    ├─ Tokenizer: 按中英文规则拆分
    └─ Token Filter: 小写、停词删除等
    ↓
词项列表: [我, 喜欢, 学习, elasticsearch, 和, lucene]
    ↓
构建倒排索引
    ├─ 词项 | 文档列表 | 位置
    ├─────────────────────────────
    ├─ 我   | [Doc1]  | [0]
    ├─ 喜欢 | [Doc1]  | [1]
    ├─ 学习 | [Doc1]  | [2]
    ├─ es   | [Doc1]  | [3]
    ├─ 和   | [Doc1]  | [4]
    └─ lucene | [Doc1]  | [5]
    ↓
写入Segment
    ├─ 倒排索引部分(磁盘)
    ├─ 文档存储部分(磁盘)
    └─ segment metadata
    ↓
搜索时查询
    输入: "学习elasticsearch"
    分词: [学习, elasticsearch]
    ↓
查询倒排索引
    学习 → [Doc1] ✓
    elasticsearch → [Doc1] ✓
    ↓
命中Doc1, 返回结果
```

### 流程图5：Segment合并与优化（Segment Merge）

```
初始状态: 多个segment
    ├─ Segment1 (100条文档)
    ├─ Segment2 (50条文档)
    ├─ Segment3 (30条文档)
    ├─ Segment4 (20条文档)
    └─ Segment5 (新数据, 小segment)
         ↓
Lucene优化策略检测
    └─ 小segment过多 → 触发merge
         ↓
合并过程
    ├─ 读取Segment1-5的倒排索引
    ├─ 合并所有词项(去重合并)
    ├─ 重新分配docId
    ├─ 合并处理被删除的文档
    └─ 写入新Segment(200条)
         ↓
合并后
    ├─ Segment_merged1 (200条)
    ├─ Segment6 (新增)
    └─ (旧segment逐步删除)
         ↓
优势:
    1. 减少segment数量
    2. 提升查询性能(扫描segment数少)
    3. 清理已删除文档(减少磁盘占用)
    4. 改进文件缓存效率

时机: 
    - 定期合并(后台)
    - 手动触发(_forcemerge)
```

```
数据采集层 → 数据处理层 → 存储检索层 → 可视化层
```

## 速查表

### 常用Mapping类型

```json
// 文本字段
{ "type": "text", "analyzer": "standard" }        // 全文搜索
{ "type": "keyword" }                              // 精确值

// 数字字段
{ "type": "long" }                                 // 整数
{ "type": "double" }                               // 浮点数

// 日期字段
{ "type": "date", "format": "yyyy-MM-dd HH:mm:ss" } // 日期

// 其他
{ "type": "boolean" }                              // 布尔值
{ "type": "geo_point" }                            // 地理位置
```

### 常用DSL查询模式

```json
// 精确查询
{ "query": { "term": { "field": "value" } } }

// 全文搜索
{ "query": { "match": { "field": "keywords" } } }

// 范围查询
{ "query": { "range": { "field": { "gte": 10, "lte": 20 } } } }

// 组合查询
{ "query": {
  "bool": {
    "must": [{ "term": { "status": "active" } }],
    "filter": [{ "range": { "age": { "gte": 18 } } }]
  }
} }
```

### 性能优化检查表

| 项目 | 检查点 |
|------|--------|
| **映射设计** | ✓ 禁用动态映射(dynamic: false/strict) |
| | ✓ 为text字段指定analyzer |
| | ✓ 不需要的字段设置index: false |
| **索引设计** | ✓ 主分片数量 = k × 数据节点数(k=1/2) |
| | ✓ 单个Shard大小 ≤ 30GB |
| | ✓ 使用时间分割索引(日/周/月) |
| **查询优化** | ✓ 优先使用filter(避免评分计算) |
| | ✓ 用bool.must_not替代not filter |
| | ✓ 合理设置size和from(避免深分页) |
| **写入优化** | ✓ 批量写入(bulk API) |
| | ✓ 调整refresh_interval(默认1s) |
| | ✓ 禁用副本(数据导入时)后再开启 |
| **监控指标** | ✓ Shard分配状态(green/yellow/red) |
| | ✓ JVM内存使用率 |
| | ✓ 磁盘空间使用率 |

### 常见问题速查

| 问题 | 解决方案 |
|------|---------|
| 索引创建后分片数不对 | 无法修改，需_split或_shrink倍增减 |
| 字段类型需要修改 | 只能新增字段，修改需_reindex重建 |
| 分词效果不好 | 检查analyzer配置，考虑使用ik_smart/ik_max_word |
| 写入性能慢 | 调整bulk size，禁用副本，增加refresh_interval |
| 查询结果排序不对 | 确认字段是否为keyword，检查sort配置 |
| 内存占用过高 | 减少Shard数量，调整JVM堆内存，检查聚合复杂度 |
