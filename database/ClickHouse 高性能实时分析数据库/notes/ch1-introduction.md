# 第1章 ClickHouse 世界初探

> 本章梳理自原文「第1章 ClickHouse 世界初探」。聚焦 OLAP 概念、ClickHouse 核心特性、单机/集群架构、客户端模型及 ZooKeeper 的角色。

---

## 1. OLAP 与 OLTP

| 维度 | OLTP (联机事务处理) | OLAP (联机分析处理) |
|------|--------------------|--------------------|
| 典型场景 | 转账、下单、增删改单条记录 | 报表、聚合、多维分析 |
| 数据量 | 每次操作 1~N 行 | 每次扫描 N 万~N 亿行 |
| 优化目标 | 低延迟单点读写、事务一致性 | 高吞吐扫描、聚合速度 |
| 存储 | 行式存储为主 | 列式存储为主 |
| 代表 | MySQL、PostgreSQL、Oracle | ClickHouse、Doris、Druid、BigQuery |

OLAP 核心价值:**快速响应、多维分析、自助决策**。

现代分析的挑战:**数据量级(TB/PB)、维度增加、实时性要求**——传统 OLTP 数据库直接跑 `GROUP BY` 已无力承担,这正是 ClickHouse 的赛道。

## 2. ClickHouse 的四大"超能力"

官方口号:*Blazingly Fast, Open Source, Column-Oriented SQL Database*。

### 2.1 列式存储 (Column-Oriented)

行式存储:`[1,'张三','北京',30], [2,'李四','上海',25], ...`
列式存储:`[1,2,3] | ['张三','李四','王五'] | ['北京','上海','北京'] | [30,25,35]`

计算 `avg(age)` 时,列存只读 age 这一列,行存得读全表 → I/O 数量级差距。

### 2.2 向量化执行 (Vectorized Execution)

传统数据库一行一行(标量)处理,ClickHouse 一批一批(向量)处理:每次从列中取出一整块(默认 8192 行)在 CPU 上做计算,充分利用 CPU Cache 与 SIMD 指令,显著降低函数调用开销。

### 2.3 高压缩比

同列数据类型相同、相似度高,易压缩。默认压缩算法是 **LZ4**(高速),也可选 **ZSTD**(高压缩比)。压缩既省存储,也减 I/O,进而提速查询。

### 2.4 MPP 架构

集群模式下,一条查询会被拆解后并行下发到所有分片节点,各节点并行计算自己持有的数据,最后由协调节点聚合结果。

## 3. 单机 vs 分布式架构

### 3.1 单节点

所有数据存储、计算都在一台机器上。适合开发、学习、小数据量。

### 3.2 分布式集群:Shard + Replica + ZooKeeper

- **分片 (Shard)**:数据水平切分,扩展存储和计算能力。
- **副本 (Replica)**:每个分片的镜像,保证宕机不丢服务。
- **ZooKeeper / ClickHouse Keeper**:协调服务——存放复制日志、分布式 DDL 任务队列、副本元数据。

```
                ┌─────────────────────────────────────┐
                │            Client (SQL)             │
                └──────────────┬──────────────────────┘
                               │
                ┌──────────────▼──────────────────────┐
                │   Distributed Table (any node)      │  路由层
                └──────┬───────────────┬──────────────┘
                       │               │
              ┌────────▼──────┐ ┌──────▼──────────┐
              │   Shard 1     │ │   Shard 2       │ ...
              │  (data 1/N)   │ │  (data 1/N)     │
              ├───────────────┤ ├─────────────────┤
              │ Replica A ◄──►│ │ Replica A ◄──► │   ZK 协调
              │ Replica B ◄──►│ │ Replica B ◄──► │   副本同步
              └───────┬───────┘ └─────────┬───────┘
                      │                   │
                      └────────┬──────────┘
                               │
                       ┌───────▼───────┐
                       │  ZooKeeper /  │
                       │   CH Keeper   │
                       └───────────────┘
```

## 4. 客户端 / 服务器模型

ClickHouse 是 C/S 架构,所有交互工具(`clickhouse-client`、DBeaver、Driver SDK)都是客户端,通过网络协议与服务端通信:

| 协议 | 端口(默认) | 用途 |
|------|------------|------|
| TCP / Native | 9000 | 性能最高,`clickhouse-client` 和大多数原生驱动使用 |
| HTTP / HTTPS | 8123 / 8443 | 通用、跨语言,curl、浏览器、JDBC 都可以走 |
| MySQL 协议 | 9004 | 用 MySQL 客户端连 ClickHouse(兼容子集) |
| PostgreSQL 协议 | 9005 | 用 psql 连 ClickHouse(兼容子集) |
| gRPC | 9100 | 现代 RPC 接入 |

```
   ┌──────────────────────┐                ┌────────────────────────┐
   │  clickhouse-client   │───TCP(9000)───►│                        │
   │  DBeaver / DataGrip  │───HTTP(8123)──►│   ClickHouse Server    │
   │  Java JDBC, Python   │                │  (Native/HTTP/gRPC...) │
   │  curl, Browser       │───HTTP(8123)──►│                        │
   └──────────────────────┘                └────────────────────────┘
```

## 5. ZooKeeper 在集群里到底做什么

ZooKeeper **不存业务数据**,只存"元数据 + 协调任务"。它是分布式集群的一致性基石。

### 5.1 数据复制流程(ReplicatedMergeTree)

```
   Client INSERT
        │
        ▼
  ┌────────────────────┐                       ┌────────────────────┐
  │ Replica A (Shard1) │                       │ Replica B (Shard1) │
  └─────────┬──────────┘                       └─────────┬──────────┘
            │  1. 本地写入新 Data Part                    │
            │  2. 在 ZK 的 /log 队列写一条 "GET_PART" 日志│
            ▼                                            │
  ┌─────────────────────────────────────────────────────▼──────────┐
  │                  ZooKeeper / ClickHouse Keeper                  │
  │   /clickhouse/tables/{shard}/{table}/log/log-NNNN  (操作日志)   │
  │   /clickhouse/tables/{shard}/{table}/replicas/...               │
  └───────────────────────────────────────────────────────┬─────────┘
                                                          │ 3. Replica B
                                                          │    监听到日志
                                                          ▼
                                              ┌────────────────────┐
                                              │ Replica B 主动     │
                                              │ 向 Replica A 拉数据│
                                              │ → 落盘 → 完成同步  │
                                              └────────────────────┘
```

**要点**:复制是**多主**的,任何一个副本写入都会广播到其他副本;数据传输走 ClickHouse 节点间的 HTTP/9009 接口,**ZK 只传递元数据/任务**,不搬业务数据。

### 5.2 分布式 DDL(`ON CLUSTER`)流程

```
   Client: CREATE TABLE ... ON CLUSTER my_cluster
        │
        ▼
  ┌─────────────────────┐
  │  任意一个 CH 节点    │── 将 DDL 任务写入 ZK ──┐
  └─────────────────────┘                        │
                                                 ▼
                              ┌────────────────────────────────────┐
                              │   ZK: /clickhouse/task_queue/ddl   │
                              │   含: query SQL + 集群名 + initiator│
                              └─┬─────────────┬───────────────┬────┘
                                │             │               │
        集群中每个节点 watch     │             │               │
        并取出与自己相关的任务   ▼             ▼               ▼
                          ┌─────────┐   ┌─────────┐    ┌─────────┐
                          │ Node 1  │   │ Node 2  │ …  │ Node N  │
                          │ 本地执行 │   │ 本地执行│    │ 本地执行│
                          │ CREATE  │   │ CREATE  │    │ CREATE  │
                          └────┬────┘   └────┬────┘    └────┬────┘
                               │             │              │
                               └─────────────┼──────────────┘
                                             ▼
                              ZK 任务节点下登记每个节点的执行结果
```

发起方等待所有节点回写结果(或超时),从而保证集群表结构最终一致。

## 6. ClickHouse vs 其他技术(选型一句话)

- **MySQL / PostgreSQL**:OLTP,适合事务和高并发单点 CRUD,不擅长大规模聚合。
- **Hive / Spark SQL**:批处理,延迟分钟到小时级,不适合在线交互查询。
- **Druid / Pinot**:专门做实时聚合,有预聚合限制,SQL 灵活度不如 CH。
- **Elasticsearch**:全文搜索强,聚合 OK 但成本高,不擅长 JOIN。
- **ClickHouse**:对结构化数据做极速聚合分析是首选;不擅长高并发单行 UPDATE/DELETE、不擅长大表之间 JOIN。

---

## 7. 开源版 vs ClickHouse Cloud

- **开源自建**:可控、零授权费用;运维复杂度高,扩缩容、备份、监控全靠自己。
- **ClickHouse Cloud**:Serverless、自动扩缩容、对象存储分离、按用量计费;免运维但有云成本。

## 8. 本章勘误区

> 原文表述总体准确,以下几处建议修正。

### ✗ 原文
> "**ZooKeeper:** 在集群中扮演着'协调者'的角色,负责管理副本之间的数据同步和一致性。"
>
> 后文补充:"a. 该副本把'我插入了某某数据块'这个**操作日志**,发布到 ZooKeeper 的一个共享任务队列里。b. 同一个分片下的其他副本,一直在'监听'这个队列。c. 它们看到新任务后,就会从那个副本那里把对应的数据块拉过来,应用到自己身上。"

### ✓ 正解 / 补充
说法方向正确,但容易让初学者误以为业务数据穿过 ZK,需要补两点:

1. **数据本体不走 ZK**。ZK 只存 `LogEntry`(包含操作类型、Part 名、源副本等元数据),实际数据块由副本之间通过 ClickHouse 节点间的 **HTTP 接口(端口 9009,`interserver_http_port`)** 直接传输。
2. 从 **v22.x 起**官方推荐用内置的 **ClickHouse Keeper** 替代 ZooKeeper,兼容 ZK 协议,运维更简单、内存更小、性能更好。原文第 7 章 提到了 Keeper,但第 1 章只字未提,容易让读者以为 ZK 是唯一选择。

---

### ✗ 原文
> "ClickHouse 默认使用 **LZ4** 压缩算法,可以达到很高的压缩比。"

### ✓ 正解 / 补充
LZ4 的特点是**速度极快**而不是**压缩比高**——它牺牲了压缩比换取吞吐。如果业务追求更高压缩比(冷数据、归档),应改用 `CODEC(ZSTD(level))`,典型场景下压缩比是 LZ4 的 1.5~2 倍,但解压速度只有约 1/2~1/3。

---

### ✗ 原文
> "在集群模式下,一个查询会被打散到多台机器(**分片**)上并行执行,最后再汇总结果。"

### ✓ 正解 / 补充
表述本身没错,但要补一句关键:**只有用 `Distributed` 表或 `cluster()` 表函数发起的查询才会自动并行**。直接查本地表(例如 `logs_local`)仍然只在当前节点执行,不会自动跨节点。

---

### ⚠ 表述模糊
> "**主键 (Primary Key):** 在 `MergeTree` 中,主键就是 `ORDER BY` 定义的键(或者其前缀)。"

### ✓ 补充
更准确的说法:**默认情况下** PRIMARY KEY = ORDER BY;但可以显式指定一个 ORDER BY 的**前缀**作为 PRIMARY KEY,使得主键索引比排序键短、占用内存更小(典型应用见 4.3 节)。`ORDER BY (a,b,c) PRIMARY KEY (a,b)` 是合法的;反向(主键更长)则不行。
