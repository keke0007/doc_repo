## 扩容背景与分类

### 1. 为什么需要扩容

**问题场景**
- 项目初期：部署3个数据库(A、B、C)，用uid%3取模分片
- 随着用户增长：数据量逐渐达到单库最佳存储容量
- 继续增加数据：导致CRUD操作变慢，影响系统响应速度

**扩容的必要性**
| 问题 | 后果 |
|------|------|
| 单库容量满 | 查询性能下降 |
| 写入吞吐量瓶颈 | 业务响应缓慢 |
| 存储空间耗尽 | 系统风险 |

### 2. 扩容分类

#### 垂直扩容 vs 水平扩容

| 维度 | 垂直扩容 | 水平扩容 |
|------|---------|---------|
| **定义** | 升级单机配置(CPU、内存、磁盘) | 增加数据库节点数量 |
| **成本** | 低，快速见效 | 高，需要数据迁移 |
| **上限** | 有天花板(单机资源限制) | 理论无限扩展 |
| **复杂度** | 低 | 高，需要分片策略 |
| **使用场景** | 短期流量增长 | 长期业务发展 |

**结论**：垂直扩容是过渡方案，水平扩容是最终解决方案。

## 扩容方案对比

### 方案1：停机迁移方案

```
┌─────────────────────────────────────────────────────────────────┐
│                    停机方案时间线                                 │
├─────────────────────────────────────────────────────────────────┤
│  发布  │  关闭   │  离线迁移  │  数据   │ 修改 │ 重启 │  回滚  │
│  公告  │ 服务   │ (拆分重分)  │  校验   │ 配置 │ 服务 │ 预案   │
└─────────────────────────────────────────────────────────────────┘
         ↓         ↓            ↓         ↓      ↓    ↓
      用户等待  无法访问   耗时长     正常     正常  正常
```

**步骤详解**
1. 发布公告：提前告知用户维护时间
2. 停止服务：关闭应用层Service
3. 离线迁移：按uid%4重新分配数据，需要重新计算分片位置
4. 数据校验：对比旧库和新库数据完整性
5. 修改配置：更新Service层的分片算法(uid%3→uid%4)
6. 恢复服务：重启Service，用户恢复访问
7. 回滚预案：每步都要有回滚机制

**优缺点**
- 优点：实现简单，数据一致性有保障
- **缺点**：用户体验差，必须停机，时间压力大，业务受损

**易混淆点**：停机方案虽然简单，但在互联网场景中不可接受。

### 方案2：停写方案

```
┌──────────────────────────────────────────────────────────────┐
│                   停写方案时间线                               │
├──────────────────────────────────────────────────────────────┤
│ 支持    │ 升级 │ 中断写操作  │ 数据  │ 修改 │ 恢复 │ 数据 │
│ 读写    │ 公告 │ (返回提示)  │ 迁移  │ 配置 │ 写   │ 清理 │
│ 分离    │      │             │       │      │      │ (DEL)│
└──────────────────────────────────────────────────────────────┘
         ↓     ↓              ↓       ↓      ↓     ↓     ↓
      可读   等待      只读，写被拦截  正常   全量   回滚
```

**核心机制**
- 启用读写分离(主库负责读写，从库负责读取)
- 在Service层拦截所有写请求：返回"服务升级中，只提供读服务"

**步骤详解**
1. 支持读写分离：确保主从架构就位
2. 升级公告：通知用户
3. 中断写操作：Service层拦截写请求
4. 数据迁移：将旧库数据按新规则分配到新库(注意：是复制，非剪切)
5. 数据校验：对比备份数据和迁移后数据
6. 修改配置：通过配置中心更新(不需要重启)
7. 恢复写操作：释放拦截，恢复读写
8. 数据清理：删除冗余数据(不影响线上一致性)

**优缺点**
- 优点：部分可用，用户可以读取数据
- **缺点**：复制数据耗时长，停写时间仍较长，需要清理冗余数据

**关键差异**：vs停机方案 = 允许读取；vs双写方案 = 停止写入

### 方案3：日志方案(binlog增量同步)

```
┌──────────────────────────────────────────────────────────────┐
│                 日志方案架构与时间线                            │
├──────────────────────────────────────────────────────────────┤
│ 旧库  │ 日志   │ 全量迁移 │ 日志增量 │ 数据  │ 切换 │ 清理 │
│ 对外  │ 记录   │         │ 追平    │ 校验  │ 新库 │ 旧库 │
│ 服务  │ 变更   │         │         │       │      │      │
└──────────────────────────────────────────────────────────────┘
  ↓    ↓       ↓         ↓         ↓      ↓      ↓
连续   记录   持续       追平到   完全   无缝   随时
服务   变更   迁移       一致     一致   切换   执行
```

**核心思路**：分离全量迁移和增量追平，允许线上持续服务

**关键步骤**

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 日志记录 | 异步记录旧库的DML变更(增、删、改)，只记录：库名、表名、主键、操作类型 |
| 2 | 全量迁移 | 研发工具迁移旧库数据到新库，可限速/分批执行，不影响线上 |
| 3 | 增量追平 | 解析日志，读取变更记录的主键，从旧库查询最新值，写入新库 |
| 4 | 数据校验 | 对比旧库和新库，确保完全一致(无限逼近过程) |
| 5 | 灰度切流 | 配置中心动态调整路由规则，逐步转移流量到新库 |
| 6 | 停写只读 | 极限场景：旧库切为只读，等待增量追平完全完成 |
| 7 | 正式切换 | 100%切换到新库提供服务 |

**日志记录的最小字段集**
```
修改库   | 修改表    | 修改主键 | 操作类型
---------|----------|----------|----------
smooth   | t_trade  | 12345    | UPDATE
smooth   | t_trade  | 12346    | INSERT
smooth   | t_trade  | 12347    | DELETE
```

**风险分析**
- 优点：线上持续服务，容错性强，可随时回滚
- **缺点**：操作繁琐，需要适配多个同步工具，成本高，周期长

**适用场景**：大数据量(TB级)，对业务连续性要求最高

### 方案4：双写方案(Canal+MQ)

```
┌────────────────────────────────────────────────────────┐
│              双写方案完整时间线                          │
├────────────────────────────────────────────────────────┤
│ 新库 │ 全量  │ Canal同步 │ 灰度 │ 切流 │ 异常修复 │ 校验 │
│ 部署 │ 迁移 │(从→新库)  │ 流量 │ 至新 │ (自动/手) │     │
└────────────────────────────────────────────────────────┘
  ↓    ↓     ↓            ↓    ↓      ↓           ↓
规划   耗时  自动增量     测试  无缝   修复孤儿   完整
```

**核心机制**：基于Canal监听从库binlog，异步写入新库

**步骤详解**
1. 增加新库：按现有节点数量部署新节点(例：2→4)
2. 全量迁移：断开主从，导入备份数据(耗时较长)
3. 增量同步：
   - 开启Canal服务，监听旧库从库
   - 重启主从同步关系
   - 从库收到日志后，Canal转发至新库
4. 灰度流量：通过Nginx逐步调整流量配比(例：10%→50%→100%)
5. 异常修复：
   - 场景：Canal未同步，但已切流(如下单操作，资金已扣)
   - 处理：定制程序检测异常日志，自动修复或人工处理
6. 修复异常数据：在凌晨用户少或停外网时进行切流，减少孤儿数据
7. 数据校验：校验新库数据数量的完整性

**优缺点**
- 优点：实现相对简洁，中小数据量适用，自动增量
- **缺点**：可能产生孤儿数据(写入新库但未同步)，需要异常修复机制

**适用场景**：中小数据量(GB级)，可容忍短暂不一致

### 方案5：平滑2N方案(最优实践)

```
┌────────────────────────────────────────────────────────┐
│              平滑2N方案架构(最精妙)                      │
├────────────────────────────────────────────────────────┤
│ 扩容前         │         扩容后(升级从库)              │
├─────────────────────────────────────────────────────────┤
│ A(主)  A0(从)  │ A(主)  A0(新主)                      │
│ B(主)  B0(从)  │ B(主)  B0(新主)                      │
│ 规则:uid%2     │ 规则:uid%4                           │
│                │ A和A0分别负责uid%4=0和2的数据        │
│                │ B和B0分别负责uid%4=1和3的数据        │
└────────────────────────────────────────────────────────┘
```

**关键洞察**：利用现有的主从数据副本，零数据迁移！

**步骤详解**

| 阶段 | 操作 | 时间 | 影响 |
|------|------|------|------|
| 1 | 升级从库为新主库 | 秒级 | 无 |
| 2 | 修改配置中心分片规则 | 秒级 | 无(只改路由) |
| 3 | 清理冗余数据(DELETE) | 分钟级 | 无(不影响一致性) |
| 4 | 为新主库重新配置从库 | 分钟级 | 无 |

**为什么不需要数据迁移**
- A和A0本身就是主从，数据完全一致
- A0升级为新主后，仍然有全量数据
- 只需调整分片规则，让A0处理其需要的分片范围
- 旧数据中不属于A0的部分DELETE即可

**性能指标**
- 配置更新时间：秒级(通过配置中心，无需重启)
- 总扩容时间：分钟级
- **用户感知：几乎无感知**

**扩容规则变化示例**
```
变化前(uid%2)：
  - A库: uid%2=0 (uid=0,2,4,6,...)
  - B库: uid%2=1 (uid=1,3,5,7,...)

变化后(uid%4)：
  - A库:  uid%4=0 或 uid%4=2 (uid=0,2,4,6,8,10,...)
  - A0库: uid%4=2 (uid=2,6,10,14,...) ← 原本在A库
  - B库:  uid%4=1 或 uid%4=3 (uid=1,3,5,7,9,11,...)
  - B0库: uid%4=3 (uid=3,7,11,15,...) ← 原本在B库
```

**扩容后的高可用架构**
```
清理完成后：
├─ A主库  ── A1从库(新配置)
├─ A0主库 ── A2从库(新配置)
├─ B主库  ── B1从库(新配置)
└─ B0主库 ── B2从库(新配置)

结构：2个主库→4个主库，每个主库配1个从库，共8个节点
```

**优缺点**
- 优点：
  - **零数据迁移**，只需配置变更
  - 秒级切换，无感知扩容
  - 利用现有从库，成本低
- **缺点**：
  - 前提条件严格(必须有从库)
  - 只适用2N扩容(2→4→8...)

**适用场景**：大数据量，对业务连续性要求极高，已有从库架构

## 分片规则详解

### 1. 取模分片(Modulo Hash)

```
┌─────────────────────────────────────────────────────┐
│           取模分片：uid%N 规则                        │
├─────────────────────────────────────────────────────┤
│ uid  │ uid%3 │ uid%4 │ 分片结果变化                   │
├─────────────────────────────────────────────────────┤
│  0   │  0    │  0    │ A→A                           │
│  1   │  1    │  1    │ B→B                           │
│  2   │  2    │  2    │ C→A0                          │
│  3   │  0    │  3    │ A→B0 (数据迁移!)              │
│  4   │  1    │  0    │ B→A (数据迁移!)               │
│  5   │  2    │  1    │ C→B (数据迁移!)               │
│  6   │  0    │  2    │ A→A0 (数据迁移!)              │
└─────────────────────────────────────────────────────┘
```

**特性**
- 优点：计算简单，均匀分布
- **缺点**：扩容时大量数据迁移(3→4时，约75%数据重定位)

**扩容的数据重定位问题**
```
当N从3变为4时：
- 数据迁移比例: 1 - (min(3,4)/max(3,4)) = 1 - 3/4 = 25%不迁移，75%迁移
- 即：新增一个节点，约90%的旧数据需要重新分配
```

**计算示例**
```
uid=3:
  扩容前: 3%3=0 → 分配到A库(第0个，从0开始计数)
  扩容后: 3%4=3 → 分配到D库(第3个)
  ❌ 需要迁移
```

### 2. 范围分片(Range Sharding)

```
┌──────────────────────────────────────────────────────┐
│         范围分片：按uid范围划分                         │
├──────────────────────────────────────────────────────┤
│ uid范围     │ 库    │ 扩容后                            │
├──────────────────────────────────────────────────────┤
│ 1-500000   │ A库   │ 1-500000   → A(不变)             │
│ 500001-1M  │ B库   │ 500001-1M  → B(不变)             │
│ 1M-1.5M    │ C库   │ 1M-1.25M   → C(不变)             │
│            │       │ 1.25M-1.5M → D(新库,需迁移)     │
└──────────────────────────────────────────────────────┘
```

**特性**
- 优点：扩容灵活，可按需调整范围，迁移数据明确
- **缺点**：数据分布可能不均(热点问题)，需预规划

**迁移工作量**
```
原范围: 1M-1.5M (500万条)
新范围分割:
  C库: 1M-1.25M (250万条，保留)
  D库: 1.25M-1.5M (250万条，迁移)

迁移成本: 250万条 ÷ 1500万条 ≈ 16.7% (相比取模的75%更优)
```

### 3. 一致性哈希(Consistent Hash)

```
┌────────────────────────────────────────────────────────┐
│         一致性哈希环：扩容前后数据迁移示意               │
├────────────────────────────────────────────────────────┤
│                                                          │
│          扩容前(3个节点)：              扩容后(4个节点)： │
│                                                          │
│         ╭─── A(0-120°)           ╭─ A(0-90°)          │
│       360°─ ────────────── 0°   360°─ ────────── 0°     │
│         │                        │                      │
│         ╰─── B(120-240°)         │  D(90-180°)新增     │
│         │                        │                      │
│         ├─── C(240-360°)         ├─ B(180-270°)        │
│         │                        │                      │
│         └────────────────┘       ╰─ C(270-360°)        │
│                                                          │
│  hash(uid)对应圆周上的位置，顺时针找第一个节点           │
│                                                          │
│  新增D后：                                               │
│  - uid落在(90°-180°)范围 → 从C迁移到D                  │
│  - 其他uid → 保持不变                                    │
│  - 迁移比例: 约1/(N+1) = 1/4 = 25% (相比取模优化!)    │
│                                                          │
└────────────────────────────────────────────────────────┘
```

**一致性哈希的计算过程**
```
1. 计算uid的哈希值：hash_value = hash(uid)
2. 将hash_value映射到[0, 360°)的圆周
3. 顺时针查找第一个节点的位置作为存储位置

示例(uid=12345):
  hash(12345) = 157°
  扩容前：157°在范围(120°-240°)，落到B库
  扩容后：157°在范围(90°-180°) = D库，需要从C迁移...
  不对，重新计算：
  157°在范围(90°-180°)，落到D库(新增)
  原本在(120°-240°)的B库范围内，但现在在D库
  因此需要从B库迁移到D库 ✓
```

**特性**
- 优点：
  - 扩容时只有少量数据迁移(1/(N+1)比例)
  - 节点变化影响范围小
- **缺点**：
  - 计算相对复杂
  - 需要处理热点节点(虚拟节点技术)

**虚拟节点(Virtual Node)解决热点问题**
```
单个节点：hash(A) = 120°，"A在360°上的一个点"
虚拟节点：
  - hash(A#1) = 120°
  - hash(A#2) = 200°
  - hash(A#3) = 280°
  ← A在360°上均匀分布3个位置，更均匀！
```

**对比总结**
| 分片规则 | 计算复杂度 | 扩容迁移比例 | 热点处理 | 适用场景 |
|---------|----------|-----------|---------|---------|
| 取模 | 低 | ~75% | 均匀 | 小规模 |
| 范围 | 低 | 可控 | 需预规划 | 中等规模，可预测 |
| 一致性哈希 | 中 | ~25% | 虚拟节点 | 大规模，动态扩容 |

## 平滑2N扩容方案

### 完整实现步骤

#### 阶段1：前置条件检查
```
检查清单：
☑ 所有数据库都配置了主从(高可用架构)
☑ 从库已开启binlog: log-slave-updates=on
☑ 配置中心就位(支持动态配置变更)
☑ ShardingJDBC/MyCat等中间件部署完毕
```

#### 阶段2：升级从库为新主(秒级完成)
```
操作流程：

原始架构(2主2从)：
┌─────────────────┐
│ A(主)  ← → A0(从)│  uid%2=0
├─────────────────┤
│ B(主)  ← → B0(从)│  uid%2=1
└─────────────────┘

升级后(4主)：
┌─────────────────┐
│ A(主)  ← → A1(从)│  uid%4=0
├──────────┬──────┤
│ A0(新主) ← → A2  │  uid%4=2
├─────────────────┤
│ B(主)  ← → B1(从)│  uid%4=1
├──────────┬──────┤
│ B0(新主) ← → B2  │  uid%4=3
└─────────────────┘

A0升级操作(在A0节点执行)：
MariaDB [(none)]> stop slave;           // 停止作为A的从库
Query OK, 0 rows affected

MariaDB [(none)]> reset slave;          // 重置从库状态
Query OK, 0 rows affected

MariaDB [(none)]> set global read_only=off;  // 变为读写
Query OK, 0 rows affected

(此时A0成为独立主库，数据与A完全同步)
```

**关键配置**：自增ID避免冲突
```ini
A主库配置:
  auto-increment-offset=1     # 从1开始
  auto-increment-increment=2  # 每次+2，产生奇数: 1,3,5,...

A0新主配置:
  auto-increment-offset=2     # 从2开始
  auto-increment-increment=2  # 每次+2，产生偶数: 2,4,6,...

好处：A和A0的新插入数据永不冲突(奇偶分离)
```

#### 阶段3：修改分片配置(秒级完成)

### 3. 动态扩容的代码实现

```java
// 动态添加新的数据源(扩容操作)
public void dynamicScaleOut() {
    try {
        // 1. 加载新数据源配置
        Properties newDataSourceProps = loadPropertiesFile("datasource_new.properties");
        
        // 2. 创建Druid连接池
        DruidDataSource newDataSource = (DruidDataSource) 
            DruidDataSourceFactory.createDataSource(newDataSourceProps);
        
        // 3. 配置连接池参数(可靠性)
        newDataSource.setRemoveAbandoned(true);
        newDataSource.setRemoveAbandonedTimeout(600);  // 10分钟
        newDataSource.setLogAbandoned(true);
        newDataSource.setTimeBetweenConnectErrorMillis(60000);  // 重连间隔
        newDataSource.init();
        
        // 4. 获取当前ShardingDataSource
        OrchestrationShardingDataSource dataSource = 
            SpringContextUtil.getBean("tradeSystemDataSource", 
                                      OrchestrationShardingDataSource.class);
        
        // 5. 获取现有的数据源映射
        Map<String, DataSource> dataSourceMap = 
            dataSource.getDataSource().getDataSourceMap();
        
        // 6. 加入新数据源
        dataSourceMap.put(DatasourceEnum.DATASOURCE_2.getValue(), newDataSource);
        
        // 7. 构建新的数据源配置集合
        Map<String, DataSourceConfiguration> dataSourceConfigMap = 
            new HashMap<>();
        for(String key : dataSourceMap.keySet()) {
            dataSourceConfigMap.put(key, 
                DataSourceConfiguration.getDataSourceConfiguration(
                    dataSourceMap.get(key)
                ));
        }
        
        // 8. 更新分片规则(核心!)
        String newRule = generateNewShardingRule();  // uid % 4
        replaceActualDataNodes(newRule);  // 更新actual_nodes映射
        
        // 9. 发送配置变更事件(触发动态刷新)
        dataSource.renew(new DataSourceChangedEvent(
            "/" + DruidSystemDataSourceConfiguration.DYNAMIC_SHARDING 
            + "/config/schema/logic_db/datasource",
            dataSourceConfigMap
        ));
        
        log.info("Scale-out completed successfully!");
        
    } catch (Exception e) {
        log.error("Scale-out failed: {}", e.getMessage(), e);
        // 回滚操作...
    }
}

// 生成新的分片规则(uid % 4)
private String generateNewShardingRule() {
    return "t_trade: {"
        + "  databaseStrategy: 'uid % 4',"
        + "  actualDataNodes: ["
        + "    'A': 'uid%4=0',"
        + "    'A0': 'uid%4=2',"
        + "    'B': 'uid%4=1',"
        + "    'B0': 'uid%4=3'"
        + "  ]"
        + "}";
}
```

### 4. 常见限制(务必牢记)

ShardingJDBC虽然功能强大，但存在SQL语法限制：

| 不支持特性 | 原因 | 替代方案 |
|----------|------|---------|
| 子查询 | 分布式执行困难 | 改为JOIN或应用层实现 |
| HAVING子句 | 需在分布式数据上计算 | 使用WHERE替代 |
| OR条件 | 无法路由到单一库 | 改为多次查询或UNION |
| UNION/UNION ALL | 跨库合并困难 | 应用层实现 |
| 多行INSERT | VALUES(多行) | 改为单行INSERT逐条插入 |
| DISTINCT聚合 | 分布式去重困难 | 应用层实现 |
| CASE WHEN | 跨库条件执行不一致 | 应用层实现逻辑 |
| SELECT LAST_INSERT_ID() | 无法获取全局自增 | 改为先插入再查询ID |

### 双写期间的数据一致性校验流程

```
┌───────────────────────────────────────────────────┐
│        双写方案中的数据一致性校验(关键!)            │
├───────────────────────────────────────────────────┤
│                                                    │
│ 时间线：           [全量迁移]→[增量同步]→[校验]   │
│                                                    │
│ ┌──────────────────────────────────────────────┐  │
│ │ 1. 全量迁移完成：旧库数据100%复制到新库       │  │
│ │    旧库: uid=1,2,3,4,5... (活跃,继续变更)    │  │
│ │    新库: uid=1,2,3,4,5... (静态,无变更)      │  │
│ │    差异: 新库缺少全量迁移后的增量             │  │
│ └──────────────────────────────────────────────┘  │
│                     ↓ (Canal增量同步)              │
│ ┌──────────────────────────────────────────────┐  │
│ │ 2. 增量同步进行中：旧库的新增/修改同步到新库  │  │
│ │    旧库: uid=1,2,3,4,5,6,7,8... (继续变更)   │  │
│ │    新库: uid=1,2,3,4,5,6,7...   (追平)       │  │
│ │    但同步有延迟: 毫秒→秒级                    │  │
│ └──────────────────────────────────────────────┘  │
│                     ↓ (数据校验)                   │
│ ┌──────────────────────────────────────────────┐  │
│ │ 3. 数据校验：旧库和新库数据一致性检查         │  │
│ │    ✓ 行数相同: SELECT COUNT(*) FROM both     │  │
│ │    ✓ 内容相同: SELECT checksum(*)            │  │
│ │    ✓ 无孤儿数据: 检查无主键冲突              │  │
│ │                                               │  │
│ │    可能发现的问题：                           │  │
│ │    ❌ 新库缺少某些行(Canal同步延迟)          │  │
│ │    ❌ 数据内容不同(字段值更新不同步)        │  │
│ │    ❌ 孤儿数据(新库有但旧库无)               │  │
│ └──────────────────────────────────────────────┘  │
│                                                    │
│ 校验策略(多重防线)：                               │
│ ├─ 行数校验: COUNT比对 (快速，粗粒度)             │
│ ├─ Checksum校验: 按条件分片校验 (中等，精细度)   │
│ └─ 采样对比: 随机采样N行深度对比 (慢，高精度)    │
│                                                    │
└───────────────────────────────────────────────────┘
```

**校验实现**
```sql
-- 方案1: 行数校验(快速)
SELECT COUNT(*) FROM old_db.t_trade;      -- 结果: 1000000
SELECT COUNT(*) FROM new_db.t_trade;      -- 结果: 1000000
-- ✓ 数量相同

-- 方案2: Checksum校验(精细,按主键段)
-- 按uid范围分段校验，避免全表扫描
SELECT CHECKSUM TABLE old_db.t_trade;     -- 结果: CRC值1
SELECT CHECKSUM TABLE new_db.t_trade;     -- 结果: CRC值2
-- 不同 → 需要深入排查

-- 方案3: 采样对比(高精度)
SELECT uid, name, amount FROM old_db.t_trade 
  WHERE uid IN (SELECT FLOOR(RAND()*1000000) FROM ...) LIMIT 100;
SELECT uid, name, amount FROM new_db.t_trade 
  WHERE uid IN (...) LIMIT 100;
-- 逐行对比字段

-- 方案4: 差异查询(关键!)
-- 查找在旧库但不在新库的数据
SELECT old.uid FROM old_db.t_trade old 
  LEFT JOIN new_db.t_trade new ON old.uid = new.uid 
  WHERE new.uid IS NULL;  -- ← 孤儿数据(应为0行)

-- 反向：查找在新库但不在旧库的数据(应为0行)
SELECT new.uid FROM new_db.t_trade new 
  LEFT JOIN old_db.t_trade old ON new.uid = old.uid 
  WHERE old.uid IS NULL;
```

**一致性校验的时间成本**
| 方案 | 数据量1M | 数据量10M | 数据量100M |
|------|---------|----------|-----------|
| 行数校验 | 1秒 | 3秒 | 10秒 |
| Checksum | 5秒 | 20秒 | 100秒+ |
| 采样对比(100行) | 10秒 | 15秒 | 20秒 |
| 全量对比 | 1分钟 | 10分钟 | 100分钟 |

## 原文勘误

### 错误1：autoincrement字段配置说明(第547行)

**原文**
```
auto-increment-offset=1 主键自增基数, 从1开始。
auto-increment-increment=2 主键自增偏移量，每次为2。
```

**勘误**
```
正确理解：
├─ auto-increment-offset: 自增的起始值
│  ├─ offset=1 表示从1开始: 1, 3, 5, 7, ...
│  └─ offset=2 表示从2开始: 2, 4, 6, 8, ...
│
├─ auto-increment-increment: 自增的步长(增量)
│  ├─ increment=2 表示每次+2
│  └─ increment=1 表示每次+1(普通自增)
│
├─ 双主配置(避免冲突)：
│  ├─ 主库A: offset=1, increment=2 → 产生1,3,5,7,9...
│  └─ 主库B: offset=2, increment=2 → 产生2,4,6,8,10...
│
└─ 这样两个主库的自增值永不重复(奇偶分离)！
```

### 错误2：日志方案中的"无限逼近"说法(第207行)

**原文**
```
"新库与旧库的数据追平也会是一个无限逼近的过程"
```

**勘误**
```
更准确的表述：
├─ 问题: 日志增量同步过程中，旧库继续变更，新库追平难
├─ 原因: 同步有延迟(毫秒级)，追平期间旧库还在写入
├─ 解决方案(3选1):
│  ├─ 方案A: 旧库切为只读(readonly=on)
│  │  └─ 停止新的写入，等待增量同步追上
│  ├─ 方案B: 对比后灰度切流
│  │  └─ 允许毫秒级延迟，逐步切流
│  └─ 方案C: 断点重放
│     └─ 重复重放增量日志直到幂等
│
└─ 并非真的"无限逼近"，而是有充分的容错时间
```

### 错误3：平滑2N方案的数据迁移说法(第282行)

**原文**
```
"由于之前uid%2的数据是分配在2个库里面，扩容之后需要分布到4个库中，
但由于旧数据仍存在(uid%4=0的节点,还有一半uid%4=2的数据)，
所以需要对冗余数据做一次清理。"
```

**勘误**
```
这里的表述容易令人困惑，应该是：

扩容前(uid%2)：
├─ A库: uid%2=0 (即uid=0,2,4,6,8,10,...)
└─ B库: uid%2=1 (即uid=1,3,5,7,9,11,...)

扩容后(uid%4)，A0升级为新主：
├─ A库: uid%4=0 (即uid=0,4,8,12,...) ← 从uid%2=0的数据中筛选
├─ A0库: uid%4=2 (即uid=2,6,10,14,...) ← 从uid%2=0的数据中筛选
├─ B库: uid%4=1 (即uid=1,5,9,13,...) ← 从uid%2=1的数据中筛选
└─ B0库: uid%4=3 (即uid=3,7,11,15,...) ← 从uid%2=1的数据中筛选

清理操作：
├─ A库DELETE: WHERE uid%4=2 (删除应属于A0的数据)
└─ B库DELETE: WHERE uid%4=3 (删除应属于B0的数据)

清理后结果 = 配置变更后的最终状态 (无缝对接!)
```

### 错误4：KeepAlived配置中的state字段(第794行)

**原文**
```
state BACKUP    #lvs的状态模式，MASTER代表主，BACKUP代表备份节点
```

**勘误**
```
更准确的说法：

state字段的值：
├─ MASTER: 该节点优先级更高，故障转移的主角色
├─ BACKUP: 该节点优先级较低，备用角色
│
└─ 注意：双主配置时通常都设为BACKUP + nopreempt
   (防止主库故障恢复后抢夺VIP，导致频繁切换)

示例(更安全的配置)：
[root@linux30 ~]# vi /etc/keepalived/keepalived.conf
vrrp_instance VI_1 {
    state BACKUP           # 两个都是BACKUP
    priority 100           # linux30优先级高
    nopreempt              # 不主动抢占(仅在BACKUP+优先级高时有效)
    ...
}

[root@linux31 ~]# vi /etc/keepalived/keepalived.conf
vrrp_instance VI_1 {
    state BACKUP           # 两个都是BACKUP
    priority 98            # linux31优先级低
    ...
}

效果：
├─ 正常: linux30获得VIP (priority高)
├─ linux30故障: linux31接管VIP (自动)
└─ linux30恢复: VIP不回切linux30 (nopreempt保护)
```

### 错误5：Canal同步的运作机制(第240行)

**原文**
```
"增量同步：开启Canal同步服务，监听从节点数据库，
再开启主从同步，从节点收到数据后会通过Canal服务，
传递至新的DB节点。"
```

**勘误**
```
更准确的流程：

1. 拓扑结构：
   主库(旧库) 
     ↓ (主从同步，binlog)
   从库(旧库)
     ↓ (Canal监听)
   Canal服务
     ↓ (消息队列或direct)
   新库

2. Canal的工作原理：
   ├─ Canal伪装成从库 (向MySQL声称自己是从库)
   ├─ 从旧库从库的binlog中读取DML事件
   ├─ 解析为INSERT/UPDATE/DELETE操作
   ├─ 转发到新库执行相同的DML
   └─ (如果新库是从库，会通过主从继续同步)

3. 不是"从节点收到数据后才转发"，而是：
   ├─ Canal主动读取从库binlog (pull模式)
   ├─ 独立解析和转发 (异步，无阻塞)
   └─ 可配置重试和断点续传

4. 启动顺序(关键!)：
   ① 先启动Canal (监听从库binlog)
   ② 再开启主从同步关系 (START SLAVE)
   ③ Canal自动捕获后续的DML事件
```

## 总结

**平滑扩容的本质**：
- 垂直扩容(升级单机) → 临时方案
- 水平扩容(增加节点) → 最终方案

**各方案的适用场景**：
1. **停机方案**：只用于PoC/测试环境，互联网生产**禁用**
2. **停写方案**：中小型系统(GB级)的快速方案，用户体验中等
3. **日志方案**：大数据量(TB级)，对业务连续性要求极高，实现最复杂
4. **双写方案**：中小型系统(GB-100GB)，实现相对简洁，自动增量
5. **平滑2N方案**(推荐)：大数据量，高可用架构基础上的最优选择，秒级切换

**平滑2N方案的关键优势**：
- 零数据迁移(利用现有主从副本)
- 秒级切换(配置中心动态推送)
- 用户无感知(灰度逐步过渡)
- 成本最低(复用现有基础设施)

**扩容的通用步骤**：
1. 全量迁移 → 2. 增量追平 → 3. 数据校验 → 4. 灰度切流 → 5. 完全切换 → 6. 清理下线

**一致性保障三重防线**：
1. 事前：100%完整性校验(COUNT、Checksum)
2. 事中：实时对账(每小时对比)、告警机制
3. 事后：回滚脚本、修复机制、冗长观察期

**最后记住**：**没有绝对完美的扩容方案，只有"最适合当前业务阶段的方案"**。
