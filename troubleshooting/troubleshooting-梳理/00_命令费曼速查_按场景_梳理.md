# 故障定位命令速查 · 费曼学习法 · 按应用场景

> 费曼学习法核心:用最朴素的话讲清楚"做什么 / 怎么做 / 怎么读懂结果"。
> 重点章节:网络 / 磁盘 I/O。其余资源(CPU / 内存 / 进程 / 日志)作为支撑章节。

---

## 0. 整体地图:碰到问题先看哪一类指标

```
                ┌────────────────────────────┐
                │   现象:慢 / 卡 / 异常       │
                └────────────┬───────────────┘
                             │
   ┌─────────────┬───────────┼───────────┬──────────────┐
   ▼             ▼           ▼           ▼              ▼
 CPU 高        内存高      磁盘 I/O 高   网络异常      负载高 / 不响应
 top           free        iostat       ping/mtr      uptime
 mpstat        vmstat      iotop        ss            top (load)
 pidstat -u    pmap        pidstat -d   tcpdump       ps -eL
 perf/jstack   jmap/MAT    biolatency   netstat       wchan / D 态
```

**口诀**:先看"硬件四件套"(CPU/内存/磁盘/网络) → 再看进程 → 再看线程 → 再看调用栈 → 最后看代码。

# 一、网络场景(重点)

> 网络问题最难,因为链路长。费曼式拆解:每个命令只解决一段链路。

## 1.1 场景:对方"通不通"——连通性

### `ping`:还活着吗?

* **干嘛用**:发 ICMP 包问对端"在吗",对端回"在"。
* **怎么用**:`ping -c 4 baidu.com`
* **怎么读**:
  * `time=12 ms` → 一次往返延迟(RTT)
  * `0% packet loss` → 没丢包
  * `Destination Host Unreachable` → 路由不可达
  * `Request timeout` → 防火墙/对端不回(很多服务器禁 ICMP,通不代表服务也通)

### `traceroute` / `mtr`:卡在哪一跳?

* **干嘛用**:打印从我到目标经过的每一跳路由器。
* **mtr 比 traceroute 更好**:它持续探测,实时给出每跳的丢包率和延迟。
* **怎么用**:`mtr -n -c 100 8.8.8.8`
* **怎么读**:某一跳 `Loss%` 突然变大 → 该跳网络拥塞或路由黑洞。
* **坑**:中间跳丢包但最后一跳不丢,通常没事——是中间路由器对 ICMP 限速,不是真丢。

### `telnet` / `nc`:端口通不通?

* **干嘛用**:ping 只测网络层,这俩测传输层端口(TCP)。
* **怎么用**:
  * `telnet 10.0.0.1 3306`
  * `nc -vz 10.0.0.1 3306`(更现代)
* **怎么读**:`Connected` 即端口开;`Connection refused` 端口未监听;`timeout` 防火墙拦了。

```
应用层  curl / 自家程序  ────────┐
传输层  telnet / nc / ss        │
网络层  ping / traceroute / mtr │  按层往下查
链路层  ethtool / ip link / arp │
       ────────────────────────▼
```

## 1.2 场景:DNS 解析对不对

### `dig` / `nslookup` / `host`

* **干嘛用**:把域名翻译成 IP。
* **怎么用**:
  * `dig +short baidu.com`(只看结果)
  * `dig baidu.com @8.8.8.8`(指定 DNS 服务器)
  * `dig +trace baidu.com`(看完整解析链)
* **怎么读**:`ANSWER SECTION` 里就是 IP;`SERVFAIL` / `NXDOMAIN` 是解析失败。
* **常见错**:`/etc/resolv.conf` 配错,导致 ping 域名慢 5 秒(DNS 超时)再 fallback。

## 1.3 场景:看看自家进程占了多少网络

### `iftop`:实时流量 TopN

* **干嘛用**:像 top,但显示哪个 IP 对在拉流量。
* **怎么用**:`sudo iftop -i eth0 -n`(-n 不解析 DNS)
* **怎么读**:左右箭头代表方向,后三列是 2s/10s/40s 平均带宽。

### `nicstat`:每张网卡的总览

* **干嘛用**:看 RX/TX 字节、包、利用率、错包。
* **怎么用**:`nicstat 1`(每秒刷新)
* **怎么读**:
  * `%Util` 接近 100 → 带宽打满
  * `IErr/OErr` 不为 0 → 出现错包,八成是线缆/双工不匹配

### `sar -n DEV 1`:历史 + 实时

* **干嘛用**:sar 是"网络仪表盘",所有协议层都能看。
* **常用子选项**:
  * `-n DEV`:每张网卡的 pps/bps
  * `-n EDEV`:错误统计
  * `-n TCP,ETCP`:TCP 连接 / 错误(重传率!)
  * `-n SOCK`:socket 总数
* **怎么读**:`retrans/s` 持续 > 0 → 有重传,链路有丢包或拥塞。

### `nethogs`:进程级流量

* **干嘛用**:回答"谁在偷我的带宽"。
* **怎么用**:`sudo nethogs eth0`
* **怎么读**:按进程列出实时 SENT/RECEIVED kB/sec。

## 1.4 场景:连接状态有没有异常

### `ss`(强烈推荐,替代 netstat)

* **干嘛用**:列出 socket,比 netstat 快 N 倍(直接读内核 netlink)。
* **常用咒语**:

| 想看什么 | 命令 |
|---|---|
| 所有 TCP 连接 | `ss -tan` |
| 所有监听端口 | `ss -tlnp` |
| 按状态统计 | `ss -tan state established \| wc -l` |
| 半连接队列 | `ss -ltn`(看 `Send-Q` 即 backlog) |
| 谁连了 3306 | `ss -tan '( dport = :3306 or sport = :3306 )'` |
| 进程对应连接 | `ss -tnp` |

* **关键状态**:
  * `ESTAB` 正常
  * `TIME_WAIT` 大量出现 → 主动关闭多,通常正常,但量级过大要调 `tcp_tw_reuse`
  * `CLOSE_WAIT` 大量出现 → **应用没调用 close()**,代码 Bug,几乎必现连接泄漏
  * `SYN_RECV` 堆积 → 半连接队列满,可能是 SYN flood

### `netstat -s`:协议级计数器

* **干嘛用**:查"丢包/重传/拒绝"的累计计数。
* **必看关键字**:
  * `segments retransmitted` → TCP 重传次数
  * `packets pruned from receive queue` → 接收缓冲不够
  * `times the listen queue ... overflowed` → accept 队列溢出
  * `SYNs to LISTEN sockets dropped` → 半连接溢出

## 1.5 场景:抓包看真相

### `tcpdump`:命令行抓包

* **干嘛用**:把网卡上经过的包逐字节抓下来。
* **基础姿势**:
  ```bash
  # 抓 eth0 上 3306 端口的包,保存到文件
  sudo tcpdump -i eth0 -nn -s0 -w mysql.pcap port 3306
  # -nn  不解析 IP/端口
  # -s0  抓整个包(默认只抓 96 字节)
  # -w   写入文件,后续用 wireshark 打开
  ```
* **过滤表达式速查**:

| 想抓什么 | 表达式 |
|---|---|
| 某主机 | `host 1.2.3.4` |
| 某端口 | `port 80` 或 `portrange 8000-9000` |
| 仅 SYN | `'tcp[tcpflags] & tcp-syn != 0'` |
| 仅 RST | `'tcp[tcpflags] & tcp-rst != 0'` |
| HTTP 请求 | `'tcp port 80 and tcp[((tcp[12:1] & 0xf0) >> 2):4] = 0x47455420'`(GET) |

* **滚动抓包**(偶现问题):`tcpdump -i eth0 -C 100 -W 10 -w trace.pcap`——抓满 100MB 切一个,最多 10 个。

### `wireshark` / `tshark`:可视化分析

* **干嘛用**:把 pcap 文件展开成易读的协议树。
* **关键技巧**:
  * 右键 → `Follow TCP Stream` → 看完整会话
  * 过滤:`tcp.analysis.retransmission`(只看重传)、`tcp.flags.reset == 1`(看 RST)
  * `Statistics → Conversations` → 看哪两个 IP 对话最多
* **判断慢点**:看 `Time delta from previous` 列,延迟在哪一帧暴增。

## 1.6 场景:网卡 / 链路层

### `ip`(替代 ifconfig)

* `ip addr`:看 IP 和网卡状态(UP/DOWN)
* `ip link show`:网卡 MTU、队列长度
* `ip route`:路由表——回包走哪条路
* `ip -s link`:RX/TX 错包统计(`errors`、`dropped`、`overrun`)

### `ethtool`:网卡硬件

* `ethtool eth0`:速率、双工(`Speed: 1000Mb/s`、`Duplex: Full`)
* `ethtool -S eth0`:网卡硬件计数器(rx_dropped、rx_crc_errors)
* `ethtool -g eth0`:Ring Buffer 大小,丢包时考虑调大
* `ethtool -l eth0`:多队列数量
* **判断硬件丢包**:`rx_dropped` 持续上涨 → 内核处理不过来,考虑加大 ring buffer 或开 RPS/RSS。

## 1.7 网络排障决策树(必背)

```
        现象:某接口慢 / 报错
                │
    ┌──────────┴──────────┐
    ▼                     ▼
应用层有报错?           完全连不上?
    │ 是                   │ 是
    ▼                     ▼
curl -v / 看返回码     ping 域名 ─ DNS?─→ dig 检查
    │ 5xx               通│不通
    ▼                     ▼
strace / arthas       ping IP ─ 路由?─→ traceroute/mtr
追到具体调用             通│不通
    │                     ▼
                       telnet IP port ─ 端口/防火墙?
                          通│不通
                          ▼
                       ss / tcpdump
                       看连接状态 / RST 来自谁
                          │
                          ▼
                       看 sar -n TCP / netstat -s
                       是否有大量重传
                          │
                          ▼
                       ethtool / ip -s link
                       是否硬件/驱动层丢包
```

## 1.8 网络命令"按用途索引"速查表

| 我想…… | 用啥 |

| 看 DNS 解析 | `dig +trace` |
| 看哪个进程占带宽 | `nethogs` `iftop` |
| 看每张网卡总流量 | `nicstat` `sar -n DEV` |

# 二、磁盘 I/O 场景(重点)

> 磁盘问题 = 应用觉得"卡住了"。本质就两个问题:**写不进去** / **读不出来**。

## 2.1 场景:磁盘"快满了"

### `df`:看文件系统使用率

* `df -h`:人类可读
* `df -i`:看 **inode** 使用率
* **坑**:`df` 说还有空间,但是写文件提示 `No space left`?
  * 99% 是 **inode 满了**:小文件太多。用 `df -i` 验证。
  * 1% 是文件被进程持有,删了但没释放:用 `lsof | grep deleted` 找。

### `du`:看目录占多大

* `du -sh /var/log/*`:列出每个子目录大小
* `du -h --max-depth=1 /` | sort -h:逐层往下挖
* **优化**:`du` 慢的话用 `ncdu`(交互式)。

## 2.2 场景:I/O 整体压力大吗?

### `iostat -xz 1`(必会)

* `-x`:扩展信息(默认信息几乎没用)
* `-z`:省略零行
* **输出关键列怎么读**:

| 列 | 含义 | 看什么 |
|---|---|---|
| `r/s` `w/s` | 每秒读/写次数(IOPS) | 与磁盘标称 IOPS 比 |
| `rkB/s` `wkB/s` | 每秒读/写字节 | 与磁盘带宽比 |
| `await` | **单次 I/O 平均耗时(ms)** | SSD 应 < 1ms,HDD 应 < 10ms |
| `r_await/w_await` | 读/写各自的耗时 | 看读写哪个慢 |
| `aqu-sz` | 平均队列长度 | 持续 > 1 表示排队 |
| `%util` | 设备繁忙百分比 | **不等于"满载"!** 见下面坑 |

* **`%util` 的坑**:对 SSD 和 RAID,`%util` = 100% 不代表打满——多通道下还能并发。判断 SSD 是否打满看 `aqu-sz` 和 `await`。

### `vmstat 1` 也能看一眼 I/O

* `bi`/`bo`:每秒从块设备读入/写出(KB)
* `wa`:CPU 在等 I/O 的百分比 → wa 高就是 I/O 瓶颈的强信号

### `sar -d 1`:历史磁盘 I/O

* 同 iostat,但能回看历史(`sar -d -f /var/log/sa/saXX`)。

## 2.3 场景:谁在搞 I/O?

### `iotop`(交互式)

* **干嘛用**:像 top,但按 I/O 排序。
* **怎么用**:`sudo iotop -oPa`(-o 只看正在做 I/O 的;-P 按进程;-a 累计值)
* **怎么读**:`DISK READ` / `DISK WRITE` 列就是答案。

### `pidstat -d 1`:按进程的 I/O

* `kB_rd/s` 进程每秒读字节
* `kB_wr/s` 进程每秒写字节
* `iodelay` 该进程被 I/O 阻塞的时间(很有用!)
* 配合 `-p PID` 锁定某个进程。

### 内核级:`biolatency` / `biosnoop`(bcc 工具)

* `biolatency` 把 I/O 延迟绘成直方图:
  ```
  usecs               : count     distribution
   128 -> 255         : 12       |***
   256 -> 511         : 256      |******************
   512 -> 1023        : 1023     |********************************|
  ```
  看分布而不是平均,识别长尾。
* `biosnoop` 逐 I/O 打印:`PID  COMM  DISK  T  SECTOR  BYTES  LAT(ms)`
  问题 I/O 是谁干的、读哪个扇区、耗时多少——一目了然。

## 2.4 场景:具体到哪个文件 / 哪段代码?

### `lsof`:某个文件被谁打开

* `lsof /var/log/app.log` → 列出所有持有此文件的进程
* `lsof -p 1234` → 进程 1234 打开了什么
* `lsof -nP -i :3306` → 监听 3306 的进程
* `lsof | grep deleted` → 已删除但未释放的"幽灵文件"(常见磁盘满原因)

### `/proc/[pid]/io`:进程的累计 I/O

```
rchar  / wchar    应用层 read()/write() 字节数
read_bytes        实际从磁盘读的字节
write_bytes       实际写到磁盘的字节
cancelled_write   被覆盖、最终未落盘的字节
```

* **能解释 Page Cache 的影响**:`rchar` 大但 `read_bytes` 小 → 命中缓存。

### `strace -e trace=read,write,open -p PID`

* 看进程到底在读写哪些 fd。
* **风险**:strace 用 ptrace,会让进程慢 N 倍,生产慎用,优先用 bpftrace 替代。

### bpftrace 抓写大文件的栈

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_write
  /args->count > 1024*1024/ { @[comm, ustack] = count(); }'
```
谁写了 >1MB 的块,把它的用户态栈和次数都打出来。

## 2.5 场景:Page Cache 还是真磁盘?

* `free -h` 看 `buff/cache`:占很多内存不是坏事,这是好朋友。
* `/proc/meminfo`:`Dirty` 多 → 脏页未刷,可能马上来一波写;`Writeback` 多 → 正在刷盘。
* `cachestat`(bcc):实时显示缓存命中率;
  * `HITS` 多 → 命中缓存,快;`MISSES` 多 → 真读磁盘,慢。

## 2.6 磁盘 I/O 排障决策树

```
       应用反馈慢
            │
            ▼
   iostat -xz 1 ── await 高?
        是│否
         ▼ ▼
    %util 高    问题不在磁盘,回到 CPU/网络/锁
    /aqu 大
         │
         ▼
   iotop / pidstat -d ── 哪个进程?
         │
         ▼
   该进程是 Java?
        是 │ 否
         ▼   ▼
   arthas      strace -e read,write
   profiler    或 biosnoop -p PID
   wall clock
         │
         ▼
   定位到方法/代码行 → 改算法/批量/异步
         │
         ▼
   仍解决不了 → 系统层调优:
   • 文件系统(noatime / ext4→xfs)
   • 调度器(none/mq-deadline)
   • Page Cache(vm.dirty_ratio)
   • 硬件(RAID/SSD/NVMe)
```

## 2.7 磁盘 I/O 命令"按用途索引"

| 我想…… | 用啥 |
|---|---|
| 看磁盘满没满 | `df -h` `df -i` |
| 看目录占多大 | `du -sh` `ncdu` |
| 看整机 I/O 压力 | `iostat -xz 1` `vmstat 1`(看 wa) |
| 看 I/O 延迟分布 | `biolatency`(bcc) |
| 看是哪个进程 I/O 高 | `iotop -oPa` `pidstat -d 1` |
| 看每次 I/O 细节 | `biosnoop`(bcc) |
| 看进程累计 I/O | `cat /proc/[pid]/io` |
| 看文件被谁占 | `lsof <file>` |
| 看进程打开了啥 | `lsof -p PID` `ls /proc/PID/fd` |
| 看进程的 read/write 调用 | `strace -e read,write -p PID` |
| 找已删除未释放文件 | `lsof \| grep deleted` |
| 看 Page Cache 命中 | `cachestat`(bcc) `free -h` |
| 看脏页/刷盘 | `cat /proc/meminfo \| grep -E 'Dirty\|Writeback'` |

# 三、CPU 场景(辅助)

## 3.1 整体观感

* `top` / `htop`:一屏看全
  * `us` 用户态高 → 你的代码在算
  * `sy` 内核态高 → 系统调用 / 中断 / 内核线程
  * `wa` 高 → I/O 瓶颈,跳到磁盘章
  * `si`/`hi` 高 → 软/硬中断,看 `/proc/interrupts`、`mpstat -P ALL`
  * `id` 100% 还说慢 → CPU 没在干活,问题在锁/网络/磁盘
* `mpstat -P ALL 1`:每个核分别看,避免被平均值骗
* `vmstat 1`:`r` 列(运行队列)持续 > CPU 核数就是真忙

## 3.2 进程级

* `pidstat -u 1`:看每个进程的用户/内核态 CPU%。
* `top -H -p PID` 或 `ps -eLo pid,tid,pcpu,comm`:看进程内**线程**的 CPU。
  * 拿到高 CPU 的 TID 后:`printf "%x\n" TID` 转十六进制,去 jstack 输出里 grep `nid=0x...` 定位 Java 线程。

## 3.3 调用栈层

* **Java**:`jstack PID > t.txt`,或 Arthas `thread -n 3`(直接给你 Top 3 CPU 线程的栈)
* **任何语言**:`perf top -p PID`(实时函数热点)、`perf record -F 99 -g -p PID -- sleep 30 && perf script | stackcollapse-perf.pl | flamegraph.pl > cpu.svg`(火焰图)
* **OffCPU**(线程没在跑,在等什么?):`offcputime`(bcc)或 Arthas `profiler start --event wall`。

## 3.4 用一句话区分场景

| 现象 | 解读 |
|---|---|
| us 高 | 业务代码热点 → 火焰图找 |
| sy 高 | 系统调用太多 → `strace -c` 看哪个 syscall 多 |
| wa 高 | I/O 慢 → 跳到磁盘章 |
| si 高 | 软中断(常见:网络包) → `mpstat -P ALL`、`cat /proc/softirqs` |
| id 高但响应慢 | 线程在睡 → OffCPU 火焰图 / jstack 看锁 |

# 四、内存场景(辅助)

## 4.1 整机内存

* `free -h`:**只看 `available` 列**,别被 `used` 吓到(Page Cache 算 used 但能释放)。
* `vmstat 1`:`si`/`so` 持续 > 0 → 在用 swap,性能必崩。
* `/proc/meminfo`:大表,关键字 `MemAvailable` `Buffers` `Cached` `Dirty` `Slab` `KReclaimable`。
* `slabtop`:看内核 slab(dentry/inode 暴涨常见)。

## 4.2 进程内存

* `ps aux --sort=-rss | head`:按 RSS 排个序。
* `pmap -X PID`:细看进程虚拟内存布局(每段大小、权限、对应文件)。
* `/proc/PID/status`:`VmRSS`(物理)、`VmSize`(虚拟)、`VmSwap`(被换出)。
* `/proc/PID/smaps_rollup`:RSS、PSS、USS 一行总结。

## 4.3 Java 堆/堆外

* 堆内:`jmap -dump:format=b,file=heap.hprof PID` → MAT 分析。
* 元空间:`jstat -gc PID 1000` 看 `MC/MU`。
* 堆外:
  * 开 NMT:启动加 `-XX:NativeMemoryTracking=detail`,再 `jcmd PID VM.native_memory summary`。
  * 还不够:用 `pmap` 看大段 anon 内存;再用 jemalloc + `jeprof` 看 native 分配栈。
* OOM-Killer:`dmesg | grep -i 'killed process'`,查看是谁被干掉。

# 六、日志查看(费曼版)

## 6.1 一句话搞定

> 给我一个大文件,我要找出 N 条记录、统计某种模式的频次。

经典管道:`cat / zcat → grep → awk → sort → uniq -c → sort -n`

```bash
# Top 10 访问 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# 5xx 的接口分布
grep ' 5[0-9][0-9] ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn

# 看最近 1000 行并停留
less -N +G app.log     # G 跳尾;N 行号

# 大压缩日志
zgrep ERROR app.log.2024-*.gz | less
```

## 6.2 各命令一句话

* `tail -f`:跟新内容(`-F` 文件被 rotate 也能跟)
* `less`:大文件首选(`/pattern`、`n` 下一条、`G` 末尾、`g` 头)
* `grep -E '正则'`:扩展正则;`-c` 计数;`-v` 反选;`-A/-B/-C N` 上下文行
* `awk '{print $1}'`:按列切片;`awk -F: '{...}'` 自定分隔符;BEGIN/END 块做汇总
* `sort -k2 -n`:按第二列数值排;`-u` 等价 `sort | uniq`
* `uniq -c`:相邻去重并计数(**前面必须先 sort**!)
* `wc -l`:数行

# 七、内核级"黑盒"工具(辅助)

| 工具 | 用途 | 一句话 |
|---|---|---|
| `ftrace` / `trace-cmd` | 追踪内核函数 | 想看内核某函数被谁/何时调用 |
| `perf` | 采样 / 计数 / 事件 | 最通用,火焰图必备 |
| `bcc 工具集` | 现成的 100+ 个 eBPF 工具 | execsnoop/opensnoop/biolatency/cachestat/tcpconnect/tcpretrans |
| `bpftrace` | 写一行脚本搞自定义追踪 | `tracepoint:syscalls:sys_enter_open { printf("%s %s\n", comm, str(args->filename)); }` |
| `strace -p` | 用户进程系统调用 | 简单粗暴但开销大 |
| `gdb` | 附加调试原生进程 | 看变量、看栈、设断点 |

> 实战口诀:**生产首选 bpftrace / bcc**(eBPF 低开销),strace/gdb 只在小流量或非生产用。

# 九、按"问题症状"反向查表(收尾)

| 症状 | 第一把铲子 | 第二把铲子 | 收口 |
|---|---|---|---|
| 接口 P99 突高 | 链路追踪 / Arthas trace | wall-clock 火焰图 | 改代码或调线程池 |

| 磁盘慢 | `iostat -xz` `vmstat 1` | `iotop` `pidstat -d` `biolatency` | 应用批量写/异步刷盘 |
| 丢包/慢 | `ping` `mtr` | `ss -s` `sar -n TCP` `tcpdump` | 调队列 / 改协议 |
| 连接数爆 | `ss -tan \| awk '{print $1}' \| sort \| uniq -c` | 看 CLOSE_WAIT/TIME_WAIT | 修资源关闭 / 调内核参数 |
| 负载高但 CPU 不忙 | `vmstat` 看 `b`(D 态) | `for f in /proc/*/stack; ...` | 找 D 态卡的栈 |
| 偶现 | bpftrace 条件触发 dump | 日志埋点 + 滚动 tcpdump | 复盘 → 加监控 |
