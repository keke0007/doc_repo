# 第16章 整体耗时高分析 - 知识点梳理

## 📚 核心概念

### 耗时问题的本质
- 将**时间视为资源**，应用分析框架与资源占用分析一致
- 采用**自上而下的负载视角**：最终问题反映在用户侧（UI/接口响应）
- **三层递进分析**：接口 → 子方法 → 调用栈

---

## 一、响应慢定位框架

### 分析的三个逐层深入问题

| 层级 | 问题 | 工具/数据源 | 输出 |
|------|------|-----------|------|
| **第1层：接口** | 哪个接口耗时高？ | 接口监控 / 访问日志 / arthas watch | 耗时接口名单 |
| **第2层：方法** | 接口下哪个子方法耗时高？ | arthas trace | 耗时方法链路 |
| **第3层：调用栈** | 整体哪个调用栈耗时高？ | offcpu分析 | 具体耗时点 |

---

## 二、链路追踪与定位技术

### 2.1 接口耗时定位（第1层）

#### 方案对比

| 方案 | 前置条件 | 优点 | 缺点 |
|------|--------|------|------|
| **接口监控系统** | 已部署 | 实时、聚合数据 | 需基础设施 |
| **访问日志分析** | 有日志 | 不需额外工具 | 需手动解析（Linux命令） |
| **Arthas watch** | 运行中进程 | 无依赖 | 单点数据、需手工操作 |

**Linux命令示例**（从访问日志中找耗时接口）：
```bash
# 示例：解析日志计算平均耗时
cat access.log | awk '{print $7,$8}' | sort | uniq -c
```

---

### 2.2 子方法耗时定位（第2层）

#### Arthas Trace 命令

**特点**：
- 追踪单次调用的完整方法链路
- 显示每个方法的耗时占比
- 输出明细的调用树结构

**使用流程**：
```
第1步：trace 耗时接口 → 找出最慢子方法
   示例：找到 UserService.getUserByIdCost 耗时最高

第2步：再次 trace 该子方法 → 继续深入下一层
   
第3步：（可选）用 listenerId 在已有trace基础上追加子方法跟踪
```

**效率问题**：
- 若耗时代码处于**很深的调用栈**中 → 逐层深入效率低
- **解决方案**：改用 offcpu 方法快速定位

---

### 2.3 调用栈耗时定位（第3层）

#### OnCPU vs OffCPU 分析

**线程状态转换模型**：

```
┌─────────────────────────────────────────────────────┐
│                    线程执行生命周期                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  ┌──────────────┐     阻塞     ┌──────────────┐   │
│  │   运行态      │────────────→│   睡眠态      │   │
│  │  (OnCPU)     │    解锁/IO   │  (OffCPU)    │   │
│  │ 在CPU上执行  │←────────────│ 等待资源      │   │
│  └──────────────┘     唤醒     └──────────────┘   │
│                                                     │
│  • OnCPU：线程在CPU上主动执行                        │
│  • OffCPU：线程因锁/IO阻塞，被迫离开CPU            │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**应用场景**：
- **接口耗时高** → **选择OffCPU分析** ✓
  - 原因：接口耗时通常由IO/锁等待引起，而非CPU占用
  
- **CPU占用高** → 选择OnCPU分析
  - 原因：需追踪CPU执行时间

## 三、OffCPU 火焰图分析工具矩阵

### 3.1 工具方案对比

| 工具 | 采集原理 | 依赖 | 开销 | 适用场景 | 数据含义 |
|------|--------|------|------|---------|---------|
| **bcc/offcputime** | 追踪Linux上下文切换（finish_task_switch） | Linux内核BPF | 中等 | 高权限环境 | 栈宽=线程睡眠时长 |
| **Arthas profiler (wall模式)** | 定期采集所有线程栈快照 | Arthas | 低 | 无权限限制 | 栈宽=累积采集次数 |
| **jstack** | 多次运行jstack获取栈快照 | JDK jstack | 高 | 普通环境 | 栈宽=采集次数 |
| **/proc/$pid/task/$tid/stack** | 读取伪文件获取内核栈 | 无 | 低 | 应急方案 | 内核层栈信息 |

---

### 3.2 BCC OffCPUTime 分析

**原理**：
```
Linux内核 finish_task_switch函数 
    ↓ (BPF 追踪)
采集上下文切换时的调用栈
    ↓
统计每个栈的睡眠时长
    ↓
生成OffCPU火焰图
```

**火焰图解读**：
- **栈宽度 = 线程睡眠总时间**
- 越宽的栈 = 该调用路径上线程等待（睡眠）时间越长

**限制**：需要 root/BPF 权限

---

### 3.3 Arthas Profiler Wall 采集模式

**原理**：
```
定时采样（如 100ms间隔）
    ↓
采集所有Java线程调用栈快照
    ↓
多次采样形成栈数据
    ↓
生成Wall-Clock火焰图
```

**火焰图解读**：
- **栈宽度 = 该栈被采集的次数**
- 越多被采样 = 代码执行时间越长
- **名称含义**：wall-clock（墙上挂钟）= 实际经历的时间

**数据处理要点**：
- Wall模式会采集线程池中**所有等待任务的线程**
- ⚠️ 需过滤出与**请求处理相关的线程栈**
- 否则大量空闲线程会干扰分析

---

### 3.4 Jstack 多次采样分析

**原理**：
```
循环执行jstack命令（N次，间隔M秒）
    ↓
收集多次线程栈快照
    ↓
用StackCollapse/FlameGraph处理
    ↓
生成OffCPU火焰图效果
```

**优势**：
- 无需特殊权限
- 无BPF依赖

**劣势**：
- ⚠️ jstack执行触发**SafePoint**，对高流量系统有性能开销
- **建议**：高流量系统谨慎使用，优先用profiler wall模式

---

### 3.5 /proc 伪文件栈采样分析

**数据位置**：
```
/proc/$pid/task/$tid/stack
```

**含义**：
- 记录线程 `$tid` 阻塞时的**内核调用栈**

**使用流程**：
```bash
# 示例：采集多次栈快照
for i in {1..100}; do
  cat /proc/$pid/task/*/stack >> stacks.txt
  sleep 0.1
done
# 后续用FlameGraph生成火焰图
```

**特点**：
- 无依赖、最基础的方案
- 当其他工具都不可用时的后备方案
- 需手工处理和脚本化

## 六、核心技术深度解析

### 6.1 OnCPU vs OffCPU 选择准则

**接口耗时高的典型特征**：

| 现象 | OnCPU占比 | OffCPU占比 | 推荐分析 | 原因 |
|------|----------|----------|--------|------|
| 接口响应慢 | 低（10-20%） | 高（80-90%） | OffCPU | 大量IO/锁等待 |
| CPU占用高 | 高（>80%） | 低 | OnCPU | 计算密集 |
| 数据库查询慢 | 低 | 高 | OffCPU | 网络+IO等待 |
| 锁竞争严重 | 低 | 高 | OffCPU | 线程等待解锁 |

---

### 6.2 Wall采集模式的线程过滤

**问题**：
```
Wall模式采集所有线程栈 
    ↓
线程池中大量线程处于空闲等待状态
    ↓
采集数据被空闲线程"污染"
    ↓
火焰图难以看清实际耗时
```

**过滤策略**：
```bash
# 伪代码：过滤与请求处理相关的线程
for each thread in collected_stacks:
    if thread_state == "RUNNABLE" or thread_contains("handler/processor"):
        include_in_analysis(thread)
    else if thread_in_pool and waiting():
        exclude(thread)  # 排除空闲线程
```

**工具支持**：
- Arthas profiler wall 本身可指定线程过滤条件
- FlameGraph也支持栈过滤脚本

---

### 6.3 SafePoint 开销认知

**Jstack的性能成本**：
- 每次jstack调用会触发JVM的SafePoint
- SafePoint = 暂停所有应用线程以采集一致的栈快照
- 在高流量（高吞吐）系统中累加开销明显

**高流量系统建议**：
1. **优先选择**：arthas profiler wall
2. **其次选择**：bcc offcputime (若有权限)
3. **避免**：jstack频繁调用

## ⚠️ 原文勘误

### 勘误1：第3376行 `/proc/$pid/tack/$tid/stack`

**原文内容**：
```
其实只要能获取到线程栈，就能做wall模式的offcpu分析，比如使用jstack或/proc/$pid/tack/$tid/stack伪文件。
```

**勘误**：
- **错误处**：`/proc/$pid/tack/$tid/stack`
- **应改为**：`/proc/$pid/task/$tid/stack`
- **错误类型**：笔误（tack → task）
- **影响**：实际使用命令时会报错

**正确命令**：
```bash
cat /proc/$pid/task/$tid/stack
```

---

### 勘误2：OnCPU/OffCPU概念理解（第3309行）

**原文内容**：
```
线程在运行的过程中，
- 要么在CPU上执行，称其为oncpu，
- 要么被锁或io操作阻塞，从而离开CPU进去睡眠状态，称其为offcpu
```

**澄清点**（非严格错误，但可能引起混淆）：
- OffCPU 并非线程进入"睡眠"状态，而是进入**可运行队列的等待态**或真正的睡眠态
- 线程状态更准确的描述：
  - **OnCPU**：RUNNABLE (正在运行)
  - **OffCPU**：WAITING / BLOCKED / 被调度器暂停

**建议补充**：
线程的完整生命周期包括：
- RUNNABLE (运行中) - 消耗CPU时间
- WAITING (等待锁/IO) - 消耗OffCPU时间
- BLOCKED (被锁阻塞) - 属于OffCPU

---

### 勘误3：Offcputime 上下文切换追踪（第3324行）

**原文内容**：
```
offcputime通过追踪Linux上下文切换函数finish_task_switch，以实现对线程睡眠时间的测量
```

**澄清/补充**：
- finish_task_switch 是切换完成后的回调
- 更严谨说法：追踪**上下文切换事件**及其前后的时间戳
- 结合**schedule函数**追踪线程离开CPU的时刻

**建议调整**：
"offcputime通过在内核中追踪线程调度事件（schedule/finish_task_switch），统计线程离开CPU到被重新调度运行之间的时间，即线程睡眠时间"

## 八、关键术语速查

| 术语 | 含义 | 应用 |
|------|------|------|
| **OnCPU** | 线程在CPU上执行 | 分析CPU密集型瓶颈 |
| **OffCPU** | 线程因资源等待离开CPU | 分析IO/锁/网络等待 |
| **Wall Clock** | 墙上挂钟，真实经历的时间 | Profiler采样模式名 |
| **SafePoint** | JVM所有线程暂停同步点 | jstack执行时的性能开销来源 |
| **BPF** | Berkeley Packet Filter，Linux内核可编程 | bcc工具运行基础 |
| **火焰图栈宽** | 栈条形宽度 | 代表累积耗时或采集次数 |
| **Stack采样** | 多次采集线程调用栈 | 通过频率推测耗时 |
| **上下文切换** | CPU从一个线程切换到另一个线程 | offcputime追踪的核心事件 |

## 九、总结

### 核心框架
```
耗时高问题 = 时间资源分配问题
分析思路 = 自上而下的负载分解
  L1: 接口层    (监控/日志/watch)
  L2: 方法层    (arthas trace)
  L3: 调用栈层  (offcpu火焰图)
```

### 三大关键决策
1. **接口定位**：优先用监控系统 > 日志 > watch
2. **方法定位**：调用栈浅 → trace；调用栈深 → offcpu
3. **工具选择**：有权限 → bcc；无权限高流量 → profiler；其他 → jstack/伪文件

### 核心工具排序
```
推荐度：bcc offcputime > Arthas profiler wall > jstack > /proc伪文件
便利性：接口监控 > Arthas trace > offcpu火焰图
权限要求：bcc(高) > jstack(中) > profiler wall(低) > 伪文件(低)
```
