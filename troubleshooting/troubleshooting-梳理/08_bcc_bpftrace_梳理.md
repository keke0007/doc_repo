# 08. 内核级诊断工具-bcc、bpftrace 梳理

## 第一部分：知识点详解

### 1. eBPF 介绍与演进

#### 1.1 eBPF 的定义与作用
- **BPF 早期用途**：为高效捕获网络包而开发
- **eBPF 后期扩展**：演变为通用的执行引擎
- **内核虚拟机**：类似于在内核中运行的虚拟机
- **执行流程**：执行 eBPF 字节码 → 处理 tracepoint、kprobe 等事件 → 将数据存储在 eBPF maps 中 → 输出观测数据

#### 1.2 eBPF 的可编程观测能力
- 支持多种事件源（tracepoint、kprobe、uprobe 等）
- 提供 maps 数据结构进行内核态与用户态数据交互
- 实现强大的可编程性和灵活性

---

### 2. eBPF 生态工具

#### 2.1 主要工具概览
基于 Linux 的 eBPF 机制，Linux 社区演化出多种观测工具：

| 工具 | 特点 | 用途 |
|------|------|------|
| **bcc** | 场景化诊断工具集 | 开箱即用，针对常见问题 |
| **bpftrace** | awk 风格脚本语言 | 快速编写自定义诊断工具 |

#### 2.2 bcc 与 bpftrace 的区别
- **bcc**：
  - 主要偏向于提供场景化的诊断工具
  - 示例：`runqslower` 追踪线程调度延迟，`memleak` 追踪内存泄露
  - 开箱即用，用户无需编写代码

- **bpftrace**：
  - 提供类似 awk 的脚本语言
  - 用于快速编写新的诊断工具
  - 降低 eBPF 学习门槛

---

### 3. bcc 工具集详解

#### 3.1 工具分类维度
bcc 工具集提供了大量开箱即用的诊断工具，主要覆盖以下层面：

| 层面 | 工具类型 |
|------|---------|
| **应用程序层** | 语言虚拟机诊断工具 |
| **CPU 层** | CPU 利用率、调度分析工具 |
| **内存层** | 内存泄露、分配追踪工具 |
| **磁盘层** | I/O 延迟、IOPS 分析工具 |
| **网络层** | 网络延迟、丢包分析工具 |

#### 3.2 常见应用场景关键词映射
- **请求追踪**：request、latency 相关工具
- **Java 服务器**：JVM 堆、GC 相关工具
- **网络问题**：TCP、UDP、延迟工具
- **MySQL 服务器**：查询延迟、连接追踪工具
- **磁盘问题**：I/O 延迟、热点文件工具
- **线程调度**：runq 延迟、调度延迟工具

### 4. oncpu vs offcpu 分析

#### 4.1 线程状态定义

```
线程执行周期：
┌─────────────────────┐
│  运行中（oncpu）     │
│  在 CPU 上执行       │
└──────────┬──────────┘
           │ 遇到锁或 I/O 阻塞
           ↓
┌─────────────────────┐
│  睡眠中（offcpu）    │
│  被阻塞离开 CPU      │
└──────────┬──────────┘
           │ 解锁或 I/O 完成
           ↓
      线程被唤醒
```

#### 4.2 两种分析方法

**oncpu 分析**：
- 发现 CPU 占用高的代码
- 工具：`profile`
- 应用场景：排查高 CPU 消耗问题

**offcpu 分析**：
- 发现耗时的阻塞代码
- 工具：`offcputime`
- 应用场景：排查高延迟、锁等待、I/O 等待问题

---

### 5. oncpu 火焰图（使用 bcc profile）

#### 5.1 工作原理
- 从 CPU 栈寄存器出发
- 定时采样线程栈（采样频率可配置）
- 相同栈在火焰图中合并

#### 5.2 火焰图解读
- **横轴**：栈帧宽度代表 CPU 占用时间
- **纵轴**：调用栈深度
- **越宽的线程栈** = **CPU 耗费越多**

#### 5.3 典型应用
用于诊断 CPU 密集型程序的性能瓶颈

---

### 6. offcpu 火焰图（使用 bcc offcputime）

#### 6.1 工作原理
- 追踪 Linux 上下文切换函数 `finish_task_switch`
- 实现对线程睡眠时间的精确测量
- 记录线程从睡眠到被唤醒的时间

#### 6.2 火焰图解读
- **横轴**：栈帧宽度代表线程睡眠时间
- **越宽的线程栈** = **睡眠时间越长**
- 表示代码在等待锁、I/O 等资源

#### 6.3 典型应用
用于诊断锁竞争、I/O 等待等导致的延迟问题

---

### 7. BPF CO-RE（编译一次，随处运行）

#### 7.1 bcc 脚本版的问题

**架构**：
```
bcc 脚本（Python/Lua）
    ↓
内嵌 C/C++ eBPF 代码
    ↓
运行时通过 LLVM 动态编译
    ↓
执行
```

**存在的问题**：
1. **启动开销大**：占用 CPU、内存资源
2. **依赖复杂**：需要依赖内核头文件包的安装
3. **不利于生产部署**：性能和可移植性差

#### 7.2 BPF CO-RE 的改进

**架构**：
```
BPF 源代码
    ↓
编译时处理（CO-RE 技术）
    ↓
生成小型二进制执行程序
    ↓
直接执行
```

**优势**：
- 性能更高（无运行时编译开销）
- 消除不必要的依赖
- 启动速度快
- 适合生产环境部署

#### 7.3 选择建议
**有条件的话，尽量选择 CO-RE 版本的 bcc 工具**，性能优于原始脚本版本

---

### 8. bpftrace 工具集与脚本语言

#### 8.1 bpftrace 的设计理念
- 对 eBPF 技术进行高层次封装
- 实现类似 awk 的脚本语言
- 降低使用门槛

#### 8.2 核心特性

| 特性 | 说明 |
|------|------|
| **常见语句块** | BEGIN、END、probe 块等 |
| **内置变量** | `$pid`、`$tid`、`arg0` 等 |
| **内置函数** | `sum()`、`hist()`、`printf()` 等 |
| **map 支持** | 用于数据聚合和关联存储 |

#### 8.3 使用优势
- 不需要学习复杂的 BPF 开发技术
- 快速编写自定义诊断工具
- 类似 awk，易于学习

### 9. bpftrace 实例 1：追踪 Java 应用的 SQL 耗时（从客户端视角）

#### 9.1 背景
- Java 的 MySQL 驱动使用 `sendto` 和 `recvfrom` 系统调用与 MySQL 服务器通信
- 在 `sendto` 调用时记录时间点
- 在 `recvfrom` 返回时计算时间差
- 得到相应 SQL 的耗时（包含网络往返时间）

#### 9.2 脚本关键点

```
脚本名称：trace_slowsql_from_syscall.bt

关键变量说明：
- comm：进程名称
- tid：线程号（线程 ID）
- @query[tid]：以 tid 为 key 的 map，类似线程本地变量
- @start[tid]：记录 sendto 的时间戳
```

#### 9.3 脚本逻辑流程
```
sendto 系统调用
    ↓
记录 @start[tid] = 当前时间
    ↓ (网络往返)
recvfrom 系统调用返回
    ↓
计算 耗时 = 当前时间 - @start[tid]
    ↓
打印 SQL 执行耗时
```

#### 9.4 输出示例
可以看到各 SQL 执行耗时（包含网络往返时间）

### 10. bpftrace 实例 2：追踪 MySQL 服务端 SQL 耗时（从服务端视角）

#### 10.1 问题描述
- 从调用端追踪 SQL 耗时包含网络往返时间
- 为获得更精确的 SQL 执行耗时，需要在服务端追踪

#### 10.2 追踪方法

**第一步**：定位 mysqld 进程的入口函数
- 找到 mysqld 可执行文件路径
- 确定 SQL 处理入口函数：`dispatch_command`

**第二步**：编写 uprobe 追踪脚本
- 追踪点改为 `uprobe`（用户态探针）
- 在 `dispatch_command` 入口和出口时间戳

**第三步**：计算纯 SQL 执行耗时
```
dispatch_command 函数入口
    ↓
记录时间戳 @start[tid]
    ↓
SQL 实际执行
    ↓
dispatch_command 函数返回
    ↓
计算耗时（不含网络往返）
```

#### 10.3 脚本类型对比
| 维度 | 系统调用版本 | 服务端版本 |
|------|------------|---------|
| **探针类型** | kprobe（内核函数） | uprobe（用户函数） |
| **测量范围** | 含网络往返 | 纯 SQL 执行时间 |
| **精确度** | 较低 | 较高 |

### 11. bpftrace 实例 3：追踪 MySQL SQL 扫描行数

#### 11.1 问题背景
- SQL 性能与扫描数据量密切相关
- 扫描行数多 → SQL 性能差（易入慢查询日志）
- 扫描行数适中（如 2w 条）且都在缓存中 → SQL 执行时间短 → 不被记录
- 但这类 SQL 并发量大时，会非常耗费 CPU（隐藏的性能陷阱）

#### 11.2 追踪方法

**关键函数**：`row_search_mvcc`
- MySQL 扫描数据行的函数
- 每扫一行调用一次

**追踪逻辑**：
```
SQL 执行开始
    ↓
每次 row_search_mvcc 调用，计数 +1
    ↓
SQL 执行结束
    ↓
输出扫描行数与执行时间
```

#### 11.3 脚本输出解读
- 扫描行数变大 → 耗时变长
- 扫描行数相同 → 耗时基本相同

#### 11.4 实验说明
```
测试条件：
- id 列：主键
- seq 列：没有索引（扫描基准）

结论：扫描行数是影响 SQL 耗时的关键因素
```

## 第三部分：⚠️ 原文勘误

### 勘误 1：offcputime 追踪函数名称

**原文位置**：第 1472 行
**原文内容**："offcputime 通过追踪 Linux 上下文切换函数 finish_task_switch"
**勘误说明**：
- 实际追踪的是 **`finish_task_switch`** 函数返回点（返回探针）
- 还需要追踪 **`schedule`** 或 **`__schedule`** 函数进入点（进入探针）
- 完整追踪逻辑：记录离开 CPU 时间点 → 记录返回 CPU 时间点 → 计算差值
- 原文表述过于简化，容易造成理解偏差

**更正后表述**：
"offcputime 通过追踪 Linux 上下文切换过程（进入 `__schedule` 和返回 `finish_task_switch`），以实现对线程睡眠时间的测量"

---

### 勘误 2：row_search_mvcc 函数的触发频率描述

**原文位置**：第 1537 行
**原文内容**："每扫一行调用一次"
**勘误说明**：
- 实际行为：`row_search_mvcc` 是扫描一行的原子操作，但可能有以下情况：
  1. 某些优化场景下，MySQL 可能跳过某些行（如行锁、隐藏行）
  2. 扫描可能涉及多个存储引擎调用
  3. 二级索引扫描会先扫索引再回表查询
- 因此"每扫一行调用一次"不够精确

**更正后表述**：
"row_search_mvcc 是每次从 InnoDB 表获取一行数据时被调用，追踪此函数的调用次数可近似表示扫描行数（在无行级过滤的情况下）"

---

### 勘误 3：bcc 与 bpftrace 功能定位有重叠

**原文位置**：第 1417-1419 行
**原文内容**：
- "bcc：主要偏向于提供场景化的诊断工具"
- "bpftrace：提供类似 awk 的脚本语言"

**勘误说明**：
- 实际上 bpftrace 也演化出了场景化命令集（第 1551-1555 行提到）
- 两者的区别更准确的是：
  - **bcc**：预编译的完整工具集，开箱即用，但扩展性较差
  - **bpftrace**：动态脚本语言，灵活可定制，但需要学习语言

**更正后表述**：
- "bcc：提供预编译的场景化诊断工具集，开箱即用"
- "bpftrace：提供灵活的脚本语言和相应命令集，易于定制但需学习"

---

### 勘误 4：BPF CO-RE 的"消除依赖"描述不够全面

**原文位置**：第 1481 行
**原文内容**："以提升性能并去掉不必要的依赖"

**勘误说明**：
- BPF CO-RE 消除的是**编译时依赖**（LLVM、内核头文件）
- 但仍需运行时依赖：
  - `libbpf`：BPF 加载和管理库
  - 内核 eBPF 子系统
  - 适配不同内核版本的能力（这正是 CO-RE 的核心）

**更正后表述**：
"消除编译时的 LLVM 和内核头文件依赖，生成可在不同内核版本运行的通用二进制"

---

### 勘误 5：oncpu 采样精度描述

**原文位置**：第 1460 行
**原文内容**："定时采样线程栈"

**勘误说明**：
- "定时采样"的频率很重要，会直接影响精度
- 典型采样频率（99Hz、100Hz、199Hz）意味着每秒采样 99-199 次
- 采样间隔：100Hz = 每 10ms 采样一次，细粒度代码段可能被漏掉
- 这不是绝对精确的测量，而是统计采样

**更正后表述**：
"以配置的采样频率（如 99Hz）定时采样线程栈，因此测量结果是统计近似值"

## 总结

本章重点总结：

1. **eBPF 生态**：bcc 和 bpftrace 是 eBPF 最常用的两大工具
2. **性能分析**：oncpu 和 offcpu 分析方法互补，诊断不同类型问题
3. **火焰图**：同一个火焰图工具，横轴含义因分析类型而异
4. **部署选择**：优先选用 BPF CO-RE 版本，提升性能和可维护性
5. **实践经验**：三个 bpftrace 实例展示了从系统调用到应用层的多维度追踪
6. **学习路径**：先用 bcc 工具集，再学 bpftrace 脚本语言，最后可自定义追踪
