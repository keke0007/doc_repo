## 一、为什么需要时序数据库

### 1.1 时序数据库的核心场景

时序数据库(Time-Series Database, TSDB)是为"按时间顺序持续产生的指标数据"设计的存储。典型场景:

- **运维监控**:服务器 CPU、内存、磁盘 I/O、网络流量
- **IoT/工业物联网**:传感器读数、设备震动频率、农田温湿度
- **业务指标**:每秒下单数、APP DAU、广告点击数

通用结构是 **采集 → 存储 → 查询/聚合 → 报警** 的 4 步流水线。

### 1.2 为什么不用关系型数据库

| 维度 | 关系型 DB (B+ 树) | 时序 DB (LSM-Tree 变种) |
| --- | --- | --- |
| 写入 | 随机写,叶分裂导致随机 I/O | 顺序写盘,单点可达数十万 QPS |
| 数据更新 | 频繁 UPDATE | 时序数据**只写不改**,几乎不更新历史点 |
| 冷热分层 | 默认无 | 近期热数据驻内存、历史冷数据压缩落盘 |
| 查询模型 | 行为单位、按索引随机寻址 | **按序列(series)** 整批扫描 |

> ⚠️ 原文 1.2.1 表述"叶裂变"应作 **叶分裂(B+ tree node split)**,是中文笔误,概念是对的:B+ 树插入触发节点分裂从而产生随机 I/O。

### 1.3 时序数据的核心特性

1. 时间不可倒流,**历史数据点几乎不会被更新**
2. 写多读少、写远多于读(典型 100:1 量级)
3. 冷热差别极大:常用查询通常只看最近若干分钟
4. 数据按时间天然有序

## 二、TICK 技术栈与 1.x / 2.x 演进

### 2.1 TICK 四件套(1.x 时代)

| 字母 | 组件 | 角色 |
| --- | --- | --- |
| **T** | Telegraf | 数据采集 Agent,把数据推给 InfluxDB |
| **I** | InfluxDB | 时序数据存储与查询 |
| **C** | Chronograf | Web 管理与可视化 UI |
| **K** | Kapacitor | 后台流处理与报警 |

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 业务系统/IoT │──▶│   Telegraf   │──▶│   InfluxDB   │
│   (指标源)   │   │  (采集 Agent) │   │   (存储)     │
└──────────────┘   └──────────────┘   └──────┬───────┘
                                              │
                            ┌─────────────────┼─────────────────┐
                            ▼                                   ▼
                  ┌──────────────────┐               ┌──────────────────┐
                  │   Chronograf     │◀──查询/展示──│   Kapacitor      │
                  │ (Web UI/可视化)  │               │ (流处理/报警)    │
                  └──────────────────┘               └──────────────────┘
```

### 2.2 2.x 的融合

2.x 把 I、C、K 三个组件的核心能力**全部融进单个 `influxd` 进程**:

- 内置 Web UI(替代 Chronograf)
- 内置定时任务(Task)与报警(Check / Notification),替代 Kapacitor 的大部分能力
- 仅 Telegraf 仍然是独立的采集 Agent

```
┌──────────────┐                     ┌──────────────────────────────┐
│ 业务系统/IoT │────推送数据────────▶│                              │
└──────────────┘                     │       InfluxDB 2.x           │
                                     │  ┌─────┐ ┌──────┐ ┌──────┐  │
┌──────────────┐                     │  │存储 │ │Task  │ │Alert │  │
│   Telegraf   │────推送数据────────▶│  │     │ │定时  │ │报警  │  │
└──────────────┘                     │  └─────┘ └──────┘ └──────┘  │
                                     │  内置 Web UI(替代 Chronograf)│
┌──────────────┐                     │                              │
│ Scraper Pull │◀──主动拉取(10s)────│  Scraper 任务(Pull 模型)     │
│  (Prom 格式) │                     │                              │
└──────────────┘                     └──────────────────────────────┘
```

### 2.3 1.x vs 2.x 选型要点

| 维度 | 1.x | 2.x |
| --- | --- | --- |
| 内核引擎 | TSM | 基本相同 |
| 概念命名 | database / retention policy(rp) | **org / bucket** |
| 默认查询语言 | InfluxQL(类 SQL) | **FLUX**(管道函数式) |
| FLUX 支持 | 1.7+ 有限支持 | 完整支持 |
| 管理 UI | 需要 Chronograf | 内置 |
| 集群 | 开源版自 **0.11** 起闭源 | 同样闭源,需企业版/云版 |

> ⚠️ 原文"market 现状"提到 1.X 用户更多 — 这是 2022 年的现状,**到 2024 年起 InfluxDB 3.x(基于 Apache Arrow / DataFusion)已发布**,生态正在向 3.x 迁移;新项目应优先评估 3.x。本笔记保留按原讲义 2.4 讲解。

## 三、安装部署(Linux 二进制版)

### 3.1 下载、解压、启动

```bash
# 1) 下载(讲义版本)
wget https://dl.influxdata.com/influxdb/releases/influxdb2-2.4.0-linux-amd64.tar.gz

# 2) 解压到目标路径
tar -zxvf influxdb2-2.4.0-linux-amd64.tar.gz -C /opt/module

# 3) 启动服务
cd /opt/module/influxdb2-2.4.0-linux-amd64
./influxd
```

> ℹ️ Go 编译产物是**单一静态二进制**,不依赖运行时;`influxd` 就是服务进程。

### 3.2 端口与首次初始化

`influxd` 默认监听 **8086** 端口。首次访问 `http://<host>:8086` 会进入 Setup 引导:

```
   浏览器 (http://host:8086)
        │
        ▼
┌──────────────────────────────────────────┐
│  GET STARTED                             │
│   ↓                                       │
│  填写: 用户名 / 密码 / Org(组织) / Bucket │
│   ↓                                       │
│  influxd 创建:                            │
│    • 初始 user                            │
│    • 初始 org                             │
│    • 初始 bucket(讲义中叫 test_init)     │
│    • 一个 "All Access" 类型的初始 token  │
│    • 一个抓取 /metrics 的内置 Scraper    │
└──────────────────────────────────────────┘
```

> ⚠️ 原文 3.1.7.4 提到"InfluxDB 监控数据默认会被抓取到初始化的存储桶中" — 准确说,**首次 Setup 时**系统会自动创建一个指向自身 `/metrics` 的 Scraper,把 Prometheus 格式的内部指标写入初始 Bucket。这个行为只发生一次,不是所有 Bucket 都有。

## 四、核心数据模型(必读)

> 本节合并自第 23 章附录 4,是后续所有章节的概念前置。

### 4.1 与关系型数据库的对照

| 关系型 DB | InfluxDB 2.x | 说明 |
| --- | --- | --- |
| database | **bucket** | 1.x 中叫 database + retention policy,2.x 合并为 bucket |
| table | **measurement** | 测量名,逻辑上的"表名" |
| 索引列(等值过滤) | **tag**(Tag Set) | 仅支持 string;tag 默认建索引 |
| 普通列 | **field**(Field Set) | 数值/字符串/布尔等;**不建索引** |
| 一行 | **point**(数据点) | 一个时间戳上的一组 tag+field |
| 主键 | **measurement + tag set + field key + timestamp** | 完全相同则覆盖 |

> ⚠️ 原文 23.2 写"InfluxDB 中的 fields ... 相当于未建索引的列",**field 的本质就是"未索引的列"**,这部分正确。但要补充:**对 field 做 `filter()` 过滤不会走索引、会触发全序列扫描**,在第 18 章 FLUX 优化里会再强调。

### 4.2 Series(序列) — 时序库的核心概念

```
                   ┌──────────────────────────────────────┐
                   │     Bucket(example02)                │
                   │                                       │
  measurement ───▶ │ cpu                                   │
                   │  ├─ Series #1                         │
  tag set    ───▶ │  │   tags={host=h1, cpu=cpu0}          │
                   │  │   field=usage_idle                  │
  field key  ───▶ │  │   ↓ 时间排序的连续数据点          │
                   │  │   [t1,98.1] [t2,97.5] [t3,...]    │
                   │  │                                     │
                   │  ├─ Series #2                         │
                   │  │   tags={host=h1, cpu=cpu1}          │
                   │  │   field=usage_idle                  │
                   │  │   [t1,99.0] [t2,98.7] [t3,...]    │
                   │  │                                     │
                   │  └─ Series #N ...                     │
                   └──────────────────────────────────────┘
```

**Series 的定义**:`measurement + 完整 tag set + 一个 field key` 唯一确定一条 series。
同一 series 的所有数据点在磁盘上**连续存储**,所以"按 series 整批扫描"非常快。

> ⚠️ 原文 23.3 写"唯一的 measurement、tag_set 和 field**(一个字段)** 组合是一个 series"。这个表述**正确但容易误读**:
> - **InfluxDB 的 series 定义在底层是 `measurement + tag_set` 级别**(`SHOW SERIES` 输出的就是这个)
> - **但在存储/查询的最细粒度上,每个 field key 会被拆成一条独立的 series**(因为每个 field 单独建 TSM 块)
>
> 所以原文从"存储粒度"角度讲是对的,但很多 InfluxDB 文档(包括官方)说"series = measurement + tag set"时,指的是逻辑粒度。**两种说法都对,看上下文**。日常理解记:**tag set 决定 series 数量,field 在 series 内并列存储**。

### 4.3 双索引:Tag 与 Time

```
查询路径(典型)：
┌──────────────────────────────────────────────┐
│  1) Bucket    (定位文件)                     │
│       ↓                                       │
│  2) Time Range (粗粒度切分 TSM 文件)         │
│       ↓                                       │
│  3) measurement + tag set (倒排索引定位序列) │
│       ↓                                       │
│  4) field 取值 / 时间范围内点扫描            │
└──────────────────────────────────────────────┘
```

- **时间**是天然的一级索引(数据按 `timestamp` 升序写入)
- **measurement / tag** 是倒排索引,支持只指定部分 tag 命中多条 series

### 4.4 高基数(High Cardinality)与时间线膨胀

- **基数(cardinality)** = bucket 内不同 series 的总数
- tag 值的笛卡尔积越大,series 越多 → 索引爆炸 → 读写性能下降
- **典型反例**:把 `request_id`、`user_id`、`trace_id` 这种**几乎一对一**的字段做成 tag

> ✅ 实践要点:
> - **高基数维度放 field、不要放 tag**
> - tag 值的总组合数控制在 **百万级以内** 比较安全
> - 1.x/2.x 都有 `SHOW TAG VALUES CARDINALITY` 等工具可查基数

## 六、给后续章节的前置概念清单

> 阅读后面章节前,确认你已经理解以下 7 个术语:

1. **Bucket** — 数据容器,带保留策略(retention)
2. **Org(组织)** — 多租户隔离单位,Bucket 隶属于 Org
3. **Measurement** — 类似表名
4. **Tag / Field** — 索引列 vs 普通列
5. **Series** — `measurement + tag set` 的唯一组合
6. **Point** — 一个时间戳上的一行数据
7. **Token** — API 访问凭证,后面所有客户端都靠它鉴权
