## 1. Elasticsearch 概览

### 1.1 ES 定义与作用

**定义**: Elasticsearch 是一款开源、分布式、高效的搜索引擎，基于 Lucene 构建。

**核心作用**:
- 从海量数据中**快速检索**所需内容
- 应用场景: 电商搜索、代码检索(GitHub)、日志分析、系统监控、地理位置搜索

**性能特点**:
- 优点: 海量数据快速搜索、分析、计算；实时性强
- 缺点: 占用内存较大；不支持事务

### 1.2 ES vs MySQL

| 维度 | MySQL | Elasticsearch |
|------|-------|--------------|
| 存储位置 | 硬盘 | 内存 |
| 数据模型 | 关系型 | 面向文档 |
| 适用场景 | 事务操作、数据安全 | 海量数据检索、全文搜索 |
| 查询方式 | SQL | DSL (Domain Specific Language) |
| 一致性 | 强一致性(ACID) | 最终一致性 |

**企业应用**: 两者结合使用  
- MySQL: 主要数据存储、事务操作
- ES: 搜索、分析优化、二级检索

### 1.3 Lucene 与 Elasticsearch 关系

```
Lucene (Apache 开源搜索类库)
    ↓ (2004 年: Shay Banon 基于 Lucene 开发 Compass)
    ↓ (2010 年: 重写 Compass → Elasticsearch)
Elasticsearch
```

**Lucene vs ES**:
- **Lucene**: 是 Java 搜索引擎**类库**，需要开发者编写大量代码
- **Elasticsearch**: 完整的搜索**引擎服务**，开箱即用，提供 REST API

### 1.4 技术栈: ELK (Elastic Stack)

```
Beats
  ↓ (数据采集)
Logstash
  ↓ (数据处理、转换)
Elasticsearch
  ↓ (存储、搜索、分析)
Kibana (数据可视化、查询界面)
```

### 1.5 为何选择 ES？

**搜索引擎技术排名** (热度):
1. **Elasticsearch** (目前第一名，逐年上升)
2. Solr (曾经第一，逐年下降)
3. Splunk (商业，小众)
4. 其他: Algolia, Meilisearch (新兴)

## 2. 倒排索引原理

### 2.1 正向索引 (Traditional Index)

**定义**: 根据文档 ID 快速定位文档内容

**特点**:
- MySQL 标准方式: B+ 树索引
- 优点: 根据主键查询极快
- 缺点: 模糊查询需要**全表扫描** (如 `LIKE %keyword%`)

**示例流程** (搜索包含 "手机" 的商品):
```
用户查询: title LIKE '%手机%'
  → 逐行扫描表 (ID=1,2,3,...)
  → 检查每行 title 字段是否包含 "手机"
  → 效率随数据增长急剧下降 (百万级数据灾难级)
```

### 2.2 倒排索引 (Inverted Index)

**定义**: 根据词条反向查找文档 ID，是全文搜索的基础

**两个关键概念**:

| 概念 | 定义 | 示例 |
|------|------|------|
| **文档** (Document) | 搜索的基本数据单位 | 一个网页、一条商品 |
| **词条** (Term) | 对文档分词得到的具有含义的词 | "我是中国人" → ["我", "是", "中国人", "中国", "国人"] |

### 2.3 倒排索引构建过程

**步骤**:
1. 对每篇文档进行分词，得到词条列表
2. 建立倒排表: `词条 → [文档ID列表, 位置信息]`
3. 对词条创建索引 (Hash 表或 B+ 树)，支持 O(1) 查询

**倒排表示例**:

```
词条      文档ID  位置
华为   →  [1,2,3] [pos1,pos2,...]
手机   →  [1,2,3] [pos1,pos2,...]
5G     →  [2,4]   [pos1,pos2]
```

### 2.4 倒排索引查询流程 (以 "华为手机" 为例)

```
① 用户输入: "华为手机"
  ↓ 分词
② 分词结果: ["华为", "手机"]
  ↓ 倒排表查询
③ 找到文档: [1, 2, 3] (包含 "华为") ∩ [1, 2, 3] (包含 "手机") = [1, 2, 3]
  ↓ 正向索引查询
④ 返回文档数据: doc(1), doc(2), doc(3)
```

**优势**: 无需全表扫描，词条和文档ID均已索引，查询极快

### 2.5 正向 vs 倒排索引对比

| 维度 | 正向索引 | 倒排索引 |
|------|---------|---------|
| **查询方向** | 文档 → 词条 | 词条 → 文档 |
| **构建方式** | 按文档ID | 按词条 |
| **优点** | 根据字段检索快；支持排序 | 全文搜索快；模糊查询快 |
| **缺点** | 模糊查询需全表扫描 | 只能按词条检索；不支持排序 |
| **适用场景** | 结构化查询、精确匹配 | 非结构化数据、全文搜索 |

## 3. ES 核心概念

### 3.1 文档 (Document)

**定义**: ES 中最小的存储单位，序列化为 JSON 格式

**特点**:
- 扁平或嵌套结构
- 包含多个字段 (Field)
- 每篇文档对应一个唯一的 ID

**示例**:
```json
{
  "_id": "1",
  "name": "iPhone 14",
  "price": 5999,
  "brand": "Apple",
  "specs": {
    "memory": "128GB",
    "color": "Black"
  }
}
```

### 3.2 字段 (Field)

**定义**: JSON 文档中的属性，对应 MySQL 的列 (Column)

**字段类型** (详见第 9 节):
- 字符串: `text`(分词)、`keyword`(精确)
- 数值: `long`、`integer`、`float`、`double`
- 布尔: `boolean`
- 日期: `date`
- 特殊: `object`(嵌套)、`geo_point`(地理坐标)
- 数组: 单个字段可存储数组

### 3.3 索引库 (Index)

**定义**: 相同类型文档的集合，对应 MySQL 的表 (Table)

**组织方式**:
- 用户索引: 所有用户文档
- 商品索引: 所有商品文档
- 订单索引: 所有订单文档

**特点**:
- 每个索引可含数百万文档
- 索引名全局唯一
- 索引名必须小写

### 3.4 映射 (Mapping)

**定义**: 索引库中文档的约束规则，对应 MySQL 的表结构 (Schema)

**包含信息**:
- 字段名称
- 字段数据类型
- 是否分词
- 分词器选择
- 是否参与搜索
- 嵌套字段定义

**示例**:
```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "analyzer": "ik_max_word"
      },
      "age": {
        "type": "integer"
      },
      "email": {
        "type": "keyword",
        "index": false
      }
    }
  }
}
```

**重要**: 创建后无法修改 mapping 中的现有字段，只能添加新字段

### 3.5 Type (已弃用)

**历史背景** (ES 7.x 前):
- 每个索引可以有多个 Type
- 类似关系数据库的多张表

**ES 7.0 后变更**:
- 移除 Type 概念
- 一个索引只能有一个隐含 Type: `_doc`
- ES 8.0 完全删除 Type

**原因**: 多 Type 导致存储低效、查询复杂，与关系型思维冲突

### 3.6 分片与副本 (Shard & Replica)

**分片 (Primary Shard)**:
- 将索引分成多个部分，分布在不同节点
- 默认 1 个分片
- 提高并发处理能力、存储容量
- 创建索引后无法修改分片数

**副本 (Replica Shard)**:
- 分片的备份，提高容错性和查询吞吐
- 默认 1 个副本
- 创建索引后可动态调整副本数

**示例**:
```
Primary Shard 0  →  Replica Shard 0
Primary Shard 1  →  Replica Shard 1
```

## 4. 索引库操作(CRUD)

### 4.1 Mapping 映射属性详解

| 属性 | 说明 | 示例 |
|------|------|------|
| `type` | 字段数据类型 | `text`, `keyword`, `long`, `date` |
| `index` | 是否参与搜索 (默认 true) | `true` \| `false` |
| `analyzer` | 使用分词器 (仅对 text 有效) | `ik_smart`, `ik_max_word`, `standard` |
| `copy_to` | 将值复制到另一字段 | `"copy_to": "all"` |
| `properties` | 嵌套对象的子字段定义 | `{ "firstName": {...} }` |

**常见字段类型选择**:

| 数据性质 | 选择类型 | 分词器 | 说明 |
|---------|--------|-------|------|
| 商品名称 | `text` | `ik_max_word` | 需要全文搜索 |
| 品牌、国家 | `keyword` | 无 | 精确匹配 |
| IP 地址 | `keyword` | 无 | 精确匹配 |
| 价格、评分 | `integer` \| `float` | 无 | 数值范围查询 |
| 发布日期 | `date` | 无 | 时间范围查询 |
| 图片 URL | `keyword` | 无 | `index: false` (不搜索) |
| 经纬度 | `geo_point` | 无 | 地理距离查询 |

### 4.2 创建索引库 (PUT)

**DSL 语法**:
```json
PUT /索引库名称
{
  "mappings": {
    "properties": {
      "字段名": {
        "type": "text",
        "analyzer": "ik_smart"
      },
      "另一字段": {
        "type": "keyword",
        "index": false
      },
      "嵌套字段": {
        "properties": {
          "子字段": { "type": "keyword" }
        }
      }
    }
  }
}
```

**完整示例** (酒店索引):
```json
PUT /hotel
{
  "mappings": {
    "properties": {
      "id": { "type": "keyword" },
      "name": {
        "type": "text",
        "analyzer": "ik_max_word",
        "copy_to": "all"
      },
      "address": {
        "type": "keyword",
        "index": false
      },
      "price": { "type": "integer" },
      "score": { "type": "integer" },
      "brand": {
        "type": "keyword",
        "copy_to": "all"
      },
      "city": {
        "type": "keyword",
        "copy_to": "all"
      },
      "location": { "type": "geo_point" },
      "all": {
        "type": "text",
        "analyzer": "ik_max_word"
      }
    }
  }
}
```

**特殊字段**:
- `location`: 地理坐标 `{ "lat": 31.2, "lon": 120.3 }`
- `all`: 虚拟字段，通过 `copy_to` 聚合多字段内容

### 4.3 查询索引库 (GET)

**语法**:
```json
GET /索引库名称
```

**返回内容**: 索引配置、mapping 定义、分片情况

### 4.4 获取 Mapping (GET _mapping)

**语法**:
```json
GET /索引库名称/_mapping
```

**返回**: 仅 mapping 定义部分

### 4.5 修改索引库 (PUT _mapping)

**重要限制**:
- 已有字段**不能修改** (会重建倒排索引，灾难级操作)
- 只能**添加新字段**

**语法**:
```json
PUT /索引库名称/_mapping
{
  "properties": {
    "新字段": {
      "type": "integer"
    }
  }
}
```

### 4.6 删除索引库 (DELETE)

**语法**:
```json
DELETE /索引库名称
```

**警告**: 删除后数据无法恢复，生产环境需谨慎

### 4.7 索引库操作总结

| 操作 | 方法 | 路径 | 备注 |
|------|------|------|------|
| 创建 | PUT | `/索引库名` | 含 mapping |
| 查询 | GET | `/索引库名` | 查全部信息 |
| 查询 Mapping | GET | `/索引库名/_mapping` | 仅 mapping |
| 修改 | PUT | `/索引库名/_mapping` | 仅添加字段 |
| 删除 | DELETE | `/索引库名` | 不可恢复 |

## 5. 文档操作(CRUD)

### 5.1 新增文档 (POST)

**语法**:
```json
POST /索引库名/_doc/文档ID
{
  "字段1": "值1",
  "字段2": "值2",
  "嵌套": {
    "子字段": "值3"
  }
}
```

**说明**:
- 若 ID 已存在，则覆盖 (变成修改)
- 若 ID 不存在，则新增
- ID 可自动生成 (不指定时)

**示例**:
```json
POST /heima/_doc/1
{
  "info": "黑马程序员 Java 讲师",
  "email": "zy@itcast.cn",
  "name": {
    "firstName": "云",
    "lastName": "赵"
  }
}
```

### 5.2 查询文档 (GET)

**语法**:
```json
GET /索引库名/_doc/文档ID
```

**返回**:
```json
{
  "_index": "heima",
  "_id": "1",
  "_version": 1,
  "_source": {
    "info": "黑马程序员 Java 讲师",
    "email": "zy@itcast.cn",
    "name": { "firstName": "云", "lastName": "赵" }
  }
}
```

### 5.3 修改文档

**两种方式对比**:

#### 5.3.1 全量修改 (PUT)

**特点**: 覆盖式修改，内部先删除再新增

**语法**:
```json
PUT /索引库名/_doc/文档ID
{
  "新数据": "完整的 JSON"
}
```

**示例**:
```json
PUT /heima/_doc/1
{
  "info": "黑马程序员高级 Java 讲师",
  "email": "zy@itcast.cn",
  "name": { "firstName": "云", "lastName": "赵" }
}
```

**结果**: 若字段缺失，则删除该字段

#### 5.3.2 增量修改 (POST _update)

**特点**: 仅修改指定字段，其他字段保持

**语法**:
```json
POST /索引库名/_update/文档ID
{
  "doc": {
    "要修改的字段": "新值",
    "另一字段": "新值"
  }
}
```

**示例**:
```json
POST /heima/_update/1
{
  "doc": {
    "email": "newemail@itcast.cn",
    "age": 35
  }
}
```

**说明**: 其他字段完全保持不变

### 5.4 删除文档 (DELETE)

**语法**:
```json
DELETE /索引库名/_doc/文档ID
```

**示例**:
```json
DELETE /heima/_doc/1
```

### 5.5 批量操作 (Bulk)

**场景**: 大量文档导入、删除、修改

**语法**:
```json
POST /_bulk
{ "index": {"_index": "hotel", "_id": "1"} }
{ "name": "酒店A", "price": 100 }
{ "index": {"_index": "hotel", "_id": "2"} }
{ "name": "酒店B", "price": 200 }
```

**说明**: 奇数行为操作类型，偶数行为文档数据

### 5.6 文档操作总结

| 操作 | 方法 | 路径 | 参数 |
|------|------|------|------|
| 新增 | POST \| PUT | `/_doc/ID` | JSON 文档 |
| 查询 | GET | `/_doc/ID` | 无 |
| 全量修改 | PUT | `/_doc/ID` | JSON 文档 |
| 增量修改 | POST | `/_update/ID` | `{"doc":{...}}` |
| 删除 | DELETE | `/_doc/ID` | 无 |
| 批量操作 | POST | `/_bulk` | 多行 JSON |

## 6. RestAPI 与 Java 客户端

### 6.1 Java RestClient 概述

**官方提供的 Java 客户端**:
1. **Low Level Rest Client** (已废弃)
2. **High Level Rest Client** (推荐，本课使用)
3. **Java API Client** (新一代，ES 8.0+)

**原理**: 组装 DSL 语句 → 通过 HTTP 请求发送给 ES

### 6.2 RestHighLevelClient 初始化

**第一步**: 添加依赖
```xml
<dependency>
    <groupId>org.elasticsearch.client</groupId>
    <artifactId>elasticsearch-rest-high-level-client</artifactId>
</dependency>
```

**第二步**: 配置 ES 版本 (SpringBoot 需要)
```xml
<properties>
    <elasticsearch.version>7.12.1</elasticsearch.version>
</properties>
```

**第三步**: 初始化客户端
```java
RestHighLevelClient client = new RestHighLevelClient(
    RestClient.builder(
        new HttpHost("192.168.150.101", 9200, "http")
    )
);
```

**单元测试模板**:

```java
public class HotelTest {
```

### 6.3 索引库操作 API

```java
@Test
void createIndex() throws IOException {
```

```java
void existsIndex() throws IOException {
```

### 6.4 文档操作 API

#### 6.4.1 新增文档

```java
@Test
void addDocument() throws IOException {
    // 1. 从数据库查询数据
    Hotel hotel = hotelService.getById(36934L);
    
    // 2. 转换为文档类型
    HotelDoc hotelDoc = new HotelDoc(hotel);
    
    // 3. 转换为 JSON
    String json = JSON.toJSONString(hotelDoc);
    
    // 4. 创建 Request
    IndexRequest request = new IndexRequest("hotel")
        .id(hotel.getId().toString())
        .source(json, XContentType.JSON);
    
    // 5. 发送请求
    IndexResponse response = client.index(request, RequestOptions.DEFAULT);
    System.out.println(response.getResult());
}
```

#### 6.4.2 查询文档

```java
@Test
void getDocument() throws IOException {
    GetRequest request = new GetRequest("hotel", "36934");
    GetResponse response = client.get(request, RequestOptions.DEFAULT);
    
    String json = response.getSourceAsString();
    HotelDoc hotelDoc = JSON.parseObject(json, HotelDoc.class);
    System.out.println(hotelDoc);
}
```

#### 6.4.3 修改文档 (增量)

```java
@Test
void updateDocument() throws IOException {
    UpdateRequest request = new UpdateRequest("hotel", "36934");
    request.doc(
        "price", "1000",
        "name", "新酒店名"
    );
    
    UpdateResponse response = client.update(request, RequestOptions.DEFAULT);
    System.out.println(response.getResult());
}
```

#### 6.4.4 删除文档

```java
@Test
void deleteDocument() throws IOException {
    DeleteRequest request = new DeleteRequest("hotel", "36934");
```

### 7.2 ES 集群架构与节点关系

```
┌──────────────────────────────────────────────────────────────┐
│               Elasticsearch 集群架构                           │
└──────────────────────────────────────────────────────────────┘

┌─── 节点类型 ───┐

Master Node (主节点)
  ├─ 管理集群元数据
  ├─ 管理索引创建/删除
  ├─ 管理分片分配
  └─ 选举机制: 多数投票制

Data Node (数据节点)
  ├─ 存储文档数据
  ├─ 执行搜索和聚合
  ├─ 管理分片(主 + 副本)
  └─ 最多的节点数

Coordinating Node (协调节点)
  ├─ 不存储数据，不参与选举
  ├─ 接收客户端请求
  ├─ 路由请求到数据节点
  └─ 聚合各节点结果

Ingest Node (摄入节点)
  └─ 数据预处理(可选)


┌─── 集群拓扑示意 ───┐

        Client
          ↓ (REST 请求)
    Coordinating Node
     ↗      ↓      ↖
   /        ↓        \
Data(Master)  Data    Data
  [Shard 0]  [Shard 1][Shard 2]
   [Replica]  [Replica][Replica]
   (副本)


┌─── 分片分配示意 ───┐

索引 "hotel", 5 个分片, 1 个副本:

Node 1                Node 2
├─ P0 (Primary)       ├─ P1 (Primary)
├─ R1 (Replica)       ├─ R2 (Replica)
├─ R2 (Replica)       ├─ R3 (Replica)
├─ P3 (Primary)       ├─ R0 (Replica)
└─ P4 (Primary)       └─ R4 (Replica)

P = Primary Shard (主分片)
R = Replica Shard (副本分片)
```

### 7.3 文档写入完整调用链

```
┌──────────────────────────────────────────────────────────────┐
│          一次文档写入的完整调用链 (文档生命周期)                 │
└──────────────────────────────────────────────────────────────┘

步骤 1: 客户端发送写入请求
─────────────────────────
Client
  ↓ (REST: POST /hotel/_doc/1)
  │ { "name": "酒店A", "price": 100 }
  ↓


步骤 2: 协调节点路由
─────────────────────
Coordinating Node
  ├─ 解析请求
  ├─ 计算分片: shard = hash(doc_id) % num_shards
  ├─ 查询集群状态
  └─ 确定 Primary Shard 所在节点
  ↓


步骤 3: 写入 Primary Shard
─────────────────────────
Data Node (Primary Shard)
  ├─ 接收文档
  ├─ 写入 Write Buffer (内存)
  ├─ 写入 Translog (事务日志)
  ├─ 文档变为 searchable (1 秒后，默认)
  ├─ 返回成功确认
  └─ (同时异步复制到副本)
  ↓


步骤 4: 复制到 Replica Shards
─────────────────────────────
Data Node (Replica Shard 1,2,...)
  ├─ 接收复制请求
  ├─ 写入 Write Buffer
  ├─ 写入 Translog
  └─ 返回确认


步骤 5: Primary Shard 收集确认
─────────────────────────────
Data Node (Primary Shard)
  ├─ 等待所有副本确认
  │ (可配置: wait_for=1,quorum,all)
  ├─ 所有确认后，向协调节点返回成功
  └─ 客户端收到响应


时间线:
───────
T0: 客户端 → 协调节点 (网络延迟 ~1ms)
T1: 协调节点 → Primary (路由 ~1ms)
T2: Primary 写入并复制到 Replicas (~5-50ms)
T3: 返回结果给客户端 (网络延迟 ~1ms)

总耗时: ~10-60ms (取决于网络、磁盘 I/O)


写入一致性级别:
──────────────
write_concern_level = "one"   // 仅 Primary 确认 (快速，风险)
write_concern_level = "quorum"// 大多数副本确认 (均衡)
write_concern_level = "all"   // 所有副本确认 (安全，慢速)
```

### 7.4 DSL 查询调用链路

```
┌──────────────────────────────────────────────────────────────┐
│      DSL 查询从客户端到 Lucene 的完整调用链路                  │
└──────────────────────────────────────────────────────────────┘

步骤 1: 客户端发送查询请求
─────────────────────────
Client
  ↓ (REST: GET /hotel/_search)
  │ { "query": { "match": { "name": "酒店" } } }
  ↓


步骤 2: 协调节点转发到所有分片
─────────────────────────────
Coordinating Node
  ├─ 解析 DSL 查询
  ├─ 确定查询范围 (哪些索引、分片)
  ├─ 向所有 Primary/Replica 发送查询请求
  └─ 并行执行，等待结果
  ↓


步骤 3: 每个分片执行查询
───────────────────────
Data Node (Primary Shard)
  ├─ 接收查询请求
  ├─ Lucene 层处理:
  │  ├─ Query Parser: DSL → Lucene Query Object
  │  ├─ 分词: "酒店" → ["酒店"]
  │  ├─ 倒排索引查询: 获取匹配文档 ID
  │  ├─ 计分 (TF-IDF): 计算关联度
  │  └─ 排序: 按得分降序
  ├─ 返回 Top K 结果 (文档 ID + 得分)
  └─ 返回给协调节点
  ↓


步骤 4: 协调节点合并结果
─────────────────────────
Coordinating Node
  ├─ 收集所有分片的 Top K 结果
  ├─ 全局排序: 合并多个 Top K (可能 3000+ 个)
  ├─ 取出最终 Top N (page size)
  ├─ 向相应分片请求完整文档数据
  └─ 返回给客户端
  ↓


步骤 5: 返回结果到客户端
─────────────────────────
Client
  ↓ 收到 JSON 响应:
  {
    "hits": {
      "total": 1000,
      "hits": [
        { "_id": "1", "_source": {...}, "_score": 0.95 },
        { "_id": "2", "_source": {...}, "_score": 0.85 }
      ]
    }
  }


执行阶段详解:
────────────

Query Phase (查询阶段):
  Time: ~5-20ms
  └─ 每个分片执行查询，返回 Top K (K=from+size)
     假设 size=20, 5 个分片: 5 × 20 = 100 文档 ID 返回

Fetch Phase (获取阶段):
  Time: ~1-10ms
  └─ 根据文档 ID，获取实际文档数据
     再排序，返回 Top 20


查询优化示意:
─────────────
Bad:  GET /hotel/_search?from=10000&size=20
      → 需要每个分片都返回 10020 个文档 ID
      → 协调节点排序 50100 条记录
      → 耗时: ~50-200ms

Good: GET /hotel/_search?from=0&size=20
      → 每个分片返回 20 个文档 ID
      → 协调节点排序 100 条记录
      → 耗时: ~5-20ms

=> 分页深度越深，性能越差 (Deep Pagination Problem)
```

### 9.6 分词器选择指南

| 分词器 | 使用场景 | 优点 | 缺点 |
|------|--------|------|------|
| **standard** | 英文、数字 | 精确分词 | 对中文不友好 |
| **ik_smart** | 中文、混合 | 粗粒度，性能高 | 可能漏掉部分词 |
| **ik_max_word** | 中文、混合 | 细粒度，全面覆盖 | 可能出现重复词 |

**推荐**:
- 中文内容: **ik_max_word** (索引) + **ik_smart** (查询可选)
- 英文: **standard**
- 混合: **ik_max_word**

### 9.7 易混淆点辨析

#### text vs keyword

| 维度 | text | keyword |
|------|------|---------|
| 分词 | ✅ 分词 | ❌ 不分词 |
| 使用场景 | 名称、描述、内容 | 品牌、类别、状态、ID |
| 查询示例 | `match` | `term` |
| 排序 | ❌ 不支持(通常) | ✅ 支持 |
| 模糊查询 | ✅ 支持 | ❌ 不支持 |
| 精确匹配 | ❌ 分词后匹配 | ✅ 完整匹配 |

#### match vs term

| 维度 | match | term |
|------|-------|------|
| 查询字段类型 | text (分词字段) | keyword (精确字段) |
| 查询逻辑 | 1. 分词查询词 2. 倒排表查询 | 直接倒排表查询 |
| 示例 | `{"match":{"name":"iPhone"}}` | `{"term":{"brand":"Apple"}}` |
| 模糊性 | 支持模糊匹配 | 精确匹配 |

#### POST vs PUT (新增文档时)

| 操作 | HTTP 方法 | 使用场景 | ID 行为 |
|------|---------|--------|--------|
| 新增 | POST | 不指定 ID，由 ES 生成 | UUID 自动生成 |
| 新增/修改 | PUT | 指定 ID，幂等操作 | ID 已存在则覆盖 |

#### PUT 全量修改 vs POST 增量修改

| 维度 | PUT /_doc/ID | POST /_update/ID |
|------|-------------|-----------------|
| 修改范围 | 覆盖整个文档 | 仅修改指定字段 |
| 缺失字段 | 删除 | 保留 |
| 性能 | 较慢(先删后增) | 快速(直接修改) |
| 推荐场景 | 整体替换 | 部分更新 |

#### Index vs _mapping vs _doc

```
PUT /索引名                 ← 创建索引
PUT /索引名/_mapping        ← 修改 mapping (仅添加字段)
POST /索引名/_doc/ID        ← 新增/修改文档
GET /索引名/_mapping        ← 查询 mapping
GET /索引名/_doc/ID         ← 查询文档
```

## 10. 学习重点与实战建议

### 10.1 必须掌握的概念

1. **倒排索引**: ES 性能的核心，理解分词 → 倒排表 → 查询流程
2. **Mapping 映射**: 搞不好 mapping 会导致严重性能问题，特别是 text vs keyword
3. **分片与副本**: 理解分布式存储、高可用的基础
4. **DSL 查询**: match、term、range、bool 是 80% 查询需求

### 10.2 实战项目流程

```
① 需求分析
   ↓
② 设计 Mapping (字段类型、分词器、是否索引)
   ↓
③ 创建索引库 (PUT /索引名 {...mapping...})
   ↓
④ 导入数据 (批量 Bulk 操作)
   ↓
⑤ 验证数据 (GET /_doc/ID, 搜索测试)
   ↓
⑥ 优化查询 (DSL 调优、聚合、排序)
   ↓
⑦ 生产监控 (集群健康、索引大小、查询性能)
```

### 10.3 常见坑点

1. **字段类型错选**
   - ❌ 品牌用 text → 可能被分词
   - ✅ 品牌用 keyword → 精确匹配

2. **Mapping 创建后修改**
   - ❌ 试图修改已有字段 → 创建新索引并重新导入
   - ✅ 提前规划好字段

3. **分页深度过深** (Deep Pagination)
   - ❌ GET /_search?from=100000&size=20 → 查询变慢
   - ✅ 使用 search_after 或 scroll 做大数据集遍历

4. **没有设置副本**
   - ❌ replica=0 → 节点故障导致数据丢失
   - ✅ 生产环境至少 1 个副本

## 总结速记

```
ES 是分布式搜索引擎，基于 Lucene，用于海量数据快速检索

三大概念:
  ① 倒排索引: 词条 → 文档 ID (核心原理)
  ② Mapping: 索引的结构约束 (至关重要)
  ③ DSL: JSON 风格的查询语言

MySQL vs ES:
  表 ↔ 索引库 (Index)
  行 ↔ 文档 (Document)
  列 ↔ 字段 (Field)
  Schema ↔ 映射 (Mapping)
  SQL ↔ DSL

操作方式:
  ① Kibana DSL (学习、调试)
  ② REST API (HTTP 请求)
  ③ Java RestClient (应用集成)

最常用的 DSL:
  query.match     → 全文搜索
  query.term      → 精确查询
  query.range     → 范围查询
  query.bool      → 布尔组合

字段类型选择:
  可搜索的文本 → text (+ 分词器)
  精确值 → keyword (不分词)
  数值/日期/地点 → 对应类型

Java RestClient 三步走:
  ① 创建 XXXRequest
  ② 准备参数
  ③ client.xxx() 发送
```
