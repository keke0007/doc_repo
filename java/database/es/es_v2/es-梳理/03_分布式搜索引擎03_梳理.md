## 1. 数据聚合 (Aggregations)

### 1.1 核心概念

聚合用于实现**数据统计、分析、运算**，速度远快于数据库SQL。

**三类聚合：**

| 类型 | 作用 | 常见例子 |
|------|------|--------|
| **Bucket** | 文档分组 | TermAggregation (按字段值)、DateHistogram (按日期) |
| **Metric** | 计算统计值 | Avg、Max、Min、Stats |
| **Pipeline** | 对其他聚合再聚合 | 高阶聚合 |

**聚合必须三要素：**
- 聚合名称 (自定义标识)
- 聚合类型 (terms、avg等)
- 聚合字段 (必须是 keyword、日期、数值、布尔)

⚠️ **文本(text)字段无法直接聚合，会影响结果；应使用keyword类型**

### 1.2 DSL 聚合语法

#### 1.2.1 Bucket 聚合 - 按品牌分桶

```json
GET /hotel/_search
{
  "size": 0,                    // 不返回文档，只聚合结果
  "aggs": {                     // 聚合定义
    "brandAgg": {               // 聚合名称(自定义)
      "terms": {                // 聚合类型(按字段值分组)
        "field": "brand",       // 聚合字段
        "size": 20              // 返回结果数量
      }
    }
  }
}
```

结果结构：

```json
{
  "aggregations": {
    "brandAgg": {
      "buckets": [
        {
          "key": "7天酒店",
          "doc_count": 30
        },
        ...
      ]
    }
  }
}
```

#### 1.2.2 聚合排序

默认按 `_count` (文档数量) 降序。可自定义排序：

```json
GET /hotel/_search
{
  "size": 0,
  "aggs": {
    "brandAgg": {
      "terms": {
        "field": "brand",
        "size": 20,
        "order": {
          "_count": "asc"        // 升序排列
          // "_key": "desc"      // 按key(品牌名)排序
        }
      }
    }
  }
}
```

#### 1.2.3 限定聚合范围

聚合必须配合 query 限定文档范围（对搜索结果聚合）：

```json
GET /hotel/_search
{
  "query": {
    "range": {
      "price": {
        "gte": 1000,
        "lte": 3000              // 只聚合价格在范围内的文档
      }
    }
  },
  "size": 0,
  "aggs": {
    "brandAgg": {
      "terms": {
        "field": "brand",
        "size": 20
      }
    }
  }
}
```

#### 1.2.4 Metric 聚合 - 桶内度量

先按品牌分桶(Bucket)，再对每个桶内的文档统计(Metric)：

```json
GET /hotel/_search
{
  "size": 0,
  "aggs": {
    "brandAgg": {                    // 第一层：按品牌分桶
      "terms": {
        "field": "brand",
        "size": 20,
        "order": {
          "price_avg": "desc"        // 按平均价格排序
        }
      },
      "aggs": {                      // 第二层：桶内度量
        "price_stats": {             // 统计度量名称
          "stats": {                 // 类型：获取max、min、avg、sum
            "field": "price"
          }
        },
        "price_avg": {               // 平均价格
          "avg": {
            "field": "price"
          }
        }
      }
    }
  }
}
```

结果示例：

```json
{
  "aggregations": {
    "brandAgg": {
      "buckets": [
        {
          "key": "希尔顿",
          "doc_count": 20,
          "price_stats": {
            "count": 20,
            "min": 2000,
            "max": 5000,
            "avg": 3500,
            "sum": 70000
          }
        }
      ]
    }
  }
}
```

### 1.3 RestAPI 实现聚合

#### 1.3.1 Java API 基本语法

```java
@Test
void testAggs() throws IOException {
    // 1. 准备 Request
    SearchRequest request = new SearchRequest("hotel");
    
    // 2. 准备 DSL - 设置聚合
    request.source().size(0);
    request.source().aggregation(
        AggregationBuilders
            .terms("brand_agg")           // 聚合名称
            .field("brand")               // 聚合字段
            .size(20)                     // 结果数量
    );
    
    // 3. 发送请求
    SearchResponse response = client.search(request, RequestOptions.DEFAULT);
    
    // 4. 解析响应
    Aggregations aggregations = response.getAggregations();
    Terms brandTerms = aggregations.get("brand_agg");  // 获取指定聚合
    List<? extends Terms.Bucket> buckets = brandTerms.getBuckets();
    
    // 5. 遍历结果
    for (Terms.Bucket bucket : buckets) {
        String brandName = bucket.getKeyAsString();
        long docCount = bucket.getDocCount();
        System.out.println(brandName + " : " + docCount);
    }
}
```

```java
@PostMapping("filters")

    return hotelService.getFilters(params);

// 2. Service 层 - 构建多个聚合
@Override
public Map<String, List<String>> getFilters(RequestParams params) {
    try {
        SearchRequest request = new SearchRequest("hotel");
        
        // 构建查询条件（限定聚合范围）
        buildBasicQuery(params, request);
        request.source().size(0);
        
        // 构建多个聚合
        request.source().aggregation(
            AggregationBuilders.terms("brandAgg")
                .field("brand").size(100)
        );
        request.source().aggregation(
            AggregationBuilders.terms("cityAgg")
                .field("city").size(100)
        );
        request.source().aggregation(
            AggregationBuilders.terms("starAgg")
                .field("starName").size(100)
        );
        
        // 发送请求
        SearchResponse response = client.search(request, RequestOptions.DEFAULT);
        
        // 解析结果
        Map<String, List<String>> result = new HashMap<>();
        Aggregations aggregations = response.getAggregations();
        
        result.put("brand", getAggByName(aggregations, "brandAgg"));
        result.put("city", getAggByName(aggregations, "cityAgg"));
        result.put("starName", getAggByName(aggregations, "starAgg"));
        
        return result;
    } catch (IOException e) {
        throw new RuntimeException(e);
    }
}

// 3. 辅助方法 - 提取聚合结果
private List<String> getAggByName(Aggregations aggregations, String aggName) {
    Terms terms = aggregations.get(aggName);
    List<String> list = new ArrayList<>();
    for (Terms.Bucket bucket : terms.getBuckets()) {
        list.add(bucket.getKeyAsString());
    }
    return list;
}
```

## 2. 自动补全 (Auto-Completion)

### 2.1 拼音分词器

用户搜索时可能输入：拼音、首字母、中文，需要对这些都能补全。

**安装拼音分词器：**

1. 下载：https://github.com/medcl/elasticsearch-analysis-pinyin
2. 解压
3. 放到 ES 的 plugins 目录
4. 重启 ES

**测试：**

```json
POST /_analyze
{
  "text": "如家酒店还不错",
  "analyzer": "pinyin"
}

// 输出分词结果
// "如" -> "r"
// "家" -> "j"
// "酒店" -> "jiudian"
```

---

### 2.2 自定义分词器

**Analyzer 组成三部分：**

```
Character Filters (删除/替换字符)
      ↓
   Tokenizer (分词，如 ik_max_word)
      ↓
Token Filters (大小写、同义词、拼音处理等)
```

**自定义拼音分词器配置：**

```json
PUT /hotel
{
  "settings": {
    "analysis": {
      "analyzer": {
        "text_analyzer": {                // 文本分词器（写入时用）
          "tokenizer": "ik_max_word",
          "filter": "py"
        },
        "completion_analyzer": {          // 补全分词器（写入时用）
          "tokenizer": "keyword",         // 不分词，保持整体
          "filter": "py"
        }
      },
      "filter": {
        "py": {                           // 自定义拼音过滤器
          "type": "pinyin",
          "keep_full_pinyin": false,      // 不保存完整拼音
          "keep_joined_full_pinyin": true,// 保存拼接后的完整拼音
          "keep_original": true,          // 保存原始中文
          "limit_first_letter_length": 16,// 首字母最大长度
          "remove_duplicated_term": true, // 去重
          "none_chinese_pinyin_tokenize": false
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "suggestion": {
        "type": "completion",             // 补全字段类型
        "analyzer": "completion_analyzer" // 使用补全分词器
      }
    }
  }
}
```

**⚠️ 关键注意事项：**

1. **分词器不对称**：
   - 写入(索引)时：用自定义的 `text_analyzer` 或 `completion_analyzer`
   - 搜索时：用 `search_analyzer: "ik_smart"`（只分词，不拼音）
   
2. 为什么搜索时不用拼音分词器？
   - 避免搜索到同音字（如"狮子" vs "虱子"都会匹配"s"）

```json
"name": {
  "type": "text",
  "analyzer": "text_analyzer",      // 写入时用拼音分词
  "search_analyzer": "ik_smart"     // 搜索时只用ik分词，不用拼音
}
```

```java
public class HotelDoc {
```

## 3. 数据同步 (Data Synchronization)

### 3.1 三种同步方案对比

| 方案 | 实现原理 | 优点 | 缺点 | 耦合度 |
|------|--------|------|------|--------|
| **同步调用** | hotel-admin 直接调用 hotel-demo 接口 | 实现简单 | 业务耦合高 | **高** |
| **异步通知(MQ)** | hotel-admin → MQ → hotel-demo 监听 | 低耦合 | 依赖MQ可靠性 | **低** |
| **监听 Binlog** | MySQL binlog → Canal → ES | 完全解耦 | 复杂度高、数据库负担 | **最低** |

**选择建议：** 中等规模项目推荐 **异步MQ方案**（耦合度低且实现难度适中）

---

### 3.2 MQ 异步通知方案详解

**架构流程：**

```
hotel-admin(增删改)  →  MQ(topic exchange)
                            ↓
         binding (hotel.insert / hotel.delete)
                            ↓
      hotel.insert.queue / hotel.delete.queue
                            ↓
         hotel-demo (监听并消费消息)
                            ↓
              更新 Elasticsearch
```

#### 3.2.1 MQ 常量定义

```java
package cn.itcast.hotel.constants;

public class MqConstants {
    // 交换机名称
    public final static String HOTEL_EXCHANGE = "hotel.topic";
    
    // 队列名称
    public final static String HOTEL_INSERT_QUEUE = "hotel.insert.queue";
    public final static String HOTEL_DELETE_QUEUE = "hotel.delete.queue";
    
    // 路由键(RoutingKey)
    public final static String HOTEL_INSERT_KEY = "hotel.insert";  // 用于新增、修改
    public final static String HOTEL_DELETE_KEY = "hotel.delete";  // 用于删除
}
```

#### 3.2.2 hotel-demo MQ 配置

```java
package cn.itcast.hotel.config;

import cn.itcast.hotel.constants.MqConstants;
import org.springframework.amqp.core.*;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MqConfig {
    
    // 声明 Topic 交换机
    @Bean
    public TopicExchange topicExchange(){
        return new TopicExchange(MqConstants.HOTEL_EXCHANGE, true, false);
    }
    
    // 声明新增/修改队列
    @Bean
    public Queue insertQueue(){
        return new Queue(MqConstants.HOTEL_INSERT_QUEUE, true);
    }
    
    // 声明删除队列
    @Bean
    public Queue deleteQueue(){
        return new Queue(MqConstants.HOTEL_DELETE_QUEUE, true);
    }
    
    // 新增队列与交换机绑定
    @Bean
    public Binding insertQueueBinding(){
        return BindingBuilder
            .bind(insertQueue())
            .to(topicExchange())
            .with(MqConstants.HOTEL_INSERT_KEY);
    }
    
    // 删除队列与交换机绑定
    @Bean
    public Binding deleteQueueBinding(){
        return BindingBuilder
            .bind(deleteQueue())
            .to(topicExchange())
            .with(MqConstants.HOTEL_DELETE_KEY);
    }
}
```

#### 3.2.3 hotel-admin 发送消息

```java
package cn.itcast.hotel.web;

import cn.itcast.hotel.constants.MqConstants;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/hotel")
public class HotelController {
    
    @Autowired
    private RabbitTemplate rabbitTemplate;
    
    @Autowired
    private IHotelService hotelService;
    
    // 新增酒店
    @PostMapping
    public void saveHotel(@RequestBody Hotel hotel){
        hotelService.save(hotel);
        // 发送消息到 MQ
        rabbitTemplate.convertAndSend(
            MqConstants.HOTEL_EXCHANGE,
            MqConstants.HOTEL_INSERT_KEY,
            hotel.getId()  // 传递酒店ID
        );
    }
    
    // 修改酒店
    @PutMapping()
    public void updateById(@RequestBody Hotel hotel){
        if (hotel.getId() == null) {
            throw new InvalidParameterException("id不能为空");
        }
        hotelService.updateById(hotel);
        // 发送消息到 MQ（修改也走insert队列，因为是update操作）
        rabbitTemplate.convertAndSend(
            MqConstants.HOTEL_EXCHANGE,
            MqConstants.HOTEL_INSERT_KEY,
            hotel.getId()
        );
    }
    
    // 删除酒店
    @DeleteMapping("/{id}")
    public void deleteById(@PathVariable("id") Long id) {
        hotelService.removeById(id);
        // 发送消息到 MQ
        rabbitTemplate.convertAndSend(
            MqConstants.HOTEL_EXCHANGE,
            MqConstants.HOTEL_DELETE_KEY,
            id
        );
    }
}
```

## 4. ES 集群 (Cluster)

### 4.1 集群核心概念

**为什么需要集群？**

1. **海量数据存储** - 单机存储量有限
   - 解决方案：分片(Shard)
   - 将索引逻辑拆分为N个分片，分布到多个节点

2. **单点故障** - 单机宕机导致数据丢失
   - 解决方案：副本(Replica)
   - 对分片进行备份，存储到不同节点

**关键术语：**

| 术语 | 定义 | 说明 |
|------|------|------|
| **Cluster(集群)** | 一组拥有相同 cluster name 的节点 | 最小集群=1个节点 |
| **Node(节点)** | 集群中的一个 Elasticsearch 实例 | 每个实例是一个节点 |
| **Shard(分片)** | 索引的逻辑拆分单位 | 数据分散存储，提高容量 |
| **Primary Shard** | 主分片 | 原始数据分片，负责写入 |
| **Replica Shard** | 副本分片 | 主分片的备份副本，负责读取 |

**分片与副本示意：**

```
集群配置: 3个分片 + 1个副本

┌─────────────────────────────────────┐
│         ES 集群(cluster)             │
├──────────────┬──────────────┬────────┤
│   Node-0     │   Node-1     │ Node-2 │
├──────────────┼──────────────┼────────┤
│ Primary-S0   │ Primary-S1   │Primary │
│ Replica-S1   │ Replica-S2   │Replica │
│              │              │-S0     │
└──────────────┴──────────────┴────────┘

每个分片都有1个副本，分布在不同节点
- Node-0: 主S0, 副S1
- Node-1: 主S1, 副S2
- Node-2: 主S2, 副S0
```

### 4.2 集群节点角色划分

**默认情况：** 每个节点同时具有所有角色

**生产集群：** 应按职责分离（避免业务相互干扰）

#### 4.2.1 四种节点角色

```
┌──────────────────────────────────────────────────────────────┐
│                   ES 集群节点角色                              │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Master Node           Data Node        Ingest Node          │
```

### 4.3 脑裂问题 (Split-Brain)

#### 4.3.1 脑裂产生原因

```
正常集群:
  Node-1(Master) ←→ Node-2 ←→ Node-3
        (主)           (从)    (从)

网络分区(脑裂):
  Node-1(Master)         Node-2 ←→ Node-3
        (从)              (重新选主)

① 网络故障：Node-1 与 Node-2、3 失联
② 节点失活：Node-2、3 认为 Node-1 宕机，重新选主
③ 多主出现：Node-1 自成集群(1个主)，Node-2、3 产生新主(2个主)
④ 数据分歧：两个集群数据无法同步，造成不一致

网络恢复后：
  Node-1(Master-1)  ←→  Node-2(Master-2) ←→ Node-3
  
集群状态不一致 → 数据丢失风险
```

#### 4.3.2 脑裂解决方案

**需满足条件：** 选票超过 `(eligible节点数 + 1) / 2` 才能当选主

```
3个节点集群:
  选票需求 = (3 + 1) / 2 = 2 票
  
网络分区:
  Node-1: 1票 (不足2票，不当选)
  Node-2、3: 2票 (满足2票，当选主)
  
结果: 集群中只有1个主，无脑裂
```

**配置(ES7.0+ 已默认)：**

```yaml
discovery.zen.minimum_master_nodes: 2  # 对应 3个节点的场景
# 一般规则: (节点数 + 1) / 2
```

### 4.4 集群分布式存储

#### 4.4.1 分片路由原理

**文档到分片的映射：**

```
文档ID通过Hash算法计算应该存到哪个分片

Hash(routing_id) % shard_number = shard_id

routing_id: 默认是文档的 _id
shard_number: 索引的分片数量

示例：
假设 shards=3, 3个节点
  document(id=1) → hash(1) % 3 = 1 → 存到 Shard-1
  document(id=2) → hash(2) % 3 = 2 → 存到 Shard-2
  document(id=3) → hash(3) % 3 = 0 → 存到 Shard-0
```

**⚠️ 重要约束：**

- **索引创建后，分片数不能修改！** (改变 shard_number 会破坏路由)
- 副本数可以动态调整

#### 4.4.2 文档新增完整流程 (Coordinating Node 视角)

```
Client 发送新增请求
         ↓
    [1] 计算路由
    document(id=1) → hash(1) % 3 = 1
    决定存到 Shard-1 (Primary)
         ↓
    [2] 路由到数据节点
    Shard-1 Primary 在 Node-3
    发送请求到 Node-3
         ↓
    [3] 写入主分片
    Node-3 接收文档
    写入本地存储
         ↓
    [4] 同步副本
    Shard-1 Replica 在 Node-1
    异步复制文档到 Node-1
         ↓
    [5] 返回成功
    Coordinating Node 将结果返回给 Client

关键点:
• Coordinating Node: 可以是任意节点
• Primary Shard: 必须在其对应的节点上
• Replica Shard: 可以在任意其他节点
• 写入: 只写 Primary(副本异步复制)
```

---

#### 4.4.3 读写路径对比

| 操作 | 路径 | 说明 |
|------|------|------|
| **写(Create/Update)** | Coordinating → Primary Shard → Replica(异步) | 先写主后写副 |
| **读(Get/Search)** | Coordinating → Primary 或 Replica (轮询) | 读任意即可，负载均衡 |
| **删除(Delete)** | Coordinating → Primary Shard → Replica(异步) | 同新增流程 |

### 4.5 集群分布式查询

#### 4.5.1 查询两阶段模式 (Query + Fetch)

```
用户发送搜索请求(keyword="酒店")
         ↓
┌─────────────────────────────────────────────┐
│        PHASE-1: 分散阶段 (Scatter)           │
├─────────────────────────────────────────────┤
│ Coordinating Node 将请求分发到所有分片      │
│ (包括 Primary 和 Replica)                   │
│                                              │
│  分布式查询请求发送到:                      │
│  • Shard-0 (Node-1)   → 符合条件文档ID列表 │
│  • Shard-1 (Node-2)   → 符合条件文档ID列表 │
│  • Shard-2 (Node-3)   → 符合条件文档ID列表 │
│                                              │
│  每个分片返回:                               │
│  - 符合条件的文档ID                          │
│  - 排序字段值(如 score)                      │
│  - 分页偏移(from, size)                      │
│                                              │
└─────────────────────────────────────────────┘
         ↓
    结果汇聚排序
    Coordinating Node 合并结果，按score降序
    获取 top-N 文档ID
         ↓
┌─────────────────────────────────────────────┐
│        PHASE-2: 聚集阶段 (Gather)            │
├─────────────────────────────────────────────┤
│ 根据 top-N 文档ID获取完整文档                │
│ 从对应分片拉取完整数据(包含所有字段)        │
│                                              │
│  再次请求到:                                 │
│  • Shard-0: 获取 doc_id_A, doc_id_C       │
│  • Shard-1: 获取 doc_id_D                 │
│  • Shard-2: 获取 doc_id_B                 │
│                                              │
│ 返回最终结果给 Client                       │
│                                              │
└─────────────────────────────────────────────┘
         ↓
    返回结果给用户
    包含: 总命中数、具体文档(含所有字段)
```

**性能特点：**

- Phase-1 (Query): 快速(只需返回ID和score)
- Phase-2 (Fetch): 较慢(需传输完整文档)
- 如果返回数据量大，Phase-2 可能成为性能瓶颈

### 4.6 集群故障转移 (Failover)

#### 4.6.1 故障转移完整流程

```
初始集群状态:
┌──────────┬──────────┬──────────┐
│ Node-1   │ Node-2   │ Node-3   │
│ [Master] │ [Slave]  │ [Slave]  │
├──────────┼──────────┼──────────┤
│Primary-S0│ Replica  │ Replica  │
│Replica-S1│Primary-S1│ Replica  │
│          │          │Primary-S2│
│          │Replica-S2│Replica-S0│
└──────────┴──────────┴──────────┘

[故障发生]
Node-1 突然宕机 → 无法访问
         ↓
Master election (重新选举主节点)
Node-2 和 Node-3 检测到 Node-1 失联
进行选举: 选票 (2 > (3+1)/2 = 2)
Node-2 当选为新主节点
         ↓
故障转移 (Failover - 数据迁移)
新主(Node-2) 检测到:
  ✗ Shard-0 没有副本(原副本在 Node-1, 已离线)
  ✗ Shard-2 没有副本(原副本在 Node-1, 已离线)
        ↓
启动分片重新分配:
  • Shard-0: 从 Node-2 迁移到 Node-3
    (Node-1 的 Replica-S0 升级为新的 Primary-S0)
  • Shard-2: 从 Node-3 迁移到 Node-2
    (创建新的 Replica-S2)
        ↓
新状态:
┌──────────┬──────────┬──────────┐
│ Node-1   │ Node-2   │ Node-3   │
│[离线]    │[Master]  │          │
├──────────┼──────────┼──────────┤
│ -        │Primary-S0│Primary-S2│
│ -        │Primary-S1│Replica-S0│
│ -        │Replica-S2│Replica-S1│
└──────────┴──────────┴──────────┘

数据无丢失，集群继续服务
```

#### 4.6.2 故障转移关键机制

| 阶段 | 操作 | 参与者 | 时间 |
|------|------|--------|------|
| **检测** | Master 监控节点心跳 | Master | 实时 |
| **选举** | 失主后重新选举 | 其他节点 | 秒级 |
| **转移** | 分片从故障节点迁出 | Master 指挥 | 分钟级 |
| **恢复** | 新增副本恢复 | 数据节点 | 数分钟~ |

## 5. 核心流程图总结

### 5.1 文档写入完整流程

```
┌──────────────────────────────────────────────────────────────┐
│              ES 文档写入完整流程 (Write Path)                 │
└──────────────────────────────────────────────────────────────┘

        Client (应用)
           │ PUT /hotel/_doc/1
           │ {"name": "如家酒店", "price": 200}
           ↓
    ┌─────────────────────┐
    │  Coordinating Node   │ (可选，任意节点)
    │  • 路由计算          │ hash(doc_id) % shard_num
    │  • 负载均衡          │ → 确定 target_shard
    └──────────┬──────────┘
               ↓
    ┌─────────────────────────────┐
    │ Primary Shard Write Path     │
    │ (主分片所在节点)             │
    │                              │
    │ [1] 写入 Translog           │ (磁盘预写日志，保障可靠性)
    │     └→ 单条日志记录          │
    │                              │
    │ [2] 写入 Memory Buffer       │ (内存缓冲)
    │     └→ 文档存入内存索引       │
    │                              │
    │ [3] Refresh (近实时)         │ (默认每1秒)
    │     Buffer → Segment         │
    │     └→ 创建一个新Segment     │
    │     └→ 文档可被搜索          │
    │                              │
    │ [4] Flush (持久化)           │ (默认每30秒或1GB)
    │     Segment → 磁盘           │
    │     Translog 清空            │
    │                              │
    └────────────┬────────────────┘
                 ↓
    ┌─────────────────────────────┐
    │ 副本 Replica Shard          │ (异步复制)
    │ • 接收主分片的 Segment       │
    │ • 写入本地内存和磁盘         │
    │ • 返回 ack 给主分片         │
    └─────────────┬───────────────┘
                  ↓
    ┌──────────────────────────┐
    │  返回响应 (Success/Fail)   │
    │  给 Coordinating Node      │
    └───────────┬────────────────┘
                ↓
         Client 收到结果

关键时间点:
├─ Translog写入 (毫秒级): 文档已持久化，故障恢复可用
├─ Buffer写入 (毫秒级): 文档在内存
├─ Refresh (1秒): 文档可被搜索(近实时)
├─ Flush (30秒/1GB): Translog清空，恢复更快
└─ 副本同步 (异步): 不阻塞写入返回

ES 特性:
✓ 异步副本: 主分片不等待副本 ack，即可返回成功
✓ 近实时: 1秒内文档可被搜索 (refresh频率)
✓ 高可靠: Translog保证故障恢复
```

```
┌────────────┬────────────┬────────────┐
│ Node-1     │ Node-2     │ Node-3     │
├────────────┼────────────┼────────────┤
│Primary-S0  │Primary-S1  │Primary-S2  │
│Replica-S1  │Replica-S2  │Replica-S0  │
└────────────┴────────────┴────────────┘

分配规则:
1. 主分片均匀分布在所有节点
2. 副本不能与主分片在同一节点
3. 多副本时在不同节点轮转
4. 保证数据高可用

故障场景:

[Node-1 宕机]
                ↓
缺失分片:
  ✗ Primary-S0 无法访问 (但 Replica-S0 在 Node-3)
  ✗ Replica-S1 无法访问 (但 Primary-S1 在 Node-2)

Master 触发重新分配:
┌────────────┬────────────┬────────────┐
│ OFFLINE    │ Node-2     │ Node-3     │
├────────────┼────────────┼────────────┤
│            │Primary-S1  │Primary-S2  │
│            │Replica-S0  │Replica-S1* │
│            │            │(新增)      │
└────────────┴────────────┴────────────┘

* Replica-S0 原本在 Node-3，现升级为 Primary-S0
* 新建 Replica-S0 在 Node-2 (替代故障的 Replica-S1)

分片状态转变:
UNASSIGNED → INITIALIZING → STARTED
  (未分配)    (初始化中)    (已就绪)
```

## 6. 易混淆点详解

### 6.1 Refresh vs Flush

| 维度 | Refresh | Flush |
|------|---------|-------|
| **目的** | 使文档可被搜索 | 持久化到磁盘 |
| **操作** | Memory Buffer → New Segment | Segment → 磁盘文件 |
| **频率** | 1秒(默认) | 30秒或1GB(默认) |
| **Translog** | 不清空 | 清空 |
| **故障恢复** | 数据可能丢失 (Translog恢复) | 安全，数据不丢失 |
| **性能** | 频繁，较高成本 | 较少，较低成本 |
| **配置** | `refresh_interval: 1s` | `flush_threshold_size: 1gb` |

**流程关系：**

```
文档写入流程:
Memory Buffer
    ↓ [Refresh 1秒]
Segment (可搜索)
    ↓
Segment + Translog
    ↓ [Flush 30秒或1GB]
Disk (安全存储)
    ↓
清空 Translog
```

### 6.2 Primary Shard vs Replica Shard 写入路径

| 维度 | Primary (主) | Replica (副) |
|------|------------|-----------|
| **写入** | ✓ 接收写请求 | ✗ 不接收写请求 |
| **读取** | ✓ 可读 | ✓ 可读 |
| **同步** | 主动发送给副本 | 被动接收主发送的副本 |
| **故障** | 宕机后副本升级为主 | 宕机无影响，创建新副本 |
| **返回** | 不等待副本 ack | 返回前不影响主 |
| **数据一致** | 必须持有最新数据 | 可能延迟(异步) |

**写入流程对比：**

```
客户端写入:
    ↓
Coordinating Node 计算路由
    ↓
┌─────────────────────┐
│ Primary Shard 写入  │
│ • Translog 记录    │
│ • Memory Buffer    │
│ • 返回成功         │
│ • (同时异步同步副本)│
└─────────────────────┘
    ↓ (异步，不阻塞)
┌─────────────────────┐
│ Replica Shard 写入  │
│ • 接收数据          │
│ • 写入本地          │
│ • 返回 ack 给主    │
└─────────────────────┘

✓ 异步副本: 主分片不等待副本完成，立即返回成功
✓ 特点: 写入快，但可能副本延迟
```

### 6.3 分片数 vs 副本数

| 维度 | 分片数 | 副本数 |
|------|--------|--------|
| **定义** | 索引逻辑拆分单位 | 分片的备份数量 |
| **创建** | 索引创建时指定 | 创建时指定，创建后可调整 |
| **修改** | ❌ **不能修改** | ✓ 可随时调整 |
| **影响** | 影响路由算法 | 不影响路由 |
| **作用** | 提高容量、并发性能 | 提高可用性、读性能 |
| **成本** | 增加分片数 = 增加磁盘占用 | 增加副本数 = 磁盘占用翻倍 |
| **查询** | 查询所有分片(Phase-1多) | 查询任意副本(负载均衡) |

**规划建议：**

```
分片数规划:
• 小集群(1-3节点): 3个分片
• 中集群(3-10节点): 节点数个分片
• 大集群(10+节点): 根据数据量分配

副本数规划:
• 开发环境: 0(不需要高可用)
• 测试环境: 1(基本保障)
• 生产环境: 1-2(高可用)

示例:
生产环境, 5个节点, 500GB数据
→ number_of_shards: 5
→ number_of_replicas: 1
→ 总存储: 500GB × 2 = 1TB
```

### 6.4 Translog 持久化时机

| 操作 | Translog 状态 | 说明 |
|------|-------------|------|
| **文档写入** | 立即持久化 | 每条写操作记录到磁盘日志 |
| **Refresh** | 保留 | Buffer 清空，但 Translog 继续积累 |
| **Flush** | 清空 | Segment 持久化后，Translog 清空 |
| **故障恢复** | 重放 | 重启后重放 Translog 中未 Flush 的操作 |

**Translog 工作流程：**

```
文档写入
    ↓
┌─────────────────────┐
│ 写入 Translog(磁盘) │ ← 持久化
│ 写入 Memory Buffer  │
└─────────────────────┘
    ↓ (1秒后)
[Refresh]
    ↓
┌─────────────────────┐
│ Memory Buffer      │
│ → New Segment      │ (内存)
│ Translog 保留      │ (磁盘，继续记录)
│ 文档可搜索         │
└─────────────────────┘
    ↓ (30秒或1GB后)
[Flush]
    ↓
┌─────────────────────┐
│ Segment 持久化      │ → 磁盘文件
│ Translog 清空       │
└─────────────────────┘
    ↓
┌─────────────────────┐
│ 故障情况:           │
│ 在 Refresh 和 Flush│
│ 之间宕机            │
│ Translog 还保留着  │
│ → 重启后重放恢复   │
└─────────────────────┘
```

### 6.6 Query vs Search_Analyzer

| 维度 | analyzer | search_analyzer |
|------|----------|-----------------|
| **使用时机** | 创建索引、写入文档时 | 执行搜索查询时 |
| **作用** | 如何切割和处理文本 | 用户输入的搜索词处理 |
| **应用场景** | 拼音+中文分词(写入) | 仅IK分词(搜索) |
| **防止误匹配** | ✗ 可能导致同音字混淆 | ✓ 用不同的分词器避免 |

**正确配置示例：**

```json
"name": {
  "type": "text",
  "analyzer": "text_analyzer",        // 写入:拼音+中文
  "search_analyzer": "ik_smart"       // 搜索:仅IK(不拼音)
}

// 搜索时使用 search_analyzer
GET /hotel/_search
{
  "query": {
    "match": {
      "name": "狮子"  // 用 ik_smart 分词，而不是 text_analyzer
    }
  }
}
```

## 9. 常见问题 FAQ

**Q1: 为什么创建索引后分片数不能修改？**

A: 分片数影响路由算法 hash(id) % shard_num。修改分片数会导致文档路由错误。如需修改，只能重建索引并重新导入数据。

**Q2: 副本是否立即同步？**

A: 否，副本是异步同步的。主分片成功写入后立即返回，副本在后台异步复制。故障恢复时由 Translog 保证可靠性。

**Q3: 搜索时为什么 search_analyzer 不用拼音分词器？**

A: 避免同音字混淆。如"狮子"和"虱子"都会被拼音分词为"s"开头，造成不精确。搜索时使用 ik_smart 保证精确性。

**Q4: 集群脑裂何时发生？**

A: Master 与其他节点网络隔离时。如果选票规则不当，可能出现两个 Master，导致数据分歧。

**Q5: Flush 与 Refresh 的区别是什么？**

A: 
- Refresh (1秒): Buffer → Segment，文档变可搜索，但未持久化
- Flush (30秒/1GB): Segment → 磁盘，数据安全持久化，Translog清空

**Q6: 一个分片的副本能有多少个？**

A: 理论上无限，但实际受节点数限制。例如 3 个节点，最多 2 个副本(主+2副=3个副本总共分布在3个节点)。

**Q7: 如何处理数据同步延迟？**

A: 
- 提高 refresh_interval 频率
- 关键业务使用同步调用方案
- 使用 Translog 保证恢复可靠性
