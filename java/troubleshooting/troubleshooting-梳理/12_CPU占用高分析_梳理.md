# 12. CPU 占用高分析 - 知识梳理

## 第一部分：知识点章节化

### 1. 资源占用分析视角

#### 1.1 分析思路：自底向上逐步细分
资源占用高问题应采用**自底向上**的分析方法，逐步细分资源占用，找到问题根因。

对于 CPU 高占用问题，分析链路为：
- **用户态 vs 内核态**：CPU 占用主要来自哪个模式？
- **哪个进程**占用 CPU 最多？
- **哪个线程**在该进程中占用 CPU 最多？
- **哪个调用栈**在该线程中占用 CPU 最多？
- **哪个请求数据**（如 SQL、URL）占用 CPU 最多？

#### 1.2 关键词汇
调用栈、请求数据、内核线程、flush 线程、GC、线程、业务代码、SQL、中断、系统调用、MySQL 进程、Java 进程、用户态、系统态、操作系统、内存、CPU、磁盘、网络、硬件资源。

#### 1.3 特殊说明
- 对于业务系统，一般找到具体调用栈即可排查问题
- 对于 MySQL、Nginx 等系统，由于各种请求的调用栈大致相同，需进一步细化到具体请求数据（SQL、URL）
- 使用 perf、BCC 等内核级工具可直接采集包含用户态和内核态的完整调用栈

### 2. CPU 使用率详解

#### 2.1 各种 CPU 使用率指标
| 指标 | 说明 |
|-----|------|
| **us** | 非 niced 进程花费的 CPU 时间占比（用户态进程） |
| **ni** | niced 进程花费的 CPU 时间占比（用户态，低优先级进程） |
| **sy** | 内核进程花费的 CPU 时间占比（内核态） |
| **id** | 内核空闲进程花费的 CPU 时间占比（空闲，不含磁盘 IO 等待） |
| **wa** | 等待磁盘 IO 完成花费的 CPU 时间占比（IO 等待） |
| **hi** | 处理硬件中断花费的 CPU 时间占比（硬中断） |
| **si** | 处理软件中断花费的 CPU 时间占比（软中断） |
| **st** | 被其它虚拟机偷取的 CPU 时间占比（虚拟化环境） |

#### 2.2 用户态 CPU 使用率（us + ni）
**us 指标**：非 niced 进程的 CPU 时间占比
**ni 指标**：niced 进程的 CPU 时间占比

Linux 进程优先级体系：
- **初始优先级（NI 列）**：表示进程的初始优先级，数值越小优先级越高，可通过 `renice` 调整
- **当前优先级（PR 列）**：表示进程的当前优先级，默认 PR = NI + 20
  - Linux 调度器可能根据需要动态调整进程的当前优先级

#### 2.3 内核态 CPU 使用率（sy + hi + si）

**系统调用（syscall）**：
- 由用户空间程序触发，请求操作系统服务
- 示例：访问磁盘（open/read/write）、网络（socket/recvfrom/sendto）等
- 内核接收后切换到内核态执行处理逻辑

**中断**：
- 计算机系统在执行程序过程中，由紧急事件或外部设备请求暂时中止当前程序
- 处理完后返回被中断位置继续执行原程序
- 示例：磁盘中断、网络中断

中断分为两部分处理：
- **硬中断**：由硬件直接触发，执行过程中需禁用中断，必须快速执行以避免中断信号丢失
- **软中断**：为尽快执行完硬中断，Linux 设计了软中断来处理硬中断中可延迟的部分

**内核线程**：
- Linux 内核管理一批后台线程执行特定任务
- 示例：kswapd（内存回收）、ksoftirqd（软中断处理）、kworker（通用工作队列）
- 一般以 k 开头命名

**内核态 CPU 占用来源**：
- sy：由系统调用、缺页异常、内核线程占用
- hi：硬中断处理占用
- si：软中断处理占用
- st：虚拟机时间偷取

#### 2.4 空闲 CPU 使用率（id + wa）

**id 指标**：空闲 CPU 时间占比（不含磁盘 IO 等待）
**wa 指标**：等待磁盘 IO 完成的 CPU 时间占比

两者均代表 CPU 空闲，区别在于：
- **id**：CPU 处于真正空闲状态
- **wa**：CPU 空闲，但存在线程阻塞在磁盘 IO 上等待

Linux 设计 wa 指标的目的：便于判断 CPU 空闲较多时，是否由磁盘阻塞导致

#### 2.5 快速识别方法
通过 `top` 命令即可识别：
- CPU 占用是进程（用户态，关注 %CPU、us）
- 还是内核态占用高（sy、hi、si）
- 还是 CPU 空闲（id、wa）

### 3. 进程 CPU 高占用分析

#### 3.1 分析层级
1. **什么进程**占用 CPU 高？
2. **什么线程**占用 CPU 高？
3. **哪个调用栈**占用 CPU 高？
4. **哪个请求数据**占用 CPU 高？

#### 3.2 Java 进程 CPU 高分析链路

**第一步：识别高 CPU 进程**
```bash
top
# 查看 %CPU 列，发现高占用进程 PID
```

**第二步：识别进程内高 CPU 线程**
```bash
top -H -p <PID>
# 查看 %CPU 列，发现高占用线程 TID
```

**第三步：获取线程调用栈**
```bash
jstack <PID> | grep <TID_in_hex>
# 查看该线程的完整调用栈
```

**第四步（可选）：快速定位调用栈**

如果问题代码执行时间较短（如 280ms），手工操作可能错过问题代码，此时可使用：
```bash
# Arthas thread -n 命令（合并线程检测与栈采集）
thread -n 4
# 获取 CPU 占用前 4 个线程的调用栈
```

#### 3.3 Java 火焰图分析

**Arthas profiler 命令**：
```bash
profiler start
# ... 运行业务 ...
profiler stop
profiler dumphtml
```

**原理**：
- 定时从 CPU 栈寄存器采集正在 CPU 上运行的线程栈
- 占用 CPU 越多的调用栈，被采集到的次数越多
- 火焰图中越宽的栈，执行时间越长，需重点关注

**优点**：
- 跳过找进程、找线程的步骤
- 一步到位定位具体调用栈
- 特别适合性能优化场景

#### 3.4 非 Java 进程 CPU 高分析

**工具选择**：
- perf record
- BCC 工具集中的 profile 命令

**分析流程**（以 perf 举例）：
```bash
perf record -F 99 -p <PID> -- sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

**火焰图生成**：
- 下载地址：https://github.com/brendangregg/FlameGraph
- 生成的火焰图直观展示调用栈占用情况

#### 3.5 MySQL 进程 CPU 高分析示例

**情景**：从火焰图观察到 row_search_mvcc 函数栈较宽

**分析步骤**：
1. 通过搜索得知 row_search_mvcc 用于扫描 SQL 的行数据
2. 调用栈上无法直接看出具体问题
3. 需进一步细化到具体 SQL 级别

**问题发现**：
- 慢查询日志可能遗漏扫描数据量大但单个执行不慢的 SQL
- 当量大时，这类 SQL 也会导致 CPU 高

**解决方案**：
- 使用函数追踪工具（如 bpftrace）追踪具体 SQL
- 通过行数扫描与耗时关联分析

**bpftrace 追踪示例**：
```bash
# 追踪 MySQL 中 row_search_mvcc 的扫描行数
bpftrace -e 'tracepoint:...scan_rows...'
```

**发现规律**：
- 扫描行数增大 → 耗时增长
- 需要优化查询条件或建立合适索引

#### 3.6 四层剖析总结
| 层级 | 工具 | 说明 |
|-----|------|------|
| 进程 | top | 快速定位高 CPU 进程 |
| 线程 | top -H -p PID / jstack | 定位进程内高 CPU 线程 |
| 调用栈 | jstack / arthas thread -n / perf / BCC | 定位调用栈 |
| 请求数据 | bpftrace / 慢查询日志 | 细化到 SQL 或具体请求 |

### 4. 系统态 CPU 高占用分析

#### 4.1 系统态 CPU 占用三大来源
系统态 CPU 占用（sy + hi + si）主要由以下三部分组成：
1. **系统调用**
2. **中断**（硬中断 + 软中断）
3. **内核线程**

#### 4.2 系统调用占用分析

**特点**：
- 由用户进程触发
- 可追踪具体调用来源

**诊断工具**：BCC 工具集的 syscount 命令
```bash
syscount -i 1
# 显示系统调用统计信息及触发进程
```

**分析目标**：
- 找出哪些进程的系统调用最多
- 示例：发现 mysqld 的系统调用次数最多

**优化方向**：
- 减少系统调用次数（如批量 IO）
- 使用更高效的系统调用

#### 4.3 中断占用分析

**快速识别**：
- 通过 `top` 命令查看 hi（硬中断）和 si（软中断）占用比例
- 若 hi + si 较高（如 > 10%），需进一步诊断

**详细诊断工具**：

**方法一：系统文件查看**
```bash
cat /proc/interrupts    # 硬中断统计
cat /proc/softirqs      # 软中断统计
watch -d 'cat /proc/interrupts'  # 动态查看中断次数增长
```

**方法二：irqtop 命令**
```bash
irqtop
# 解析上述文件数据，直观展示中断占用情况
# 可看出：软中断 CPU 占用主要由磁盘与网络引起
```

**方法三：BCC 工具**
```bash
# 硬中断诊断
hardirqs -i 1

# 软中断诊断
softirqs -i 1
```

**常见中断类型**：
- 磁盘中断：通常由高 IO 操作引起
- 网络中断：由高网络流量引起
- 计时器中断：系统时钟相关

#### 4.4 内核线程占用分析

**识别内核线程**：
- 一般以 k 开头命名（如 kworker、kswapd、ksoftirqd）
- 通过 `pidstat` 命令查看内核线程的 %system 占用

**诊断命令**：
```bash
pidstat -u 1 | grep ^k
# 显示以 k 开头的内核线程的 CPU 占用
```

**常见内核线程**：
- **kworker/u257:0+flush-8:0**：文件系统脏页刷新到磁盘
- **kswapd**：内存页面回收
- **ksoftirqd**：软中断处理

**pidstat %system 三大来源**：
1. 系统调用占用
2. 缺页异常占用
3. 内核线程占用

**缺页异常查看**：
```bash
pidstat -r 1
# 使用 -r 选项可查看缺页中断情况
```

#### 4.5 系统态 CPU 占用的火焰图分析

**原理**：采集整个系统（而非单个进程）的调用栈

**命令**：
```bash
# perf 采集
perf record -e cycles:k -F 99 -a sleep 30

# 或 BCC profile
profile -k 30

# 生成火焰图
perf script | stackcollapse-perf.pl | flamegraph.pl -k > syscpu.svg
```

**火焰图分析**：
- 可直观看出系统态 CPU 占用在哪
- 可区分三大来源：
  - 系统调用栈
  - 缺页中断栈
  - 内核线程栈

**示例**：
- 火焰图中宽栈 = 系统调用（如 open/read/write）
- 火焰图中宽栈 = 缺页中断处理
- 火焰图中宽栈 = 内核线程（如 kworker）

### 5. 空闲 CPU 高占用分析

#### 5.1 情况一：id% 使用率高（CPU 真正空闲）

**定义**：CPU 处于真正空闲状态，无任务运行

**原因分析**（两种可能）：

**原因一：系统流量不足**
- 没有业务流量进入系统
- 或由于网络丢包导致流量未进系统

**具体检查项**：
- TCP 连接队列配置过小 → 导致连接丢弃
- Socket 接收缓存配置过小 → 导致包丢弃

**优化方向**：增大相关队列或缓存大小

**原因二：线程全部被阻塞**
- 所有线程都被阻塞（磁盘 IO、网络 IO 等）
- 无线程占用 CPU 资源
- 请求的耗时会明显增大

**诊断方向**：参考《耗时高分析》相关章节

#### 5.2 情况二：wa% 使用率高（CPU 因 IO 等待空闲）

**定义**：CPU 处于空闲状态，但存在线程阻塞在磁盘 IO 上

**原因分析**（两种可能）：

**原因一：磁盘性能问题**
- 磁盘 IO 响应缓慢
- 应用频繁等待磁盘操作完成

**诊断工具**：
```bash
iostat -x 1
# 查看 %await 等指标，判断磁盘是否有明显性能退化

ioping /dev/sda
# 检测磁盘 IO 性能
```

**优化方向**：
- 检查磁盘硬件状态
- 优化磁盘 IO 模式（如预读、批量操作）
- 升级磁盘硬件

**原因二：网络存储性能问题**
- 使用 NFS 等网络文件系统
- 由于网络较慢，wa% 较高可能属正常现象

**优化方向**：
- 改进网络存储配置
- 考虑本地缓存方案
- 评估是否迁移到本地存储

#### 5.3 快速判断表
| CPU 指标 | 含义 | 可能原因 |
|---------|------|--------|
| id% 高 | CPU 真正空闲 | 流量不足 / 线程全部阻塞 |
| wa% 高 | CPU 因 IO 等待 | 磁盘性能差 / 网络存储慢 |
| id% + wa% 都高 | CPU 大量空闲 | 系统负载不高或应用存在阻塞 |

### 6. CPU 调优方案

#### 6.1 CPU 调优工具

| 调优工具 | 作用 | 示例 |
|---------|------|------|
| **超线程控制** | 关闭/开启 CPU 超线程 | `echo off > /sys/devices/system/cpu/smt/control` |
| **查看超线程状态** | 检查超线程是否开启 | `cat /sys/devices/system/cpu/smt/active`（1=开启） |
| **cpupower** | 调整 CPU 能耗状态 | `cpupower frequency-set -f 3.5G` |
| **taskset** | 进程绑核，提升 CPU 缓存命中率 | `taskset -pc 1-2 13333` |
| **renice** | 调整进程优先级 | `renice -n -5 -p <PID>` |
| **irqbalance** | 将中断均衡到各 CPU 上 | 启用后自动均衡 |

**关键概念**：
- **进程绑核**原理：进程固定在某些 CPU 核心上运行，提高 CPU 缓存命中率，进而提升 IPC（每周期指令数），最终提升性能
- **超线程**：物理核的虚拟化，可提升吞吐量但单线程性能无改善
- **中断均衡**：防止所有中断集中在某个 CPU，影响其它任务

#### 6.2 JVM JIT 调优

**JIT 编译基本概念**：
- JVM JIT 将 Java 字节码即时编译成可直接执行的二进制指令
- 加快代码执行，是 JVM 性能优化的重要环节

**常见 JIT 调优参数**：

| 参数 | 说明 | 使用场景 |
|-----|------|---------|
| **-XX:+TieredCompilation** | 启用分层编译（JDK8+ 默认开启）<br/>启动时用 C1 编译器，热点代码用 C2 | 平衡启动速度和运行效率 |
| **-XX:InitialCodeCacheSize** | 初始 Code Cache 大小 | Code Cache 频繁满的系统 |
| **-XX:ReservedCodeCacheSize** | 最大 Code Cache 大小 | Code Cache 频繁满的系统 |
| **-XX:+UseCodeCacheFlushing** | Code Cache 满关闭 JIT 编译前，是否回收 | 避免 JIT 完全关闭 |
| **-XX:CICompilerCount** | JIT 编译线程数 | CPU 核数充足时，考虑增大 |
| **-XX:+PreserveFramePointer** | 保留帧指针（frame pointer） | 使用 perf/BCC 分析 Java 性能 |

**Code Cache 满的影响**：
- 新的热点代码无法编译
- JIT 编译关闭，代码回到字节码执行
- 性能明显下降

**PreserveFramePointer 作用**：
- 保留栈帧指针便于遍历调用栈
- 使 perf、BCC 等工具能准确采集 Java 调用栈

#### 6.3 代码优化

**优化本质**：使用更低时间复杂度的算法或更高效的数据结构

**常见优化方向**：

| 优化方向 | 具体方法 | 效果 |
|---------|---------|------|
| **数据结构优化** | List.contains → HashMap.containsKey | O(n) → O(1) |
| **初始化优化** | 指定 List 初始大小 | 减少动态扩容次数 |
| **缓存利用** | 缓存计算结果，避免重复计算 | 显著提升性能 |
| **正则优化** | `id:.*,name:.*` → `id:[^,]*,name:[^,]*` | 减少回溯，加快匹配 |
| **计算优化** | long 替代 BigDecimal | 提升精度计算性能 |
| **序列化优化** | 使用高性能序列化库 | 减少 CPU 占用 |
| **零拷贝** | 使用内存映射、直接缓冲区 | 减少数据复制 |
| **SIMD 指令** | 利用向量化指令 | 并行处理多个数据 |
| **SQL 优化** | 全表扫描 → 索引扫描 | 穷举 → 树搜索 |
| **缓存友好** | 使用数组/ArrayList 而非 LinkedList | 提升 CPU 缓存命中率 |

**优化案例**：
- 全表扫描问题：建立合适的索引，将算法复杂度从 O(n) 降低到 O(log n)
- 正则回溯问题：使用原子性字符类，减少正则引擎的回溯尝试次数
- 缓存命中问题：ArrayList（连续内存）vs LinkedList（离散内存）

## 附录：关键概念补充

### A1. CPU 占用率的本质
CPU 占用率 = 用户态时间占比 + 内核态时间占比
- 用户态：应用代码执行
- 内核态：系统调用、中断、缺页异常、内核线程等

### A2. 空闲率的妙用
- id% 高且 wa% 低：系统确实空闲
- id% 高且 wa% 高：系统被磁盘阻塞
- id% 低且 wa% 高：磁盘繁忙
- id% 低且 wa% 低：系统满载

### A3. 火焰图如何解读
- **横轴**：调用栈的宽度（采样次数），宽度越宽占用 CPU 时间越长
- **纵轴**：调用栈的深度（函数嵌套层级）
- **颜色**：仅用于区分不同函数，无实际含义
- **最宽的栈**：需重点优化的地方

### A4. 为什么需要四层分析
1. **进程层**：识别问题来源进程
2. **线程层**：定位高占用线程
3. **调用栈层**：精确到函数级别
4. **请求数据层**：针对 MySQL/Nginx 等，找出具体 SQL/URL

### A5. 工具选择建议
- **快速诊断**：top、pidstat、iostat
- **深度分析**：perf、BCC、Arthas
- **即时编译**：Arthas（Java）、flame graphs（通用）
