## 核心知识框架

### 1.1 问题现状分析

**常见困境**：
- 遇到程序问题时，缺少体系化认识与经验导致无从下手
- 有怀疑的点但不知如何确认
- 诊断工具繁多，难以判断当前应该使用哪个工具

**解决方向**：建立系统化、分层级的故障排查方法论

---

### 1.2 软件技术栈概览

**涉及的技术领域** (按层级分类)：

| 层级 | 技术工具/语言 | 关键概念 |
|------|-------------|---------|
| **应用层** | Java、JVM | 进程、线程、堆内存 |
| **框架层** | Arthas | 在线诊断、动态追踪 |
| **代码层** | GDB、Strace | 代码执行、系统调用 |
| **系统层** | Perf、BCC、BPFtrace | 性能分析、内核事件 |
| **网络层** | TCPdump、Ngrep、Netstat | 数据包、连接状态 |
| **操作系统** | Top、Free、Iostat、Iftop | CPU、内存、磁盘、网络 |
| **硬件资源** | ps、基础工具 | 进程、资源占用 |

## 故障排查工作流

### 2.1 三步骤工作法

```
第一步：看日志
    ↓
第二步：检查资源占用
    ↓
第三步：使用诊断工具逐层定位
```

#### 第一步：看日志 (最重要)
- **原则**：往往各种高级命令分析半天，最后发现日志已经反映出问题原因
- **最佳实践**：从日志入手能快速定位大多数问题

#### 第二步：检查资源占用
- **检查维度**：CPU、内存、磁盘、网络等
- **作用**：
  - 在资源不足的情况下，任何性能问题都是自然结果
  - 帮助确定排查视角（自下而上 vs 自上而下）

#### 第三步：使用诊断工具定位
- **方法**：根据问题线索，使用合适工具逐步深入
- **示例**：接口响应慢 → 使用 Arthas trace 命令逐层检查各层耗时

## 二种分析视角

### 3.1 视角一：资源分析视角（自底向上）

**分析起点**：硬件资源使用率

**分析链条**：
```
发现问题：CPU 资源占用高
    ↓
第一步：什么进程占用 CPU 多？
    ↓
第二步：什么线程占用 CPU 多？
    ↓
第三步：什么代码占用 CPU 多？
    ↓
根因：找到具体的代码热点
```

**核心工具**：
- jstack：线程堆栈分析
- jmap：内存分析
- Java、Arthas、GDB、JVM、Strace、Perf、BCC、BPFtrace
- 操作系统工具：Top、Free、Iostat、Iftop

**适用场景**：
- 系统整体资源占用率高
- 需要找到资源消耗的具体代码路径

---

### 3.2 视角二：负载分析视角（自顶向下）

**分析起点**：应用层指标

**分析链条**：
```
发现问题：接口响应耗时高
    ↓
第一步：Controller 层耗时高吗？
    ↓
第二步：Mapper 层处理耗时高吗？
    ↓
第三步：SQL 执行耗时高吗？
    ↓
根因：找到具体的瓶颈层级
```

**核心工具**：
- jstack：线程堆栈分析
- jmap：内存分析
- Java、Arthas、GDB、JVM、Strace、Perf、BCC、BPFtrace
- 操作系统工具：Top、Free、Iostat、Iftop

**适用场景**：
- 应用层接口性能问题
- 需要按业务链条逐层分解耗时

## 诊断工具分类体系

### 4.1 二维分类法

诊断工具按两个维度分类：

**维度一：运行态**
- 用户态工具
- 内核态工具

**维度二：功能类型**
- 指标类
- 剖析类
- 追踪类

---

### 4.2 详细分类表

#### 指标类工具（收集、展示基础指标）

| 工具 | 运行态 | 作用 | 说明 |
|------|------|-----|------|
| ps | 用户态 | 列举进程 | - |
| netstat | 用户态 | 网络连接状态 | - |
| top | 内核态 | CPU 占用概览 | 只能反映一些概况指标 |
| free | 内核态 | 内存占用概览 | 只能反映一些概况指标 |
| iostat | 内核态 | 磁盘 I/O 概览 | 只能反映一些概况指标 |
| iftop | 内核态 | 网络流量概览 | 只能反映一些概况指标 |
| sar | 内核态 | 系统活动报告 | - |
| arthas | 用户态 | Java 应用诊断 | 多功能诊断工具 |

---

#### 剖析类工具（分析程序内部状态）

| 工具 | 运行态 | 作用 | 说明 |
|------|------|-----|------|
| jstack | 用户态 | 线程堆栈分析 | 能查看线程状态、调用栈 |
| jmap | 用户态 | 内存分析 | 能查看对象分布、堆内存 |
| arthas | 用户态 | Java 应用剖析 | 能查看类加载、内存等 |
| gdb | 用户态 | 程序调试 | 用户态下的代码级调试 |
| perf | 内核态 | 性能剖析 | 采样分析、火焰图 |
| bcc | 内核态 | 内核事件分析 | eBPF 工具集 |

---

#### 追踪类工具（追踪程序执行细节）

| 工具 | 运行态 | 作用 | 说明 |
|------|------|-----|------|
| arthas | 用户态 | 方法调用追踪 | trace 命令可逐层追踪 |
| gdb | 用户态 | 代码级追踪 | 逐行执行追踪 |
| perf | 内核态 | 系统调用追踪 | 事件级追踪 |
| bcc | 内核态 | eBPF 追踪 | 灵活的内核事件追踪 |
| bpftrace | 内核态 | 高级 eBPF 追踪 | 更易用的 eBPF 语言 |
| tcpdump | 内核态 | 网络数据包追踪 | 完整的数据包内容 |

## 常规排查思路

### 5.1 排查三部曲

```
问题出现
    ↓
【第一步】看日志
    · 查看应用日志、系统日志
    · 往往能快速定位根因
    · 如果日志信息充分，直接解决问题
    ↓
【第二步】检查资源占用
    · Top：整体 CPU/内存
    · Free：内存详情
    · Iostat：磁盘 I/O
    · Iftop：网络流量
    · 判断是否资源不足导致问题
    ↓
【第三步】使用诊断工具
    · 根据资源占用情况，选择分析视角
    · 资源占用高 → 资源分析视角（自下而上）
    · 应用性能差 → 负载分析视角（自上而下）
    · 使用合适的工具逐层定位
    ↓
问题解决
```

### 5.2 分视角的工具选择

**资源分析视角（自下而上）**：
- 前置：Top、Free、Iostat 确认资源占用高
- 工具链：Perf → Jstack → Arthas trace

**负载分析视角（自上而下）**：
- 前置：监控系统确认接口性能差
- 工具链：Arthas trace → 业务日志 → SQL 慢查询

## 原文勘误

### 7.1 硬性错误

**勘误 1**：第 387 行（第 06 章节）
- **原文**："同时，了解资源占用情况，也有助于确定问题排查视角，是基于资源视角自下向上排查，还是负载视角自上而下排查。"
- **分析**：此处逻辑表述有歧义。根据上下文，资源占用**高**时应该选择资源分析视角，而不是绝对的高或低决定视角选择。
- **建议**：改为 "了解资源占用情况有助于确定排查视角：若资源占用高，采用资源分析视角自下而上排查；若资源充足但应用性能差，采用负载分析视角自上而下排查。"

**勘误 2**：第 416-418 行（第 08 章节工具分类表）
- **原文**：表格中 Arthas 同时出现在"用户态-指标类"和"用户态-追踪类"
- **分析**：Arthas 确实具备多功能属性，但在表格中重复出现造成分类混乱。
- **建议**：可在表格下方注明 "Arthas 是多功能工具，支持指标采集、内存剖析、方法追踪等多种功能，不仅限于单一分类"
