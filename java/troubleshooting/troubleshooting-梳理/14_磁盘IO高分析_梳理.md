# 14. 磁盘 IO 高分析

## 1. IO 关键指标

### 1.1 IOPS（Input/Output Operations Per Second）
- **定义**：磁盘每秒完成的操作数（读写请求数）
- **观测命令**：`iostat -dxz 1`
- **含义**：高 IOPS 表示磁盘在频繁处理请求，可能导致响应延迟

### 1.2 吞吐量（Throughput）
- **定义**：磁盘每秒读写数据的字节数（kB/s）
- **计算单位**：kB/s（kilobytes per second）
- **观测方式**：`iostat` 输出的 `kB_read/s` 和 `kB_wrtn/s`
- **影响因素**：数据块大小、顺序/随机 IO 特性

### 1.3 磁盘利用率（%util）
- **定义**：磁盘处理 IO 请求的时间百分比
- **阈值**：>80% 表示磁盘压力较大，可能成为性能瓶颈
- **含义**：不等同于 CPU 繁忙度，高利用率可能伴随较长队列延迟

### 1.4 平均等待时间（await）
- **定义**：IO 请求从提交到完成的平均时间（毫秒）
- **组成**：await = 磁盘服务时间 + 等待队列时间
- **优化目标**：减少 await 能直接改善应用响应时间

### 1.5 平均服务时间（svctm）
- **定义**：磁盘实际处理单个 IO 请求的时间（毫秒）
- **诊断用途**：svctm 高表示磁盘硬件性能有问题；await >> svctm 表示队列等待严重

## 2. 核心诊断工具

### 2.1 iostat
```bash
# 查看磁盘整体 IO 情况
iostat -dxz 1
```
- **-d**：仅显示磁盘统计
- **-x**：显示扩展统计（包括 await、svctm、%util）
- **-z**：跳过无 IO 活动的设备
- **间隔参数**：每秒采集一次数据

**关键输出字段**：
- `r/s`、`w/s`：每秒读写 IOPS
- `kB_read/s`、`kB_wrtn/s`：读写吞吐量
- `r_await`、`w_await`：读写请求平均等待时间
- `%util`：磁盘利用率

### 2.2 pidstat -d
```bash
# 查看进程级磁盘 IO 统计
pidstat -d 1
```
- **功能**：显示每个进程的磁盘 IO 读写情况
- **关键指标**：
  - `kB_rd/s`：进程每秒读 KB
  - `kB_wr/s`：进程每秒写 KB
- **诊断**：快速定位哪个进程是磁盘 IO 消耗大户

### 2.3 iotop
```bash
# 类似 top 的磁盘 IO 监控工具
iotop
```
- **实时性**：动态显示各进程磁盘 IO 排行
- **直观性**：进程、PID、读写速率一目了然

### 2.4 filetop（BCC 工具）
```bash
# 查看进程读写的具体文件
filetop -p `pgrep java`
```
- **功能**：列出指定进程打开的文件及其 IO 操作数
- **诊断**：确定是哪个文件被频繁读写（如日志文件）

### 2.5 stackcount（BCC 工具）
```bash
# 采集内核函数调用栈
stackcount-bpfcc -f vfs_write
```
- **功能**：跟踪内核函数调用链路，显示调用频率
- **用途**：定位非 Java 程序的高 IO 调用源头

### 2.6 Arthas Profiler（Java 程序）
```bash
# Java 程序中采集 CPU 调用栈
profiler start
profiler stop
```
- **优势**：可追踪 Java 应用的 write 操作调用栈
- **诊断**：找到高频 IO 操作的代码位置

### 2.7 ioping
```bash
# 检测磁盘性能指标
ioping /dev/sda
```
- **功能**：测试磁盘 IO 延迟
- **输出**：单次 IO 操作的耗时（类似 ping）
- **诊断**：区分 IO 高是应用原因还是磁盘硬件退化

## 3. Page Cache 的影响

### 3.1 Page Cache 作用
- **缓存机制**：文件系统为频繁访问的数据建立内存缓存
- **读操作加速**：命中缓存的读请求不需访问磁盘，大幅降低 IO
- **写操作优化**：应用写操作先写入 cache，后台异步回写磁盘

### 3.2 缓冲与回写对 IO 的影响
- **减少 IOPS**：多次写合并为一次磁盘写，降低 IO 操作频率
- **提高吞吐量**：批量写操作比零散写性能更优
- **延迟风险**：缓存中的数据断电或宕机可能丢失

### 3.3 观测 Page Cache
```bash
# 查看 cache 内存占用
cat /proc/meminfo | grep -i cache
```
- **Cached**：文件缓存大小
- **Buffers**：块设备缓冲大小
- **宜量**：cache 占用 30-50% 内存较为合理

## 4. 磁盘 IO 高的三层分析框架

### 4.1 第一层：整体诊断（找磁盘）
```
命令：iostat -dxz 1
关注点：
  - %util > 80% → 磁盘成为瓶颈
  - await 远大于 svctm → 队列等待严重
```

### 4.2 第二层：进程诊断（找进程）
```
命令：pidstat -d 1 或 iotop
关注点：
  - 哪个进程的 kB_wr/s 最高
  - 读操作多还是写操作多
```

### 4.3 第三层：文件和调用栈诊断（找代码）
```
命令流程：
  ① filetop -p <PID>       → 确定文件
  ② arthas profiler 或 stackcount → 得到调用栈
  ③ strace -p <PID> -e openat,write → 验证操作
```

## 6. 调优思路

### 6.1 操作系统级调优

#### (1) 调整 IO 优先级
```bash
# 使用 ionice 调整进程的 IO 优先级
ionice -c 3 -p <PID>    # idle 级别（后台 IO）
ionice -c 2 -p <PID>    # best-effort（普通级别）
ionice -c 1 -p <PID>    # realtime（实时级别）
```

#### (2) IO 调度策略
```bash
# 查看/修改 IO 调度器
cat /sys/block/sda/queue/scheduler

# 常见调度器：
#  - noop：最简单，无延迟
#  - deadline：确保截止时间
#  - cfq：公平队列分配
#  - mq-deadline：多队列 deadline
```

#### (3) 预读参数
```bash
# 查看/修改文件系统预读大小
cat /sys/block/sda/queue/read_ahead_kb
echo 256 > /sys/block/sda/queue/read_ahead_kb    # 调整为 256KB
```

### 6.2 应用编码优化

#### (1) 数据缓存
- **目标**：减少对磁盘的直接访问
- **实现**：
  - 内存缓存热点数据（如 Redis）
  - 应用层缓存（HashMap、Cache2k）
  - 数据库缓冲池（Buffer Pool）

#### (2) 增大缓冲区
```java
// 使用更大 Buffer 的 Reader
BufferedReader br = new BufferedReader(new FileReader(file), 8192 * 4);
// 默认 8KB，可改为 32KB 或更大
```

#### (3) 避免随机 IO
- **原理**：磁盘随机 IO 需要寻道时间，顺序 IO 性能优势明显
- **实践**：
  - 数据库采用缓存写 + redo log 顺序写备份策略
  - 批量处理数据而非逐条处理
  - 优化数据库查询避免全表扫描

#### (4) 数据索引
- **作用**：快速定位数据，避免全盘/全表扫描
- **应用**：
  - 文件系统使用 inode 索引
  - 数据库使用 B+ Tree 索引
  - 日志系统使用 offset 索引

#### (5) 日志优化
```java
// 异步日志写入
AsyncAppender asyncAppender = new AsyncAppender();
asyncAppender.addAppender(fileAppender);  // Logback 配置

// 减少日志级别
logback.xml: <root level="WARN"/> 而非 DEBUG
```

## 7. 案例分析：磁盘 IO 高的完整诊断

### 场景
应用运行缓慢，磁盘 IO 占用高达 95%。

### 诊断过程

**第 1 步**：整体诊断
```bash
$ iostat -dxz 1
Device  r/s    w/s   kB_read/s  kB_wrtn/s  r_await  w_await  %util
sda     15     800   120        3200       5        12       95
```
- **发现**：磁盘利用率 95%，写操作 IOPS 远高于读操作

**第 2 步**：进程定位
```bash
$ pidstat -d 1
PID     kB_read/s  kB_wrtn/s
12345   0          2800       # Java 应用写入最高
```

**第 3 步**：文件定位
```bash
$ filetop -p 12345
RW  FILE                    BYTES
W   /var/log/app.log        2800
```

**第 4 步**：调用栈追踪
```bash
# Arthas 采集调用栈
profiler start
# ... 等待 60 秒 ...
profiler stop

# 结果：显示 logback 的 FileAppender.write() 调用最频繁
# 调用树：Thread.run() → Logger.info() → FileAppender.write() → vfs_write()
```

### 根因
日志级别设置过低（DEBUG），导致 logback 频繁写日志。

### 解决方案
1. 修改日志级别为 WARN
2. 配置异步日志写入
3. 增加日志缓冲区大小

### 优化效果
- 磁盘 IO 降低至 20%
- 应用响应时间改善 70%

## 10. 总结

### 核心诊断框架
1. **整体诊断**：用 `iostat -dxz 1` 查看磁盘全局统计，关注 %util、await、svctm
2. **进程定位**：用 `pidstat -d 1` 或 `iotop` 找高 IO 进程
3. **文件定位**：用 `filetop -p <PID>` 确定具体读写的文件
4. **调用栈追踪**：用 `arthas profiler`（Java）或 `stackcount-bpfcc`（其他程序）定位代码
5. **性能确认**：用 `ioping` 检测磁盘硬件是否退化

### 关键优化策略
- **应用层**：缓存、增大缓冲、批量处理、索引、异步写
- **系统层**：调整 IO 调度器、预读参数、进程优先级
- **硬件层**：升级磁盘或改用 SSD

### 预防措施
- 设置合理日志级别（避免频繁 IO）
- 使用异步日志框架
- 定期监控 Page Cache 利用率
- 对关键路径做 IO 优化
