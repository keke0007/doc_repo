## 2. 网络连通性检测

### 2.1 DNS层检测 - dig/nslookup/host

**工具特点**：检测域名解析层连通性

**dig命令用途**：
- 查询DNS解析结果
- 获取解析到的IP地址
- 观察DNS查询耗时

**关键指标**：
- 返回的IP地址正确性
- Query Time：DNS查询耗时（毫秒级）
- 权威应答vs递归应答

**示例解读**：
```
对比预期IP - 判断DNS是否被污染或劫持
耗时 >100ms - DNS解析可能存在问题
```

---

### 2.2 IP层检测 - ping/mtr

#### **ping 命令**

**原理**：ICMP协议，通过Echo-Request/Echo-Reply测试IP连通性

**关键参数**：
- 往返时间（RTT）：Request→Response总耗时
- 丢包率：丢失的数据包百分比
- Min/Max/Avg/Stddev：最小/最大/平均/标准差

**性能指标判断**：
```
RTT < 10ms   ✓ 本地网络
10-50ms      ✓ 同机房
50-100ms     △ 跨地域
> 100ms      ✗ 严重延迟或问题
丢包 > 1%    ✗ 网络质量问题
```

**限制说明**：
- 某些防火墙会禁止ICMP
- ping往返时间 ≠ 单向延迟

#### **mtr 命令**

**原理**：结合ping和traceroute，逐跳检测路由路径

**关键参数**：
- Hop：经过的路由节点序号
- Host：每跳的主机地址
- Loss%：该跳的丢包率
- Avg/Best/Wrst：该跳的平均/最小/最大延迟
- StDev：标准差，波动幅度

**分析要点**：
```
丢包集中在某一跳 → 该跳设备问题
延迟在某跳陡增    → 该跳之后网络质量下降
均匀丢包           → 链路质量整体问题
```

**应用场景**：向运营商反馈网络问题证据

---

### 2.3 TCP层检测 - telnet/nc/hping3

#### **基本原理**
TCP三次握手完成即表示端口连通，由操作系统内核完成，与进程性能无关

#### **hping3 命令**

**用途**：检测特定服务端口是否开放

**关键特性**：
- 基于TCP握手检测
- 测量RTT准确反映网络延迟
- 不涉及应用层，不测试服务功能

**重要提示**：
```
端口连通 ≠ 服务正常运行
端口RTT ≠ 进程处理耗时
TCP握手是内核动作，应用还未参与
```

#### **telnet/nc 命令**

**简单场景**：快速验证端口开放性
- `telnet host port` - 交互式测试
- `nc -zv host port` - 快速连接测试

---

### 2.4 应用层检测 - curl/wget

#### **HTTP协议检测**

**curl 一键诊断**：单条命令覆盖所有层
```
DNS解析 → TCP连接 → HTTP请求 → 响应接收
```

#### **分阶段耗时统计**

**curl 时间分解**：
| 指标 | 含义 | 问题诊断 |
|------|------|---------|
| `time_namelookup` | DNS查询完成时间 | >100ms → DNS问题 |
| `time_connect` | TCP连接建立完成时间 | 大幅增长 → 网络连接问题 |
| `time_starttransfer` | 首字节响应时间 | 增长 → 服务端处理慢 |
| `time_total` | 整体耗时 | 流量下载慢 |

**计算逻辑**：
```
DNS耗时 = time_namelookup
TCP耗时 = time_connect - time_namelookup
TTFB(首字节) = time_starttransfer - time_connect
接收耗时 = time_total - time_starttransfer
```

**实际应用**：
- 对比HTTP协议客户端日志
- 识别缺失的盲区（连接池、锁、GC等待）
- 精确定位性能瓶颈

---

### 2.5 检测流程总结

```
应用请求失败
  ↓
1. dig 检查 DNS 是否解析正确
  ├─ 无结果 / 错误IP → DNS问题
  └─ 正常 → 继续
  ↓
2. ping 检查 IP 层连通性
  ├─ 无应答 / 高丢包 → IP层问题
  └─ 正常 → 继续
  ↓
3. mtr 检查路由路径
  ├─ 某跳丢包高 → 中间网络问题
  └─ 正常 → 继续
  ↓
4. hping3/telnet 检查 TCP 端口
  ├─ 连接拒绝 / 超时 → 端口关闭或防火墙
  └─ 连接成功 → 继续
  ↓
5. curl 检查应用层
  ├─ 分析 time_* 指标定位具体阶段
  ├─ time_connect 大 → 网络问题
  ├─ time_starttransfer 大 → 服务端问题
  └─ time_total 大 → 响应下载慢
```

## 3. 常用网络命令

### 3.1 连接统计 - netstat/ss

#### **netstat 概览**

**基本用法**：统计各状态socket数量

**关键状态与处理**：

| TCP状态 | 数量过多时原因 | 处理方案 |
|--------|---------------|---------|
| `ESTABLISHED` | 正常连接堆积 | 检查应用吞吐量 |
| `TIME_WAIT` | 主动关闭方积累 | 优化TCP参数 / 使用连接池 |
| `CLOSE_WAIT` | 被动方未关闭连接 | **检查代码连接泄露** |
| `LISTEN` | 被动监听状态 | 正常，表示服务在监听 |
| `SYN_RCVD` | 收到SYN但未完成握手 | 可能SYN Flood攻击 |

**重点关注**：
- **TIME_WAIT过多** → 端口耗尽风险，需连接复用或参数优化
- **CLOSE_WAIT过多** → 代码bug，连接未主动关闭

#### **netstat 连接来源统计**

**用途**：快速了解当前系统连接分布

```bash
# 统计各远程IP的连接数
netstat -an | grep ESTABLISHED | awk '{print $5}' | sort | uniq -c | sort -rn

# 统计本地监听端口
netstat -tnlp | grep LISTEN
```

#### **ss 命令**（netstat升级版）

**优势**：
- 性能更好（基于netlink而非/proc解析）
- 实时性更强
- 显示内核内部状态更详细

---

### 3.2 网卡层丢包 - ifconfig/ethtool

#### **ifconfig 丢包检测**

**显示字段**：
```
RX packets  : 接收包数
RX errors   : 接收错误数
RX dropped  : 接收丢弃数
TX packets  : 发送包数
TX errors   : 发送错误数
TX dropped  : 发送丢弃数
```

**丢包判断**：
```
丢包率 = (RX dropped + RX errors) / RX packets
      = (TX dropped + TX errors) / TX packets
```

#### **ethtool 详细统计**

**高级诊断**：`ethtool -S <interface>` 获取网卡统计详情

**关键指标**：
- `rx_csum_offload_errors` - 校验和卸载错误
- `rx_buffer_overflow` - 接收缓冲区溢出（重要！）
- `tx_queue_0_drops` - 发送队列丢弃

---

### 3.3 IP/TCP层统计 - netstat -s / nstat

#### **netstat -s 统计**

**显示内核层丢包、重传等**：

```
Packets received with checksum errors
Packets dropped in receive queue
TCPRetrans : TCP重传包数量（关键指标）
TCPTimeouts : TCP连接超时数
```

**问题诊断**：
- 重传率高 → 网络丢包严重
- 超时多 → 连接不稳定或超时参数过小

#### **nstat -a 详细统计**

**扩展视图**：提供更细粒度的网络统计

---

### 3.4 IP配置与路由 - ip/ifconfig / route

#### **ip addr / ifconfig**

**查看**：
- 本地IP地址配置
- 网卡的MTU设置
- 网卡状态（UP/DOWN）

#### **ip route / route -n**

**查看路由表**：
```
目标网段 | 网关 | 网卡 | 优先级
```

**路由问题诊断**：
- 默认路由是否正确
- 是否有到目标网络的路由条目
- 多条路由时的优先级

## 4. 丢包检测与定位

### 4.1 丢包来源分层

```
应用层丢包 ← 应用代码/缓冲区
  ↓
TCP/IP层丢包 ← netstat -s 检测
  ├─ TCP连接队列满
  ├─ IP分片重组失败
  └─ IP缓冲区溢出
  ↓
网卡驱动层丢包 ← ifconfig/ethtool 检测
  ├─ RX buffer overflow
  ├─ TX queue drop
  └─ 硬件缓冲区不足
  ↓
物理链路丢包 ← ping丢包率、mtr丢包
```

### 4.2 内核丢包定位 - bcc/stackcount

**工具**：BCC (BPF Compiler Collection)

**原理**：eBPF追踪内核 `kfree_skb` 函数，获取调用栈

**用途**：
- 定位内核丢包调用栈
- 找到丢包的具体代码位置
- 区分丢包原因（缓冲区满、校验错误、过滤等）

**备选工具**：`dropwatch` 也可用于丢包追踪

---

### 4.3 完整丢包排查流程

```
发现丢包
  ↓
1. ping <目标> 确认网络丢包情况
  ├─ 丢包 > 0 → 继续
  └─ 无丢包 → 应用层问题
  ↓
2. mtr <目标> 定位丢包所在跳
  ├─ 集中在某跳 → 该跳之后有问题
  └─ 均匀分布 → 全链路问题
  ↓
3. ifconfig <网卡> 查看网卡丢包
  ├─ RX/TX dropped 增长 → 网卡层问题
  └─ 正常 → IP/TCP层问题
  ↓
4. netstat -s 查看IP/TCP统计
  ├─ TCPRetrans 高 → 严重丢包
  ├─ 队列溢出 → TCP连接队列满
  └─ 校验错误 → 硬件问题
  ↓
5. bcc stackcount -k kfree_skb 定位内核丢包栈
   ↓
6. ethtool -S <网卡> 获取详细硬件统计
```

## 5. 网络抓包工具

### 5.1 抓包流程 - tcpdump

#### **原理与流程**

```
线上环境（生产）
    ↓
tcpdump 抓取网络包
    ↓
压缩（可选，文件大时）
    ↓
下载到本地
    ↓
wireshark 分析
```

#### **tcpdump 常用选项**

| 选项 | 含义 | 示例 |
|------|------|------|
| `-i <interface>` | 指定网卡 | `-i eth0` |
| `-w <file>` | 写入pcap文件 | `-w capture.pcap` |
| `-r <file>` | 读取pcap文件 | `-r capture.pcap` |
| `-c <count>` | 抓取包数量 | `-c 1000` |
| `-s <size>` | 每包捕获字节数 | `-s 0`（不截断）|
| `-n` | 不做DNS反解 | 加速输出 |
| `-v / -vv / -vvv` | 详细程度 | 越多越详细 |
| `filter` | 数据包过滤器 | `port 80` |

#### **常见过滤器**

```bash
# 基础过滤
tcpdump -i eth0 host 192.168.1.1
tcpdump -i eth0 port 3306
tcpdump -i eth0 'tcp port 80 or port 443'

# 复杂过滤
tcpdump -i eth0 'src 192.168.1.1 and dst 192.168.1.2 and port 8080'

# 保存到文件（文件较大时压缩）
tcpdump -i eth0 -w - 'port 3306' | gzip > mysql.pcapz
```

#### **性能考虑**

```
大文件处理：tcpdump输出 → gzip压缩 → 下载 → 本地wireshark分析
时间成本：抓包时间 × 秒 × 包速率 = 文件大小
```

### 5.2 分析工具 - wireshark

#### **5.2.1 基础界面**

**四个核心区域**：
```
[菜单栏 & 工具栏]
    ↓
[显示过滤器区] ← 重要：过滤条件在这里
    ↓
┌─ [包列表区] ─────────────────────┐

└───────────────────────────────────┘
    ↓
[包详情区]（展开查看每层协议）
    ↓
[包数据区]（十六进制原始数据）
```

#### **5.2.2 协议解析配置**

**场景**：非标准端口的协议识别

**示例：MySQL在3961端口**
```
wireshark 默认规则：
  80/8080 → HTTP
  3306 → MySQL
  
配置步骤：
  Analyze → Decode As → 选择端口 & 协议
  → 设置 3961 → MySQL
```

**类似场景**：
- HTTP在非80端口
- gRPC在自定义端口
- 自定义二进制协议

#### **5.2.3 过滤包 - 显示过滤器**

**过滤器语法**：

| 过滤条件 | 示例 | 用途 |
|---------|------|------|
| 基础协议 | `tcp` | 仅显示TCP包 |
| 端口过滤 | `tcp.port == 80` | 指定端口 |
| IP过滤 | `ip.addr == 192.168.1.1` | 指定IP |
| 复合条件 | `ip.addr == 192.168.1.1 and (tcp.port == 8080 or tcp.port == 3306)` | 多条件AND/OR |
| 协议字段 | `mysql.query contains "id=24218"` | 协议特定字段 |
| 正则匹配 | `tcp.payload ~ "select"` | 包数据中的正则 |
| 响应码 | `http.response.code == 200` | HTTP状态码 |

**高级用法**：
```
# 过滤出SELECT类SQL
mysql.query ~ "^select"

# 过滤出特定SQL字段
mysql.query contains "WHERE user_id="

# 过滤包含特定字符串的TCP流
tcp.payload ~ "error"
```

**重要说明**：
- 不支持的协议 → 使用 `tcp.payload` 过滤
- 显示过滤器在包已捕获后应用（与capture filter不同）

#### **5.2.4 查找包**

**查找vs过滤的区别**：

| 操作 | 行为 | 用途 |
|------|------|------|
| 显示过滤器 | 过滤包列表显示 | 批量过滤同类包 |
| 查找（Find） | 定位到特定包，不过滤列表 | 逐个定位目标包 |

**查找方式**：
```
Method 1: 显示过滤器查找
  Ctrl+F → 输入过滤表达式 → Enter
  ↓
  定位第一个匹配包 → 继续查找下一个

Method 2: 包数据正则查找
  Ctrl+Alt+F → 选择"Packet bytes"
  → 输入正则表达式（如 select）
  ↓ 
  逐包定位包含该字符串的包
```

#### **5.2.5 自定义列**

**默认列显示**：IP、协议、长度等

**添加自定义列的步骤**：
```
Preferences → Columns → New
  ↓
输入列名 + 字段名
  ↓
包列表新增该列，可点击排序
```

#### **常用TCP分析列**

| Flags | `tcp.flags` | TCP标志位（SYN/FIN/RST/ACK） |

**应用场景**：诊断调用端慢、服务端快问题

#### **5.2.6 包列表排序**

**操作**：点击表头列名 → 升序/降序

**常见排序应用**：

```
# 查找响应最慢的包
① 过滤显示所有响应包
② 按 tcp.time_delta 倒序
③ 最前面的包 = 响应最慢的包

# 查找最大的包
① 不过滤
② 按 Length 倒序
③ 快速识别大流量包（可能是问题）
```

### 5.3 案例：调用端慢、服务端快的诊断

#### **问题背景**

```
场景：
  调用端报告：请求耗时 500ms
  服务端报告：处理耗时 10ms
  
困惑：
  为什么调用端耗时这么长？
  是调用端问题？网络问题？还是服务端问题？
```

#### **根本原因分析**

**全链路日志的盲区**：

```
调用端耗时 500ms 包含：
  ├─ 锁等待时间
  ├─ 连接池等待时间
  ├─ GC暂停时间
  ├─ 实际网络请求耗时
  └─ [应用处理前的系统级延迟]

服务端处理耗时 10ms 可能缺失：
  ├─ 请求到达但无空闲线程等待时间
  ├─ 任务队列等待时间
  └─ [应用处理前的排队延迟]

真相：
  应用间的实际网络交互不反映在日志中！
```

#### **通过网络抓包精准定位**

**关键洞察**：

```
TCP ACK包 → 由操作系统内核回复（快速）
响应数据包 → 由进程处理后回复（取决于进程处理速度）

判断标准：
  ACK_RTT 快 + 响应包 RTT 慢 = 服务端处理慢
  ACK_RTT 快 + 响应包 RTT 快 = 调用端慢（非网络非服务端）
  ACK_RTT 慢 + 响应包 RTT 慢 = 网络慢
```

---

#### **诊断步骤**

**步骤1：过滤响应包并按时间排序**

```
① 在调用端抓包
② 过滤显示所有响应包
③ 添加 tcp.time_delta 列（当前包与上一个TCP包的间隔）
④ 按 tcp.time_delta 倒序排列
   ↓
   最前面的包 = 响应最慢的包
```

**步骤2：找到最慢的响应包**

```
选中该包
观察关键指标：
  - tcp.time_delta : 响应包的往返时间
  - tcp.analysis.ack_rtt : ACK确认的往返时间
```

**步骤3：查看该连接的所有包**

```
① 选中最慢的响应包
② 右键 → 对话过滤器 → TCP
③ 清除其他过滤条件（显示 No 升序）
   ↓
   只显示该TCP连接的所有包
   按时间顺序查看请求→ACK→响应
```

**步骤4：比较ACK_RTT与tcp_delta**

```
情况1：tcp.analysis.ack_rtt 小（如 1ms），tcp.time_delta 大（如 400ms）
结论 → 【服务端处理慢】
原因：网络很快回复ACK，但服务端处理慢才回复响应

情况2：tcp.analysis.ack_rtt 小（如 1ms），tcp.time_delta 也小（如 5ms）
结论 → 【调用端慢】
原因：响应很快回复，但调用端没有及时发出下一个请求

情况3：tcp.analysis.ack_rtt 大（如 200ms），tcp.time_delta 也大（如 400ms）
结论 → 【网络慢】
原因：ACK和响应都慢
```

### 6.3 TCP三次握手与四次挥手定位丢包/RST

```
【TCP三次握手 - 连接建立】

Client                          Server
  │                              │
  ├──────── SYN (seq=1000) ─────>│
  │  状态：SYN_SENT              │ 状态：SYN_RCVD
  │                              │
  │<─── SYN+ACK (seq=2000) ──────┤
  │  状态：ESTABLISHED           │ 状态：ESTABLISHED
  │                              │
  ├────── ACK (seq=1001) ───────>│
  │                              │
  └──── 连接建立，可交换数据 ────┘

【丢包诊断】
情况1：Client收不到SYN+ACK
→ hping3显示超时 → TCP连接建立失败
→ 检查：防火墙、Server进程、网络

情况2：Server从不收到ACK
→ Server连接进入TIME_WAIT
→ wireshark显示：SYN+ACK 后无ACK
→ 检查Client网络问题

─────────────────────────────────────

【TCP四次挥手 - 连接关闭】

Client                          Server
  │                              │
  ├─────── FIN (seq=5000) ──────>│
  │  状态：FIN_WAIT_1            │ 状态：CLOSE_WAIT
  │                              │
  │<────── ACK (seq=5001) ───────┤
  │  状态：FIN_WAIT_2            │ 状态：CLOSE_WAIT
  │                              │ (此时可能继续接收，但不再发送新数据)
  │                              │
  │<─────── FIN (seq=6000) ──────┤
  │  状态：TIME_WAIT             │ 状态：LAST_ACK
  │                              │
  ├────── ACK (seq=6001) ───────>│
  │  状态：CLOSED                │ 状态：CLOSED
  │                              │
  │ 等待2*MSL时间后完全关闭      │

【丢包与异常诊断】

1. RST (重置)出现时机：
   ├─ Server收到未知连接的包 → 回复RST
   ├─ Server进程异常退出 → 回复RST
   ├─ 客户端连接超时 → 回复RST
   └─ wireshark显示：包含RST标志

2. TIME_WAIT过多 → 积累原因：
   ├─ 短连接频繁创建销毁
   ├─ 主动关闭方积累（2*MSL ≈ 60s）
   ├─ 解决方案：TCP参数优化 / 连接复用
   └─ netstat -an | grep TIME_WAIT | wc -l

3. CLOSE_WAIT过多 → 严重问题：
   ├─ 被动关闭方未调用close()
   ├─ 代码连接泄露bug
   ├─ 必须修复代码
   └─ netstat -an | grep CLOSE_WAIT | wc -l

【在wireshark中追踪】
① 过滤：tcp.flags.fin==1 or tcp.flags.rst==1
② 查看FIN/RST的发送方 → 定位主动关闭方
③ 对比是否有对应的ACK → 判断是否丢包
④ 时间间隔 → 判断延迟
```

### 6.4 应用层→网络分层诊断决策图

```
┌────────────────────────────────────────┐
│  应用接口调用失败 / 超时 / 响应慢       │
└─────────────────┬──────────────────────┘
                  │
        【第一步：快速诊断】
                  │
        ┌─────────v──────────┐
        │ curl -w "@fmt.txt" │
        │ http://server:port │
        └────────┬───────────┘
                 │
         ┌───────v────────┐
         │ 分析time_*     │
         └───┬───┬────┬───┘
             │   │    │
    ┌────────┘   │    └────────────────┐
    │            │                     │
    v            v                     v
[DNS耗时]  [TCP连接耗时]          [响应耗时]
    │            │                     │
    v            v                     v
(>100ms)    (>50ms)                (长)
    │            │                     │
    v            v                     v
DNS问题    网络/防火墙             服务端慢
    │      IP/TCP异常             应用处理
    │      端口不通                缓冲区满
    │                              线程饱和
    v                                  v
【第二步：细化诊断】

DNS问题 → dig/host检查DNS解析
  └─ 返回值错误 → DNS污染
  └─ 超时 → DNS服务器不通

TCP连接慢 → mtr <server> 检查路由
  └─ 某跳丢包高 → 中间网络问题
  └─ RTT大 → 跨地域或网络质量差

响应慢 → tcpdump + wireshark分析
  ├─ 确认ACK_RTT vs tcp_time_delta
  ├─ ACK快响应慢 → 服务端处理慢
  ├─ 都快 → 调用端本身慢（非网络）
  └─ 都慢 → 网络质量问题

【第三步：深度排查】

如果响应慢属于"服务端处理慢" →
  ├─ 检查服务端日志 (应用耗时)
  ├─ 使用profiler (CPU火焰图)
  ├─ 查看进程资源 (top / htop)
  └─ 必要时strace跟踪系统调用

如果响应慢属于"网络慢" →
  ├─ 检查网卡统计 (ifconfig / ethtool)
  ├─ 查看路由 (mtr / traceroute)
  ├─ 向网络运维反馈 (提供mtr截图)
  └─ 考虑修改tcp参数 (tcp_wmem / tcp_rmem)

如果响应慢属于"调用端慢" →
  ├─ 检查调用端代码 (锁、连接池、GC)
  ├─ 使用调用端profiler分析
  ├─ 验证是否真的发送了请求
  └─ 检查是否在等待系统资源
```
