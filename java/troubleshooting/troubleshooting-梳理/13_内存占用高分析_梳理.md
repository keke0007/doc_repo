## 1. Linux物理内存体系

### 1.1 内存层级划分：Node - Zone - Page

#### Node（节点）划分
- **NUMA架构**：多CPU机器采用NUMA（非统一内存访问）架构
- **本地vs远程**：每个CPU有配套的本地内存，访问本地内存快，访问远程内存慢
- **Node概念**：一组CPU+内存被称为一个Node节点
- **查看命令**：
  ```bash
  numactl -H              # 查看NUMA节点信息
  numactl --interleave=all  # NUMA内存交织分配
  ```

#### Zone（区域）划分
| Zone类型 | 说明 | 适用场景 |
|---------|------|--------|
| DMA | 最低地址段内存 | IO设备DMA访问 |
| DMA32 | 支持32位地址总线 | 64位系统中DMA设备 |
| NORMAL | 其余内存 | 常规内存分配 |

- **查看命令**：`cat /proc/zoneinfo`

#### Page（页面）分类
| 页面类型 | 说明 | 回收策略 |
|---------|------|--------|
| free | 未分配页面 | N/A |
| anon | 匿名页(进程动态分配) | 可swap或回收 |
| file | 文件相关页面 | 可直接或同步后回收 |
| dirty | 被修改的脏页 | 需先同步到磁盘 |

- **查看命令**：`cat /proc/pagetypeinfo`

### 1.2 缓存机制

#### Buffer与Cache区别
| 类型 | 概念 | 用途 |
|-----|------|------|
| **Buffer** | 块缓存 | 缓存块设备(磁盘)元数据如超级块、inode等 |
| **Cache** | 文件缓存 | 缓存文件数据内容 |

- **常见误解**：Buffer是写缓冲、Cache是读缓存 ❌
- **事实**：两者都涵盖读写操作 ✓

#### Slab内存分配
- **机制**：Linux基于对象的内存分配机制，类似对象池
- **优势**：避免频繁malloc/free系统调用
- **查看命令**：
  ```bash
  cat /proc/slabinfo      # 查看所有slab
  slabtop                  # 动态查看slab占用
  ```

### 1.3 free命令输出解释

```
                total        used        free      shared  buff/cache   available
Mem:            16Gi       3.5Gi       5.2Gi      128Mi      7.2Gi       12Gi
Swap:          2.0Gi      512Mi       1.5Gi
```

| 指标 | 含义 |
|-----|------|
| **Mem.total** | 总物理内存 |
| **Mem.used** | 已使用anon内存 |
| **Mem.free** | 空闲内存 |
| **Mem.buffers** | 块缓存大小 |
| **Mem.cache** | 文件缓存+slab大小 |
| **Mem.available** | 可用内存(约=free+buffers+cache) |
| **Swap.used** | 已使用swap(anon页swapout) |

## 2. Linux虚拟内存与进程内存布局

### 2.1 虚拟内存段划分

```
┌─────────────────────────────────────┐
│  栈 (Stack)                         │  向下生长
│  - 线程运行时栈数据                  │
├─────────────────────────────────────┤
│  内存映射段 (Memory-Mapped)         │  
│  - mmap动态申请内存区域              │
├─────────────────────────────────────┤
│  堆 (Heap)                          │  向上扩展(brk)
│  - 进程动态内存区域                  │
├─────────────────────────────────────┤
│  数据段 (.data)                     │  只读/固定
│  - 全局变量、常量                   │
├─────────────────────────────────────┤
│  代码段 (.text)                     │  只读/固定
│  - 程序指令                         │
└─────────────────────────────────────┘
```

### 2.2 pmap命令与进程内存分析

```bash
pmap -x <pid>  # 查看进程虚拟内存布局
```

| pmap字段 | 含义 |
|---------|------|
| **Address** | 内存段起始地址 |
| **Kbytes** | 虚拟内存段大小 |
| **RSS** | 实际分配物理内存大小 |
| **Dirty** | 被修改的脏内存大小 |
| **Mode** | r(读)/w(写)/x(执行)权限 |
| **Mapping** | 映射文件(anon表示匿名) |

**应用技巧**：
- 保存前后时间点的pmap数据对比
- 识别新增或增长的内存块
- 使用strings检查/proc/$pid/mem内容

## 3. Java内存模型

### 3.1 Java内存区域划分

```
┌─────────────────────────────────────────────────────┐
│           Java Process Virtual Memory              │
├─────────────────────────────────────────────────────┤
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │  Java堆区 (Heap)                           │   │
│  │  - 对象分配与存储                            │   │
│  │  - GC管理区域                               │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │  Java非堆区 (Non-Heap)                      │   │
│  │  ├─ MetaSpace (类/常量存储)                 │   │
│  │  ├─ Code Cache (JIT编译代码)               │   │
│  │  ├─ Direct ByteBuffer (直接内存)           │   │
│  │  ├─ Mapped ByteBuffer (文件映射)           │   │
│  │  ├─ Thread (线程占用)                      │   │
│  │  └─ GC占用内存                              │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │  Native分配区                               │   │
│  │  ├─ JNI malloc (JNI机制分配)                │   │
│  │  └─ IO malloc (IO操作分配)                  │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 3.2 Java堆 vs 非堆 vs Native

| 区域 | 管理方式 | GC | 常见问题 |
|-----|--------|-----|--------|
| **堆** | JVM自动GC | 有 | 对象泄漏、内存溢出 |
| **MetaSpace** | 自动清理(类卸载) | 部分 | 类加载泄漏 |
| **Code Cache** | JVM管理 | 有 | 编译过多导致满 |
| **直接内存** | 手动释放 | 无 | 用户需显式close |
| **Native** | malloc/free | 无 | 指针泄漏 |

## 4. 内存分配与回收机制

### 4.1 虚拟内存分配流程

```
┌─────────────────┐
│  进程调用malloc │
└────────┬────────┘
         │
         ▼
┌─────────────────────────┐
│  glibc malloc处理       │
│  - 查询缓存内存块       │
│  - 若无，调用brk/mmap   │
└────────┬────────────────┘
         │
         ▼
┌─────────────────────────┐
│  brk/mmap系统调用       │
│  申请虚拟内存地址空间   │
│  (不分配物理内存)       │
└────────┬────────────────┘
         │
         ▼
┌─────────────────────────┐
│  返回虚拟内存地址给应用 │
│  真实物理内存由缺页延迟分配
└─────────────────────────┘
```

**glibc缓存机制**：
- malloc/free不是1:1调用系统调用
- glibc缓存一定量内存块，达到阈值才归还
- 导致进程占用内存比理论值大
- 可使用`malloc_stats()`查看缓存情况
- 可使用`malloc_trim()`主动回收缓存

### 4.2 物理内存分配：缺页中断

```
进程访问虚拟内存
     │
     ▼
┌─────────────────────┐
│  页表查询物理页     │
│  (未映射→缺页异常) │
└────────┬────────────┘
         │
         ▼
┌─────────────────────────────────┐
│  缺页中断处理                   │
├─────────────────────────────────┤
│ Minor Fault:                    │
│ - 分配新物理页                  │
│ - 不需从磁盘/swap加载           │
│                                 │
│ Major Fault:                    │
│ - 分配新物理页                  │
│ - 需从磁盘/swap加载数据到页    │
└─────────────────────────────────┘
```

### 4.3 内存回收机制与水位控制

#### 内存水位（Watermark）

```
内存空闲量变化轨迹：

HIGH  ───────────────── 安全水位
      │ (正常分配)
LOW   ───────────────── 触发异步回收(kswapd)
      │ (缓慢下降)
MIN   ───────────────── 同步等待回收(direct reclaim)
      │ (快速下降)
      
查看: grep -E 'pageoutrun|allocstall' /proc/vmstat
调优: vm.watermark_scale_factor
```

#### 页面回收策略

| 页面类型 | 回收行为 | 前置条件 |
|---------|--------|--------|
| **anon page** | swap到磁盘后回收 | swap启用 |
| **file page(clean)** | 直接回收 | 始终可回收 |
| **file page(dirty)** | 同步到磁盘后回收 | I/O操作 |

**swappiness参数**：
```bash
vm.swappiness=30  # 推荐值30-50
# 值越大，回收anon page比例越大
# 1: 尽量避免swap
# 100: anon page与file page比例相等
```

#### 最坏场景：三种磁盘I/O

当启用swap且内存紧张时，单次内存分配可能产生三类I/O：

1. **anon page swap out**：页面写入swap分区
2. **dirty page同步**：脏页数据同步到磁盘
3. **major fault**：加载swap或mmap文件数据到内存

## 5. 高内存占用分析方法

### 5.1 分析决策树

```
系统内存占用高
│
├─ 是否进程占用多 ──NO──▶ 内核占用多
│                        └▶ 检查：bcc memleak、驱动Bug
│
└─ YES ──▶ 找占用最大进程
           │
           ├─ 是Java/C++应用
           │  │
           │  └─ Java进程 ──▶ 分析JVM内存区域
           │                 │
           │                 ├─ 堆占用高
           │                 │  └▶ jcmd / jmap → MAT分析
           │                 │
           │                 ├─ MetaSpace占用高
           │                 │  └▶ jcmd VM.classloader_stats
           │                 │     arthas classloader + profiler
           │                 │
           │                 └─ 堆外(Native)占用高
           │                    └▶ tcmalloc/jemalloc/mtrace
           │                       + arthas profiler
           │
           ├─ 文件缓存/Slab占用多
           │  └▶ free -wh / vmtouch / slabtop
           │
           ├─ 是否OOM被杀
           │  └▶ dmesg | grep -i oom
           │
           └─ glibc缓存占用多
              └▶ malloc_stats() / malloc_trim()
```

### 5.2 逐层分析方法

#### 第一层：判断进程vs内核占用

```bash
# 查看top输出的内存占用分布
top -b -n 1 | head -20

# 计算所有进程占用总和
ps aux | awk '{sum+=$6} END {print sum " KB"}'

# 对比 free 输出的 used 值
free -h
```

#### 第二层：找占用最多的进程

```bash
# 按内存倒序排列
top -b -n 1 -o %MEM | head -20

# 或使用排序
ps aux | sort -k 4 -rn | head -10
```

#### 第三层：分析Java进程内存区域

```bash
# 查看堆大小
jcmd <pid> GC.heap_info

# 查看非堆区域(MetaSpace/Direct等)
arthas> memory

# 更详细的内存统计(需开启NMT)
jcmd <pid> VM.native_memory summary
```

## 6. 堆内内存泄露诊断

### 6.1 堆占用高分析流程

```
堆占用高
│
├─ 使用 jmap -histo:live <pid>
│  查看类直方图
│  │
│  ├─ 若看到异常大对象
│  │  └▶ 确认是泄漏 → 找调用栈
│  │
│  └─ 若直方图正常
│     └▶ 转向堆转储分析
│
├─ 生成堆转储 hprof 文件
│  jmap -dump:live,format=b,file=heap.hprof <pid>
│  (需停止流量，可能导致长时间暂停)
│
└─ 使用 MAT 分析 hprof
   │
   ├─ 找 GC Root 引用链最长的对象
   │
   └─ 展开查看调用栈代码
      └▶ 找到泄漏点
```

### 6.2 MAT分析步骤

1. **生成堆转储**
   ```bash
   jmap -dump:live,format=b,file=heap.hprof <pid>
   
   # 或配置自动dump
   java -XX:+HeapDumpOnOutOfMemoryError \
        -XX:HeapDumpPath=/home/logs/ \
        -jar app.jar
   ```

2. **MAT图形分析**
   - 打开heap.hprof → Leak Suspect Report
   - 查看Retained Size最大的对象
   - 追踪GC Root → 对象引用链
   - 定位Java代码行号

## 7. MetaSpace内存泄露诊断

### 7.1 常见原因

- **类加载泄漏**：自定义ClassLoader加载的类未卸载
- **动态类生成**：fastjson/cglib每次生成新类，未复用ClassLoader
- **反射缓存**：类反射信息缓存未清理

### 7.2 诊断工具链

```
MetaSpace占用高
│
├─ jcmd <pid> VM.classloader_stats
│  ├─ 快速查看ClassLoader加载类数量
│  └─ 识别异常ClassLoader
│
├─ arthas classloader
│  ├─ 查看所有ClassLoader
│  └─ 对比前后变化，发现新增ClassLoader
│
└─ arthas profiler -d 60 --include-param
   ├─ 采集60秒CPU采样
   ├─ 搜索 loadClass 调用栈
   └─ 找到类加载源头
```

### 7.3 典型案例：fastjson SerialzeConfig

```java
// ❌ 错误：每次创建SerializeConfig，产生新ClassLoader
for (int i = 0; i < 10000; i++) {
    SerializeConfig config = new SerializeConfig();
    fastjson.toJSONString(obj, config);
}
// 结果：加载10000次新类 → MetaSpace爆满

// ✅ 正确：复用SerializeConfig
private static final SerializeConfig CONFIG = new SerializeConfig();
for (int i = 0; i < 10000; i++) {
    fastjson.toJSONString(obj, CONFIG);
}
// 结果：只加载一次类 → MetaSpace正常
```

## 8. 堆外Native内存泄露诊断

### 8.1 三种诊断工具对比

| 工具 | 原理 | 优点 | 缺点 | 风险 |
|-----|------|------|------|------|
| **tcmalloc** | Hook malloc/free | 快速定位 | 需更换内存分配器 | ⚠️ 中等风险 |
| **jemalloc** | Hook malloc/free | 更佳控制 | 需更换内存分配器 | ⚠️ 中等风险 |
| **mtrace** | glibc内置 | 无额外库 | 只记录操作 | ✓ 低风险 |

### 8.2 tcmalloc诊断流程

```bash
# 1. 安装tcmalloc
sudo yum install gperftools-libs

# 2. 使用LD_PRELOAD启动应用
export LD_PRELOAD=/usr/lib64/libtcmalloc.so.4
java -jar app.jar

# 3. 生成堆转储
pprof --pdf /path/to/heap > heap.pdf
```

输出显示内存分配的调用栈及字节数

### 8.3 mtrace诊断流程

```bash
# 1. 在应用中启用mtrace
# 编写C语言wrapper调用 mtrace()

# 2. 采样一段时间
sleep 60

# 3. 关闭mtrace，生成日志
export MALLOC_TRACE=/tmp/malloc_trace.log
# ... 应用运行 ...
unset MALLOC_TRACE

# 4. 分析泄漏
mtrace /path/to/binary /tmp/malloc_trace.log

# 5. 统计泄漏次数
# 查找 Caller 出现次数最多的地址
# 如: 0x7efe715e4b88 泄露1010次 → 基本确认泄漏
```

### 8.4 arthas profiler追踪malloc

```bash
arthas> profiler start --event malloc

# 运行一段时间后采样
arthas> profiler stop --format jfr

# 生成火焰图
```

### 8.5 常见堆外内存泄漏点

| 类/方法 | 泄漏原因 | 解决方案 |
|--------|--------|--------|
| **GZIPInputStream** | JNI实现，未close | 必须try-with-resources |
| **DirectByteBuffer** | 用户未释放 | 显式close或使用cleaner |
| **Native库** | malloc未free | 检查库的释放逻辑 |
| **mmap文件** | 未unmap | 使用MappedByteBuffer.force()后unmap |

## 9. OOMKiller与进程保护

### 9.1 OOMKiller工作机制

```
系统内存极度紧张
(低于min水位)
     │
     ▼
内存回收无可回收页面
     │
     ▼
触发OOM Killer
     │
     ▼
对所有进程打分
├─ 内存占用量(权重大)
├─ 进程优先级
├─ oom_score_adj值
└─ 其他因素
     │
     ▼
选择bad_process打分最高的进程
     │
     ▼
强制kill进程释放内存
```

### 9.2 确认进程被OOMKiller杀死

```bash
# 查看内核日志
dmesg | tail -50 | grep -i oom

# 输出示例：
# Out of memory: Kill process java(1234) score 651 ...
# Killed process java(1234) total-vm:16000000kB ...
```

### 9.3 保护关键进程

```bash
# 查看进程oom_score
cat /proc/<pid>/oom_score
# 值越大越容易被杀

# 查看oom_score_adj
cat /proc/<pid>/oom_score_adj

# 使用choom降低优先级(避免被杀)
choom -p <pid> -n -500  # 设置调整值为-500

# 永久配置：修改/etc/security/limits.conf
<user> - memlock unlimited
```

### 9.4 监控OOMKiller活动

```bash
# 查看当前oom killer运行情况
grep -i oom /var/log/syslog

# 实时监控
tail -f /var/log/syslog | grep -i oom

# 计数统计
dmesg | grep -c "Killed process"
```

## 10. 内存调优策略

### 10.1 Linux内核参数调优

#### NUMA相关

```bash
# 启用NUMA内存交织(各node均匀分配)
numactl --interleave=all java -jar app.jar

# 禁用zone_reclaim(允许跨node使用内存)
sysctl -w vm.zone_reclaim_mode=0
```

#### 内存水位调优

```bash
# 调整high/low/min水位差值
sysctl -w vm.watermark_scale_factor=10  # 默认10

# 查看当前水位
grep -E 'pages_free|pages_min|pages_low|pages_high' /proc/vmstat
```

#### Swap相关

```bash
# 减少anon page被swap的倾向
sysctl -w vm.swappiness=10  # 默认30

# 禁用swap(生产环境推荐)
swapoff -a

# 再次启用swap
swapon -a
```

#### 超额申请控制

```bash
# vm.overcommit_memory 说明
# 0: 启发式检查(默认)
# 1: 允许申请超过物理内存
# 2: 只允许申请 (RAM + Swap) * overcommit_ratio

sysctl -w vm.overcommit_memory=2
sysctl -w vm.overcommit_ratio=80  # 允许申请物理内存的80%
```

### 10.2 缓存管理调优

```bash
# 脏页相关参数
sysctl -w vm.dirty_background_bytes=104857600   # 100MB
sysctl -w vm.dirty_bytes=209715200              # 200MB

# 手动清除page cache与slab
echo 3 > /proc/sys/vm/drop_caches

# slab缓存回收激进度
sysctl -w vm.vfs_cache_pressure=200  # 默认100，值越大越积极
```

### 10.3 Native程序调优

#### 内存分配器替换

```bash
# 从ptmalloc2替换为jemalloc
export LD_PRELOAD=/usr/lib64/libjemalloc.so.1
java -jar app.jar

# jemalloc优势：
# - 内存碎片控制更好
# - 性能更高
# - 多线程伸缩性好
```

#### 内存锁定(防止swap)

```bash
# 锁定进程虚拟内存(mlock)
# 编写C程序调用 mlockall(MCL_CURRENT | MCL_FUTURE)
```

### 10.5 编码优化

#### 减少对象创建

```java
// ❌ 避免：一次性读取大文件
byte[] data = Files.readAllBytes(Paths.get("huge_file.bin"));
process(data);

// ✅ 推荐：流式处理
try (InputStream is = new FileInputStream("huge_file.bin")) {
    byte[] buffer = new byte[8192];
    int len;
    while ((len = is.read(buffer)) != -1) {
        process(buffer, len);
    }
}
```

#### 队列与线程池限制

```java
// ✅ 有界队列防止无限积压
BlockingQueue<Task> queue = new LinkedBlockingQueue<>(10000);
ExecutorService pool = new ThreadPoolExecutor(
    10, 20,
    60, TimeUnit.SECONDS,
    queue,
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

#### 分页查询

```java
// ❌ 避免：一次性查询百万级数据
List<User> allUsers = db.query("SELECT * FROM users");

// ✅ 推荐：分页查询
for (int page = 1; page <= totalPages; page++) {
    List<User> pageUsers = db.query(
        "SELECT * FROM users LIMIT " + pageSize + 
        " OFFSET " + (page-1)*pageSize
    );
    process(pageUsers);
}
```

## 总结

本章深入讲解了从Linux内存体系 → 进程虚拟内存 → Java内存模型的完整架构，及其对应的诊断工具链：

**核心流程**：
1. 定位进程 vs 内核占用（top / ps）
2. 定位JVM内存区域（jcmd / arthas / NMT）
3. 根据区域类型选择诊断工具（jmap / profiler / tcmalloc / mtrace）
4. 追踪调用栈找到泄漏源头（MAT / arthas profiler）
5. 修复+内核/JVM参数调优

**三个典型场景**：
- 堆占用高 → jmap + MAT
- MetaSpace占用高 → classloader + profiler  
- Native占用高 → tcmalloc/mtrace + profiler

**防护机制**：
- OOMKiller通过choom降低优先级保护
- glibc缓存通过malloc_trim及时回收
- swap、缓存、水位参数平衡内存和I/O

实践建议：建立监控告警，关注RSS增长趋势，早期发现内存泄漏征兆。
