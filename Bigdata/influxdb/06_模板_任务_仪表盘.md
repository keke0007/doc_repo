## 一、InfluxDB 模板(Template)

### 1.1 模板是什么

模板 = **一份 YAML 文件 + 一系列 InfluxDB 资源声明**,包含:

```
Template (xxx.yml)
├─ Bucket(存储桶)
├─ Telegraf 配置
├─ Dashboard(仪表盘)
├─ Check / Notification Rule / Notification Endpoint(报警三件套)
├─ Task(定时任务)
├─ Variable(变量)
└─ Label(标签)
```

**目标**:开箱即用 — 下载、`influx apply -f xxx.yml`,从采集到报警全套就绪。

**社区模板仓库**:`https://github.com/influxdata/community-templates`

### 1.2 安装模板的两种方式

```
┌────────────────────────────────────────────────────────────────┐
│  方式 A: Web UI                                                │
│    Settings → Templates → 粘 URL → Apply                       │
├────────────────────────────────────────────────────────────────┤
│  方式 B: influx CLI(推荐,可脚本化)                            │
│    influx apply -f <URL or 本地文件>                           │
└────────────────────────────────────────────────────────────────┘
```

执行后 CLI 会**先列出将创建的资源**,要 `y` 确认才会真正写入 — 避免和现有资源(同名 bucket 等)撞车。

### 1.3 Stack(模板实例)概念

```
Template(yml 文件)  ──── apply ────▶  Stack(运行实例)
                                          │
                                          ├─ Stack ID(09ee20c80d692000)
                                          └─ 关联的所有资源 ID 列表

删除 Stack ─▶ 关联资源**全部删除**
```

CLI 命令:

```bash
influx stacks                                  # 列出所有 stack
influx stacks update --stack-id=xxx --name=...  # 重命名
influx stacks remove -o atguigu --stack-id=xxx  # 删除整个 stack(及其资源)
```

### 1.4 完整模板使用流程(Docker 监控示例)

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  1. 找模板                                                       │
│     https://github.com/influxdata/community-templates             │
│              │                                                   │
│              ▼                                                   │
│  2. influx apply -f .../docker/docker.yml                        │
│              │                                                   │
│              ▼                                                   │
│  3. CLI 弹出资源清单 ── 用户 y 确认                              │
│              │                                                   │
│              ▼                                                   │
│  4. InfluxDB 创建:                                              │
│     • Bucket "docker" (7d retention)                            │
│     • Telegraf 配置 "Docker Monitoring"                         │
│     • Dashboard "Docker"                                        │
│     • 4 个报警 (cpu/mem/disk/non-zero exit)                     │

│              │                                                   │

```

### 1.5 模板的两个明显缺陷

#### 缺陷 1:FLUX 版本兼容性差

```
模板里可能嵌入 FLUX 脚本
        ↓
InfluxDB 2.0  ↔  FLUX 0.131
InfluxDB 2.4  ↔  FLUX 0.179   (4 个 InfluxDB 版本 → 50 个 FLUX 版本)
        ↓
新版可能删除/重命名旧 FLUX 函数,导致旧模板在新 InfluxDB 报错
```

**典型例子**:`csv.from(url: ...)` 在 InfluxDB 2.3 后被废弃,使用 sample-data 模板会在第 11 行报错。

#### 缺陷 2:生态比不上 Grafana

| 维度 | InfluxDB Dashboard | Grafana |
| --- | --- | --- |
| 社区活跃度 | 一般 | 极高 |
| InfluxDB 数据源的仪表盘数量 | 几十个 | 1117+(讲义当时) |
| 模板维护 | 半停滞 | 活跃 |
| 报警接入面 | 内置但渠道有限 | 极丰富(Slack/PagerDuty/钉钉/...) |

> 💡 **生产推荐**:InfluxDB 只做存储 + 查询,**仪表盘和报警交给 Grafana**(把 InfluxDB 当数据源)。

## 二、定时任务(Task)

### 2.1 任务的本质

**Task = 周期调度的 FLUX 脚本**。FLUX 是脚本语言,所以 Task 不止能查数据,还能:

- HTTP 调用外部服务(`http.post`)
- 把聚合结果**写回 InfluxDB**(`to(bucket:)`)
- 计算条件并发出报警(底层就是把数据投到 `_monitoring` bucket,见 07 章)

> 💡 **InfluxDB 抓取任务(Scraper)的本质也是 Task** — 内部就是一段:
> ```flux
> import "experimental/prometheus"
> prometheus.scrape(url: "http://host/metrics")
> ```
> 只是 UI 把它单独划成一类。

### 2.2 4 种创建任务的途径

```
┌────────────────────────────────────────────────────────────────┐
│  途径 1: influx CLI(推荐,可版本化)                           │
│    ./influx task create --org atguigu -f example_task.flux     │
├────────────────────────────────────────────────────────────────┤
│  途径 2: HTTP API                                              │
│    POST /api/v2/tasks { "orgID":..., "flux":"..." }            │
├────────────────────────────────────────────────────────────────┤
│  途径 3: Data Explorer                                         │
│    SUBMIT 查询后 → SAVE AS → TASK                              │
│    ⚠️ Web UI 会偷偷给你的 FLUX 加一个 to(bucket) 把结果写回    │
├────────────────────────────────────────────────────────────────┤
│  途径 4: Notebook                                              │
│    Action Cell → Schedule a Task                               │
└────────────────────────────────────────────────────────────────┘
```

### 2.3 任务的 FLUX `option task` 配置块

```flux
option task = {
    name:   "example_task",
    every:  30s,           // 每 30 秒执行一次
    offset: 0m,            // 数据迟到补偿(下文详解)
}
// 或者用 cron
// option task = { name: "...", cron: "0 * * * *" }

import "json"
import "http"

from(bucket: "test_init")
  |> range(start: -30s)
  |> filter(fn: (r) => r._measurement == "go_goroutines")
  |> first(column: "_value")
  |> map(fn: (r) => {
        status_code = http.post(
            url:  "http://localhost:8080/",
            data: json.encode(v: r),
        )
        return {r with status_code: status_code}
     })
```

> ⚠️ 原讲义 13.2.5 代码块里 `filter(fn: (r) => r["measurement"] == "go_goroutines")` 漏了下划线,**应是 `r["_measurement"]`**。漏了下划线脚本永远查不到数据(同 03 章勘误第 11 条)。

### 2.4 完整任务调用链(讲义示例)

```
┌────────────────────────────────────────────────────────────────────┐
│  InfluxDB Task Scheduler (每 30s 触发)                             │
│                              │                                     │
│                              ▼                                     │
│  执行 FLUX 脚本                                                    │
│                              │                                     │
│       ┌──────────────────────┼──────────────────────┐              │
│       ▼                      ▼                      ▼              │
│   from(bucket)           filter +              json.encode         │
│   range(start)           first                       │             │
│       │                      │                       ▼             │
│       └──────▶ TSM 引擎 ◀────┘                  http.post (FLUX) ─┐
│                查到 1 条 _value                                    │
│                                                                    │ ▼
│                                                            ┌──────────────────┐
│                                                            │ SimpleHttpPost   │
│                                                            │ Server (用户应用)│
│                                                            │ port 8080        │
│                                                            └──────────────────┘
│                                                                    │
│                              ◀───── 返回 status_code(200/4xx/...) │
│                              │                                     │
│                              ▼                                     │
│              map 拼上 status_code 列 → 表流                       │
│                              │                                     │
│                              ▼                                     │
│              任务执行完毕,记录到 task run history(SQLite)        │
└────────────────────────────────────────────────────────────────────┘
```

### 2.5 数据迟到问题与 `offset`

**问题**:任务每 30s 执行,查最近 30s 的数据。但**网络/采集**有延迟,本该在 1:20 入库的数据可能 1:32 才落地 → 1:30 的任务运行时还查不到它 → **漏数据**。

```
没有 offset:
       T=1:30 任务触发                  T=2:00 任务触发
       │ 查窗 [1:00, 1:30]              │ 查窗 [1:30, 2:00]
       ▼                                 ▼
       ── 1:20 数据本应在这里
                  ▲
                  │ 1:32 才迟到入库 ← 错过了!
                  │
       这条点永远不会被任何一次任务查到

有 offset=5s:
       T=1:35 任务才触发(实际推迟 5s)
       │ 查窗仍然是 [1:00, 1:30]
       ▼
       ── 1:20 数据已经在 1:32 入库 → 1:35 查时能命中 ✓
```

```flux
option task = {
    name:   "example_task",
    every:  30s,
    offset: 5s,    // ← 延迟触发,但查询窗口不变
}
```

**`offset` 的语义**:**只推迟"什么时候执行",不改变"查什么数据范围"**。

### 2.6 调度表达式:`every` vs `cron`

| 写法 | 适用 |
| --- | --- |
| `every: 30s` / `every: 5m` / `every: 1h` | 固定间隔 |
| `cron: "0 * * * *"`(每小时整点) | 复杂日历调度 |

可以参考 `https://www.runoob.com/linux/linux-comm-crontab.html` 或在线 cron 生成器。

### 2.7 Web UI 创建任务的"小动作"

**Web UI 通过 SAVE AS → TASK 创建任务时**:

1. 自动在脚本最前**插入 `option task = {...}`**
2. **强制要求选 Output Bucket**,自动在脚本末尾追加 `|> to(bucket: "<OutputBucket>")`,**把结果回写到 InfluxDB**

```
你写的:                                    Web UI 实际保存的:
from(bucket: "src")                         option task = {name:"...", every:"30s"}
  |> range(start: -30s)                     from(bucket: "src")
  |> filter(...)                              |> range(start: -30s)
                                              |> filter(...)
                                              |> to(bucket: "<你选的OutputBucket>")  ← 加了这句
```

> ⚠️ **如果你的任务本不该回写数据**(比如只是发 HTTP 到外部),用 Web UI 创建会把数据多写一份到 bucket 里 — **既污染存储又费 IO**。
>
> **干净的做法是用 `influx task create -f xxx.flux`**,文件里的 FLUX 一字不改。

## 三、仪表盘(Dashboard)

### 3.1 仪表盘的内部结构

```
┌────────────────────────────────────────────────────────────────┐
│  Dashboard "System"                                            │
│                                                                │
│  ┌──── Variable(顶部下拉菜单) ────────────────────────────┐  │
│  │  CPU = [cpu0 ▼]                                          │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  ┌── Cell 1 ──┐   ┌── Cell 2 ──┐   ┌── Cell 3 ──┐            │
│  │ FLUX 查询  │   │ FLUX 查询  │   │ FLUX 查询  │            │
│  │     ↓      │   │     ↓      │   │     ↓      │            │
│  │ Graph      │   │ Single Stat│   │ Band Chart │            │
│  └────────────┘   └────────────┘   └────────────┘            │
│                                                                │
│  ┌── Note Cell(Markdown 说明) ──┐                           │
│  └────────────────────────────────┘                           │
└────────────────────────────────────────────────────────────────┘
```

**关键点**:**每个 Cell 背后都是一段独立的 FLUX 脚本**;打开仪表盘的瞬间,所有 Cell 的 FLUX 同时执行。

### 3.2 仪表盘控件速查

| 按钮/菜单 | 功能 |
| --- | --- |
| 刷新图标 | 手动重新执行所有 Cell 的查询 |
| `ENABLE AUTO REFRESH` | 自动刷新(支持 5s/10s/30s/1m/...) |
| `Local` | 显示时区切换(Local / UTC) |
| 时间范围下拉 | 同步控制所有 Cell 的查询时间窗 |
| `+ ADD CELL` | 添加图表 Cell |
| `+ ADD NOTE` | 添加 Markdown 说明 Cell |
| `Show Variables` | 显示/隐藏顶部变量下拉 |
| Annotation 开关 | Shift + 鼠标点画参考线 |
| `...` 菜单 | 全屏 / 黑夜模式 |

### 3.3 变量(Variable)

#### 三种类型

```
┌─────────────────────────────────────────────────────────────────┐
│  Type: Query (动态)                                             │
│    import "influxdata/influxdb/schema"                          │
│    schema.tagValues(bucket: "example02", tag: "cpu")            │
│      → 实时从数据查出当前所有 cpu 标签值                        │
├─────────────────────────────────────────────────────────────────┤
│  Type: Map(静态键值对)                                         │
│    {"prod": "bucket-prod-id", "dev": "bucket-dev-id"}           │
├─────────────────────────────────────────────────────────────────┤
│  Type: CSV(静态值列表)                                         │
│    cpu0                                                         │
│    cpu1                                                         │
│    cpu2                                                         │
│    cpu1|cpu2     ← 正则字符串,配合 regexp.matchRegexpString 用 │
└─────────────────────────────────────────────────────────────────┘
```

#### Cell 中引用变量

```flux
from(bucket: "example02")
  |> range(start: v.timeRangeStart, stop: v.timeRangeStop)   // 内置时间变量
  |> filter(fn: (r) => r.cpu == v.CPU)                       // 用户自定义变量 CPU
```

**特殊内置变量**:

| 变量 | 含义 |
| --- | --- |
| `v.timeRangeStart` | 仪表盘顶部时间窗起点 |
| `v.timeRangeStop` | 仪表盘顶部时间窗终点 |
| `v.windowPeriod` | 系统根据时间范围自动算的窗口大小 |

#### 示例:用 CSV 变量 + 正则一次显示多条 series

```flux
import "regexp"

basedata = from(bucket: "example02")
  |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
  |> filter(fn: (r) => r._measurement == "cpu")
  |> filter(fn: (r) => r._field == "usage_user")
  |> filter(fn: (r) =>
        regexp.matchRegexpString(r: regexp.compile(v: v.cpuxxx), v: r.cpu))

basedata |> aggregateWindow(every: 1m, fn: median, createEmpty: false) |> yield(name: "median")
basedata |> aggregateWindow(every: 1m, fn: max,    createEmpty: false) |> yield(name: "max")
basedata |> aggregateWindow(every: 1m, fn: min,    createEmpty: false) |> yield(name: "min")
```

把 `v.cpuxxx` 设为 `cpu1|cpu2`,就同时显示两条 series。

> ⚠️ 原文 14.4.3 代码块写 `regexp.matchRegexping`/`Guamempty` — 都是**OCR 识别错误**。真实函数名:
> - `regexp.matchRegexpString`(讲义代码解释里就拼对了)
> - `aggregateWindow(every:.., fn:.., createEmpty: false)`(不是 `Guamempty`)

### 3.4 Band Chart(带边界的折线图)

```
        ┌─ upper(max)
        │
    ╭───┴───╮      ┌─ main(median)
    │       │   ╭──┘
────┴───────┴───┴───────  ← lower(min)
```

UI 配置:`Customize → Aggregate Functions`,分别指定 Upper / Main / Lower 三列。要求 FLUX 输出**三个 yield**:对应 `max` / `median` / `min` 三个名字。

## 四、模板 / 任务 / 仪表盘的关系图

```
┌────────────────────────────────────────────────────────────────────┐
│                       InfluxDB Template                            │
│                                                                    │
│  ┌──── Bucket ────────────┐   ┌──── Telegraf 配置 ────────────┐   │
│  └────────────────────────┘   └────────────────────────────────┘   │
│                                                                    │
│  ┌──── Dashboard ─────────┐   ┌──── Task ────────────────────┐    │
│  │  Cells(每个 = FLUX) │   │  option task = {every: ...}    │    │
│  │  Variables           │   │  FLUX 查询 / 写回 / 报警       │    │
│  └────────────────────────┘   └────────────────────────────────┘   │
│                                                                    │
│  ┌──── Check / Notification(报警三件套,见 07 章) ────────────┐  │
│  └────────────────────────────────────────────────────────────┘    │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
        │                                       ▲
        │  influx apply -f xxx.yml              │
        │                                       │
        ▼                                       │
   一次性创建以上所有资源,绑定到一个 Stack(实例)
```

**实战体感**:模板是"一键装系统",Task 是 "cron 跑 FLUX",Dashboard 是 "FLUX 结果的可视化封装"。三者底层最终都是 FLUX 脚本。

## 五、本章勘误小结

| # | 原文位置 | 原文说法 | 实际情况 |
| --- | --- | --- | --- |
| 1 | 13.2.5 example | `filter(fn: (r) => r["measurement"] == ...)` | 漏下划线,**应为 `r["_measurement"]`**,否则永远不命中 |
| 2 | 13.4 | 默认是 cron 5 字段 | InfluxDB Task 的 cron **支持 5、6、7 字段**(6 字段为带秒,7 字段含年);讲义说"5、6、7"是 easy-cron 工具的能力,InfluxDB Task 本身底层用 `robfig/cron`,**完整支持 5/6 字段** |
| 3 | 13.5 | "InfluxDB 抓取任务背后就是定时执行的 FLUX 脚本" | ✅ 概念对的,**但需要在 `experimental` 包,生产慎用**(API 不稳定);讲义没提示 |
| 4 | 14.3.4 example | `Guamempty: false` | **应为 `createEmpty: false`**,讲义因 PDF 排版被识别错;同理 `aggregateWindow` 参数名 |
| 5 | 14.4.3 example | `regexp.matchRegexping` | **应为 `regexp.matchRegexpString`**(讲义文字部分已经写对,代码块是 OCR 错) |
| 6 | 12.3.1 | "InfluxDB 2.4 的 FLUX 版本是 0.179,Influx2.0 就是 0.131.0。4 次迭代就能让 FLUX 相差 40 多个版本" | ✅ 论据正确;**补一点**:截至 InfluxDB 2.7+,FLUX 已转入维护模式,新功能转移到 InfluxDB 3.x 的 SQL/PyFlow,旧模板兼容问题只会更严重 |
| 7 | 13.2.7 | "option task 在 Data Explorer SUBMIT 时不会生效" | ✅ 正确;**因为 `option task` 是给 Task Scheduler 读的,Data Explorer 一次性查询不解析它** |
| 8 | 14.2 控件描述 | 把"开启注解(Annotation)"描述为"添加参考线" | 准确说,Annotation 在 2.4 加入,是**在时间轴上标记事件点**(可以是简单 vline,也可以是 range);Shift+click 是快捷创建 |
| 9 | 12.2.4 | "Telegraf 启动前要声明 INFLUX_TOKEN/INFLUX_HOST/INFLUX_ORG" | ✅ 对;**讲义没说为什么**:这三个变量是 docker 模板的 telegraf 配置文件里用 `${INFLUX_TOKEN}` 这种 placeholder 引用的,启动时由 Telegraf 自身做环境变量替换 |
