## 一、InfluxDB 行协议(Line Protocol)— 必修

> 第 21 章

### 1.1 一行的结构

```
measurement,tag1=v1,tag2=v2 field1=fv1,field2=fv2 1556813561098000000
└─────────┘└──────────────┘└──────────────────┘└──────────────────┘
     │            │                  │                   │
     │            │                  │                   └─ Unix 时间戳(可选)
     │            │                  └─ Field Set       
     │            └─ Tag Set(可选)
     └─ Measurement(必需)

   ↑           ↑                    ↑
   │           │                    │
   无空格,逗号连接                   未转义空格分隔
```

**核心规则**:
- **measurement 与第一个 tag 之间用逗号 `,` 连接,不能有空格**
- Tag Set / Field Set 内部用逗号分隔多个键值对
- **`tag,tag,tag` ↔ `field,field,field` 之间是 *第一个* 未转义空格**
- **Field Set ↔ Timestamp 之间是 *第二个* 未转义空格**

### 1.2 4 个组成部分

| 元素 | 必需? | 大小写敏感 | 数据类型 | 典型用途 |
| --- | --- | --- | --- | --- |
| **measurement** | ✅ | ✅ | string | 表名 |
| **Tag Set** | ⛔ 可选 | ✅ | key/value 都是 **string** | 索引维度(host/region/...) |
| **Field Set** | ✅ 至少 1 个 | ✅ | float/int/uint/string/bool | 具体的指标值 |
| **Timestamp** | ⛔ 可选 | — | Unix 时间戳(默认纳秒) | 不写则取服务端当前时间 |

> ⚠️ **规则陷阱**:
> - measurement 和 tag key 都**不能以 `_` 下划线开头**(下划线是 FLUX 系统列保留前缀)
> - **tag 的值只能是 string**(数值类 tag 也会被存为字符串)
> - field 值不允许换行 — 如果是 string field 必须用双引号引起来

### 1.3 各类型 Field 的字面量

```
# float (默认):
myMeasurement fieldKey=1.0
myMeasurement fieldKey=1
myMeasurement fieldKey=-1.23e+78

# integer(尾巴加 i):
myMeasurement fieldKey=123i

# uinteger(尾巴加 u):
myMeasurement fieldKey=42u

# string(必须双引号):
myMeasurement fieldKey="this is a string"

# boolean(t/T/true/TRUE 或 f/F/false/FALSE,不要加引号):
myMeasurement fieldKey=true
myMeasurement fieldKey=t
myMeasurement fieldKey=FALSE
```

### 1.4 整数范围

| 类型 | 范围 |
| --- | --- |
| int | `-9223372036854775808i` ~ `9223372036854775807i` |
| uint | `0u` ~ `18446744073709551615u` |

### 1.5 时间戳精度

写入 `/api/v2/write` 时 URL 参数 `precision=` 指定:

| precision | 单位 | 时间戳示例 |
| --- | --- | --- |
| `ns`(默认) | 纳秒 | `1556813561098000000` |
| `us` | 微秒 | `1556813561098000` |
| `ms` | 毫秒 | `1556813561098` |
| `s` | 秒 | `1556813561` |

### 1.6 注释

以 `#` 开头的整行被忽略:

```
# 这是一行注释
myMeasurement fieldKey="value" 1556813561098000000
```

### 1.7 行协议处理流程图

```
┌──────────────────────────────────────────────────────────────────┐
│  客户端(SDK / curl / Web UI / Telegraf)                         │
│  生成行协议文本                                                  │
└────────────────────────────────┬─────────────────────────────────┘
                                 │
                                 │ POST /api/v2/write
                                 │   ?org=xxx&bucket=xxx&precision=ns
                                 │ Content-Type: text/plain
                                 │ Authorization: Token xxx
                                 │ Body: <行协议文本>
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│  influxd HTTP Handler                                            │
│  ├─ 鉴权(Token 检查)                                           │
│  ├─ 行协议解析器                                                │
│  │     • 分词(measurement/tag/field/timestamp)                 │
│  │     • 类型推断或显式类型(i/u/" "/t/f)                       │
│  ├─ Schema 校验(若 bucket 为 explicit schema)                   │
│  ▼                                                               │
│  WAL(写前日志) ──▶ MemTable ──▶ TSM 文件                       │
│         + TSI 索引(measurement + tag set 倒排)                  │
└──────────────────────────────────────────────────────────────────┘
```

## 二、拓展的带注释 CSV(Annotated CSV)

> 第 20 章

### 2.1 为什么 FLUX 需要给 CSV 加注释

普通 CSV 不带类型信息:

```csv
m,host,used_percent,time
mem,host1,64.23,2020-01-01T00:00:00Z
```

主流解决思路是"客户端类型推断"或"显式声明列类型",**FLUX 选择第三条路 — 在文件最前面加 `#` 注释行**。

> 💡 **重要事实**:你查询 InfluxDB 通过 HTTP API 时,**返回的就是 Annotated CSV**。SDK / Web UI 帮你把它解析成结构化对象,但底层就是这个格式。

### 2.2 4 种拓展注释

#### `#datatype` — 列类型映射

```csv
#datatype measurement,tag,double,dateTime:RFC3339
m,host,used_percent,time
mem,host1,64.23,2020-01-01T00:00:00Z
```

| 注释类型 | InfluxDB 角色 |
| --- | --- |
| `measurement` | 这列是 measurement |
| `tag` | 这列是 tag |
| `field` | 这列是 field(类型不限,详见下) |
| `dateTime` | 这列是时间戳,可加格式后缀 |
| `ignored` | 忽略此列 |
| `string` | string field |
| `double` | float field |
| `long` | int field |
| `unsignedLong` | uint field |
| `boolean` | boolean field |

**dateTime 子格式**:

```
#datatype dateTime:RFC3339         ← 2006-01-02T15:04:05Z
#datatype dateTime:RFC3339Nano     ← 2006-01-02T15:04:05.999999999Z
#datatype dateTime:number          ← Unix 纳秒
#datatype dateTime:2006-01-02      ← 自定义 Go time layout
```

**数值类型的高级格式**:

```
#datatype "long: .,"           ← 小数点 + 千位分隔符(用 . 作小数点、, 作千位)
#datatype "boolean:y,Y,1:n,N,0" ← 自定义 true/false 值
```

> ⚠️ **OpenMetrics/Prometheus 也走"格式即标准"路线,但 FLUX 这种"注释行"方式让 CSV 能在 Excel 里打开还不乱**。

#### `#group` / `#default`(原文未细讲,但实际常用)

```csv
#group false,false,true,false       ← 这列是不是 GroupKey
#default _result,,,                 ← 缺失值的默认填充
#datatype string,long,string,double
```

#### `#constant` — 给所有行追加固定列

```csv
#constant measurement,m
#constant tag,dataSource,csv

host,value,time
h1,1,2020-01-01T00:00:00Z
```

等价于行协议:`m,host=h1,dataSource=csv value=1 ...`

**语法**:`#constant <datatype>,<column-label>,<column-value>`(measurement 是特例不需要 label)。

#### `#timezone` — 数据所在时区

```csv
#timezone +0800
```

数据是相对 UTC 偏移 8 小时。如果时间字符串里已经带时区(如 `Z` 或 `+08:00`)就不需要。

#### `#concat` — 由其它列拼出新列

```csv
#concat,dateTime:2006-01-02,${Year}~${Month}~${Day}
Year,Month,Day,Hour,Minute,Second,Tag,Value
2020,05,22,00,00,00,test,0
```

> 💡 主要用于"把日期拆成多个列了,需要重组"。

### 2.3 严格模式

```
#datatype long:strict,double:strict
```

类型不匹配时**整行导入失败**;不加 `:strict` 则尝试截断/兼容。

### 2.4 自定义分隔符

```
sep=;
```

放在文件最开始,把分隔符从 `,` 改为 `;`。

> ⚠️ 原文 20.3 例子写 `seq=;` — **拼写错误,正确是 `sep=`**(seperator)。

### 2.5 简短注释(列头内嵌)

```csv
m|measurement,location|tag|Hong Kong,temp|double,pm|long|0,time|dateTime:RFC3339
weather,San Francisco,51.9,38,2020-01-01T00:00:00Z
weather,,52.1,,2020-01-01T00:00:00Z
```

格式:`列名|类型|默认值`,默认值可空(用空字符串)。等价的注释行写法是 `#datatype` + `#default` 组合。

## 三、Prometheus 数据格式

> 第 22 章

### 3.1 行结构

```
metric_name{label1="v1",label2="v2"} 42.5 1556813561098
└────────────────────────────────┘  └──┘ └─────────────┘
        指标名 + 标签集               值     Unix 毫秒时间戳(可选)
                                          ↑          ↑
                                          第 1 个空格  第 2 个空格
```

| 元素 | 必需? | 备注 |
| --- | --- | --- |
| 指标名 | ✅ | 类似 measurement |
| 标签集 | 可选 | `{k="v",k="v"}`,**值必须是字符串** |
| 值 | ✅ | **必须是 float**(包括整数也按浮点存) |
| 时间戳 | 可选 | **Unix 毫秒**(注意!不是纳秒) |

### 3.2 vs InfluxDB 行协议

| 维度 | Prometheus | InfluxDB Line Protocol |
| --- | --- | --- |
| 一行一个指标 | ✅ | ✅ |
| 同一行可多个值 | ❌(单一 value) | ✅(多 field) |
| 默认时间戳精度 | **毫秒** | **纳秒** |
| 数值类型 | 仅 float | float / int / uint / string / bool |
| 标签值类型 | 仅 string | 仅 string(tag) |
| 注释 | `# HELP` / `# TYPE` 元数据 + `# ...` | `# ...` |

### 3.3 完整 Prometheus 文本格式示例

```
# HELP go_gc_duration_seconds A summary of the pause duration.
# TYPE go_gc_duration_seconds summary
go_gc_duration_seconds{quantile="0"} 3.7819e-05
go_gc_duration_seconds{quantile="0.5"} 0.000115633
go_gc_duration_seconds_sum 0.015866833
go_gc_duration_seconds_count 88
# HELP go_goroutines Number of goroutines that currently exist.
# TYPE go_goroutines gauge
go_goroutines 1222
```

`# HELP` / `# TYPE` 是**元数据行**(描述指标含义 + 类型);四种 type:`counter` / `gauge` / `histogram` / `summary`。

### 3.4 OpenMetrics

OpenMetrics 是 CNCF 标准化的"Prometheus 数据格式++"。**100% 向后兼容 Prometheus**,补充了 OpenMetrics-only 的功能(exemplar、UTF-8 metric names 等)。**新项目应优先 OpenMetrics**。

### 3.5 InfluxDB 与 Prometheus 数据的转换

```
                          Prometheus 数据格式
                                 │
                    ┌────────────┴────────────┐
                    │                          │
            InfluxDB 内置 Scraper      Telegraf prometheus input
                    │                          │
                    └────────────┬────────────┘
                                 │
                                 ▼
                    转成 InfluxDB Series:
                    ┌─────────────────────────────────────────┐
                    │ measurement = metric_name(或拆分)       │
                    │ tags        = labels                    │
                    │ field       = "value" 或 le/quantile 等 │
                    │ timestamp   = Unix 毫秒 → 纳秒          │
                    └─────────────────────────────────────────┘
```

> 反过来,InfluxDB 也可以**导出**给 Prometheus(通过 `/api/v1/prom/read` 等兼容端点),但常见做法仍是 Grafana 直接同时连两者。

## 四、时间的标准与格式

> 第 24 章

### 4.1 历史链:GMT → UT → UTC

```
┌──── GMT (1884, 格林尼治标准时间) ────┐
│  天文观测确定的英国格林威治本初子午线  │
│  0 度经线 → 0 时区                    │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──── UT (1928, 世界时) ────┐
│  以 GMT 子夜为 0 点,通过 │
│  天文观测衡量"一天多长"   │
└──────────────┬───────────┘
               │  天文观测有误差,地球自转变慢
               ▼
┌──── TAI (1955, 国际原子时) ────┐
│  铯-133 原子辐射 9,192,631,770  │
│  周 = 1 秒                      │
│  以 GMT 1958-01-01 00:00 起步   │
└──────────────┬─────────────────┘
               │
               ▼
┌──── UTC (1970+, 世界协调时) ───────────────┐
│  • 秒长用 TAI(精确)                       │
│  • 但通过"闰秒"机制让 UTC 贴近 UT(贴近天文)│
│                                            │
│  闰秒:某一分钟可能有 61 秒 (1分60秒)       │
│  对计算机程序破坏性大                       │
│  → 国际上正在讨论废止闰秒                  │
└────────────────────────────────────────────┘
```

**实战记忆**:
- GMT 是早期标准、UTC 是现代标准
- 严格说 GMT ≠ UTC,**但宽松场景可以等同**
- 现在写 "GMT" 通常指 **0 时区**(地理),而非时间标准

### 4.2 时区 = UTC + 偏移

```
北京时间 = UTC + 08:00      记法:UTC+08:00 / GMT+0800
东京     = UTC + 09:00
洛杉矶   = UTC - 08:00(冬令) / UTC - 07:00(夏令)
```

- **偏移不限于整小时**:UTC+12:45(查塔姆群岛)、UTC+05:30(印度)
- **偏移上限超过 ±12 小时**:有的国家用 UTC+14:00
- **避免用 CST/CCT 等三字母缩写**:CST 可能是
  - China Standard Time(中国)
  - Central Standard Time(美国中部)
  - Cuba Standard Time(古巴)
  - Australian Central Standard Time(澳大利亚)

### 4.3 ISO 8601 与 RFC 3339

```
┌──── ISO 8601 (国际标准化组织, 1988+) ────┐
│  完整描述日期 / 时间 / 区间 / 周历        │
│  非常灵活,有些写法可读性差              │
│  例:2022-242T16:55:17/PT3H (不直观)      │
└──────────────────────────────────────────┘

┌──── RFC 3339 (IETF, 2002) ────┐
│  ISO 8601 的"互联网友好子集"  │
│  砍掉小众/歧义写法,可读性好  │
│  例:2022-09-03T14:13:00Z       │
└───────────────────────────────┘
```

**关系**:`RFC 3339 ⊂ ISO 8601`,InfluxDB 时间戳输出统一用 RFC 3339。

### 4.4 RFC 3339 时间字符串详解

```
2022-09-03 T 14:13:00.123456789 Z
└────────┘ │ └────────────────┘ │
   日期    │     时分秒.纳秒    │
           │                    │
       分隔符 T                 时区
                                ├─ Z = UTC(0 时区)
                                ├─ +08:00 = UTC+8
                                └─ -07:00 = UTC-7
```

合法变体:
```
2022-09-03                          ← 仅日期
2022-09-03T14:13:00Z                ← 秒级精度
2022-09-03T14:13:00.000Z            ← 毫秒
2022-09-03T14:13:00.123456789Z      ← 纳秒
2022-09-03T22:13:00+08:00           ← 同上时刻 (北京)
```

### 4.5 在 JavaScript 中验证

```js
// 取当前时间(浏览器本地)
let x = new Date()
// Sat Sep 03 2022 14:44:29 GMT+0800 (中国标准时间)

// 转 RFC 3339 / ISO 8601
x.toISOString()
// "2022-09-03T06:44:29.000Z"  ← 时区被转成 0 时区
```

### 4.6 Unix 时间戳与闰秒

```
Unix 时间戳:从 1970-01-01T00:00:00Z 起到现在的"秒数"
            (不论你在地球哪里,这个值都一样)

精度变体:
   1556813561              ← 秒
   1556813561098           ← 毫秒
   1556813561098000        ← 微秒
   1556813561098000000     ← 纳秒(InfluxDB 默认)
```

**Unix 时间戳怎么处理闰秒?** 答案是 **不处理 — 把时钟变慢一点滑过去**:

```
正常 23:59:59 ─▶ 应该插一秒 60 ─▶ 直接进入 00:00:00
                      ↑
              Unix 时间戳在这里通过"放慢时钟"平滑过渡
              (Linux 上对应的是 NTP smear / Google Time)
```

**优点**:Unix 时间戳永远是单调递增的整数,程序逻辑简单。
**代价**:闰秒前后约 1 秒内,精度略低于真实物理时间。

## 五、四种数据/时间格式的对照表

| 用途 | 推荐格式 |
| --- | --- |
| **写入** InfluxDB | Line Protocol(行协议) |
| **导入** CSV → InfluxDB | Annotated CSV |
| **从 Prometheus 抓取**指标 | Prometheus 文本 / OpenMetrics |
| **时间戳字段** | RFC 3339 字符串 或 Unix 纳秒 |
| **从 InfluxDB HTTP API 取数据** | Annotated CSV(自动) |
| **代码中比较时间** | Unix 纳秒整数 |
| **日志/给人看的时间** | RFC 3339 |

## 六、本章勘误小结

| # | 原文位置 | 原文说法 | 实际情况 |
| --- | --- | --- | --- |
| 1 | 20.3 | `seq=;` | **拼写错误**,正确是 `sep=;`(separator 缩写) |
| 2 | 20.4 简短注释例子 | 例子里第三行 `weather, 53.6, 171, 2020-01-01T00:00:00Z` 看上去字段数少了一列 | 简短注释允许列里**省略默认值列**(因为列头已经声明默认值),但**示例文本里应明确"location 列被省略而用默认值 Hong Kong 填充"** |
| 3 | 21.2 measurement | "不可以用下划线 `_` 打头" | ✅ 对;**补充**:tag key / field key 也都不能以 `_` 开头(保留给 FLUX 系统列) |
| 4 | 21.7.6 Unix Timestamp 示例 | `myMeasurementName fieldKey="fieldValue" 1556813561098000000` | ✅ 对的;但讲义没明说该时间戳是**纳秒**(13 位是毫秒,16 位是微秒,19 位是纳秒) |
| 5 | 21.4 Field Set | "字段集的键是大小写敏感的" | ✅;**补充**:**同一个 series 内,同一个 field key 在不同时间点上的 value 类型必须一致**;前一秒写 `temp=1i`、后一秒写 `temp=1.0` 会触发 type conflict 写入失败 |
| 6 | 22.1 Prometheus | "近期 Prometheus 技术热度高涨" + "OpenMetrics" | ✅;**截至 2024**,OpenMetrics 已被 Prometheus 项目正式吸收为默认输出格式,新版本可直接说"Prometheus 即 OpenMetrics" |
| 7 | 22.2 默认时间戳 | 只说"Unix 时间戳" | **应明确是 Unix 毫秒**;讲义第 22.2 (4) 写"毫秒",但前文未强调,易和 InfluxDB 的纳秒混淆 |
| 8 | 24.3 国际原子时定义 | "国际原子时的秒长以格林威治时间 1958-01-01 0 时的秒长为基准" | 准确说,**TAI 起算时刻**是 1958-01-01 00:00:00 UT,**当时 TAI = UT2**;现在 TAI 已经领先 UTC 约 37 秒(累计闰秒) |
| 9 | 24.8 ISO 8601 描述 | "ISO 8601 是一种标准的时间格式" | ✅;**更准确**:ISO 8601 不止是时间格式,还包括周历、时间区间、持续时间等表达式,所以才会有"2022-242T...PT3H"这种序数日 + 时区间组合 |
| 10 | 24.11 RFC 3339 vs ISO 8601 | "RFC 3339 表述都能第一时间反应过来" | ✅ 思路对;**精确说**:RFC 3339 强制了 `YYYY-MM-DD` 格式 + `T` 分隔 + 时区后缀,**剔除了 ISO 8601 中的"基本格式(无分隔符)"和"周日期"等子集** |
| 11 | 24.12.2 | "Unix 时间戳处理闰秒的答案是减慢时钟" | ✅ Linux 的常见做法是 NTP 平滑(Google smear / Facebook 24h smear);**严格按 POSIX 定义,Unix 时间戳的某些秒数会被"复用"(同一秒值表示两个真实时刻)**。两种实现方式都存在 |
