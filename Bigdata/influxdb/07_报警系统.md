## 一、报警的本质:周期 FLUX 任务

> 监控 = "每隔一段时间对数据计算 + 比阈值 + 触发动作"

InfluxDB 2.x 的报警系统**底层就是定时任务(Task)**,但 UI 把它单独拆出来,以"三件套"的形式让用户配置。

```
                    ┌────────────────────────────────────────────────────────────┐
                    │       InfluxDB 报警三件套 (Alerts)                         │
                    │                                                            │
                    │   ┌────────────┐    ┌───────────────────┐                  │
                    │   │   CHECK    │    │ NOTIFICATION      │                  │
                    │   │ (检查任务) │───▶│   RULE (规则/路由)│                  │
                    │   └─────┬──────┘    └────────┬──────────┘                  │
                    │         │                    │                             │
                    │         │ 写入                │ 查询 + 路由                 │
                    │         ▼                    ▼                             │
                    │   ┌────────────────────────────────────┐                   │
                    │   │  _monitoring Bucket (内置)         │                   │
                    │   │   • statuses(check 状态历史)      │                   │
                    │   │   • notifications(通知历史)       │                   │
                    │   └────────────────────────────────────┘                   │
                    │                              │                             │
                    │                              ▼                             │
                    │                  ┌───────────────────────┐                 │
                    │                  │ NOTIFICATION ENDPOINT │                 │
                    │                  │  (HTTP / Slack /      │                 │
                    │                  │   Pagerduty)          │                 │
                    │                  └───────────┬───────────┘                 │
                    └──────────────────────────────┼─────────────────────────────┘
                                                   │
                                                   ▼
                                            外部接收方
```

## 二、三件套的角色

| 组件 | 中文 | 角色 | 本质 |
| --- | --- | --- | --- |
| **Check** | 检查 | 周期跑 FLUX,把数据评估为 4 个级别状态 | **Task**,结果写入 `_monitoring` |
| **Notification Endpoint** | 报警终端 | 把消息发到外部 | HTTP / Slack / PagerDuty 客户端 |
| **Notification Rule** | 报警规则 | 路由:从 `_monitoring` 查最近状态,匹配到的发给某个 Endpoint | **Task**,查 `_monitoring` + 发送 |

### 2.1 四个状态级别

```
CRIT(critical) — 严重紧急
WARN(warning)  — 警告
INFO            — 普通信息
OK              — 状态良好
```

## 三、完整工作流(Check + Rule + Endpoint)

```
┌──────────────────────────────────────────────────────────────────────────┐
│  时刻 T  (周期触发,如 15s 一次)                                          │
│                                                                          │
│  Step 1: CHECK 任务运行                                                  │
│  ┌──────────────────────────────────────────────────────────────────┐    │
│  │  from(bucket: "example_alert")                                   │    │
│  │    |> range(start: -15s)                                         │    │
│  │    |> filter(fn: r => r._measurement=="co" and r._field=="value")│    │
│  │    |> aggregateWindow(every:15s, fn: max)                        │    │
│  │    |> monitor.check(crit: r.value > 0.04, warn: r.value > 0.01, │    │
│  │                     ok:   r.value <= 0.01, ...)                  │    │
│  └──────────────────────────────┬───────────────────────────────────┘    │
│                                 │                                        │
│                                 ▼ 写入                                   │
│  ┌──────────────────────────────────────────────────────────────────┐    │
│  │  _monitoring  Bucket                                              │    │
│  │  measurement="statuses"                                           │    │
│  │  tags={ _check_id, _check_name, _level }                          │    │
│  │  fields={ _message, _source_*, value, ... }                       │    │
│  └──────────────────────────────────────────────────────────────────┘    │
│                                                                          │
│  Step 2: NOTIFICATION RULE 任务(独立调度,如 15s 一次)                  │
│  ┌──────────────────────────────────────────────────────────────────┐    │
│  │  monitor.from(start: -15s)              ← 查 _monitoring          │    │
│  │    |> filter(fn: r => r._level == "crit")                         │    │
│  │    |> filter(fn: r => r._check_name == "CO_Alert")                │    │
│  │    |> monitor.notify(                                              │    │
│  │         endpoint: http.endpoint(url:"http://host:8080")(mapFn:...) │    │
│  │       )                                                            │    │
│  └────────────────────────┬─────────────────────────────────────────┘    │
│                           │                                              │
│                           ▼ HTTP POST(JSON)                              │
│  ┌──────────────────────────────────────────────────────────────────┐    │
│  │  外部服务(SimpleHttpPostServer / 睿象云 / Slack ...)            │    │
│  └──────────────────────────────────────────────────────────────────┘    │
│                                                                          │
│  Step 3: 同时,在 _monitoring 中也会留下 notifications 测量              │
│           (用于 Web UI 的 Alert History 显示)                            │
└──────────────────────────────────────────────────────────────────────────┘
```

> 💡 **关键认知**:Check 和 Rule **不是直接通信** — 而是 **Check 写 `_monitoring`,Rule 周期性扫 `_monitoring` 然后路由发送**。这就是为什么 Rule 也需要"调度间隔"。

## 四、Check 详解

### 4.1 两种 Check 类型

| 类型 | 触发条件 |
| --- | --- |
| **Threshold Check**(阈值检查) | 字段聚合值 vs 阈值范围 |
| **Deadman Check**(死人检查) | 某序列**多长时间没有新数据** |

### 4.2 创建 Threshold Check 的关键点

```
Define Query 阶段(只能用 Query Builder,不能 Script Editor)
   ┌─ Bucket: example_alert
   ├─ _measurement: co
   ├─ _field: value     ← One Field 必填项,即使只有一个 series 也要选
   └─ 聚合: max(根据需求选,不是 mean)

Configure Check 阶段
   ┌─ Schedule Every: 15s
   ├─ Status Message Template: shell 风格 ${...}
   │     模板内可访问数据字段:r.code,r.value(对应行协议里的 tag/field)
   └─ Thresholds(为 4 个级别配置阈值)
        CRIT  当 value > 0.04
        WARN  当 value 介于 0.01 和 0.04
        INFO  (可空)
        OK    当 value < 0.01
```

> ⚠️ 原文 19.3.6 操作描述 "_field=value 添加到过滤条件",**应明确说**:Web UI Check 创建器**要求 Query 必须输出单一 field**(`One Field` 验证项),否则 Check 不能保存。

### 4.3 消息模板

```
Check: ${r._check_name} is: ${r._level}
${r.code} value is: ${r.value}
```

- `r._check_name` / `r._level` 是系统注入的
- `r.code` / `r.value` 是数据里的 tag / field — **任何 series 里的字段都能 `${r.xxx}` 引用**

### 4.4 Check 写出的数据(_monitoring)

Check 把状态以行协议形式写入 `_monitoring` bucket:

```
measurement=statuses
tags = {
  _check_id, _check_name, _level,
  ... + 原数据中的所有 tag
}
fields = {
  _message, _source_measurement, _source_timestamp,
  ... + 原数据中的所有 field
}
time = <Check 触发时间>
```

## 五、Notification Endpoint(报警终端)

### 5.1 三种内置类型

| 类型 | 协议 | 适用 |
| --- | --- | --- |
| **HTTP** | POST,Content-Type: application/json | 通用,接入自有服务、Webhook、第三方平台(睿象云/钉钉机器人/飞书...) |
| **Slack** | Slack Webhook | 海外团队即时通讯 |
| **PagerDuty** | PagerDuty Incident API | 海外标准 on-call 工具 |

### 5.2 HTTP Endpoint 的关键限制

```
Web UI 创建 HTTP Endpoint 时:
  • 能配:URL、Auth 方式(None/Basic/Bearer)、HTTP Method
  • 不能配:请求体的 JSON 结构 — 字段名是系统固定的
```

**默认请求体结构**(SimpleHttpPostServer 收到的):

```json
{
  "_check_id":             "0a0adfc75eddc000",
  "_check_name":           "CO_Alert",
  "_level":                "crit",
  "_measurement":          "notifications",
  "_message":              "Check: CO_Alert is: crit\n01 value is: 0.06",
  "_notification_endpoint_id":   "0a0b1b37bae0a000",
  "_notification_endpoint_name": "http_endpoint",
  "_notification_rule_id":       "0a0b1fe01cfb3000",
  "_notification_rule_name":     "hahaha",
  "_source_measurement":   "co",
  "_source_timestamp":     1664244990000000000,
  "_start":                "2022-09-27T02:16:15Z",
  "_status_timestamp":     1664244990000000000,
  "_stop":                 "2022-09-27T02:16:45Z",
  "_time":                 "2022-09-27T02:16:45Z",
  "_type":                 "threshold",
  "_version":              1,
  "code":                  "01",
  "value":                 0.06
}
```

> ⚠️ **这就是 Web UI 报警的最大短板**:**HTTP Endpoint 的 body 格式硬编码**,无法定制。如果第三方平台(如**睿象云**)要求另一种 schema,Web UI 这条路就走不通。
>
> 解决办法:**用 Notebook → Export Alert Task 生成 FLUX 脚本,手改 `body` 局部变量**(下文第七节详解)。

## 六、Notification Rule(报警规则)

### 6.1 字段

| 字段 | 含义 |
| --- | --- |
| **Schedule Every** | 规则任务多久跑一次扫 `_monitoring` |
| **Conditions** | 状态级别勾选(crit/warn/info/ok 至少一个) |
| **Tag Filter** | `_check_name == "CO_Alert"` 这类标签过滤 |
| **Endpoint** | 选哪个 Endpoint 发送 |
| **Message Template** | 可覆盖 Check 的默认消息 |

### 6.2 Rule 的本质

```flux
// Rule 背后就是这样一段 FLUX(monitor.from 是 _monitoring 的 helper):
import "influxdata/influxdb/monitor"

monitor.from(start: -15s)
  |> filter(fn: (r) => r._level == "crit")
  |> filter(fn: (r) => r._check_name == "CO_Alert")
  |> monitor.notify(
       endpoint: http.endpoint(url: "...")(mapFn: (r) => {
         body = {r with _version: 1}
         return {headers: {"Content-Type": "application/json"},
                 data: json.encode(v: body)}
       }),
       data: notification,
     )
```

## 七、Notebook 直通底层(自定义 body)

### 7.1 痛点回顾

睿象云的 REST API 要求 body 是:

```json
{
  "app": "<appkey>",
  "eventId": "...",
  "eventType": "trigger",
  "alarmName": "...",
  "alarmContent": {...},
  "priority": 1
}
```

但 Web UI HTTP Endpoint 的 body 是系统固定 schema → **直接对接不上**。

### 7.2 解决方案:Notebook → Export Alert Task

```
左侧 Notebooks ─▶ Set an Alert 模板
       │
       ▼
   配置查询 + 阈值 + Endpoint URL
       │
       ▼
   EXPORT ALERT TASK
       │
       ▼
   生成一段可编辑的 FLUX
       │
       ▼
   粘到 Data Explorer,改 `body` 局部变量为睿象云格式
       │
       ▼
   Tasks → CREATE TASK → 粘改好的脚本,设 every / offset
```

### 7.3 Notebook 生成的脚本结构(逐段拆解)

```flux
// (1) 导包
import "strings"
import "regexp"
import "influxdata/influxdb/monitor"     ← Check + Notify 全靠它
import "influxdata/influxdb/schema"      ← fieldsAsCols
import "experimental"
import "http"
import "json"

// (2) Task 调度配置
option task = {
    name:   "Notebook Task for local_xxx",
    every:  10m,
    offset: 0s,
}

// (3) 仪表盘/笔记本上下文变量(Task 模式可固化)
option v = {timeRangeStart: -24h, timeRangeStop: now()}

// (4) Check 元数据(给 _monitoring 写入用)
check = {
    _check_id:   "local_xxx",
    _check_name: "Notebook Generated Check",
    _type:       "custom",
    tags:        {},
}

// (5) Notification Rule + Endpoint 元数据
notification = {
    _notification_rule_id:       "local_xxx",
    _notification_rule_name:     "Notebook Generated Rule",
    _notification_endpoint_id:   "local_xxx",
    _notification_endpoint_name: "Notebook Generated Endpoint",
}

// (6) 数据源查询
task_data = from(bucket: "example_alert")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "co")
    |> filter(fn: (r) => r._field == "value")

// (7) 阈值谓词函数(供 monitor.check 调用)
trigger = (r) => r.value > 0.04

// (8) 消息模板函数
messageFn = (r) =>
    "${strings.title(v: r._type)} for ${r._source_measurement} triggered at ${time(v: r._source_timestamp)}!"

// (9) 报警主流程
task_data
    |> schema.fieldsAsCols()                        // 把 _field/_value 二维列转横(field 名当列名)
    |> set(key: "_notebook_link", value: "http://host:8086/orgs/.../notebooks/...")
    |> monitor.check(                                // 评估状态,写 _monitoring
        data:      check,
        messageFn: messageFn,
        crit:      trigger,
        // warn, info, ok 也可用 — Notebook 默认只生成一个 crit
    )
    |> monitor.notify(                               // 路由 + 发送
        data: notification,
        endpoint: http.endpoint(url: "http://host:8080")(
            mapFn: (r) => {
                body = {r with _version: 1}        // ★ 改这里!对接外部平台就改 body
                return {
                    headers: {"Content-Type": "application/json"},
                    data: json.encode(v: body),
                }
            },
        ),
    )
```

### 7.4 为什么用 monitor.* 而不是 if/else + http.post

```
反对做法:
  filter(fn: r => r.value > 0.04) |> map(fn: r => http.post(...))

  缺点:
    × 不会留下任何 Check 状态历史
    × Alert History UI 看不到
    × 重复触发 / 抑制 / 去重逻辑都要自己实现

推荐做法:monitor.check + monitor.notify
  ✓ 写入 _monitoring,Alert History 自动显示
  ✓ Web UI 可观测
  ✓ 状态/通知历史完整保留
```

> 💡 **`schema.fieldsAsCols()`** 的作用:把 InfluxDB 的"列存"形式
> ```
> _field=value _value=0.05
> _field=other _value=...
> ```
> **转成横表**:
> ```
> value=0.05 other=...
> ```
> 这样 `monitor.check` 里的 `r.value` 才能直接取到。

## 八、改进架构 — 引入睿象云做双向监控

### 8.1 单向架构的隐患

```
InfluxDB ──告警─▶ 睿象云 ──电话──▶ 工程师

问题:如果半夜 InfluxDB 自己挂了,它就发不出告警 → 你睡得很好但其实出事了。
```

### 8.2 引入业务可用性检测(BAM)

```
                       ┌──────────────┐
       ┌──告警(出)──▶│              │──电话──▶ 工程师
       │              │   睿象云     │
   InfluxDB ◀─探活─── │              │
                       └──────────────┘
                       (每 15min 探一次 /health)
```

**关键链路**:

```
睿象云 BAM (业务可用性检测)
   │ 每 N 分钟 (免费版最短 15min)
   │
   ▼
HTTPS GET  http://<公网地址>/health
   │
   ▼
内网穿透(花生壳 / Frp / Cloudflare Tunnel)
   │
   ▼
内网 InfluxDB:8086 → 返回 200 + JSON
   │
   ├─ 2 秒内响应 → 正常
   ├─ 2-5 秒    → 缓慢
   ├─ >5 秒      → 非常缓慢
   └─ 非 200    → CRIT
   │
   ▼
睿象云告警规则评估
   │
   ├─ 严重条件:过去 15 分钟可用率 ≠ 100% → 触发
   └─ 警告条件:同上
   │
   ▼
分派策略 → 报警行为(Webhook / 电话 / 短信)
   │
   ▼
通知具体人员
```

### 8.3 睿象云核心概念映射

| 睿象云术语 | InfluxDB 对应 | 说明 |
| --- | --- | --- |
| 报警规则(检查任务) | **Check** | 评估触发条件 |
| 报警行为 | **Notification Endpoint** | 发送方式(Webhook/邮件/电话) |
| 报警策略 | **Notification Rule** | 路由:把哪个规则的告警送到哪个行为 |
| 分派策略 | **+ 人员分派**(InfluxDB 没有) | 通知到具体的人 |
| REST API | 入站 Webhook | 接收 InfluxDB 推过来的告警 |
| 业务可用性检测 | 无对应 | 外部对 InfluxDB 做反向探活 |

### 8.4 双向报警的完整架构

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│   ┌──────────────┐    1. CHECK 任务运行                                │
│   │              │       ↓                                              │
│   │   InfluxDB   │   2. _monitoring 写入                                │
│   │              │       ↓                                              │
│   │   (内网)     │   3. Notification Rule 任务                          │
│   │              │       ↓                                              │
│   └──────┬───────┘   4. HTTP POST(自定义 body)                         │
│          │               │                                              │
│          │               ▼                                              │
│          │       ┌───────────────────┐                                  │
│          │       │  睿象云 REST API  │                                  │
│          │       │  (智能告警平台)   │ ── 分派策略 ─▶ 工程师手机       │
│          │       └───────────────────┘                                  │
│          │                                                              │
│          │ 5. 内网穿透(花生壳)                                       │
│          │       ↑                                                      │
│          │       │  HTTP GET /health                                    │
│          │       │  (每 15 分钟)                                        │
│          │       │                                                      │
│          │       └─── 公网 URL ←──┐                                    │
│          │                        │                                     │
│          │                ┌───────────────────┐                         │
│          │                │  睿象云 BAM 平台  │                         │
│          │                │  (业务可用性检测) │ ── 不通 → 通知工程师   │
│          │                └───────────────────┘                         │
│          ▼                                                              │
│   ┌──────────────┐                                                      │
│   │ phddns 客户端 │                                                      │
│   │ (花生壳)      │                                                      │
│   └──────────────┘                                                      │
└─────────────────────────────────────────────────────────────────────────┘
```

**双保险**:
- InfluxDB 自检 → 数据异常告警
- 睿象云外检 → InfluxDB 自身宕机告警

## 九、实战注意事项

### 9.1 Check 的查询时间窗 vs 调度间隔

```
合理:
  every: 15s, query: -15s  (扫描刚入库的数据)

可能漏数据:
  every: 30s, query: -10s  (10s 窗 < 30s 调度,会漏 20s 的数据)

数据迟到场景:
  every: 30s, query: -30s, offset: 5s
  → 推迟 5s 触发,但仍然查最近 30s 的窗口
```

### 9.2 `_monitoring` Bucket 保留策略

```
默认 retention: 7 天
   ↓
意味着 7 天前的 statuses 和 notifications 不可查
   ↓
长期合规留痕 → 用 Task 把 _monitoring 数据降采样写到自己的 audit bucket
```

### 9.3 Deadman Check 的常见用法

```flux
import "influxdata/influxdb/monitor"

from(bucket: "sensors")
  |> range(start: -1m)
  |> filter(fn: (r) => r.device_id == "sensor-01")
  |> monitor.deadman(t: experimental.subDuration(d: 1m, from: now()))
  |> monitor.check(
       crit: (r) => r.dead == true,
       ...
     )
```

适用:**心跳缺失检测**(传感器掉线、Telegraf 失联)。

### 9.4 何时不要用 InfluxDB 内置报警

| 场景 | 推荐 |
| --- | --- |
| 简单 CO/温度/CPU 阈值,内网部署 | InfluxDB 内置 |
| 复杂去重 / 升级降级 / on-call 排班 | **PagerDuty / 睿象云 / OpsGenie** |
| 接钉钉/飞书/企业微信群机器人 | Webhook → Notebook 自定义 body |
| 需要图表附件 / 富文本通知 | **Grafana Alerting**(比 InfluxDB 强很多) |

## 十、本章勘误小结

| # | 原文位置 | 原文说法 | 实际情况 |
| --- | --- | --- | --- |
| 1 | 19.3.4 数据模板 | `co, code=01 value=0.001` | 行协议中 measurement 后**不能有空格**,正确:`co,code=01 value=0.001`。多处样本数据都犯了这个错(同 02 章勘误) |

| 3 | 19.3.13 工作原理图 | 描述 Rule 是定时任务 | ✅ 对,但应强调 **Rule 的调度间隔不要小于 Check 的调度间隔**,否则会因为 Check 还没写入而漏发 |
| 4 | 19.5.2.2 example | `option task = {... every: 15s, of...` | 截断了,完整应是 `every: 15s, offset: 0s`(或 `10m, 0s`,与上下文呼应) |
| 5 | 19.5.2.5 example | `r["measurement"]`,`r["field"]` 都漏下划线 | 应是 `r["_measurement"]` / `r["_field"]`(同 03 章勘误第 11 条) |
| 6 | 19.5.2.6 | "`trigger = (r) => r["undefined"] > 0`" | OCR/排版问题,实际应是 `r.value > 0.04` 或 `r._value > 0.04`(取决于 fieldsAsCols 是否调用过) |
| 7 | 19.4.7 | "InfluxDB 的报警终端就是没法去设置发送的数据格式" | ✅ 完全正确,这是 **Web UI 限制**;但 Notebook + monitor.notify + 自定义 mapFn **可以**自由定制 body |
| 8 | 19.6.5.1 健康检查地址 | "对 /health 接口发起 GET 不需要 token" | ✅ 对;**但要注意 /health 在某些 2.x 版本已被标记为废弃**(见 05 章 Java 客户端勘误);**生产应改用 `/ping`** |
| 9 | 19.3.6 配置阈值 | UI 上的"is above / is below" | 应补充:**还有 `is outside range`(在某范围之外)** — 比如 InfluxDB 实测温度 < -40 或 > 80 都视为传感器异常 |
| 10 | 19.5.2.8 (4) | "body 是发送 POST 请求的请求体。r 是表流里面的数据" | ✅ 关键描述;**还要补充**:`mapFn` 是 `(r) => {...}`,每条记录调用一次,**返回值必须有 `headers` 和 `data` 两个键** |
