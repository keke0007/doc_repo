# 把 AGENTS.md 改了十遍都不听劝，一行 Git 钩子直接让 AI 满分照办

*By 随机比特 (@XShude)*

![Banner](<把%20AGENTS.md%20改了十遍都不听劝，一行%20Git%20钩子直接让%20AI%20满分照办.assets/image-01.jpg>)

![Image](<把%20AGENTS.md%20改了十遍都不听劝，一行%20Git%20钩子直接让%20AI%20满分照办.assets/image-01.jpg>)

项目根目录下的 AGENTS.md 已经膨胀到了四百多行。为了让编程智能体不再直接调用底层的 observability 原生日志库、统一走公司内部封装的 diagnostics 模块，研发团队在这份规范文档里先后试过了加粗、全大写、连敲三个感叹号，甚至加上了违反此条将引发生产事故的严厉警告。  
  
会话刚启动的前两轮，智能体表现得异常乖巧，生成的代码全都规规矩矩地引入了 diagnostics 模块。然而一旦进入深水区，等到智能体连续翻阅十几份源码、跑了三轮单元测试、忙着排查一处隐蔽的空指针异常时，第七轮提交的代码里又赫然出现了一行刺眼的 observability 直接调用。  
  
遇到这种屡教不改的现场，绝大多数团队的第一反应是继续去改 AGENTS.md，试图用更严厉的措辞补上第十一版警告。这种努力从物理机制上就注定了徒劳，因为在长对话里，写在静态文档里的死规矩早已被模型抛在了脑后。  
  
01  
  
SECTION 01  
  
文档越写越厚大模型反而越跑越健忘  
  
研发团队习惯把 AGENTS.md 或 CLAUDE.md 当成智能体的员工手册，每次在代码审查里踩一个坑，就往文档里追加一条严禁事项。这种前置全量注入的做法，恰恰撞上了自回归语言模型最脆弱的注意力衰减规律。  
  
会话刚开启时，整份规则文档紧贴着用户输入，在注意力矩阵里占据着极高权重。随着排障过程推进，上下文窗口里迅速涌入数万个令牌的源码切片、终端堆栈与编译报错。开头的 AGENTS.md 被越推越远，在一维令牌序列中逐渐退化为微弱的背景白噪音。  
  
当智能体把全部算力集中在修复眼前的编译报错时，它的生成概率高度受最近几轮的局部代码片段支配。如果历史业务代码里恰好残留着旧版的 observability 用法，模型就会顺着上下文惯性直接照抄。继续往文档里堆砌三百条互不相干的禁令，不仅消除不了预期与生成结果之间的偏差与漂移（delta and drift），还会把模型正常写代码的注意力彻底挤垮。写在文档里的编码规范只是供模型参考的软建议，只有挡在提交入口并把报错变成提示词的钩子才是物理铁律。  
  
02  
  
SECTION 02  
  
提交代码当场报错把规矩塞回注意力焦点  
  
要彻底治住智能体的健忘症，工程师 Geoffrey Huntley 给出了一个极其干脆的实战解法：停止在 AGENTS.md 里苦口婆心写小作文，直接把那条改了十遍的日志禁令删掉，换成几行 git pre-commit hook 脚本。  
  
这套机制的精妙之处在于完全顺应了智能体的运行本能。在日常编写和调试代码的过程中，上下文里干干净净，半句关于 diagnostics 的规则都不提，不浪费哪怕一个令牌的注意力预算。只有当智能体改完代码、信心满满地敲下 git commit 准备交差的那一毫秒，挡在提交入口的钩子脚本才会瞬间介入。

![Image](<把%20AGENTS.md%20改了十遍都不听劝，一行%20Git%20钩子直接让%20AI%20满分照办.assets/image-02.jpg>)

钩子脚本只做一件极简的确定性检查：扫描本次暂存区的 git diff 增量代码。一旦发现新增代码里出现了绕过 diagnostics 直接调用 observability 模块的语句，脚本立刻返回非零退出码掐断提交，同时在标准错误流里弹出一句直白的修复提示词。  
  
为什么写在开头文档里的规则频频失效，塞进提交报错里却能立刻拿到十分满分（ten out of ten）的执行效果。原因在于编程智能体天生受近因效应支配，它会死死盯着最后一次终端命令的报错输出不放。把架构红线写成提交钩子并在报错流里塞入修复提示词，就是在智能体犯错的精确毫秒把规则塞回注意力焦点。  
  
03  
  
SECTION 03  
  
静态文档只留地图把红线全踢进钩子里  
  
把规则从静态文档迁移到提交钩子，只需要在仓库的 .git/hooks/pre-commit 中放入一段五行的检查脚本：  
  
●●●  
#!/usr/bin/env bash  
if git diff --cached -U0 | grep -E '^\+.*observability' >/dev/null; then  
echo "提交被拒绝：严禁直接调用 observability 模块。请将暂存区中的相关调用全部替换为内部封装的 diagnostics 库后重新提交。" >&2  
exit 1  
fi  
  
这段脚本把冰冷的进程退出码与自然语言修复提示词组合在了一起。非零退出码负责在物理层面封死违规代码入库的通道，标准错误输出里的那句中文提示则充当了按需触发的精准提示词，引导智能体在十秒内自己改好代码并重新提交。

塞进 AGENTS.md 静态文档  
  
下沉为 pre-commit 提交钩子  
  
注入时机

上下文开销  
  
每轮对话持续消耗令牌并稀释注意力  
  
平时零开销，不占半点推理预算  
  
物理约束力  
  
概率性软建议，对话越长越容易遗忘  
  
非零退出码硬熔断，违规代码绝不落盘  
  
适用内容  
  
项目目录结构、构建命令与测试入口  
  
禁用特定底层库、分层边界与格式红线

在工程实践中，这套模式有着清晰的分工边界。需要高层业务权衡的设计取舍依然要靠人工把关，但凡是能用代码差异、依赖路径或语法树规则判定的架构红线，都应当从文档里清理出去。将静态规则文档瘦身为五十行以内的项目地图，把所有代码禁区变成会开口教人改代码的提交钩子，才是管住编程智能体的终极解法。
