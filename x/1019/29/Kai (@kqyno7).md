# Kai (@kqyno7)

当 Claude 写了 90% 的代码，代码评审该怎么做  
  
Anthropic 给出了行业范本：在 PR 合并量翻倍的情况下，revert 率反而下降了超 40%  
  
他们没有取消 Code Review，而是完成了范式转移：从“代码有没有人肉看过”，转变为“可能出什么问题、哪层机制拦截最有效”  
  
核心打法与硬核工程细节梳理：  
  
📊 告别虚荣指标  
• 不再盯“评审覆盖率”，转而压缩“等待人类审批时间”  
• 人力成本 = 评审时间 + 修复坏代码时间，盲目加人只会制造瓶颈  
• 目标明确：最多 1 个人类在 loop 中，以 revert 率和事故率为硬性指标  
  
🛡️ 七层纵深防御体系  
1. PR 前自我验证：Claude 必须出示测试输出、截图或构建日志等实证；全新上下文的第 2 个 Agent 交叉评审 diff  
2. 强制 AI 评审：多 Agent 并行排查 + Verifier Agent 投票过滤，实质性意见占比从 16% 跃升至 54%  
3. 阻塞性安全扫描：独立通道，存在未解决风险直接禁止合并  
4. 自动化严检：类型、lint、跨平台测试，模板强制填写测试方法与回滚预案  
5. 基于风险的分级审批：低风险自动合，中风险 1 人，高风险 2 人；AI 批准不可替代人工，每次新 commit 必须重新审批  
6. 合并队列与分级灰度：先走内部员工，再到 latest 渠道，最后推进至 stable  
7. 秒级检测与回滚：特性开关无需重新发版；事故复盘必问“哪一层本该拦住它”  
  
⚙️ 极具参考价值的 2 个工程实践  
• 把评审器自身做成 Eval 系统：将历史事故 PR 沉淀为测试集，每天自动跑分优化评审 Agent，把主观感觉变成客观目标函数  
• 终结 AI 评审的“死循环”：曾出现 AI 给 AI 提了 50 多轮 Review，其中 59% 竟在翻旧账；团队落地“3 轮封顶退回、仅审增量 diff、标注问题类别而非单行、禁止重复提报”，5 轮以上 PR 比例直接从 8.9% 骤降至 1.5%  
  
👤 人类工程师的最终生态位  
• 决定方向、品味与需求范围  
• 把关高危核心：计费逻辑、CI 流程、更新流程  
• 制定能被模型模仿的标准架构范式  
• 审阅事实证据而非逐行肉眼查语法  
• 承担最终交付的上线责任  
  
这套机制为正在落地 AI Reviewer 的团队提供了极高价值的工程落地方案
