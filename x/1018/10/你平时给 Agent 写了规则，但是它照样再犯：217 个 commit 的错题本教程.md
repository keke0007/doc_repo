# 你平时给 Agent 写了规则，但是它照样再犯：217 个 commit 的错题本教程

*By 阿良｜AI 工作流 (@RealYDT)*

![Banner](<你平时给%20Agent%20写了规则，但是它照样再犯：217%20个%20commit%20的错题本教程.assets/image-01.jpg>)

9 月 21 日，我发了一篇文章，讲 AI 交接里写着「测试全过」，下一轮该怎么验收。

两天后，Agent 跟我确认这篇发没发，我说没发。它就把这篇记成了未发布。

这是我回头翻自己仓库时翻出来的。两个仓库，4 个月，217 个 commit，其中 176 个带着 Claude 的署名，大部分是 Agent 写的。前几天看了 WquGuru 拆解 magpie 的文章，我照着里面那本 Agent 错题本的规则一条条翻，找出 9 条错题，有 5 条在 3 个以上不同的日子里出现过。

最扎心的是，有两条错早就写成了规则、加了检查，后来照样又犯了。上面那件事，就是其中一条的第三次。

![Image](<你平时给%20Agent%20写了规则，但是它照样再犯：217%20个%20commit%20的错题本教程.assets/image-02.jpg>)

这篇写给已经在用 AGENTS.md、CLAUDE.md 管 Agent，但规则全靠自己想起来才改的人。文中有错题本模板和回填命令，文末贴了每日夜审提示词，可以直接拿去跑。

# magpie 的错题本是怎么回事

先交代来源。下面这段全部来自 WquGuru 的文章，magpie 的仓库我自己没拉下来核对。

按他的拆解，magpie 的 CLAUDE.md 只引用两个文件。AGENTS.md 是路由表，告诉 Agent 干什么活先翻哪份文档。LESSONS.md 是错题本，Agent 每天夜里把当天的 commit 过一遍，只找三种问题：

- 修完又返工的
- 压根不该合进来的
- 验证做得太糙的

每找到一条就记一条，一句规则，一段原因，挂上 commit 号当证据，最后一行写 Seen 1×。同一条在 3 个不同日子的复盘里都出现，就从错题本挪进代码规范，变成每个 PR 都要逐条对的硬规则。

我看完第一反应是，这个我也有一半。

我的仓库里早就有路由表（AGENTS.md），也有一份记忆晋升清单，规定一条经验要从 candidate 走到 verified 再到 accepted。缺的是前面那一步：**谁来发现错题**。

一直以来都是我自己撞上了，或者 Agent 在某次任务里顺手发现了，才会补一条规则，从来没有定期回头翻过。

# 第一个问题：我的仓库太小了

magpie 一天能有一两百个 commit，错题本攒几天就有样本。我这两个仓库加起来，4 个月平均下来一天不到两个 commit，有的天一个都没有。

照搬「每天夜审」，前两周很可能什么都升不上来。

所以我改了一步，先回填历史。让 Agent 把 4 个月的 commit 一次性导出来，按 magpie 的三类找错题，Seen 的日期按「发现并修它的那个 commit」的日期算，同一天发现多次只算一次。

导出用的就是一条 git log：

core.quotepath=false 是给中文路径用的，不加的话文件名会变成一串八进制转义。两个仓库导出来一共 670KB 左右。

217 个标题全部读完，挑出 58 个可疑的读了正文和 diff。剩下 159 个只看了标题，这部分里有没有漏掉的错题，我不知道。

# 回填出来的 9 条，挑 3 条讲

## 稿子里的数字会过期，出现了 7 次

这是次数最多的一条，Seen 7×，从 08-05 到 09-23 跨了 7 个不同的日子。

形状都一样：写稿时凭记忆或从上一版抄了一个数字，过几天证据变了，稿子没跟着变。贴几个：

- 恢复演练那篇写验证器有 46 项检查，脚本里实际是 49 项
- Agent Plugins 那篇写测了 4 个客户端，实际测的是 3 个
- 技能数量在不同文件里先后写成 72、74、76
- 同一份读数，状态文件里一处写 7 条，另一处写 6 条

最要命的是第二个。那篇文章的线上版本是在改正之前构建的，**错的数字已经发出去了**。

当时的发布记录倒是老实，专门写了一句「线上正文已过期」，没有假装线上和本地一致。这算是错题本里的 Done right。

7 次分散在好几篇文章和状态文件里，每次是不同的数字，靠「写的时候小心点」防不住。

## 改了忽略规则，证据被悄悄挡在外面，出现了 4 次

我的内容仓库用的是 deny-by-default，默认什么都不进版本管理，再逐个放行。

问题在于按名字匹配的规则。比如为了防止凭据进仓库，有一条 *token*。它把一张早就打过码、已经发布的成品图挡了出去，因为那张图的文件名里有 tokens。第二天，同一条规则又按目录名挡掉了一组证据图。

最大的一次是 09-23。Agent 一数，63 张被正文用 Markdown 图片语法引用的图片不在仓库里，最早一张从 07-18 起就是坏图。换台机器 clone 下来，这些文章的配图全是裂的。

整整两个多月，没有任何东西报警。

修的做法每次都一样，逐个文件放行，不放宽通配。这条是我觉得最适合做成机器检查的：已跟踪的 Markdown 里引用到的图片，必须也被跟踪。

## 扫描范围没先划清，出现了 3 次

递归扫描不知道一个目录属于哪套系统。

最险的一次，图片统计脚本扫进了一个商单工作区，目录名直接进了待发布的非商单稿子。另一次，~/.claude/skills 下面多出一个 synced\ 目录，206 个 Anthropic 官方技能文件被当成快照缺失，检查一下子变红。

就在今天开会话的时候，验证器又报了一个 fail，原因是一个 __pycache__ 里的 .pyc 被算进了技能快照的哈希。形状一模一样。

这条的第三个日子我归得有点勉强：那次是 git-ignored 的本地状态被拿去比对，跟前两次接近但不完全一样。如果不算，它就只有 Seen 2×。我在错题本里把这个判断写明了。

# 真正让我停下来的，是已经晋升过的两条

前面 3 条都是新的晋升候选，之前没有对应的规则。另外两条不一样，它们早就晋升过了。

**第一条：发布了要当场记录。**08-05 和 08-07 各漏记过一篇已发布的文章，两次都是我截图给 Agent 看才发现的。08-07 当天，Agent 就给验证器加了一项发布覆盖检查。

第三次就是开头那篇。09-23 它被写进豁免名单，第二天我把帖子链接发给 Agent，才发现 09-21 下午就已经在线上了。那次是在有检查、也问过我的情况下漏掉的：一篇教人别轻信交接记录的文章，它自己的发布记录，是被我亲口确认错的。

今天这项检查报的是 14 个工作区没有发布记录。其中多少是真发了没记，我还没核对。

**第二条：路径不能依赖盘符。**恢复演练发现，入口文件用绝对路径引用自己的规则文件，换个盘就断。08-05 修掉的当天，这条就写进了 AGENTS.md。

08-24，内容仓库里又出现了一个指向规则仓库的裸相对路径。

magpie 的门槛是「Seen 3× 就升成硬规则」。我这两条都升了，还是复发了。

![Image](<你平时给%20Agent%20写了规则，但是它照样再犯：217%20个%20commit%20的错题本教程.assets/image-03.jpg>)

我翻来覆去看了这两条，差别在升到了哪儿。第一条升成的是一个 warning，它会提醒，但不拦任何东西。第二条升成的是一行写在规则仓库入口里的字，另一个仓库的会话每次有没有读到它，我没法证明。

打个比方，一个是在路口立块牌子写「慢行」，一个是直接铺一条减速带。牌子立了，赶时间的车照样开过去。

所以我现在的判断是：**升级不等于拦住**。要看它升到了哪：一个会拦的检查，还是一行等人想起来的字。

这只是两个样本，说是规律还太早。但它正好是 magpie 原文没讲到的地方，因为按 WquGuru 的描述，magpie 的硬规则是每个 PR 审查都要逐条对的，本来就是会拦的那种。

# 我自己也看走眼了一次

这个得交代。

回填之前，我先让 Agent 扫了一遍标题出选题卡。卡里写了一句「历史里已有返工信号」，证据是规则仓库 10-13 连着的两个 commit，标题一字不差，都是「update tutorial-flow snapshot hash」。同一天改两次同一个哈希，看着就像改错了又改。

读完 diff，不是。那天技能本身改了两次，一次加了一行标题偏好，一次按新数据改写了这一行，每次都如实记录了。同样形状的还有 3 组，全都排除了。

![Image](<你平时给%20Agent%20写了规则，但是它照样再犯：217%20个%20commit%20的错题本教程.assets/image-04.jpg>)

只看标题判返工，误报率很高。**所以夜审提示词里我加了一条硬要求：看起来像返工的，先读 diff 再判断，读完不是的单独记进「误报」一节。**

这一节我会一直留着。错题本要是只记命中，不记看错的，过几个月就没人知道它的判断有多准了。

# 和 magpie 有意不一样的地方

有两处我没照抄。

第一，不自动晋升。magpie 是 Agent 写、审、合、发都自己来，人只守几道闸门。我的规则仓库里写明了，长期边界的改动必须我自己确认。所以 Seen 满 3 次只标「晋升候选」，写明建议升到哪个文件，升不升我来定。

第二，先回填再夜审。低频仓库不回填，等夜审攒满 3 个日子可能要一个月。回填的代价是 Seen 的日期是事后归的，不是当时发现的，这个限制我写在了实验说明里。

# 想自己搭一套的话

错题本一条长这样，基本照搬 magpie 的格式，加了一行状态：

步骤就三步：

1. 用上面那条 git log 把历史导出来，让 Agent 按三类找错题，生成第一版
2. 之后每天跑一次夜审提示词，只审当天的 commit，新问题从 Seen 1× 起
3. 某条满 3 个不同日子，标成晋升候选，你决定升到哪：会拦的检查，还是规则文件里的一行字

第 2 步用的夜审提示词贴在文末，可以直接复制。

动手之前，可以先问自己几个问题：

- 你的仓库里，上一次规则是谁发现要改的？你自己，还是 Agent？
- 你已经写下的规则里，哪几条有检查在拦，哪几条只是一行字？
- 如果今晚让 Agent 回头翻一遍最近一个月的 commit，你猜最多的会是哪一类错？

# 现在的状态

回填做完了，9 条错题，5 条 Seen ≥ 3×，3 条新的晋升候选，4 组误报。每日夜审还没开始跑，晋升也还没决定。

判断都是同一个 Agent 做的（Claude Opus 5.5，2026-10-17），没有交叉复核。159 个 commit 只看了标题。只看 commit，没看会话日志，所以那种会话里改了又改、最后只提交一版的返工，这次看不到。

接下来我会让它每天夜审，跑一段时间再回来更新：新的错题有多少，误报有多少，以及那两条已经复发过的，有没有第三次。
