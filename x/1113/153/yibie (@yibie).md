常驻 agent 的五个原语  
  
Anthropic 最近写了一篇工程文章，拆「常驻 agent」（always-on agent）怎么搭。这种 agent 会跨会话记住上下文，没人盯着也会自己动手，但它并不是真的一直跑，而是大部分时间在睡觉，收到事件就干一轮活（一个 run），存好信息再睡。  
  
让这套循环转起来的外围架构，Anthropic 归成五个原语：事件收件箱、定时器、记忆、权限、发件箱。  
  
事件收件箱解决「谁来叫醒它」。webhook、定时任务、后台作业都不直接调 agent，而是写进一个持久队列，由唯一的 worker 取出来开 run。直接调 agent 的麻烦是：两个事件同时到会开出互相竞争的 run，worker 崩了事件就丢了。收件箱是唯一事实来源，还能按来源 ID 去重，把用户连发的几条消息合并成一轮。  
  
定时器让 agent 能主动，分两种。跟进是 agent 给自己设的死线，比如过会儿看对方回没回；排期是固定周期的任务，比如每日简报。它们存在独立的表里，调度器定时轮询，到期了就往收件箱投一个事件。  
  
记忆要独立存储，比 worker 活得久。原则是只存查不到的东西：用户指令、用户偏好、已经说过什么、每个任务干到哪。如果信息本来就在 issue tracker 这类系统里，就存一个指针。  
  
权限是风险最高的一块，因为 run 带着用户的凭证、又没人盯。Anthropic 的做法是凭证不进 agent 环境，由外面的代理在请求发出时代为注入；高危动作用分类器拦截，重要决策挂起等用户批准。挂起时 run 结束、会话存到调用中途，用户的答复作为事件进收件箱，下一轮再接着跑，worker 期间可以去处理别的事。  
  
发件箱对应「怎么把活带给用户」。常驻 agent 在后台干活，用户只收结果和少量细节，不看全程推理。多数情况一个发送工具就够，只有要控消息节奏、或需要错误恢复时才值得做正式发件箱。Anthropic 建议先让 agent 安静一点，用评测慢慢调消息量。  
  
模型变便宜、判断力变好，是这类 agent 回潮的前提。文中给的数字是，Opus 5.5 在一个长周期编程基准上，每解决一个任务比 Opus 5 便宜 78%，而典型工作负载上只便宜 40%。长周期任务从降价里吃到的红利最大，只是模型这部分在文章里只是背景，主体讲的都是工程件。
