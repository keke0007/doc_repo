# 码良 (@cxjwin)

最近在治理项目的 Harness 基建，发现几个挺值得深思的问题。  
  
1. 知识库到底有没有用？  
  
大量 Markdown 文档写完就再也没人维护。代码已经迭代了好几个版本，知识库还停留在过去。AI 读得越认真，可能错得越离谱。  
  
2. Skill 到底有没有用？  
  
项目里沉淀了几百个 Skill，却没有完善的埋点和评测体系。不知道哪些被频繁调用，哪些真正提升了效率，哪些甚至在拖后腿。  
  
只知道 Skill 越来越多，却不知道整体能力有没有变强。  
  
3. 门禁到底靠不靠谱？  
  
很多工程规范还停留在 Rules、Markdown 和 Prompt 层面，依赖模型自觉遵守。  
  
换一个模型、换一个 Harness，可能就失效了。原本应该由工程工具保障的确定性约束，反而交给了概率性的模型。  
  
4. Harness 的健康度怎么衡量？  
  
模型能力不断升级，势必会逐渐内化过去需要依靠 Rules、Skills 才能完成的能力。  
  
那么，之前辛辛苦苦沉淀的东西，现在到底是正收益、负收益，还是毫无作用？  
  
没有基线，没有对照实验，也没有持续评测。我们甚至不知道什么时候该做加法，什么时候该做减法。  
  
5. 最佳实践在哪里？  
  
每个人都有自己的 AI Coding 工作流，各用各的 Harness，各写各的 Rules、Skills。  
  
有些所谓的最佳实践，可能还是一年前的古法 AI Coding 技巧。个人经验缺乏验证，也很难真正转化为团队的工程能力。  
  
⸻  
  
这让我想到一个问题：古法编程时代有软件架构师，AI Coding 时代，是不是也应该有 Harness 架构师（Harness Architect）？  
  
传统架构师负责系统架构、技术选型、模块边界、性能和稳定性。  
  
而 Harness 架构师，可能需要关注另一套体系：  
  
如何组织上下文，让 AI 正确理解项目？  
如何设计 Tools、Rules、Skills，明确能力边界？  
如何构建不依赖特定模型和 Harness 的工程门禁？  
如何通过 Evals 和可观测性，证明每项基建的实际收益？  
如何随着模型升级，持续淘汰过时甚至产生负收益的能力？  
  
传统架构师设计的是软件如何运行，Harness 架构师设计的是 AI 如何参与软件工程。  
  
过去我们追求的是代码复用、模块解耦、架构演进。  
  
未来可能还需要追求上下文治理、能力复用、行为约束和持续评测。  
  
而且我越来越觉得，好的 Harness 架构师，不是能沉淀多少个 Skill、写多少行 Rules，而是知道哪些东西根本不需要存在。  
  
模型越来越强，Harness 未必应该越来越重。  
  
AI Coding 的下半场，可能不再是比谁更会使用 AI，而是比谁更懂得如何工程化地管理 AI。
