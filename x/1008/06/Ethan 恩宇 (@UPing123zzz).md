# Ethan 恩宇 (@UPing123zzz)

一个月，我只做一个面 RAG 岗不会被问穿的项目。  
  
我给自己排了一个月，做一个能拿去面 AI RAG 工程师的项目。公司里我已经在碰检索和问答，客户文档又脏又碎，教程那套 embed 一下、top-k 丢给模型，交上去面的时候一问就漏。所以这一个月我不打算堆名词，每一步留对照。  
  
数据集不用那二十篇干净博客。我要 PDF、扫描件、表格、产品码、缩写、前后文互相指的，开源里财报、维修手册、政策库都行，量级拉到几千文件。库看业务。权限、文档状态、用户要和检索待在同一个 Postgres 里，就用 pgvector，不为了简历去换一个专用库。没有这摊业务表，检索还要过滤、混合、以后量会涨，再上 Qdrant 或 Milvus。放弃另一个的理由写在 README 第一段。  
  
分块比换模型值钱。固定 500 token 一切，只当对照组。正文按标题和段落切，表格单独抽，图和复杂版面走 Docling 这一类解析，别把表压成一行字。另外两版也要跑：父子块，小块负责被检索到，父块才送进模型；入库前给每块补一句它在原文哪一节、在回答什么。后一版公开评测里能把检索失败打掉一截，但入库要花钱，token 成本和召回变化都记下来。三版进同一套题，不口头宣布布局分块更高级。  
  
检索从第一天就不上纯向量。企业文档里法规编号、型号、缩写，语义经常放过去。dense 加 BM25，RRF 融合，先召回 50 左右，再用 cross-encoder 收到 5 到 8 条。面试问你怎么知道语义会漏，别背定义。我准备 40 到 80 条查询，标好期望块，分开跑纯向量、混合、混合加重排，记 Recall@k、MRR、命中率。漏掉的贴出来，多半是编号、否定条件、跨段限制。这页比架构图有用。  
  
模型按盒子选。先定每次问答能花多少钱、p95 能等多久，盒子里放 3 个模型，同一批题看忠实度、答案有没有被上下文撑住、会不会自己补。强模型可以当 judge，但抽 20 条自己看，它会偏心写得长的。留下的不一定最聪明，是在成本和延迟里没崩的那个。  
  
top-k=3、temperature=0 不当结论。生成温度对 RAG 的影响通常没检索大，要扫的是召回宽度、重排后留几条、overlap、块大小。每改一个跑同一套题。有一次我把送进模型的块加多，忠实度反而掉了，脏上下文把回答带跑。这种记录比默认参数像样。  
  
新东西放在基线打不过的题上。查询改写和多查询对付口语和缩写。HyDE 对付问法和文档用词差很远的题，对已经有精确词的题可能帮倒忙，分组看，不全量开。GraphRAG 只在坏案例里反复出现跨文档比较、实体对不齐、多跳时再上，图的构建成本和脏实体比教程脏。Agentic 更后，单次检索答不了、需要改策略再查，才给一个有停止条件的循环。检索变多不等于生成变好，token 会先爆。哪类题升级了，哪类题不该升级，这个要能说出来。  
  
最后一周部署，AWS 或 Azure 都行。一条请求的检索、重排、生成、token、延迟要能串起来。打一波并发，看向量库 p95、连接池、冷启动。日志里抓一次答错，要能回溯到是切块切坏了，还是重排把对的块挤掉了。仓库里放架构、评测表、失败案例、成本、我否掉的方案。面试官翻到失败案例，会比翻到一张 Agentic 架构图更快信。  
  
一个月可能做不成检索研究员，但是够交出一个每个决定都有对照的仓库。
