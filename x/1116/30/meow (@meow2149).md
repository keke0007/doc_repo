# meow (@meow2149)

Pi 和 OMP 明明是同源的两个 Coding Agent，现在却走出了两条不同的路线。  
  
很多人可能不知道，OMP（Oh My Pi）并不是从零开发的竞品，而是从 Mario Zechner 的 Pi 项目分叉出来的。  
  
两者都保留了终端交互、TypeScript 扩展、会话管理和多模型支持，但后续的发展方向明显不同。  
  
Pi 更强调精简内核，把工作流的决定权交给用户；OMP 则把大量高频编程能力直接集成进 Agent，追求开箱即用。  
  
这两种思路具体带来了什么差异？从架构、原生工具、扩展兼容、模型支持、上下文管理和生态几个方面对比一下。  
  
一、为什么走向不同的路线？  
  
▪︎ Pi：精简内核，按需扩展  
  
Pi 的基础工具主要是 read、write、edit 和 bash。它不预设一套完整的开发流程，而是允许用户通过 TypeScript 扩展注册工具、拦截事件、修改上下文、定制界面。  
  
子 Agent、计划模式、权限确认等工作流可以通过社区扩展实现。  
  
需要特别说明的是，Pi 现在已经内置 MCP 和 Codemode，不再是早期完全依赖插件接入 MCP 的状态。但总体上仍坚持让用户自行组合工作流。  
  
▪︎ OMP：保留扩展能力，强化原生工具  
  
OMP 沿用了 Pi 的 Agent 架构和扩展思路，但将开发中常用的能力直接集成到了运行环境。  
  
根据官方 README，目前提供 31 个内置工具，覆盖代码分析、调试、子 Agent、搜索、浏览器和桌面操作等场景，部分工具需要额外配置才能启用。  
  
它还引入了约 8 万行 Rust 原生代码，用于 Shell、文件搜索、AST 分析和桌面控制等底层能力。  
  
所以两者的核心区别不是能不能扩展，而是哪些功能应该由 Agent 自带，哪些应该交给用户决定。  
  
二、原生编程能力差异  
  
▪︎ 代码理解和编辑  
  
Pi 主要依靠基础文件工具和 Shell，代码导航、结构化修改等能力可以通过扩展或外部工具补充。  
  
OMP 原生集成 LSP、AST 搜索与编辑，以及基于 DAP 的调试能力。  
  
例如跨文件重命名可以借助语言服务器更新引用；程序出现异常时，Agent 可以通过调试器查看断点、调用栈和变量，而不只是反复修改代码、运行测试。  
  
OMP 还提供 Hashline 编辑机制，通过行内容锚点定位修改位置，并在文件发生变化时拒绝不匹配的编辑，减少错误替换。  
  
▪︎ 多 Agent 协作  
  
Pi 不默认提供子 Agent 工作流，社区的 pi-subagents 可以实现任务分发、并行执行、串联工作流和后台任务。  
  
OMP 则内置 task 工具，支持子 Agent 并行执行、隔离工作区、结构化结果返回，还可以在 Agent Hub 中查看运行状态和介入任务。  
  
▪︎ 联网和电脑操作  
  
Pi 可以通过 pi-web-access 等扩展增加联网搜索、网页读取和其他外部能力。  
  
OMP 自带 web_search、browser 和 computer 工具。  
  
其中 browser 面向网页及浏览器控制，computer 则可以操作真实桌面窗口、获取屏幕截图、发送系统级输入，并读取系统无障碍信息。  
  
这些能力 Pi 并非无法实现，只是通常需要自行接入。  
  
三、扩展体系还能兼容吗？  
  
两者都支持 TypeScript 扩展，但已经不能简单看成同一个插件平台。  
  
▪︎ Pi  
  
通过 Pi Package 分发扩展、Skills、提示词模板和主题，支持 npm、Git 安装，也有统一的官方包目录。  
  
▪︎ OMP  
  
有独立的插件管理与 Marketplace 机制，支持 npm、Git 和本地插件，还兼容 Claude Code 的 Marketplace 目录格式。  
  
OMP 也保留了 Pi 扩展兼容层，可以识别部分 Pi Package 声明，并对旧包导入进行兼容处理。  
  
但这不代表所有 Pi 插件都能直接使用。  
  
两边的内部 API、配置目录和运行机制已经出现差异，部分依赖 Pi 内部接口的插件仍可能遇到兼容问题。  
  
如果已经积累了大量 Pi 自定义扩展，迁移到 OMP 前最好逐个验证。  
  
四、模型支持和路由机制  
  
▪︎ Pi  
  
官方支持 Anthropic、OpenAI、Google、OpenRouter 等多家模型提供商，既能使用 API Key，也支持部分订阅账号授权。  
  
通过 /model 切换模型，也可以使用 models.json 或扩展增加自定义 Provider。  
  
它更偏向让用户自行决定当前会话使用哪个模型，以及如何组织调用。  
  
▪︎ OMP  
  
官方列出 60 多个 Provider，并进一步提供基于任务角色的模型路由。  
  
例如 default 负责普通任务，smol 处理低成本子任务，slow 用于深度推理，plan 用于规划。  
  
不同角色可以配置不同模型，还支持失败回退链、多个凭据轮换，以及按项目路径限制可用模型。  
  
不过，Provider 数量不等于模型效果。两者都可以使用相同的基础模型，实际差别更多来自工具设计、提示词和执行流程。  
  
五、上下文和长期任务处理  
  
两者都保留了会话树，可以通过分支切换和上下文压缩管理长会话。  
  
▪︎ Pi  
  
支持自动压缩历史消息，也允许扩展接管压缩和上下文构建。  
  
可以按自己的需求决定保留什么历史、如何生成摘要，以及是否引入长期记忆。  
  
▪︎ OMP  
  
在此基础上增加了更复杂的上下文维护机制，包括工具输出裁剪、多种压缩策略，以及可选的后台预压缩。  
  
比较特别的是 Snapcompact：它可以把部分历史记录渲染为紧凑图片，供支持视觉输入的模型读取，减少对传统文本摘要的依赖。  
  
OMP 还提供可选的持久记忆机制，允许 Agent 保存、检索和更新跨会话知识。  
  
但上下文策略更复杂，不代表一定更省 Token 或更准确，具体效果仍需要同模型、同任务测试。  
  
六、生态和维护成本  
  
截至 11 月 16 日，Pi 官方 npm 包目录收录 5,366 项，涵盖扩展、Skills、提示词模板和主题。  
  
OMP 没有找到可以直接与这个数字对照的统一插件收录量，但它支持自己的插件、Marketplace，以及部分 Pi 和 Claude Code 生态内容。  
  
从现成的统一包目录来看，Pi 的生态更容易检索和统计。  
  
从内置能力和跨工具配置兼容来看，OMP 的集成程度更高，减少了用户自行寻找、安装和组合插件的工作。  
  
代价也很明确：OMP 的原生代码和功能模块更多，维护面更大；Pi 保持较小的核心，但需要用户投入更多配置和扩展工作。  
  
七、到底应该选哪个？  
  
▪︎ 选 Pi  
  
如果你喜欢精简的终端 Agent，希望自己设计工具、命令、子 Agent 和上下文策略，或者想基于 SDK 构建自己的 Agent 系统，Pi 更适合。  
  
它的优势是扩展自由度高，不需要接受一整套预设的工作流。  
  
▪︎ 选 OMP  
  
如果你主要用 Agent 完成实际编程任务，希望直接使用 LSP、调试器、子 Agent、浏览器和 Computer Use，不愿意逐个寻找和组合插件，可以优先试 OMP。  
  
它的优势是开发工具集成完整，很多复杂能力不需要自己搭建。  
  
两者都支持 SDK 和 RPC，并不是只有 Pi 能用于二次开发。  
  
我个人更倾向于这样选：  
  
如果是自己开发和深度定制 Agent，我会选 Pi。  
  
如果是每天把 Agent 当作主要编程工具，希望安装后就有一套完整的开发能力，我会先试 OMP。  
  
Pi 把更多选择权留给用户，OMP 把更多能力提前做好。  
  
它们从同一个项目出发，却对 Coding Agent 应该做成什么样，给出了两种不同的答案。
