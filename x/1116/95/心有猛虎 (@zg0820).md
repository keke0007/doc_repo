这是《深入理解 AI Agent：设计原理与工程实践》（GitHub 50k+ Star）的姊妹篇，作者李博杰（@bojieli）。上一本讲「怎么基于模型写应用」，这本往下挖一层：模型跑在什么上面，为什么慢，为什么贵，怎么从硬件约束反推系统设计。Apache-2.0 开源，全书正文、配图、计算工具、实验记录都在仓库里，还有简体中文 / 英文 / 繁体中文 / 俄语四个版本。  
  
—— 一、为什么需要这本书 ——  
  
作者的动机来自一个很朴素的观察：大多数软件工程师不写操作系统、编译器、芯片，却仍要学操作系统、编译原理、体系结构，因为申请内存、读文件、调函数背后都有资源与时间代价。基于模型开发应用也一样——延迟差几倍，产品体验就完全不同；成本差一个数量级，商业模式跟着变。  
  
更深层的变化他叫「编程抽象的上移：从操作系统到模型上下文」。传统系统要为事先未知的各种程序提供通用能力，优化总在可编程性与性能之间取舍；如今 LLM 成了最重要的应用，从算子执行到分布式调度都可以针对特定模型和加速器架构优化，模型设计甚至反过来适应硬件（README 里举的例子是 DeepSeek V4/V4.1 重新设计长上下文表示）。他的结论很锋利：**模型成了 LLM 时代的操作系统，AI Infra 成了 LLM 时代的计算机体系结构**。  
  
而《计算机体系结构：量化研究方法》是体系结构领域的入门经典，AI Infra 领域却还缺一本从硬件约束和模型架构出发、量化推导系统设计的书——这就是写作动机。  
  
—— 二、这本书的方法论：从约束推导设计 ——  
  
贯穿全书的方法只有一句：先明确任务与质量要求，列出计算、存储、通信和依赖关系，对照硬件的容量、带宽、算力做数量级估算。  
  
他特别强调这类估算「人容易出错，AI 也一样」，并列了四个典型漏项：只算权重读取忘了 KV 缓存；按峰值算力推算速度却不查带宽能否供给；把工作平分给多张卡却遗漏卡间通信；漏掉任何一项，结论就可能偏离几倍甚至几个数量级。

（2/5）估算还有第二层用意，来自他读博时导师张霖涛博士的叮嘱：优化一定要做到物理所允许的极限。所以书里的顺序是「先按第一性原理算出硬件允许的上限，再看实测离上限还有多远」——差距不是模型漏了项，就是系统有可以去掉的开销。  
  
从 FPGA 加速 Bing 搜索排序、昇腾 AKG 算子生成到 UB 万卡互联，作者反复遇到同一条线索：**数据搬移**。全书因此反复追问五个问题——搬什么、搬多少、搬几次、经过哪里、谁必须等它。这五问是我读 README 时觉得最值钱的部分，它把「系统优化」这种玄学话题拆成了可逐项核对的清单。  
  
—— 三、十二章内容地图 ——  
  
第 1 章 初识 AI Infra：一次生成需要多少显存、计算和数据读写。我抽读了正文，它从「应用如何通过代码、模型与上下文共同表达任务」讲起，沿一次请求的处理路径用容量/算力/带宽回答三个问题：数据能否放下、回答要等多久、增加加速器或改变数据表示能带来多少收益。还借用华为半导体首席科学家廖恒博士的「十八层宝塔」，把全书划成从应用到硬件的六层分工。  
  
第 2 章 模型架构：注意力、历史状态与专家结构如何改变系统需求。  
第 3 章 推理与训练负载：任务阶段、到达模式和状态寿命如何影响资源需求。  
第 4 章 加速器架构：如何在计算、存储、带宽、功耗与成本之间取舍。  
第 5 章 算子与运行时：融合、复用、并发和调度如何减少执行开销。  
第 6 章 超节点：多设备协作如何平衡容量、吞吐和同步代价。  
第 7 章 数据中心网络：带宽、通信方式和拥塞如何影响计算效率。  
第 8 章 推理优化：批处理、KV 管理、卸载与推测解码何时有效。  
第 9 章 分布式推理：如何放置计算和状态，处理扩缩容与恢复。  
第 10 章 训练系统：如何安排显存、通信和重算。  
第 11 章 资源调度与运行环境：模型服务和工具环境如何共享资源、减少等待。  
第 12 章 端边云协同：任务放本地、边缘还是云端，如何兼顾效果、延迟和成本。  
  
注意章标题全是问句——这不是目录凑数，是全书「先提问再算」的风格。目录本身就是一张系统设计的问题清单。

（3/5）—— 四、它不只是书：配套工具链很完整 ——  
  
README 里最让我意外的是「可执行」的程度。仓库不只是 Markdown：  
  
1. **配套计算工具** `calculations/`：静态计算只需 Python 3.10+ 标准库，无需 GPU 或模型权重。两条命令就能上手——  
`python3 calculations/calc.py models` 查看支持的模型；  
`python3 calculations/calc.py forward --model qwen3-8b --tokens 8192 --format md` 估算 Qwen3-8B 在 8192-token prefill 下的逐算子资源需求。  
工具附模型配置和结果索引，可以换一组模型和输入复算书里的数字。  
  
2. **配套实验** `experiments/`：按章节 `experiments/chXX/XX-YY/` 存放，每个实验附运行方法、输入条件和结果说明；需要 GPU 的会注明硬件与依赖，没有设备也可以先读已有记录。  
  
3. **Git LFS 的克制设计**：论文和较大的测量记录合计约 20 GB，`.lfsconfig` 默认跳过所有 LFS 文件，克隆时工作区只留指针——正文、配图、静态计算都不需要它们。复现某个实验时按需拉：`git lfs pull --include="experiments/ch05/05-01/**" --exclude=""`。这个细节很见工程素养：不把 20 GB 压给每个只想读书的人。  
  
4. **多格式自动发布**：正文唯一来源是 `manuscripts/` 下的 Markdown，GitHub Actions 在 PR 上检查网站与四种语言的 PDF/EPUB 构建，推送 `main` 后自动发布 Release 并部署在线阅读站。PDF 由 XeLaTeX 排版（公式、表格、脚注、交叉引用完整），EPUB 适合手机，在线版有章节导航、全文搜索和深色模式。  
  
5. **社区翻译**：英文版 @tg1482、繁体中文版 @edward821220、俄语 community edition @ilkruglov，都是社区贡献。译本数字、公式和引用以中文原版为准。

（4/5）—— 五、适合谁读，怎么读 ——  
  
README 给的定位：已经调用过模型 API、或在自己机器上跑过模型，想进一步弄清「为什么慢、怎么降成本」的人。系统、网络、芯片方向的工程师和研究者也能看到各层设计与实际模型任务的联系。需要一点 Python、线性代数和计算机系统基础。  
  
它甚至给了按角色的阅读路线：  
- 做模型应用和推理服务：重点读 8、9 章，再看 11、12 章；遇到容量/算子/通信问题回 4—7 章追原因。  
- 做系统或网络：重点 5—7 章，再看 9、10 章。  
- 做芯片与体系结构：重点 4—7 章，结合后续任务算例看硬件指标怎么转成服务能力。  
- 系统学习：按目录顺序读，配合计算工具和实验逐步核对。  
  
作者还建议：遇到书里的算例，先自己估一下再看推导和实验结果；也可以换成你正在用的模型和硬件，看结论是否改变。这句话把「读书」变成了「复现实验」。

（5/5）—— 六、我对这个项目的三点判断 ——  
  
第一，**它填的是真空白**。中文技术书里讲 Agent 开发、讲 prompt、讲框架的很多，从 HBM 带宽、KV 缓存、卡间互联往上推系统设计的极少。而这恰好是 2026 年做 AI 应用最贵的那部分能力——模型能力可以调 API 买到，成本和延迟的差距只能靠 infra 理解补。  
  
第二，**「量化」二字不是营销**。全书的方法是把每个设计决策都还原成可算的数：多少字节、多少 FLOPs、多少带宽、谁等谁。配套的 [calc.py](http://calc.py) 让这些数可以复算、可以换参数重跑。这比「某方案性能更好」这类结论有用得多——你拿到的是判断方法，不是结论。  
  
第三，**它诚实标注了状态**：README 明说「书稿仍是初稿，正在持续修订」，并开了勘误 Issue 模板，欢迎指出数字算错、单位量级不对、引用与原文不符。一个 50k Star 姊妹篇的作者愿意把未定稿公开接受逐条纠错，这种开放度在中文技术书里少见，也意味着现在正是参与的好时机。  
  
—— 七、一句话总评 ——  
  
如果说《深入理解 AI Agent》教你在模型之上搭应用，这本《深入理解 AI Infra》教你看清模型之下那台机器：一次 token 生成背后，数据搬了几次、卡在哪一层、上限在哪。AI 应用竞争到下半场，差距会越来越多地落在这层——**模型大家都能调，谁能把每个 token 的成本和延迟算明白，谁才有定价权**。
