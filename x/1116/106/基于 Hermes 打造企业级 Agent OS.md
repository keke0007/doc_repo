# 基于 Hermes 打造企业级 Agent OS

*By Aron厚玉 (@aronhouyu)*

![Banner](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-01.jpg>)

过去的 4 个月，我们的团队一直在使用基于 Hermes 的架构处理大部分的自动化业务。

包括：信息搜集、整理、汇报、统计、决策、信息流转、跨部门与跨企业协作。

到今天，我依然觉得基于 Hermes 的 Agent 是一套自主性非常高的应用架构。

此时需要感谢 Hermes 的开源（Hermes 打点钱啊）。

到今天为止，我们的 Agent 每天处理 200+ 项自动化任务，这些都是基于一套 Mac 电脑、几台外部服务器加 Hermes Agent 完成的，所以有了这篇文章。

希望大家在 Personal AI Agent 之外，也会对企业级 Agent OS 的设计、架构以及应用层有一些常规的认识。

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-02.jpg>)

# 一、技术选型：为什么是 Hermes？

Hermes 的 Agent 在各种 Agent 普及的今天，依然是目前完成度极高的自主 Agent 运行框架之一：

自带MEMORY.md 与 USER.md 持久化记忆，基于 SKILL.md 的技能自进化闭环，多平台统一网关；

包括 Telegram、Slack、飞书、Discord，以及 Cron 定时任务和子 Agent 的并行调度能力。

**简单理解：开箱即用，可以在同一台服务器上跨平台部署多个 Agent 协同工作。**

但是，当你把这一套部署在个人端的 Agent，直接推向一家 300 人、横跨运营、采购、库存、仓库、定价、财务、销售、客服等环节的公司时，系统往往会顶不住。

而最近也看了好多 Agent，发现他们的思路都是基于个人 Agent，套壳在不同场景，只能执行几个简单的工作任务，本质根本不是企业级的 Agent 系统。

所以，其实我个人理解的，目前的答案依然是hermes。

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-03.jpg>)

# 二、什么是真正的企业级 Agent OS？

企业级 Agent OS，本质不是几个可以处理小工作的 Agent；

个人理解更像是一套把**多角色、多组织、权限、实时业务信息、知识记忆、安全等多内容都集中管理起来、基于多用户架构的系统**。

简单点说，如果 Personal Agent 的目的是：一个人怎么使用 AI 提效；

那企业级的 Agent 解决的是：**几十上百人跨部门协作时，如何让人类和 Agent 在同一套业务下一起串联工作流，以及对组织经验的复利沉淀。**

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-04.jpg>)

**所以前置有几个要求：**

1. **权限以及隔离：**不能让每一个 Agent 都可以执行扫描本机文件、读取他人文件等操作。毕竟如果销售看了财务的文件，会是一件很头疼的事情。而且跨部门协作需要校验之后的异步完成，单纯的提示词安全等级会很低，所以必须从根源上对 Agent 进行分组、分权限等工作。
2. **共享业务状态：**对于实时业务台账等数据信息进行共享，并且可以承接多个渠道的内容，目的是把高频的运营成本降低。
3. **组织记忆：**说到底还是 RAG + Markdown，毕竟人话有时候是会遗忘的；员工在使用中也会出现因为上下文压缩导致记忆丢失的问题。这部分就需要做组织记忆，并且把一些常用的 Skill、规则放在单一的空间。
4. **控制面板：**所有系统都需要人来运维，公司最核心的数据、GMV、密钥等等，谁能改、谁能看就很重要；同时会加一层沙盒模式，因为外部内容在进入 Agent 整个系统前，都需要经过沙盒隔离与清洗，保障本地的数据安全。
5. **权限挂载：**这里有个之前踩过的小坑。基于权限挂载，会做成一个类似动态路由的东西——财务打开只看财务，销售打开看销售；而且他们各自的 Agent 都没有擅自更改自己权限、跨部门、产出子 Agent 等能力。
6. **资产沉淀：**对一家公司来说，谁都是可以被更换的，只有运营时候的数据是最重要的。例如：今天 Claude 封控松一点，那就用 Claude；明天 DeepSeek 更便宜，那就马上切。不同的模型供应商之间，本身就是几个月以内互相更替、互相追平，算力本身就会越来越便宜，他们只是 token 的供给者、燃料而已；解耦之后不做强行的绑定关系。

只有工作流、记忆，才是越用越值钱的核心资产。

那么基于上面的需求，可以整理出相应的改造架构和内容。

# 三、基于 Hermes 的企业级改造架构

明确了企业级 Agent OS 的需求，下一个问题是：如何基于 Hermes 的当前框架来做改造

众所周知，当前的 Hermes 依然是按照单用户的 Profile 来设计的。

所以我们的改造思路是：基于 Hermes 的推理循环，在上方搭建共享业务工作区；并在下方垫一层企业级控制面板和权限网关。

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-05.jpg>)

1. **权限分组与跨部门异步协作**  
底层会使用 Hermes 的多 Profile 机制，按照部门、职能拆分出不同的 Agent 角色：  
个人 Agent：权限针对不同的员工本人，使用者是张三、李四等不同的员工。  
部门 Agent：销售部、采购部等，使用者是大部分的 AI + 群聊，严禁私聊，并且各自有独立的数据目录。  
跨部门协作：当销售需要财务核对一笔回款的时候，由控制面板验证权限请求，给财务部门 Agent 发起一条异步的 Agent-to-Agent 任务。  
财务部门 Agent 会在自己的隔离环境中完成相关工作，把输出的简单状态（回款 / 未回款）等脱敏内容传给销售 Agent。  
这么做的好处：不会暴露敏感信息，也可以实现不同 Agent 之间的协作。
2. **状态共享**  
无论是邮件渠道，还是群聊的商品退换、制作流程，前端门店的订单，全部都由 Agent 做隐性提取，写入同一套后端数据库。  
不同业务端的 Agent 只需要读取数据库的内容，就可以把一些微信文档、口头通知等内容都消灭掉。
3. **记忆分层（RAG + Markdown）**  
为了解决短对话被上下文压缩导致的记忆丢失，需要把记忆拆分成两部分。  
Markdown 对应业务数据，例如供应商是谁、如何处理报表、如何产出报表、如何找信息等等。  
特点：MD 本身体积可控、高度浓缩，并且可以被人工处理；Agent 干活的时候可以被定向读取，甚至直接注入问题，所以大部分的工作沉淀都在 MD 里。  
RAG：公司几百号人运行几个月后，内容其实不可能全部写到 MD 里。所以 RAG 主要处理以下几类问题：  
比如：*“上个月 12 号采购和运营在群里讨论，为什么临时把 A 供应商的账期改成了预付 30%？”*  
这种**具体某天、某件事的来龙去脉**不会写进通用 SOP，但员工因为上下文压缩忘了之后，可以靠 RAG 按语义从历史对话里找到。（这部分其实飞书做得非常好）  
比如：几百份历史合同 PDF、客服工单里的客诉原话、每次周会的原始会议纪要。  
这些文件太大太杂，需要切成片段建索引，等遇到具体问题时再按需检索相关段落。  
比如：某一天遇到了一个很罕见的奇葩事件，老员工在 3 个月之前处理过一次；那这种低频 + 棘手的问题，就会在 RAG 里出现，并做相似匹配，直接复用就可以了。

# 四、落地实操：基于 Hermes 从 0 到 1 跑通企业级 Agent OS

从 MVP 原则出发，最忌讳上来就憋三个月，毕竟现在所有人都等不起。

所以执行的 DDL 是：在 1 周内让 Agent 跑起来，同时先覆盖 2 个部门的 Agent 架构。

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-06.jpg>)

## 第一步：搞一台服务器或 Mac

- **硬件选择**：  
**轻量起步**：一台 4 核 8G 以上内存的云服务器（阿里云 / 腾讯云即可），或者公司内网放一台 **Mac**。
- **核心原则**：服务器只负责跑网关、数据库和沙盒调度，不跑本地大模型权重——推理全走外部 API，所以不需要买昂贵的 GPU 显卡。

## 第二步：安装 Hermes Agent，建好角色 Profile

核心 Agent 底座直接用 Nous Research 开源的 **Hermes Agent**，支持 Linux、macOS 和 WSL2，MIT 协议开源，模型无关且自带记忆、Skills 闭环与 Cron 定时调度：

- **开源地址**：[NousResearch/hermes-agent](https://github.com/nousresearch/hermes-agent)
- **一键安装**：curl -fsSL [raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh) | bash
- **企业化目录拆分（关键）**：装完后不要所有人都用默认主目录，而是按部门和员工建独立 Profile 目录（/data/hermes/dept/sales、/data/hermes/dept/finance、personal/zhangsan）。
- 配合网关路由，**部门 Agent 仅绑定群聊、代码层禁用私聊**，确保销售和财务从物理目录下就彻底隔开

## 第三步：接入必备的开源组件

单靠 Hermes 只能管好单个 Agent，要把多部门协作、共享台账、RAG 记忆、模型热切换和权限卡死，建议直接复用 GitHub 上最成熟的开源组件来拼装：

# 四、如何实际推进业务？

既然前面都是计划，落地的时候还是老办法

找部门负责人，可以问他一些很实际的问题：

**他们在日常工作中，有哪些是定期 / 每天需要执行 3 次以上的重复动作，哪些是需要反复找人的。**

这部分就是沟通和工作的摩擦点。

因为信息已经存在了，处理的方式也大同小异，真正耗时的，就是把不同零散的信息整合到一起，让 Agent 进行推动。

例如：销售有客户付款截图，需要问财务到没到账；财务确认后，再通知仓库；仓库发现订单号不完整，又回来找销售。

整个过程每个人都没做错，但一笔订单还是被来回传了几遍。

这部分大部分都是 workflow 的一部分，所以可以满足 4 点：

1. **是否频繁发生**
2. **是否值得做**
3. **能不能通过数据倒推**
4. **失败了哪个员工来接手（背锅）**

还有，例如企业的一些中层工作。

其实就是决策、分析、判断，以及每天向上级汇报各种报表（此处请对号入座）

那这种工作中的大部分，其实也可以被 Agent 化。

# 五、权限的具体设置 Demo

Hermes 的 Profile 本身可以管理配置、记忆、会话等内容。

但是如果目录分开，需要一部分的权限更改以及二次开发。

我们一般把具体的权限拆分成几个层级：

![Image](<基于%20Hermes%20打造企业级%20Agent%20OS.assets/image-08.jpg>)

1. **员工身份：**谁发起任务、属于哪个公司、当前担任什么岗位、是否有临时授权，都由认证与人员系统确认。
2. **Agent 身份：**销售 Agent 有自己的服务身份，财务 Agent 也有自己的服务身份。它们可以代表获授权的流程执行任务。
3. **工具权限：**工具权限其实还可以继续拆分，但目前相对简单一些。大部分工作不会直接读取数据库，而是给它一个业务工具的接口 + 快照，例如订单汇款状态、本任务进度等等。这样可以稍微减轻数据库的压力。
4. **子 Agent：**其实子 Agent 是一样的，包括数据范围、它可以调用的工具等等，都是通过简单的调度中间完成的。

# 六 Skill 的控制及更新

对于 Skill，其实也是踩过坑的。

因为大部分员工不管你什么 Skill、什么内容，上来就聊。

聊不对了，上下文压缩后出现问题，就开始抱怨：

**“你这破玩意根本不好用，反应又慢，又智障。”**

所以为了应对这种问题，我们想到一个简单的办法：

统一做一个大的 Skill 仓库。

每一次都自动化更新并下发：

例如：今天张三的销售 Agent，学会了自动根据数据计算报表。

那晚上下班后，会有一个 Skill 的 Agent，把张三、李四、王五等等所有的聊天内容都汇总一遍，并分类，制作出不同的 Skill。

提交仓库，并下发回去，让每一个 Agent 可以自动安装并更新。

并且每次更新都有版本记录（感谢版本记录，以及上面的md）。

所以这部分其实就是持续的自我进化、持续 loop 的过程。

基本就这样，一个相对简单、可以自主、可控、多入口、统一集中管理的 Agent 框架，就可以搞起来了。

剩下的，直接让你的 Agent 去读取这个文档，并给你实操的细节就好了。

这套东西其实不难，和之前的企业内部管理很相似

只不过自由度更高，灵活度更高，而且可以接入不同的im。

比如我的团队，现在把slack，外部的erp，小程序，飞书等等都集成在一台服务器上。
