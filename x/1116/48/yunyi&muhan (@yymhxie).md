# yunyi&muhan (@yymhxie)

这两天 @andrewdsouza 有篇长文转得很多，标题叫《Nobody Trusts Your Agent》，核心一句话：Agent 可以采取行动，但只有 principal 能承担责任。  
  
他举了一个很多人都听过的案例：2022 年，加拿大一位乘客在加航官网问客服机器人丧亲票价怎么算，机器人说可以先全价买、事后再申请折扣。这根本不是加航的政策。乘客去申请被拒，告到仲裁庭，加航居然辩称机器人的话不归它负责，仲裁员直接驳回，判航空公司赔。  
  
这个案例在企业服务里其实特别典型。很多企业 AI 项目卡在 POC 之后上不了生产，原因往往不是模型答得不够好，而是客户方没人敢签字：它说错了算谁的？它做错了谁来赔？  
  
我们一贯的看法：  
  
一、承诺类的内容，不能让模型「生成」。票价政策、退款规则、合同条款、价格折扣，这些都是确定性规则。正确的做法是规则放在代码或规则表里，模型只负责理解用户在问哪一条，然后由系统把规则原文取出来回答。加航那个问题，本质上就是让模型自由发挥了一条政策。这也是我一直坚持的：确定性逻辑放进代码，用测试守住；只有真正需要推理的部分交给模型，再单独做 eval。  
  
二、权限边界要先于能力设计。Agent 能查什么、能改什么、能对外承诺到什么程度，要在系统层面卡死，不能写在提示词里「请不要……」。同一时间 FBI 在预警 ARTEX 这种被拿去自动化入侵的 Agent 框架，建议也是最小权限。对内对外一个道理：权限给多了，迟早出事。  
  
三、每一个动作都要能追溯到「谁授权的」。企业客户最关心的不是 Agent 多聪明，而是出了问题能不能查清楚：哪条输入、哪个版本的规则、哪个人批准的上线。审计日志、版本、审批记录，这些看起来很土的东西，才是让客户敢签字的底气。  
  
四、要明确「什么时候交给人」。不确定的、金额超阈值的、涉及投诉和法律风险的，就该升级到人工。这不是 Agent 能力不够，而是责任必须落在有人担的地方。  
  
D'Souza 在文章里预测 2027 会是 AI「principal」之年，也就是让 AI 用自己的名义做事、并为结果承担后果。这个方向能不能走通不好说。但在今天的企业服务现场，现实很简单：principal 就是客户自己，Agent 每一句话都代表客户的品牌。  
  
所以 FDE 在客户现场，除了把 Agent 做出来，更重要的是帮客户把责任链设计清楚：哪些规则必须硬编码、哪些动作必须审批、哪些场景必须转人工、出了错怎么回溯和兜底。这些想清楚了，客户才敢把 Agent 推到真实业务里。  
  
模型越来越强，这件事反而越来越重要。能力越大，说错一句话的代价也越大。
