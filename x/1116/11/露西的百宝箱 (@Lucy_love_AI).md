# 露西的百宝箱 (@Lucy_love_AI)

有篇中国团队发的论文，标题直接把做 AI Agent 的人问住了：《Harness Engineering 的终结》。  
  
核心就一句话：围绕模型外面那圈东西，可能不用再靠人手一行行写了。  
  
过去做一个 Agent，工具、指令、工作流、执行逻辑，全靠人设计，然后这套结构一用就是几个月。论文提了另一个思路：为什么不让系统自己去改自己的基础设施？  
  
做法不复杂：  
1. 用一个 40 亿参数的小模型，专门看系统哪里失败、哪里报错。  
2. 每次提出 8 个改进方案。  
3. 每个方案都跑一套题和测试来打分。  
4. 只留下真正跑出更好结果的那个改动。  
  
关键点在于，主模型始终不动。一直在变的是 Agent 的 harness 和执行结构。  
  
这个思路不绑定某个模型或框架，可能会改变大家搭 Agent 的方式。  
  
更值得注意的是人的角色变化：从不停写代码、调系统，转成设计测试和成功标准。也就是说，你得清楚自己到底要 Agent 干什么，以及怎么判断它真的变好了。  
  
未来真正的竞争力，可能不是谁更会写 Agent 的代码，而是谁更会评估它、改进它。  
  
整篇论文压成一句：写代码之前，先把考试题设计好。

---

这套思路怎么用到自己的项目里？不用一上来就搭新框架，可以把这个循环加到现有 Agent 上：  
  
1. 建一套测试：20 到 50 个真实任务，Agent 得能跑。  
2. 记录表现：哪里成了、哪里败了、为什么。  
3. 找个小模型帮忙：分析错误，给出几个更好的 Prompt、Skill 或 Workflow 版本。  
4. 逐个验证：每个版本都跑同一批任务，打分。  
5. 只留赢家：只保留真正提升表现的改动。  
6. 做好版本管理和回滚：每个改动都要能查、能退。  
  
几个要点：  
主模型可以保持不变。  
最终测试集要和优化模型分开。  
敏感改动别跳过人工确认就直接上生产。  
  
起步可以先优化三样：Prompt、Skills、Workflow。  
之后再逐步扩到工具选择、记忆、错误处理，甚至 Agent 的执行架构。  
  
核心就一句：别猜什么改动能让 Agent 变好，去测，让结果说话。
