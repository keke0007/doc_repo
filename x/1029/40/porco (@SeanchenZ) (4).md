工业 AI 到底是怎么接入自动化产线的？  
最近研究了一种 AOI + Machine Learning（机器学习）+ 工站控制系统 的架构，发现它比简单地让 AI 识别一张图片复杂得多。  
整个系统可以拆成五层：  
① 感知层：AOI 视觉采集  
工业相机负责拍摄产品，工站 IPC 保存原始图像。图像采集、光源、曝光和 ROI（感兴趣区域）的稳定性，直接影响后续模型的判断。  
② 通信层：API 解耦  
设备程序不直接运行 AI 模型，而是通过 API 调用独立的推理服务。  
请求中包含产品追溯标识、图像类型和存储路径。  
这样设备控制程序与 AI 模型可以相对独立地升级，不需要把所有算法都塞进设备软件。  
③ 推理层：ML 缺陷检测  
模型分析图像后，返回结构化 JSON：  
className：缺陷类型  
bbox：缺陷所在区域  
score：检测得分  
decision：PASS / FAIL  
modelVersion：模型版本  
这里的 AI 主要做视觉检测和分类，不是大语言模型，也不需要 Agent 自主规划。  
④ 决策层：工站控制  
这层才是我认为最有工程价值的地方。  
模型给出 PASS，不代表可以无条件放行；模型给出 FAIL，也不意味着必须直接报废。  
工站控制程序根据预设规则，决定继续动作、允许复测还是进入不良处理流程。  
如果模型超时、服务断开、图像缺失，系统同样需要明确的异常处理策略。  
AI 负责识别，控制程序负责执行。两者之间必须有清晰的权限边界。  
⑤ 追溯层：MES / SFC 数据闭环  
检测结果、模型版本、响应时间、产品标识和异常信息都要能够追溯。  
否则模型今天判断 PASS，明天发生批量质量异常，工程师连当时使用了哪个版本、看了哪张图片都查不清楚。  
  
⸻  
  
从自动化工程角度看，这类架构还有几个绕不开的问题：  
误检率和漏检率如何验证？模型推理延迟会不会影响 CT 和 UPH？换模型之后如何确保判定标准一致？AI 服务不可用时如何保证设备安全？  
这些问题比单纯讨论模型识别准确率更接近生产现场。  
我现在对工业 AI 的一个判断是：  
模型只是系统中的一个模块。真正困难的是把它接入已有设备、动作控制、质量规则和追溯体系，并且在网络不稳定、模型误判和设备异常时依然能够可靠运行。  
一个 AI Demo 能识别缺陷，不代表它已经具备上产线的能力。

最近在研究，一个 AI Token 中转站到底是怎么搭建出来的？  
  
发现这东西的原理并不复杂，本质就是一个 AI API Gateway（API 网关）。  
  
它不是凭空生成 Token，而是把多个模型供应商的 API 接入统一管理。  
  
整个流程：  
  
用户请求 → 中转服务器 → API Key 验证 → 余额/额度检查 → 模型路由 → 上游 API → 返回结果 → Token 用量计费。  
  
如果想自己搭建，甚至不用从零开始写。  
  
GitHub 上已经有现成的开源项目：LiteLLM。  
  
技术栈可以这样选：  
  
LiteLLM：统一 API 接口、模型路由  
PostgreSQL：用户、密钥、账单数据  
Redis：缓存、限流  
Docker + Nginx：部署与 HTTPS  
虚拟 API Key：按用户分配权限和额度  
  
先跑通一个 MVP，就能实现多模型调用、用量统计、额度限制和故障切换。  
  
但如果想把它做成真正对外收费的中转站，难点就来了。  
  
上游 API 授权、计费准确性、并发控制、Key 泄露、滥用防护、服务商条款、用户数据隐私……  
  
尤其要区分：正规 API 网关和倒卖第三方账号 Session Token，根本不是一回事。  
  
转发一个 API 请求没什么技术含量。真正有技术含量的是：当有人刷爆额度、上游限流、服务异常时，你的系统还能不能守住成本和权限边界。
