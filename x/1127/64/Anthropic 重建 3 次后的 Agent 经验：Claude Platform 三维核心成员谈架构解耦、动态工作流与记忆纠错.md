# Anthropic 重建 3 次后的 Agent 经验：Claude Platform 三维核心成员谈架构解耦、动态工作流与记忆纠错

*By meng shao (@shao__meng)*

![Banner](<Anthropic%20重建%203%20次后的%20Agent%20经验：Claude%20Platform%20三维核心成员谈架构解耦、动态工作流与记忆纠错.assets/image-01.jpg>)

Agent 能跑通一次，和能连续工作数小时，是两件不同的事。

Anthropic 自己也绕过弯路：先为了内部提效建设基础设施，再为应用重新搭建，做到第三次，才意识到很多工作一直在重复。外部客户也遇到同样的问题：已经有 Messages API、Claude Code 或 Agent SDK，却依然难以稳定地大规模运行 Agent。

Claude 官方这场对谈，请来了 Claude Managed Agents 产品经理 **Jess Yan**、Managed Agents 技术团队成员 **Michael Cohen**，以及 Claude Platform 技术团队成员 **Lance Martin**。

他们聊的重点，是**模型之外那套决定 Agent 能否长期工作的系统**：执行环境坏了怎么办，多 Agent 怎样协调，成本如何控制，以及记忆为什么会让 Agent 反复犯同一个错误。

其中最值得关注的变化是：**让基础设施承担恢复，让工作流承担协作，让离线整理承担记忆纠错。**

## 1. 为什么只有模型 API，还不足以把 Agent 带到生产环境？

团队开了一个玩笑：**Agent 不就是一个 while 循环吗？**

从最小原型看，确实可以这样理解：调用模型，执行工具，把结果交回模型，再继续。可一旦任务变长、用户变多，那个循环外面就会长出大量工程要求。

模型擅长终端操作、执行 Bash、修改文件，就需要文件系统和执行环境；重复流程适合封装成 Skills，就需要技能加载机制；接入 MCP，就得管理外部服务凭证，避免凭证泄漏。

再往外，还有故障恢复、上下文管理、提示缓存，以及多 Agent 的调度和费用约束。

**Claude Managed Agents 要承接的，就是这些反复出现的共性工作。**它提供一套开发者 API 和接口，在原始模型调用之上提供可配置的 Agent 运行能力。

这也解释了为什么“模型升级”常常会带来框架维护成本：以前用来补齐模型短板的技巧，到了新模型上，可能已经没有必要。

官方配套架构文举了一个例子：Sonnet 4.5 接近上下文上限时，可能过早结束任务，团队曾用上下文重置应对；换到 Opus 4.5，同一行为不再出现，原有重置机制便成了额外负担。

平台希望把这类跟随模型演进的维护尽量集中起来，减少每家企业重复适配的工作。当然，业务逻辑、权限配置和验收标准，仍然要由使用方负责。

## 2. 最关键的架构调整：别把整个 Agent 塞进一个容器

**团队最早的方案非常直接：把 Agent 的运行控制逻辑放进沙箱，让 Claude 在里面工作。**

这里的 **Harness**，是 Agent 的运行控制层：负责调用模型、执行循环、路由工具调用和管理上下文。它不等于模型本身。

把这些东西全部装进一个容器，原型容易搭，但故障也被绑在了一起。

如果容器卡住或退出，而此前状态没有保存到数据库或检查点，一整场会话就可能丢失。工作持续数小时后，这种风险很难接受。

**团队最终把系统拆成三个相对独立的部分：**

- **Claude 与 Harness**：负责推理、协调和发出工具调用。
- **沙箱与工具**：负责执行代码、编辑文件、访问外部能力。
- **独立持久化的会话事件日志**：保存发生过什么，支持恢复和重新读取历史。

拆开之后，**沙箱变成一个可替换的执行组件。**它坏了，运行控制层接收到工具错误，再根据任务需要恢复或重新创建执行环境，不必连同整场任务一起报废。

官方架构文还补充：Harness 自身也可以替换。因为会话日志保存在外部，新的 Harness 能重新读取事件记录，继续处理工作。

这里的可靠性思路很务实：不要求每个运行实例永远不坏，而是让实例坏掉后，工作仍然有恢复依据。

它也改变了资源分配方式。过去，每启动一个 Agent，可能都要先准备容器、拉取仓库、启动进程；现在，暂时不需要沙箱的会话，可以先开始推理，真正用到时再配置执行环境。

官方架构文章报告，这套架构使 **p50 首 token 延迟下降约 60%，p95 下降超过 90%**。这些数字来自配套技术文章，并非对谈公布的新跑分；衡量的是开始输出前的等待时间，不能写成整项任务快了 60% 或 90%。

## 3. 解耦也在改变安全边界与上下文管理

这种拆分不只是为了可用性。

在早期耦合设计里，Agent 生成的不可信代码与部分凭证处于同一个环境。提示注入一旦诱导模型读取环境信息，就可能触及不该暴露的秘密。

配套架构文介绍，结构性的改进是把敏感凭证放到执行沙箱够不到的地方。例如，MCP 的 OAuth 凭证保存在独立的安全存储中，由代理服务代为调用外部服务，避免直接把凭证交给生成代码的环境。

这并不意味着 MCP 调用天然安全，更不意味着 Agent 得到了任意操作外部系统的授权。凭证隔离解决的是秘密如何保管，工具权限和用户确认解决的则是哪些动作可以做。

另一个容易混淆的概念，是会话记录与上下文窗口。

**模型当前看见的内容，只是会话历史的一部分。**为了控制上下文长度，系统可能压缩或移除旧内容；但如果完整事件记录独立保存，后续仍可以按需回查，而不用完全依赖早先那份摘要。

这样，历史如何保存，与本轮给模型看什么，就能分别演进。

恢复能力也有边界：保住日志不等于任意外部操作都可以安全重试。对支付、发信、修改业务数据等有副作用的动作，应用仍要处理幂等、重复执行和人工确认。这是采用这类架构时需要补上的业务设计。

## 4. 动态工作流：让 Claude 为当前任务编写协作程序

多 Agent 的早期形式相对简单：一个协调者，给几个长期存在的子 Agent 发消息，再收回结果。

这种方式有用，但复杂任务常常需要更丰富的结构：根据中间结果分支、对某个步骤循环、多路并行收集信息，再合并成统一输出。

访谈中的 **Flows，也就是动态工作流**，把编排能力进一步交给 Claude：让它在运行时编写程序，组织不同 Agent 及其结果流转。

例如，一项大量文档审查任务，可以先并行阅读不同材料，再汇总冲突信息，对仍有疑点的部分补充检查。这是帮助理解机制的例子：关键在于，阶段和分支可以由程序承接，不必每一步都由主 Agent 逐条传话。

**官方文档把两种方式区分得很清楚：**

- **子 Agent 委派**：主 Agent 自己决定下一步，读取汇报后，还可以继续追问。
- **动态工作流**：主 Agent 写出编排程序，服务器在后台运行，各阶段结果由程序传递和组合。

后台工作流运行时，主会话还可以与用户沟通、查看进度，而不用一直承担所有协调细节。

成本优化也与此有关。团队提到，开发时用最强模型处理复杂任务很正常，但规模扩大后，可以让能力更强的模型负责协调，把适合的子任务交给其他模型。

不过，这不是模型可以随意选择任何模型。按官方文档，工作流临时定义的 Agent 默认使用主 Agent 的模型；如果需要混用模型，需要事先提供相应的预定义 Agent。

**多 Agent 也不自动等于便宜。每个参与者都会消耗 token，沟通、重复调查和复核同样有开销。**视频没有给出通用的成本降幅或完成率提升比例。预算与成本优化是团队强调的重点方向，不能据此把所有设想写成已经自动解决的问题。

## 5. 不仅修改答案，也修改完成任务的组织方式

对谈把动态工作流与 **Outcomes** 联系到了一起。

Outcomes 的作用，是告诉系统最终交付物应该是什么样，以及怎样判断是否达标。

按官方文档，开发者需要提供明确的评分标准，也就是 Rubric。运行控制层会配置评估器，在独立上下文窗口中检查交付物，再将哪些标准通过、哪些没有通过的反馈交给 Agent。

随后，Agent 可以继续修改，直到满足条件，或达到迭代上限、被中断等终止边界。

这里有个值得注意的扩展：过去，我们容易把“改进结果”理解成修改提示词、补充材料、重写输出。但如果工作流本身也可以调整，Agent 就还能改变任务分解和协作方式。

比如，发现结果缺少独立交叉核对，下次就可以增加复核环节；某一步覆盖不足，可以重新拆分并行任务。这些是理解机制的例子，不是视频给出的产品实测案例。

**协作结构由此成为可以优化的对象。**

但目标是否写对，仍然决定优化方向。评分标准含糊，系统就可能在错误指标上反复改进；评估器使用独立上下文，也不等于它一定判断正确。

对代码、数据分析和业务操作，自动评分最好与测试、事实核对或人工验收配合。模型认为达标，只能算验收证据的一部分。

## 6. 记忆为什么会越积越乱？因为写入时看不到后来发生的事

**对谈后半段最有意思的部分，是 Agent 的记忆。**

Agent 正在做任务时，只能根据当时掌握的信息，判断哪些内容值得记住。它的写入往往服务于当前任务，未必会与所有旧记忆逐条核对。

任务一多，记忆库就可能出现重复、矛盾、过时信息，甚至把一次错误判断保存成长期经验。

因此，**能写记忆，不等于已经形成了可靠的长期记忆。**

**团队介绍的 Dreaming，可以理解为一个独立的离线整理过程：**把过去的会话日志和已有记忆放在一起，回头检查实际发生了什么、当时记下了什么，再合并、整理和纠错。

对谈用 Pokémon 游戏举例。Claude 曾经把某个东西的位置记错，后续走到相关环节时，又依据这条错误记忆采取行动，反复陷入问题。

启用 Dreaming 后，系统能对照之前的游戏记录和错误条目，修正记忆，再继续推进。

这是一个具体、直观的案例，但视频没有公布样本规模、完整对照结果或统一成功率，因此不能据此推导所有长期任务都能获得同样收益。

**Dreaming 也不是模型真的在睡觉，更不是在后台更新模型权重。这里改变的是外部记忆内容。**

官方 Dreams API 文档进一步说明：一次任务读取一个已有记忆库，以及 **1—100 个历史会话**，生成一个新的、重新组织的记忆库。输入记忆库保持不变，用户可以检查输出，不满意也可以弃用。

这一点很重要：整理后的版本不必直接覆盖旧版本，给审核和回退留下空间。

## 7. 真正值得保留的基础能力，是版本记录与审计

团队回顾，当初推出记忆功能时，对大规模表现和一些潜在问题还在探索，但已经确定两件事很重要：**版本管理和完整的审计记录。**

有了这些基础，后续加入 Dreaming 就更自然。记忆本来就会持续变化，离线整理只是另一种触发变化的方式。

官方记忆文档也说明，**每次修改都会生成不可变的记忆版本，支持追踪和时间点恢复。**

这类能力不如“Agent 自动学习”醒目，却是长期使用时很实际的保障：出了问题，能看见是哪条记忆变了、变化前是什么，以及是否需要恢复。

同时，不要把所有名为 Dreaming 的实现混成一套机制。官方 Dreams API 输出新记忆库；官方另一个自定义工作流示例，则允许开发者选择提示词、模型和输入，并原地更新记忆库。是否自动替换、是否定时运行，要看具体实现。

对谈中的游戏实验采用定时触发，在若干轮游戏后离线整理。这是该实验的安排，不代表所有用户都默认拥有同样的后台调度。

## 8. 客户案例说明接口有价值，但还不是普遍收益的证明

**团队分享的客户使用方式比较分散：有人用沙箱隔离客户代码、支持应用分析；有人使用记忆；还有人使用 Outcomes。**

其中一个法律领域创业公司的故事是，公司向不同岗位员工开放能力后，非开发者也开始结合 Claude Code 等工具，为自己的业务流程搭建定制 Agent，数小时内就能做出个人化助手。

团队由此提出一个判断：企业员工不采用 AI，有时未必是模型能力不足，也可能是接口离他们的工作太远。

这个观察值得参考，但案例没有公开公司名称、部署规模或严格的生产率测量，不能把“数小时做出助手”写成普遍的企业交付承诺。

产品状态同样需要分清：**视频说明将 Managed Agents 与动态工作流标为 Beta，将 Dreaming 标为研究预览。**功能可用不等于所有场景已经成熟；持久化会话与记忆也意味着需要认真处理数据保存、访问范围和清理策略。

## 我自己的感受

这场对谈最有价值的地方，**是把 Agent 的几个“聪明表现”，还原成了具体工程问题。**

能连续工作，背后需要可恢复的状态；能多人协作，背后需要可追踪的编排；能积累经验，背后需要对错误记忆的修正机制。

我尤其认同两点。

**第一，组件可以替换，证据不能随便丢。**执行环境、运行控制层乃至当前工作流都可能改变，但会话记录、版本历史和评估反馈，应该成为后续恢复与纠错的依据。

**第二，长期记忆的价值，不只看它能记住多少，还看它能否改掉已经记错的东西。**如果只有追加，没有整理和回退，持续使用也可能持续放大偏差。

不过，动态编排和自动记忆整理，都会把更多判断交给模型。采用它们时，仍然要保留模型之外的约束：明确权限、费用上限、独立测试，以及高风险动作的人类确认。

**对正在做 Agent 的团队，我会先问三个问题：**

1. 执行环境突然消失，任务能从哪里继续？
2. 增加一个 Agent，收益和额外成本怎样被观察？
3. 一条错误记忆反复影响结果时，能否找到来源、纠正并回退？

这三个问题有了清楚答案，再谈更长的运行时间、更复杂的团队和更强的记忆，才更有底气。
