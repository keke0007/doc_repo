# Ontology Engineer，先把同一件事对齐

*By astaxie (@astaxie)*

![Banner](<Ontology%20Engineer，先把同一件事对齐.assets/image-01.jpg>)

最近一直在想，Agent 接到企业真实系统里以后，下一步会卡在哪。

[Token 要有人管](https://x.com/i/article/2122555670977552630)，[流程已经确定时，也不该每次让模型自己排下一步](https://x.com/i/article/2122946616390828032)。这些我都写过。可接口一旦接上，还有一层更容易被跳过：同一个词，在不同系统里未必是同一件事。

我越来越觉得，企业 Agent 落地卡住的地方，不只是工具接得够不够多，而是同一件事在各系统里的含义有没有对齐。

做这层工作的人，我愿意叫 Ontology Engineer，负责业务对象含义对齐与关系约束的工程师。下面用一个假设的「订单」把这件事说清楚，不是某个真实客户的项目记录。

## 接上 API，还不等于查到了同一张订单

假设一家公司已经把 ERP、CRM 和工单系统接到了 Agent。MCP 也好，普通 API 也好，三个系统都能调。演示时很顺利：一句话发出去，三边都有返回。

业务人员接着说：查一下这张订单现在什么状态，客户有没有催过。必要的话，帮我把收货地址改对。

ERP 里的订单，可能是销售单，带着物料号和发货状态。CRM 里的订单，可能还停在商机或合同，客户编号跟 ERP 不是同一套。工单系统里也有「订单」，常常只是客服备注里的一串号，有时是内部服务单号。

按字面去搜，三边都能给出结果。Agent 可能看到 CRM 里合同还待签字，ERP 里已经有发货记录，工单里又写着客户在催。它很擅长把这些拼成一段通顺的话，告诉你「订单已发货，同时还在等客户确认」。听起来像掌握了全局，其实可能把三张不同的单据认成了同一件事。

SKU 也一样。ERP 用物料编码，电商用 SKU，CRM 用产品名。客户在一个系统里是客户编号，在另一个系统里是账户，在第三个系统里是下单邮箱。名称相近，并不等于同一实体。

如果这一步只是查错，后面还能人工纠正。一旦 Agent 被允许改地址、关工单、触发补发，写到错误对象上，纠正成本会高很多。权限此时往往是对的，错的是它认准的那张单。

**接口通了，只说明 Agent 能发请求。对象有没有对齐，要另外做。**

## 要对齐的是含义，不只是字段名

把字段改成同一个英文名，解决不了这件事。order_id、OrderNo、单据编号可以全部叫「订单号」，仍然可能指向不同生命周期里的不同记录。

先要对的是标识。这张订单在 ERP 里是哪个 ID，在 CRM 里对应哪条记录，工单又引用哪一个。一对多很常见：一笔合同拆成多张发货单，一张客服工单又挂了好几笔订单。映射要允许这种结构，也要写清楚反向怎么查。

对不上的，应该进待核对队列，把两边拿到的原始标识、出现位置和失败原因留下来，交给认得这些系统的人。别让 LLM 挑一个「最像」的补上。相似度很高的客户名、只差一位的单号、曾经用过的旧编码，都很容易被补成一条看起来合理的边。

再看字段归属。收货地址以谁为准？合同金额被谁改过算数？不同系统都允许编辑时，要有冲突规则，而不是谁最后写入谁赢，更不是模型当场决定。有些字段可以同步，有些只能引用，有些改动必须走原来的审批。

生命周期也不一样。CRM 里「已成交」，在 ERP 里可能才刚建单，在仓储里可能已发货，在工单里可能还是「处理中」。Agent 对外说「这张订单已完成」，得先说清楚完成的是哪一段。状态可以对，但不要暗中合并成一个新的「完成」。

关系约束也要写明白：订单必须属于一个客户；一个 SKU 不能同时指向两个有效物料；作废的订单不应再被当成可发货对象。这些约束最好落在系统里，而不是只写在 prompt 里。换一个模型、换一轮对话，写在提示词里的关系很容易被忘掉。

找不到映射、关系不成立、状态互相打架，都该停下来等人核对。猜测补全，看起来聪明，错单会顺着后面的流程一直走。

## 画图谱、接 MCP，都替不了这层

RAG 能把制度、说明书和历史工单找出来，帮忙解释规则。它不负责告诉你，这两个 ID 是不是同一张订单。文档里写过「以 ERP 为准」，也不等于系统里已经有可执行的映射。

MCP 让 Agent 比较方便地调用工具。工具在，不等于对象已经清楚。同一个动词「查询订单」，后面仍可能打到完全不同的表。接上 MCP，解决的是怎么调用，不是调用的究竟是哪一个对象。

把关系画成 Ontology 或知识图谱，有时有用，尤其是要表达对象之间的约束。可图本身不会自动产生可靠映射。没有人确认过的边，只是又一份文档。先上很重的建模平台，也很容易变成先维护图，再回头处理 Agent 真正会碰到的那几个对象。

我更想先选一个真正被 Agent 碰得到的对象，把各系统里的标识、关键字段、状态和关系写清楚，再让流程去用它。先跑通这一小块，待核对队列里积下的问题，往往比一张完整的企业对象图更早暴露真相。

Harness 可以把权限、审批和失败路径托住。流程引擎可以管步骤、状态和重试。TokenHub 这类企业 Token 管理，管的是请求走哪、谁有权限、用量和账单能否对上。这些都很必要。可要是对象都认错了，权限给对了，步骤也会跑在错误的单据上，Token 也会花在查错东西上。

**模型可以整理线索，不能替你完成未确认的对齐。**

## 这层工作，最好能被流程直接用上

Ontology Engineer 在这里要做的，是让 Agent 和流程在动手前知道：当前到底在处理哪一个对象，能做什么，不能做什么。先写一本很全的企业词典，往往还轮不到被流程用上。

还是这张假设的订单。先和各系统的负责人确认，哪个系统在哪个阶段是事实来源。写出标识怎么映射，哪些字段谁说了算，状态如何对应，对不上时谁来处理待核对队列。队列里每一条最好都能回到原始记录，而不是只剩模型当时的一句摘要。没有负责人的队列，问题还是会回流到对话里，让模型再猜一次。系统改版、字段更名之后，映射也要一起改，不能默认旧关系永远有效。

第一版不必覆盖所有对象。能先把「查订单状态、不要改错单、对不上就停」做对，已经比接上十个工具更接近能交付。改地址、催发货、开退货，可以等这条查询路径站稳后再加。每加一个会写数据的动作，就多检查一次：它作用的是已确认的对象，还是又回到了按名字搜索。

流程确定的步骤，仍然交给确定性的引擎；需要读材料和判断的地方，再交给 Agent。只是两者都要站在已经对齐的对象上，而不是各自对词。对象一变，约束还在，不必为每个新动作重讲一遍「订单是什么」。

我自己还没有把这层做成一个独立产品。但每次把 Agent 往真实系统里接，都会重新碰到它。

如果你也在接企业系统，不妨先只盯一个对象，把各系统里的名字、ID、状态和找不到时的处理写下来。对不齐的地方先露出来，再决定让 Agent 做什么。
