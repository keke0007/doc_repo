# porco (@SeanchenZ)

收到一位x好友的来信，给我发的FDE学习资料，里面有一个观点非常值得学习深思：Agentic Flywheel（自主持续改善飞轮）。  
  
传统的软件交付往往以系统上线、功能验收作为项目终点。而这套机制认为，系统上线才是业务持续改善的起点。  
  
它将整个改善过程拆解为四个阶段：  
  
01｜Run（受控执行）  
  
Agent 基于 Ontology 中定义的对象、关系、规则、权限和状态转换执行任务。确定性操作交给代码，不确定性问题交给 AI 推理，高风险操作由人工审批，执行结果通过独立证据验证。  
  
02｜Sense（摩擦感知）  
  
持续记录业务运行中的摩擦：  
  
哪些操作频繁触发人工审批？  
哪些规则经常被特批绕过？  
哪些流程反复执行却没有产生实际价值？  
哪些异常始终无法通过现有流程解决？  
  
这些数据不仅是运行日志，也是下一轮业务改善的输入。  
  
03｜Propose（自主提案）  
  
Agent 根据历史执行记录、异常数据和审批结果，主动识别流程瓶颈，向业务负责人提交规则与流程修订建议，并提供相应证据。  
  
04｜Evolve（受控进化）  
  
业务负责人审核提案，确认改善方案后，更新业务规则、权限和底层 Ontology，再进入下一轮执行。  
  
整个过程形成闭环：  
  
受控执行 → 摩擦感知 → 自主提案 → 受控进化 → 再次执行。  
  
这套机制让我联想到制造业一直强调的 PDCA 持续改善循环。  
  
过去，工程师需要主动收集异常、分析数据、组织会议、提出改善方案，再推动跨部门执行。  
  
而 Agentic Flywheel 尝试将其中的信息收集、异常识别、证据整理和改善提案逐步自动化，同时将业务决策权保留在人手中。  
  
这里有一个重要的边界：AI 可以主动发现规则的问题，但不能未经授权自行修改规则。  
  
我认为，这也是 FDE 一个值得长期研究的方向。  
  
交付一个能够解决当前问题的 Agent，只是第一步。如何让系统在日常运行中持续发现新的业务问题，并形成有证据、可审批、可验证的改善闭环，才是更有长期价值的工程能力。  
  
当然，这套机制目前仍需要真实业务数据和生产环境验证，不能仅凭架构设计就认定它能够实现持续改善。
