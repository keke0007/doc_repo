# AetherKernel | 以太内核 (@AetherKernelX)

分享一期关于Skill开发的经验和体感  
  
Skill 最怕的不是写得少，而是越修越臃肿  
  
有几个坑，比 Skill 写法本身更值得注意  
  
1. 别把每个 Bad Case 都变成一条永久规则  
  
先分清是触发错误、流程缺陷、工具问题，还是模型本身的不稳定  
  
比如 Agent 漏掉测试步骤，不一定需要加一句「必须运行测试」  
  
可能是 Skill 没定义完成条件，也可能是测试环境根本不可用  
  
根因不同，修法完全不同  
  
2. 警惕规则之间的隐性冲突  
  
前面写「遇到异常自动修复」  
  
后面又写「禁止修改非目标文件」  
  
当修复依赖修改配置文件时，Agent 到底该听哪个？  
  
规则不是越多越安全，缺少优先级和冲突处理，反而容易让执行路径变得不可预测  
  
3. 别用模型的自我评价验证 Skill  
  
Agent 说「已严格遵循 Skill」，不代表真的遵循了  
  
要看实际 tool calls、文件 diff、测试结果  
  
尤其是禁止操作，最终结果正常，也不代表中间没有越界  
  
4. 修改 Skill 必须做回归  
  
修复一个 Bad Case 后，至少重跑原失败场景、相邻场景和不该触发的场景  
  
否则很容易出现 A 场景稳定了，B 场景却退化了  
  
5. 能变成确定性约束的，就别一直堆 Prompt，固化脚本优先  
  
比如禁止修改指定目录、输出必须符合 Schema、关键文件必须存在  
  
能在执行层校验，就别只靠 SKILL.md 反复强调  
  
Skill 应该像代码一样做回归，而不是像补丁一样无限叠加
