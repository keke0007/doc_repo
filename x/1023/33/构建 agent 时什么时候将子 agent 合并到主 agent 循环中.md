# 构建 agent 时什么时候将子 agent 合并到主 agent 循环中

*By 南晚Nanwan (@snwiki238337)*

![Banner](<构建%20agent%20时什么时候将子%20agent%20合并到主%20agent%20循环中.assets/image-01.jpg>)

这篇是对于 Claude 发布的一篇文章：[Building agents：When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) 的一篇翻译，我读下来感觉写的很好，不论是当做教程还是一个指南都很好，对于做开发的也有一定启发。所以有了这篇译文。  
  
这篇文章讲的主要是当你碰到一个 agent 问题的时候，如果你不知道什么时候该向你的多 agent 系统种加入子 agent 的时候，你可以参考这篇文章。  
  
在 Claude Platform 中构建 agent 时，相比于使用更多的子 agent 工作，如果采用逐步披露的上下文和工具、减少子 agent 的数量，可以在降低成本和延迟的同时提升你的工作质量。以下是介绍何时以及如何进行这种迁移。  
  
如果你已经在 Claude Platform 中构建了一个包含多个子 agent 的 agent，可以使用 Claude Platform 的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)，查看哪些子 agent 适合折叠进入主 agent 循环。这个工具包会运行一个引导式工作流，识别你的模式、评估替代方案，并验证最佳方法。其中还会包含一个演示，你可以先在模拟系统上尝试使用，再在你的 agent 上运行。_  
  
子 agent 是一个拥有自己的上下文窗口、工具和指令，并由协调器编排的 agent。是 agent 设计的核心组件。它们在验证、并行工作和模块化权限管理方面很有效。Claude 自己在使用 Claude Platform 构建的许多自有 agent 中都使用了它们，例如 Claude 的[多 agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。  
  
然而最近 Applied AI 团队发现了一种企业 agent 部署模式，就是可以将路由器、规划器和领域子 agent 折叠加入主 agent 循环后，能够从中受益。在[Claude 团队对多个企业部署进行的比较](https://claude.com/blog/the-anatomy-of-effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)中，一个配备 skill 的单一 agent 在质量方面经常胜过一个通过一条提示处理所有事情的设计和子 agent  
设计，而且每项任务的成本和延迟通常也比带有 skill 的单一 agent 更低。

例如一家公司发现，其面向客户的 agent 中包含十几个专业子 agent，这使得持续维护符合品牌的体验变得困难，并且还增加了延迟，用户体验也不尽人意。  
  
我们还经常看到一些遵循熟悉演进路径的 agent 设计方案，比如：意图分类器、固定的多步骤推理流水线、用户细分桶、独立的推荐分支，以及位于最上层的多 agent 编排器。  
  
在这些情况下，反馈通常是其中大部分的结构都在替模型完成它已经不再需要外部完成的工作。一个清晰的系统提示、4-5 个轻量数据工具，以及严格的输出约束，就足以覆盖大部分使用场景。

![🎥 Video](<构建%20agent%20时什么时候将子%20agent%20合并到主%20agent%20循环中.assets/image-02.jpg>)

需要明确的几点是子 agent 仍然有其适用场景，包括研究前沿。建议以下情况可以使用子 agent：

-  单个 agent 循环因上下文膨胀而出现可测量的性能下降
- 多个任务需要并行处理，并使用任务完成后即可丢弃的全新上下文窗口
- 单个 agent 难以选择合适的工具，或者系统提示中存在相互冲突的指令

但 Claude 团队经常看到企业为每个团队或问题类型都提供一个独立的子 agent，最终 agent 架构变成了组织架构图的复制品（康威定律）。  
  
本文将结合 Claude 在大型组织中构建 agent 时学到的最佳实践，解释什么时候应该考虑将子 agent 加入进主 agent 循环。

## 大型组织构建 agent 时的失败模式

大部分的企业通常希望构建一个 agent，将多个产品和能力统一到一个客户界面中。  
  
通常每项能力都由一个独立团队负责，因此企业会先让每个团队分别构建自己的 agent，然后由中央平台团队在其上构建一个编排器。这可以采用多种结构，包括编排器-子 agent 结构，或将特定 agent 作为 MCP 工具暴露出来的单一 agent。  
  
这看起来像是一个最简单的解决方案，但会立即引入以下几个复杂性：

1. 上下文管理：你需要决定 agent 之间需要交换哪些上下文，而且在来回传递的过程中经常会丢失上下文细节。
2. 子 agent 泛滥：每个团队都交付自己的子 agent，因此企业最终会拥有数百个相互重叠的子 agent，却没有强制执行的标准，也没有明确的负责人。
3. Frankenprompt：每个团队如果都向系统提示添加一句话，最终会导致规则相互冲突，而且没有一致的声音。
4. 未经审核和过度局部化的评估：每个人都添加自己的评估体系，并且这些评估针对自己的子任务进行了过度的优化。没有人去负责维护整个评估集，而领导层则基于被稀释且过度局部化的分数做出决策。
5. 延迟：多 agent 架构的复杂性会增加延迟。一位客户将其多 agent 工具链与单 agent 循环进行评估后发现，后者的运行速度大约快了 2 倍。

## 使用具有渐进式披露的 agent 循环

上文所述的编排器-子 agent 设计，是协调跨团队构建的专业 agent 的一种合理方法，但通常更有效的方法可能是通过 skill 逐步披露上下文，以及通过 mcp 工具搜索逐步披露工具。换句话说，agent 先看到 skill 和工具的简短描述，只有在需要时才会完整加载它们。  
  
这种方法有三个理由可以成立：

- 共享上下文会产生更好的答案：对于运行时间较长的 agent，我们希望来自多个不同任务的上下文都保留在主上下文窗口中，最好不损失细节。看过每个早期的步骤结果的 agent 可以将它们联系起来，这会带来比一组由子 agent 返回的摘要更丰富的输出以及更好的洞察。这也意味着[更少的上下文窗口和更少的信息损失型交接](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)。
- 渐进式披露可以防止上下文膨胀问题：这项技术允许团队构建能够完成多种任务的单一 agent，而无需将所有上下文立即加载到一个很长的系统提示中。这消除了团队此前跨子 agent 拆分工作的主要原因。事实上，我们[将 Claude Code 面向更高级模型的系统提示减少了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)，其中包括与逐步披露 skill 和工具相关的删减。
- 模型的能力更强了：从 Opus 4.5 开始，模型具备了在单个循环中管理远超大多数团队预期的工作量的能力。你无法关闭 Opus 5.5 和 Fable 5.1 的思考功能，而近期的模型也越来越多地叙述自己的进展并在过程中检查工作，这使得一些工具链元素变得多余。每个新模型都让你可以将更多决策从工具链中移出，交给模型本身完成。更简单的循环也更容易迁移到下一个模型；在我们帮助客户进行的迁移中，僵化的多 agent 结构往往正是阻碍新模型承担更多工作的因素。

单 agent 循环设计需要纪律：需要精心管理的系统提示、能在正确时机触发的 skill 和工具描述，以及对上下文窗口、记忆和记笔记的有意识处理。本文将在后续章节深入探讨迁移和设计方面的考量。  
  
应由一个中央团队负责端到端质量和系统提示，并在每个新工具和评估上线前对其进行审核。保持这个中央团队规模较小，有助于快速迭代，并降低大型组织中的协调成本。  
  
如果你选择多 agent 路线，应从可能奏效的最简单的模式开始（生成器-验证器、编排器-子 agent 或其他模式）。通过按上下文划分：给每个子 agent 分配一项几乎不需要系统其他部分信息的工作，并让它返回一个紧凑的结果，来有效划分边界（适合的候选包括独立的研究路径、具有清晰接口的独立组件，或黑盒验证）。当 agent 按问题类型拆分时，它们会陷入“电话游戏”，在每次交接中来回传递信息，并不断降低保真度。

## 如何将子 agent 折叠进主 agent 循环

许多团队已经在生产环境中拥有一个编排器和一组专业 agent。以下是我们建议努力实现的单循环设计：

- 一个模型和一个上下文窗口运行开放式工具循环，并由工具链设置限制（轮次和成本预算、写入闸门）。
- 每一轮中模型发出一批工具调用。工具链并行运行这些调用，并将原始结果返回给同一个模型，由模型决定下一步：再发出一批调用、向用户提问，或给出答案。
- 当模型回答或达到[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时，循环会停止。回答后可以选择运行目标检查或验证器检查。
- 模型在第一轮将计划写入上下文，并随着结果到达而修订计划。这是它与编排器和专业 agent 设置之间的主要变化：编写计划的模型也是执行计划的模型，因此它可以在回合中途改变计划。
- 上下文仍然会被加载，并由 agent 自身管理：

1. 不再需要通过规则目录去重写计划的代码步骤，因为模型会决定每一步。
2. 顺序和领域流程转移到skill中。
3. 硬性限制（验证、审批闸门）以及对话过程中出现的其他任何内容（例如记忆查询）转移到工具中。
4. 代码仍然可以用于加载任何成本低且几乎总是相关的内容（例如实体解析步骤），以及处理循环所调用工具内部的机械性部分（负载构建、流解析、恢复澄清流程）。

这种单循环设计也有助于实现许多团队正在努力实现的最终状态（一个理解用户高层目标并代表用户采取行动的 agent），因为它将 agent 学到的一切都保留在一个上下文中。  
  
以下建议介绍团队如何分阶段从多 agent 系统转向单 agent 循环，以及多个团队如何在这一过程中继续为该 agent 做出贡献。

任务完成评估

第一步是创建一个评估集，帮助你判断是否应该将某个子 agent 折叠进主 agent 循环。我们看到行之有效的评估结构是：由中央团队负责一套共享的端到端评估集，同时每项 skill 都配有由其负责团队交付的小型评估集。即使只有 10 个黄金示例，也足以开始。  
  
根据评分标准对 agent 的最终消息进行评分，是跟踪答案质量的良好起点。在你仍然拥有编排器时，还应该跟踪路由准确性（它是否选对了子 agent？）。折叠子 agent 后，应该改为检查 agent 是否加载了正确的 skill 或调用了正确的工具。随着时间推移，朝着任务完成评估努力会很有帮助，因为在比较架构时，这一点最为重要。  
  
在内部系统难以重放、用户参与难以模拟的环境中，这可能会很复杂。Claude 团队内部采用过的一种有效方法是在重要事件上记录时间戳，以便之后重放这些事件，作为有针对性的评估运行。

随时间减少子 agent

向单 agent 循环演进需要将子 agent 折叠进工具和 skill 中。可以通过合并领域子 agent、将它们作为工具调用，或用 skill 和工具替代它们来完成。

![🎥 Video](<构建%20agent%20时什么时候将子%20agent%20合并到主%20agent%20循环中.assets/image-03.jpg>)

合并领域 agent  
  
在第一次合并之前，先构建一个小型端到端评估。然后从使用最多的子 agent 开始，按共享上下文进行折叠。  
  
[合并专业 agent](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)，这些 agent 会串联使用彼此的输出、接触相同的数据，或经常被一起调用。例如，如果生产流量中有相当大一部分是先调用一个专业 agent、再调用第二个专业 agent，那么这就是一个紧密耦合的组合，适合将其合并为一个领域 agent。

作为工具调用的子 agent  
  
当上述三个条件中的一个适用，而你仍然保留一个子 agent 时，让主 agent 将子 agent 作为工具调用可能会很有效，这样主 agent 就可以继续与用户进行对话。  
  
只有当子 agent 需要直接与用户交流时，我们才建议进行完整交接，让子 agent 接管对话。其他所有内容都可以在主循环中通过 skill 加工具来完成。  
  
这样，你可以为子 agent 定义共享的响应模式，让主 agent 根据真实数据验证结论，并缩减最终综合步骤的输入。这是一个很好的第一步，因为你不需要重写子 agent。在决定将任何子 agent 折叠进主 agent 之前，这也能让你在任务完成评估上获得一个基线。

然而，一些失败模式仍然会存在：

- 每个专业 agent 都有自己的提示、上下文、负责团队和评估
- 每次调用仍然会返回一个有损摘要
- 每次调用仍然是一个会增加延迟的嵌套模型循环

通过 skill 和工具将子 agent 折叠进入主 agent  
  
一次将一个子 agent 折叠进主 agent：把每个子 agent 的提示转换为 skill，把 API 调用转换为 MCP 工具。比较有无子 agent 时的评估表现，然后决定保留哪些。  
  
比较时不要只检查最终分数，还要看看哪些任务发生了变化。我们在一个示例支持 agent 上进行测试时发现，将一个子 agent 折叠进另一个子 agent 降低延迟，但也破坏了一个原本一直通过的流程。主 agent 持有订单查询工具并自行作答，没有向配送专业 agent 询问交付日期。  
  
每次变更前，确保你的评估中包含生产环境中会一起运行的每条 agent 链所对应的任务，以及 agent 绝对不能违反的每条规则所对应的任务；并且每项任务都运行多次，因为像这次这样的故障，在两次运行中只出现了一次。

多个团队如何为单一 agent 做出贡献  
  
领域推理可以从知识库、skill 和 MCP 工具中检索。各个团队可以将其负责范围从 agent 转移到 skill 和工具上，同时由一个小型中央团队负责系统提示和端到端质量。这包括在新 skill、工具和评估上线之前对其进行审核。

MCP 工具  
  
当 agent 需要采取行动、从系统读取实时数据，或以固定形式返回结果时，工具是合适的选择。迁移期间，也可以使用工具继续调用子 agent。我们建议按照用户意图对工具进行分组（而不是每个 API 对应一个工具），因为一旦系统提示中的工具定义超过 30-50 个，工具选择往往会下降。  
  
使用带有延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，限制硬性前置条件，并将任何需要的前置条件移入工具中。例如如果 Y 需要 X 的输出，Y 的工具会检查这一点，并返回模型可以执行的指令。每用户权限的处理方式也相同。每个工具都会检查调用用户可以查看或执行的内容，并返回模型能够读懂的普通拒绝信息，因此一个循环可以服务具有不同访问权限的用户，而无需为每个权限级别设置独立 agent。  
  
skill  
  
当 agent 需要了解团队如何开展工作，例如专业子 agent 提示原本承载的步骤、规则和判断时，skill 是合适的选择。  
  
我们发展 skill 库的方法，是将维护工作交还给编写 skill 的人。Claude 可以借助能够构建、测试和清理其他 skill 的 skill，承担其中的大部分繁重工作。  
  
为防止 skill 泛滥，可以让每个团队的 DRI 负责其 skill，并确保这些 skill 编写良好、彼此有区分，并随适当的评估一起交付。

-  skill-creator 允许你编写新的 skill，使其从一开始就具有良好的结构，并审核现有 skill，以精简、去重和重构它们。
- skill-doctor 允许你查看 skill 库中每项 skill 的成本及其实际使用频率，并删除无效负担。

知识库  
  
对于 agent 仅在部分时间需要的参考材料，知识库是合适的选择。事实和参考材料（政策、指标定义、产品规格）可以放在模型调用的搜索或查询工具之后，也可以作为参考文件随 skill 一起交付。避免让[代码检索这些上下文并将其粘贴到提示中](https://claude.com/blog/seeing-like-an-agent)

## 加速这项工作的工具

我们最近[发布](https://code.claude.com/docs/en/commands)了一组 Claude API skill，可以帮助完成上述大部分工作。我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)将这些 skill 串联在一个引导式工作流中，用于评估多 agent 系统并将其迁移到单 agent 循环。它包含一个演示，你可以在对真实系统运行之前先行尝试：

-  claude-api build-eval：可以帮助创建第一套由中央团队负责的端到端评估集，或由各团队随其 skill 交付的小型评估集
- claude-api prompt-audit：可以标记提示、skill 和工具描述中为旧模型编写的指令，并以差异形式提出修复建议。可以在系统提示上运行它，以找出为早期模型添加、如今却使 agent 变慢或更加僵化的规则。每个团队的 DRI 也可以在自己的 skill 和工具描述上运行它。
- claude-api hillclimb：可以基于现有评估迭代改进应用。这可以用于“已折叠 vs 已保留”的比较（将一个子 agent 折叠进 skill 加工具后，让它迭代改进 skill 和工具描述，并查看折叠版本是否达到或超过子 agent 版本），也可以用于改进系统提示。
- claude-api cost-optimize：可以分析调用的去向，并针对提示缓存、删减不需要的输入和输出令牌、工作量以及模型选择等选项提出节省成本的方案，每次只进行一项变更。这有助于降低特定设计的成本和延迟。

随着模型的不断发展，我们对如何最好地使用模型的理解，以及围绕最佳实践的指导，也会随之发展。这使得任何单一架构都不如其背后的原则重要：进行衡量，一次只改变一件事，并保留经得起检验的内容。  
  
这是其中一个这样的案例。随着模型能力增强、aagent 运行时间变长，你的更多子 agent 可以变成 skill 和工具。不过，你不必一步完成这一转变。构建一个小型端到端评估，折叠进一个子 agent；只有当折叠版本的得分更低时，才将其保留为子 agent，然后不断重复这一过程。
