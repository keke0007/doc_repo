# yunyimuhan (@yymhxie)

这两天看了 LangChain 公开的 Content Studio，一个在 Slack 里接需求、做社媒图、PPT 和宣传视频的设计 Agent。已经交付了 3000 多份素材，单次请求成本中位数从 8 美元左右降到了 0.5 美元。  
数字不是最想聊的，想聊的是他们走过的一段弯路。一开始他们预制了 115 个 UI 组件，想把输出框稳，结果设计越来越像模板。等模型变强了，他们把大部分硬编码规则删掉，效果反而更好。  
这个弯路我们也走过。之前做一个客户交付项目，工程师把所有逻辑都写进了 prompt。prompt 越写越长，越来越难调，结果也不稳定，给客户演示的时候效果很差。我当时给他的建议就一条：先把确定性的规则逻辑和需要 LLM 推理的逻辑分开。确定性的部分写成代码，用明确的测试用例兜住；真正需要做 eval 的，只有推理那部分。不这么拆，项目很难推进下去。  
LangChain 也是这个思路。配色、字体、排版这些能量化的，直接写成代码检查；设计师的主观反馈，连同为什么这么改，一起沉淀进 Skill。理由一定要留下来，不然下一个人或者下一代模型，根本判断不了这条经验还成不成立。  
Memory 也是一样，不是记得越多越好。他们每个项目结束后提炼有证据的经验，在后续任务里验证，有用的才更新进去。很多团队的 Memory 其实就是只进不出的日志，记得越多越乱。  
所以我觉得 Agent 交付之后，Harness 得有人持续运营。哪些规则是业务硬约束要一直留着，哪些只是当年模型不够强时打的补丁，模型升级后就该删掉，这得有人定期去审。模型厂商不会替你干这事，客户 IT 也很难判断，这正是 FDE 该干的活。  
给 Agent 加规则谁都会。敢删，并且知道该删哪条，才是真功夫。
