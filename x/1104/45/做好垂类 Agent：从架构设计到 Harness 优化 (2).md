# 做好垂类 Agent：从架构设计到 Harness 优化

*By Fliaping (@fliaping)*

![Banner](<做好垂类%20Agent：从架构设计到%20Harness%20优化%20(2).assets/image-01.jpg>)

完整博客版：[从 Deep Agents 到可靠的 Agent Runtime](https://blog.fliaping.com/domain-agent-harness-engineering/)

“帮我看看昨天的评测为什么没过。”

这句话听起来简单，实际却包含好几个判断：找哪次任务、用哪个版本、看哪些失败样本，以及证据不足时还要查什么。Agent 可能每次都能正确调用工具，最后却把旧版本的报告当成了答案。

我更关心的，正是这段从“工具能调用”到“结果可交付”的距离。接入模型和工具以后，还需要让 Agent 拿到合适的上下文、遵守权限、继续未完成的任务，并知道什么时候才算完成。

这篇文章围绕 Deep Agents 展开，把这些问题拆成基座选择、运行支持、长期记忆、评测和协作五个部分。文中的案例均为通用示例，图示表达设计方法，不对应某个组织的生产架构或实测结果。

## 1. 先分清：模型说了什么，系统做了什么

一次工具调用返回成功，最容易让人放松警惕。

但“成功”可能只表示服务收到了请求。任务是否已经运行、输出是否属于正确版本、质量是否达到要求，还需要后续检查。

因此，设计 Agent 时，我会把完成证据分成三层。

**第一层是模型决定。** 模型选择了工具并生成参数，这说明它准备采取一个动作。

**第二层是环境执行。** 服务返回任务标识、文件确实写入、测试确实运行，才能说明外部发生了什么。对于异步任务，还要区分“已受理”和“已结束”。

**第三层是业务验收。** 产物存在之后，继续检查版本、质量和证据，才能判断它是否满足用户的原始目标。

![Image](<做好垂类%20Agent：从架构设计到%20Harness%20优化%20(2).assets/image-02.jpg>)

*提交场景示意。图中的三个阶段需要不同证据，模型选定动作本身不代表任务成功。*

例如，用户要求诊断失败原因，一份有样本支持的解释可能已经完成任务；用户要求修出一个达标方案，同样的解释就还不够，必须继续修改和验证。

**验收标准要跟着用户目标走。** 如果这一点没有定义清楚，后面再增加规划、记忆和子 Agent，也很难判断系统是否变好了。

## 2. 选择基座，先看哪些部分需要自己控制

基座选型不宜从功能数量开始。更有效的起点，是列出产品对执行方式的要求：进程能否长期运行、状态存在哪里、是否需要更换模型，以及工具调用前后要加哪些业务逻辑。

按这些要求，可以考虑三种接入方式。

- **复用完整 Agent 运行环境。** 通过 SDK 或服务接口接入，适合希望直接使用成熟工具与交互能力的产品。接入前要确认它开放了哪些配置、状态和事件接口。
- **嵌入可组合的 Agent 框架。** 在自己的服务中装配模型、工具和中间件，适合已有后端、需要接入身份与业务资源的团队。
- **直接构建较小的执行循环。** 适合任务范围明确、确实需要控制每次调用的场景。与此同时，状态、工具错误和中断恢复也需要自己处理。

这里用 Deep Agents 作为第二种方式的例子。它组合文件、摘要、Skill、记忆和子任务委派等能力，并通过 LangChain 和 LangGraph 组织执行。[1]

使用时，可以沿几处接口理解分工：

- 模型与工具决定 Agent 能提出和执行哪些动作。
- Backend 对接文件和命令实际运行的位置。
- 中间件在模型或工具调用前后补充逻辑。
- Checkpointer 保存图状态，Store 可承载跨会话信息。

这些接口能省掉重复建设，但还不能直接回答产品里的全部问题。比如，保存了检查点，仍要决定由哪个 worker 领取任务；提供了文件工具，仍要确定它能访问哪个用户的工作区。

**因此，基座选型还要看宿主接入成本。** 可以用一个小任务验证：提交外部作业后停止当前执行进程，再尝试找回原任务继续处理。这个实验往往比一张功能对比表更能暴露边界。

## 3. Runtime 要保住的，是下一步还能正确执行

模型能规划任务，运行系统则要为它提供可用的输入和工具，并在出错时保存恢复依据。这里有三件事值得优先设计。

上下文压缩以后，仍然能定位原任务

长对话里可能包含文档、代码、日志和多个任务结果。为了控制请求长度，需要压缩历史，但一句“评测已经发起”不足以支持后续操作。

Agent 还需要任务标识、版本和查询入口。一个可行的设计是把这些引用单独保存，摘要负责概括进展，工具负责重新查询状态。

这样，即使叙述被缩短，Agent 仍能定位原资源。不过，历史里记录的“正在运行”不能当成当前事实；再次行动前要查询最新状态。

摘要预算也要覆盖最终请求。系统指令、Skill、记忆和工具定义都会占用上下文，不能只统计聊天历史，再把其他材料无上限地追加进去。

身份由执行系统提供

用户让 Agent 读取项目 A，不意味着模型可以把参数里的项目名改成 B 后继续访问。

为避免这类问题，执行系统应根据已认证的请求确定用户与项目，再由工具入口和业务服务核验目标资源。模型可以选择动作，但不能自行声明“我现在是管理员”。

这也适用于子 Agent。委派研究任务时，可以给它更少的工具、更窄的文件范围；不能因为换了一个角色名称，就放宽父任务原有的授权。

人工确认与权限检查也需要分别处理。用户同意“继续执行”，只能说明他确认了这个动作，不会让账号获得原本没有的资源权限。

等待要能恢复，重试要有依据

假设一个批量任务需要运行半小时。提交后反复让模型询问“完成了吗”，通常没有必要；可以由执行系统保存任务标识，再用只读查询等待结果。

这里有一个容易遗漏的区别：保存了 Agent 状态，不代表外部进程、网络连接和写入动作都能恢复。LangGraph 的持久化与中断机制提供了图执行的恢复基础，外部副作用仍需要应用处理。[2]

因此，提交与等待适合分开设计：

1. 提交外部任务，保存回执和任务标识。
2. 登记等待，由后台查询原任务。
3. 拿到结束状态后，再把结果交回 Agent。

如果提交请求超时，第一件事是查清它是否已经生效。直接重新提交，可能把一次任务变成两次。

**“报错了”并不足以决定重试方式。** 查询超时、明确未执行、执行结果未知，应该走不同的恢复路径。

## 4. 长期记忆：先决定谁能用，再决定记什么

记忆可以减少重复解释，也可能把旧口径带进新任务。要把收益留下来，我建议分别设计使用范围、内容类型和加载方式。

![Image](<做好垂类%20Agent：从架构设计到%20Harness%20优化%20(2).assets/image-03.jpg>)

*通用设计建议。三个维度分别回答权限、保存价值和读取时机，不是三个串行处理步骤。*

使用范围决定谁能看到

个人偏好可以跨项目复用。例如，“先给结论，再列样本”通常只改变回答方式。

项目经验则需要更窄的范围。例如，“这个项目的日报按业务发生日统计”可以保存为用户在当前项目的记忆，避免新开会话后再次纠正，但不应自动带到其他项目。

如果希望团队其他成员也使用这条经验，可以增加共享建议与审核流程。发布后形成独立的共享条目，保留适用条件和来源，避免个人后续修改悄悄改变团队规则。

检索时也要延续这套范围：**先限定允许访问的记忆，再选择与当前任务相关的内容。** 不能先把所有用户的数据送进模型，最后再要求它忽略不该看到的部分。

内容类型决定是否值得保存

我会优先考虑四类信息：稳定偏好、用户纠正、已确认的项目决策，以及可靠资料的入口。

这些内容可能影响未来任务，因此值得保留来源和适用条件。相反，“这次先抽一小批样本”、当前进度、实时指标，以及助手提出但尚未被认可的方案，通常不适合直接保存成长期认识。

尤其要区分用户确认与模型推测。一次成功结果也不能证明执行中的每一步都是可靠经验；后台整理仍需核对它依据什么得出结论。

加载方式决定每次读多少

并不是所有记忆都需要进入每次请求。常用偏好适合精简后常驻，项目经验可以按任务读取，完整历史则留到需要核实证据时再查。

几个公开项目提供了不同参考。Codex 的记忆管线把历史抽取和整合分开；Claude Code 使用索引与主题文件组织自动记忆；Hermes 将小容量常驻记忆与历史会话检索结合。[3][4][5]

这些方式并不要求产品采用相同存储。值得借鉴的是分开处理入口、详情和证据，避免每次加载全部内容。

记忆还需要能更新和退出。对于已经变化的业务口径，应明确哪条替代哪条；来源被撤回后，也要重新检查依赖它的结论。

做完这些，再用跨会话任务验证：用户是否少纠正了一次，Agent 是否用了有效版本，切换项目时有没有串用经验。条目数量本身说明不了多少效果。

## 5. 优化 Harness，用实验决定加什么、删什么

模型换得更强以后，旧的阶段提醒未必仍然合适。

以一个通用场景为例：模型已经开始运行测试，某条根据关键词识别阶段的规则却继续提示它“先完成开发”。这时要检查的，是这条提醒有没有把任务带回已经完成的步骤。

但发现一个多余步骤，还不足以得出“控制越少越好”。有些提醒帮助模型补齐检查，有些检查本来就应该由服务端执行；修改之前要先分清它们各自的作用。

![Image](<做好垂类%20Agent：从架构设计到%20Harness%20优化%20(2).assets/image-04.jpg>)

*实验方法示意。A、B 表示对照版本，不包含任何性能实测数据。*

判断一项流程控制是否继续保留，可以从三个问题入手。

**模型现在能否自己完成这一步？**

先看实际执行记录，确认它是否还依赖提醒。若已经能稳定完成，再尝试移除，并用原有任务检查是否退步。

**它是否干扰了合理的下一步？**

需要把模型正在做的事与系统给出的提示放在一起看。如果模型已拿到足够证据，规则却仍要求重复检索，就值得做一次对照实验。

**移除以后，必须遵守的约束还在吗？**

先确认这项逻辑只是操作建议，还是承担了真实权限、版本或写入检查。后者必须在执行层继续生效，不能随提示一起删掉。

具体实验中，尽量固定模型、任务和环境，每轮只验证一个主要假设。除了任务成功率，还要看误报完成、重复副作用、恢复情况，以及全部尝试的耗时和费用。

如果同时换模型、改提示、删中间件，就只能先报告整体变化，不能把收益单独归给其中一项。

还要用未参与调整的任务验证结果。原来失败的任务通过了，说明修改可能解决了这个问题；其他任务没有明显退步，才有理由保留它。

## 6. 从助手到 Workflow，应用决定编排方式

当运行和验收方式明确以后，同一组 Agent 能力可以支持多种应用。

交互式助手从用户目标开始，重点是能处理追问和补充条件。定时任务则需要保存执行配置，明确重复触发、重试和重叠运行时怎么办。

调查类应用还要增加业务窗口、来源范围和报告验收。拿到了数据只是开始，结论仍须有证据支持。

Workflow 是另一种使用方式：把需要判断的步骤交给 Agent，同时由流程定义节点依赖和结果交接。

例如，一个通用诊断流程可以安排三个角色：分析 Agent 解释失败原因，方案 Agent 提出修改建议，复核 Agent 检查建议是否覆盖原问题。交接时传递的是原因、证据、建议和复核结论，而不是不断复制整个聊天记录。

**Workflow 负责节点之间的关系，Agent 负责节点内的判断。** 节点内可以按反馈调整步骤；下一节点何时运行、失败后如何处理、什么结果能通过，则由流程与验收条件决定。

这与主 Agent 在执行中临时委派 SubAgent 不完全相同。前者适合反复执行的固定协作关系，后者适合临时拆分清晰的研究或检查任务。

两种方式可以结合，但角色越多，需要核对的交接也越多。因此，在增加一个 Agent 前，先写清它负责什么、接收什么、返回什么，以及谁检查结果。

## 7. 开始建设前，先准备一组能暴露问题的任务

如果从零开始，我会先收集一小组真实需求，并为每个需求写下允许操作、预期产物和验收条件。然后至少覆盖以下场景：

- 信息充分时，能否完成实现、验证和交付。
- 信息缺失时，能否提出必要问题，而不是猜测。
- 提交结果未知时，能否找到原任务，避免重复创建。
- 等待结束或进程恢复后，能否继续同一任务。
- 用户切换项目时，是否仍遵守记忆和资源范围。
- 用户纠正旧口径后，后续任务是否采用新依据。
- 权限不足时，是否停下来说明原因。
- 多个 Agent 交接时，后续节点是否拿到了正确版本的产物。

先让这组任务跑起来，再根据失败记录决定补上下文、改工具、调整记忆，还是增加流程控制。每次改动都有对应问题，也就更容易判断它是否值得保留。

做 Agent 最容易看见的是回答，更难看见的是支撑回答的执行过程。把版本、权限、任务状态和验收证据接起来，才能知道一次漂亮回答背后，究竟有没有完成用户交代的事。
