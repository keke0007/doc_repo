# shenxianovo (@shenxianovo)

离职倒数第 8 天....突然想到个问题：  
  
为什么都说大厂技术岗新人 landing 难？  
  
我觉得一个原因是：学校/个人项目，基本碰不到公司里整套现成的基础设施和研发流程。  
  
=== === ===  
  
想象你是个实习生/校招生，入职第一天，Mentor 甩给你一份文档：「看看这个需求，熟悉下业务，然后开始做吧。」  
  
首先，业务本身可能就非常复杂。好不容易搞明白要做什么了，却发现自己根本不知道该怎么开发（）  
  
看起来只是一个简单的需求，实际做起来可能是这样的：  
  
先去 A 平台（需求平台）建需求单，再去 B 平台（研发平台）建开发任务，用公司提供的 AI 服务让 Agent 改代码。  
  
如果涉及数据库变更，还得提 RDS 的 DDL 工单；如果影响到数仓，还得处理 MQ 到 Hive 的数据同步，再去 C 平台（数据开发平台）修改相关任务。要是涉及 FaaS，相关函数也得跟着改。  
  
代码改完也不是直接上线。得先在预发环境测试，再走发布流水线分阶段上线。有的功能还得通过动态配置做灰度，灰度策略也要自己设计。  
  
怎么确认自己的改动真的生效了？还得看日志、指标，必要时补打点、配置监控和告警。  
  
要是碰上多区域部署，尤其是不同区域还有不同的合规要求，那就更复杂了……  
  
=== === ===  
  
这里面每个名词背后，都可能是一套系统、一套流程，甚至一个专门负责的团队  
  
厉害点的学生可能用过 GitHub Actions，用过 Azure/AWS/GCP 等云厂商的产品，搭过 Grafana/Prometheus。但很多人第一次听到这种工作安排，是真的听不懂  
  
难的往往不是写代码，而是不知道一个需求要经过哪些系统、遵循哪些流程，才算真正上线  
  
这些基础设施是为了让开发更方便而存在的。你不需要自己实现数据库、消息队列、部署系统，但光是学会怎么使用它们、理解它们之间的关系，就已经有相当高的门槛了

附一张粗糙的环境地图吧...  
  
括号里是在学校/个人项目里可能接触过的对应物：  
  
组织与权限：IAM、服务树、权限审批、工单（GitHub 权限、OAuth）  
  
计算：物理机、虚拟机、容器编排、镜像仓库、FaaS（Linux、Docker、云服务器）  
  
研发：需求平台、代码仓库、CI/CD、环境/泳道、发布流水线、动态配置、灰度发布（GitHub、GitHub Actions）  
  
数据库：RDS、NoSQL、DDL 变更、数据迁移（MySQL、PostgreSQL、MongoDB）  
  
存储：对象存储、块存储、文件存储（S3/OSS、本地文件）  
  
服务架构：RPC、服务发现、API 网关、负载均衡、多区域部署（HTTP、REST API、Nginx）  
  
中间件：MQ、缓存、配置中心、分布式锁（Kafka、RabbitMQ、Redis）  
  
可观测性：指标、日志、Tracing、打点、告警（Prometheus、Grafana、OpenTelemetry）  
  
数据：ETL、Hive、Flink、数仓分层、数据同步与调度、ClickHouse、BI（SQL、简单的数据处理脚本）  
  
AI：模型平台、模型网关、推理服务、模型评测、路由与配额（模型 API、Ollama）  
  
「知道这些东西是什么」和「知道怎么把它们组合起来完成一个需求」又是两回事（）  
后者可能才是 landing 最难的部分...
