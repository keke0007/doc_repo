# 山景城小路 (@Zen_with_AI)

小路精读了 AtlasKV 这篇论文，推荐给在做知识图谱加 LLM 的朋友。10 亿条三元组的图谱，推理时显存不到 20GB，训练只用了一张 48GB 的卡。  
  
论文要解决的问题是，怎么把超大知识图谱接到 LLM 上，又不依赖外部检索器和长上下文。作者的思路是一条链：三元组变成 Q-K-V，注入注意力层，再分层剪枝。小路带您顺着走一遍。  
  
先说背景。给 LLM 补外部知识，常见做法是 RAG，检索出文本块或子图塞进上下文，代价是检索慢、上下文长。另一条路是参数化注入，代表是 KBLaM（2024）：把知识库编码成一组 key-value 向量，直接接进自注意力层，换新知识库不用重训。但它的开销随知识条数 M 线性增长，论文里 KBLaM 处理 10 万条三元组就要 40GB 以上显存。  
  
骨架：  
  
KG->QKV->Attn->Cluster->Prune（三元组->拆成 Q-K-V->接入注意力->分层聚类->逐层剪枝）  
  
前两步解决数据问题，后三步解决规模问题。  
  
数据。KBLaM 的训练数据靠固定模板合成，询问的属性种类很少，换到没见过的属性就泛化不了。作者的观察是，图谱里的三元组 (h, r, t) 天然就是 Q-K-V 结构。  
  
KG2KV。遮住头实体或尾实体，被遮的当 value，另一个实体加上改写成名词的关系当 key。例如遮住尾实体，关系 because 改写成 cause，询问属性的多样性比例，合成方法是 0.003%，KG2KV 是 7.864%。每条三元组的平均 token 成本是 349.9 对 165.7。  
  
训练。骨干是 LLaMA3.1-8B-Instruct，只学 KG 专用的 query 头和 K、V 投影头。训练数据只抽了 2 万条三元组（来自 14.92 亿条的 ATLAS-Wiki），训练 3000 步，训练时的图谱最大只有 120 条，每 3 层注入一次知识。KBLaM 报告的是 2 万步。  
  
聚类。用 UMAP 降维，再用 GMM 把 key 聚成根、中、叶三层，每层簇的大小都取 M 的立方根，上层 key 是下层的池化。  
  
剪枝（HiKVP）。推理时只有根层 key 在 GPU，其余放在 CPU。先拿 query 和根层 key 算注意力，取 top-kR，把对应的中间层 key 搬上 GPU 再取 top-kI，最后在叶层取 top-kL，默认是 128、64、16。复杂度从 KBLaM 的 O((M+N)·N·D) 降到 O((Ct·M 的立方根+N)·N·D)，其中 N 是 query 长度，D 是维度。  
  
结果。作者在三个分布外数据集（Enron、ATLAS-Pes2o-QKV、ATLAS-CC-QKV）上，看第 15 层注意力里排第一的三元组是不是正确答案。候选 100 条三元组时，ATLAS-CC-QKV 上 KBLaM 的 Top-1 是 21.8%，AtlasKV 是 89.1%；ATLAS-Pes2o-QKV 上是 16.4% 对 87.3%。KBLaM 训练到 2 万步也只有 23.6% 和 25.5%。显存方面，ICL 超过 100 条三元组就要 48GB 以上。  
  
还有一个我喜欢的实验。作者用随机配对的 key-value 和正确配对的数据各训练一遍，前期两条损失曲线几乎重合，到某一步之后正确配对的损失明显下降。作者据此认为，模型从这一步开始学会了检索，不是死记。  
  
简单总结一下就是：AtlasKV 抓住了三元组天然是 Q-K-V 这一点，用 KG2KV 生成多样的训练数据，再用 HiKVP 把注意力的开销降到知识条数的立方根。它能在 20GB 显存里挂 10 亿条三元组，代价是丢掉图结构、损失一部分精度、多出 CPU 和 GPU 之间的搬运延迟。多跳问题怎么办，作者留给了未来工作，论文里没有给答案。
